8.3 Lab: Connecting a Robot to a PLC

Gerald Lê

01. Connecting robots to cell PLCs

A robot arm usually works inside a cell run by a programmable logic controller (PLC). Lesson 1.7 The Industrial Robot Cell showed how the PLC and the robot coordinate through handshake signals, and why safety signals travel on a separate, safety-rated path. Lesson 2.5 End-of-Arm Tooling and I/O showed the digital I/O on the controller and tool flange. This lab moves those signals onto a network.

When a cell needs to exchange numbers as well as on/off signals (recipe numbers, part counts, error codes), separate wires for each signal stop being practical, so robot controllers also offer network interfaces.

Universal Robots controllers support common industrial Ethernet protocols to link directly into plant networks. On EtherNet/IP networks, Universal Robots controllers only support EtherNet/IP Class 1 implicit I/O messaging and do not support Class 3 explicit messaging.[1] Class 1 implicit messaging provides time-scheduled, cyclic transport tailored for real-time I/O updates between a scanner and an adapter. Inside the controller memory space, the lower range of general-purpose boolean, integer, and float registers on the robot is reserved for PLC fieldbus interface usage.[1]

The Universal Robots PROFINET interface provides 10 pluggable modules, with seven modules to read data and three modules to set data.[2] The PLC reads robot data through the read modules and sends commands through the set modules.

02. Modbus TCP server architecture

Modbus TCP messages include a 7-byte MBAP header and transmit over TCP on registered port 502.[3] The MBAP header (covered in 8.2) lets the client match each response to its request.

The Modbus data model provides four primary tables comprising discrete inputs, coils, input registers, and holding registers.[4] Discrete inputs and coils store 1-bit boolean values, corresponding to digital inputs and outputs. Input registers and holding registers store 16-bit numerical values, where input registers are read-only and holding registers permit both read and write operations. Across all data tables, Modbus transmits numerical values and addresses in big-endian representation with the most significant byte transmitted first.[4]

The Universal Robots controller acts as a Modbus TCP server on port 502 to receive standard Modbus requests from clients.[5] Several clients can connect to the robot Modbus server at the same time.[5] This architecture allows a cell PLC, an operator touch panel, and an engineering workstation to communicate with the robot simultaneously over an Ethernet switch.

The Universal Robots Modbus server uses 0-based addressing.[5] The Unit Identifier and Slave ID value is ignored in the robot Modbus server.[5] External clients interact with the robot using standard Modbus function codes:

  • Reading data: The Modbus server responds to function code 0x03 to read holding registers and 0x04 to read input registers.[5]
  • Writing data: The Modbus server responds to function code 0x06 to write a single register and 0x10 to write multiple registers.[5]
  • Error handling: The server responds to errors with exception codes 0x01 for illegal function code, 0x02 for illegal data access, and 0x03 for illegal data value.[5]

03. Register mapping and bit packing

The Universal Robots Modbus TCP server provides 128 general-purpose 16-bit registers at addresses 128 to 255.[6] These general-purpose holding registers provide space to exchange recipe numbers, part counters, and handshaking flags.

In many automation cells, the primary information exchanged consists of simple binary status flags. Up to 16 binary on/off signals can be consolidated into a single 16-bit register instead of using a separate address for each.[6]

For example, an integrator can map the discrete handshake signals from Lesson 1.7 directly into the 16 bits of register 128. Bit 0 represents "Robot Ready", bit 1 represents "Cycle Start", bit 2 confirms "Part Clamped", and bit 3 indicates "Robot Working". The remaining upper bits can indicate task completion flags or error codes. Instead of issuing multiple distinct network requests, the supervisory PLC can read or write the entire cell handshake state in a single 16-bit transaction.

Within a running robot program, local scripts can access these registers directly. Registers can be read from a robot program using read_port_register, which returns an integer value between 0 and 65535.[6] The URScript command integer_to_binary_list converts an integer into a list of True and False values.[6] The converted binary list uses little-endian notation so the first element represents the least significant bit.[6]

For example, if register 128 contains integer value 5, integer_to_binary_list(5) returns a 16-element boolean list where index 0 is True (representing value 1), index 1 is False (value 2), index 2 is True (value 4), and all higher elements are False. The robot script can inspect or change any signal by accessing list indices, such as setting sample_list[3] = True. Before updating a server register, the binary list must be converted back to an integer using binary_list_to_integer.[6] The script then passes the calculated integer back to the register port.

04. Python communication with pymodbus

Python is handy for testing a cell from a laptop. The lab uses pymodbus, a Python library that implements Modbus clients and servers.

In pymodbus, a client object is created with ModbusTcpClient and connects to the target device using the connect method.[7] By default, the pymodbus ModbusTcpClient connects using socket framing on default port 502.[7] During instantiation, the client accepts the target host IP address and network port, then opens a TCP socket to the server.

The client library offers dedicated methods for reading and writing data tables. The pymodbus client provides write_register to write one register, write_registers to write several, and read_holding_registers to read holding registers.[8] The library builds the MBAP header and function code for each call.

Each communication call returns a response object that the client script checks. In pymodbus client responses, isError indicates device problems, rr.registers provides register data, and rr.bits provides coil data.[7] Calling rr.isError() allows an application to detect network errors or device rejections before attempting to parse response data.

When developing multi-threaded programs, developers must take precautions with shared network resources. The pymodbus client is not thread safe, requiring applications to ensure all calls are serialized.[7] If background threads log robot data while an operator interface sends setpoints, access to the client instance must be serialized with thread locks or command queues.

05. Lab: Talk to a Modbus server from Python

In this hands-on lab exercise, you will connect a Python client to a local Modbus TCP server. On a physical manufacturing line, an actual Universal Robots controller runs a Modbus TCP server on port 502, exposing general-purpose registers 128 to 255. Because no physical hardware is assumed for this course, you will run fake_ur_server.py, a stand-in server on port 5020 with holding registers 0 to 255, then execute client.py.

To begin, install the required library version in your Python environment: 

pip install pymodbus==3.16.1

Create the stand-in server script named fake_ur_server.py. This script allocates 256 holding registers initialized to zero and binds a TCP server to localhost port 5020: 

"""A stand-in for a robot's Modbus TCP server: 256 holding registers, all zero."""
from pymodbus.datastore import ModbusDeviceContext, ModbusSequentialDataBlock, ModbusServerContext
from pymodbus.server import StartTcpServer

# Holding registers 0-255. pymodbus numbers its data blocks from 1, so a
# block starting at 1 serves protocol addresses 0-255 (the UR server also
# uses 0-based addresses). Registers 128-255 play the role
# of the UR's general-purpose registers.
holding = ModbusSequentialDataBlock(1, [0] * 256)
device = ModbusDeviceContext(hr=holding)
context = ModbusServerContext(devices=device, single=True)

print("Modbus server listening on port 5020 (Ctrl+C to stop)")
StartTcpServer(context=context, address=("127.0.0.1", 5020))

Next, create the client script named client.py. This script connects to the stand-in server, writes values to general-purpose registers 128, 129, and 130, and reads them back: 

"""Write and read general-purpose registers on a Modbus TCP server."""
from pymodbus.client import ModbusTcpClient

client = ModbusTcpClient("127.0.0.1", port=5020)  # use port 502 for a real robot
client.connect()

# Write one register (function code 0x06), then several (0x10)
client.write_register(128, 1)
client.write_registers(129, [250, 7])

# Read them back (function code 0x03)
rr = client.read_holding_registers(128, count=3)
if rr.isError():
    print("Server returned an error:", rr)
else:
    print("Registers 128-130:", rr.registers)

client.close()

To execute the lab, follow these operational steps:

  1. Start the server: In your first terminal window, start the stand-in server: 
    python fake_ur_server.py
    The terminal confirms: Modbus server listening on port 5020 (Ctrl+C to stop).
  2. Run the client: In a second terminal window, run the client script: 
    python client.py
  3. Verify output: In the second terminal, confirm that the client prints the expected register values: 
    Registers 128-130: [1, 250, 7]

The client wrote value 1 to register 128 with function code 0x06, wrote values 250 and 7 to registers 129 and 130 with function code 0x10, and verified the writes by reading all three registers back with function code 0x03.

06. Modbus exceptions and offline simulation

When communicating across industrial networks, applications must recognize and handle protocol rejections. When a Modbus server cannot carry out a request, its exception response uses the request function code plus 0x80.[4] For example, if a client submits a read holding registers request using function code 0x03, an exception response carries function code 0x83 (calculated as 0x03 + 0x80 = 131 in decimal notation).

Modbus exception code 02 is ILLEGAL DATA ADDRESS: the address in the request is not allowed for the server.[4] In our stand-in server script, the holding register block is defined for addresses 0 to 255. Register 256 is outside this valid range.

To observe exception handling in practice, conduct a short exercise by attempting to write or read register address 256. For example, test an out-of-range read operation using the following script snippet: 

from pymodbus.client import ModbusTcpClient

client = ModbusTcpClient("127.0.0.1", port=5020)
client.connect()

# Address 256 falls outside allowable server addresses 0-255
rr = client.read_holding_registers(256, count=1)
if rr.isError():
    print("Exception response:", rr)
    print("Function code:", rr.function_code)
    print("Exception code:", rr.exception_code)

\1\n                        
Expected output:
\n                        
Exception response: ExceptionResponse(dev_id=1, function_code=131, exception_code=2)\nFunction code: 131\nException code: 2
\2, the server rejects the request with exception code 2 (ILLEGAL DATA ADDRESS). In pymodbus, this result appears as an ExceptionResponse with function_code=131 (0x03 + 0x80) and exception_code=2. Similarly, attempting to write to register 256 triggers an ExceptionResponse with exception code 2, confirming that the server rejected the unmapped address.
