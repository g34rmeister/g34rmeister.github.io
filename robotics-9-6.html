9.6 Lab: Check a Robot's State from Python

Gerald Lê

01. The Dashboard Server interface and remote control

A technician often wants to check a robot's state without walking to the teach pendant. 8.3 Lab: Connecting a Robot to a PLC exchanged registers with a robot over Modbus; UR robots also have a simpler text interface for status and commands.

The Universal Robots Dashboard Server allows remote control over a TCP/IP socket on port 29999.[1] Rather than transmitting binary fieldbus datagrams, the Dashboard Server accepts human-readable text commands and replies with plain text strings.

Communication with the Dashboard Server follows a simple stream format. Every command sent to the Dashboard Server must be terminated by a newline character.[1] In Python the newline is written \n.

Controlling a robot externally via Dashboard Server commands requires enabling Dashboard Server access and enabling Remote Control mode in settings.[2] UR's guide gives the menu paths: Settings, Security, Services, Dashboard Server; and Settings, System, Remote Control.[2]

02. Querying controller modes and execution state

Three questions give a quick picture: is the arm powered, is a safety stop active, and is a program running?

Sending the command robotmode returns Robotmode: followed by the state, which can be NO_CONTROLLER, DISCONNECTED, CONFIRM_SAFETY, BOOTING, POWER_OFF, POWER_ON, IDLE, BACKDRIVE, or RUNNING.[3]

The robot mode state Running indicates that the robot is powered on with brakes released, which is distinct from program execution.[2]

Sending the command safetystatus returns Safetystatus: followed by the safety state, which can be NORMAL, REDUCED, PROTECTIVE_STOP, RECOVERY, SAFEGUARD_STOP, SYSTEM_EMERGENCY_STOP, ROBOT_EMERGENCY_STOP, VIOLATION, or FAULT.[3]

Sending the command programState returns STOPPED if no program is running, PLAYING if a program is running, or PAUSED if paused.[3]

Sending the command running performs an execution state enquiry and returns Program running: true or Program running: false.[3]

The load command returns Loading program: with the filename on success, or File not found: or Error while loading program on failure.[3]

03. Protective stops and emergency stops

The safety status tells you which kind of stop happened (stop categories are explained in 5.4 Making a Robot Cell Safe). Two kinds matter for this lab.

A protective stop is initiated by the robot controller due to proximity to a limit, commonly associated with error code C153 or C157.[2]

During a protective stop, the robot stops playing the program while retaining electrical power.[2] That is why the robot mode can still read RUNNING during a protective stop: the arm is powered with its brakes released, even though no program is running.

An emergency stop is different. Recovering from a robot emergency stop requires manually releasing the emergency stop button before sending close safety popup, brake release, and play.[2] Someone has to be at the cell to release the button, which is the point: a person checks the cell first.

Resuming a program after unlocking a protective stop restarts execution from where it stopped rather than from the beginning.[2]

Unlike protective stop recovery, resuming execution after an emergency stop restarts the program from the beginning.[2]

The power on command must be sent before the brake release command to avoid an error message.[3] Sending the command brake release commands the robot to release its brakes and returns Brake releasing.[3]

04. The stop recovery workflow and the five-second rule

The protective stop recovery sequence via Dashboard Server commands consists of sending close safety popup, followed by unlock protective stop, followed by play.[2]

Sending the command close safety popup closes an active safety popup and returns closing safety popup.[3]

Sending the command play returns Starting program on success or Failed to execute: play on failure.[3]

Sending unlock protective stop returns Protective stop releasing on success, or Cannot unlock protective stop until 5s after occurrence. Always inspect cause of protective stop before unlocking if less than 5 seconds has passed.[3]

UR's page is not consistent about when this delay applies. When a joint encounters more than 50 protective stops within 8 hours, error 163: TOO_FREQUENT_PROTECTIVE_STOPS is triggered and imposes a 5-second delay before unlock is permitted.[3] The command reference table indicates that the unlock protective stop command fails if less than 5 seconds have passed since any protective stop occurred. However, a descriptive note located directly above the command table asserts that the 5-second delay applies only to error 163 (TOO_FREQUENT_PROTECTIVE_STOPS), and that all other protective stops can be unlocked immediately. In our lab exercises, the stand-in server follows the specification in the command table, rejecting unlock requests made within 5 seconds of the stop.

The error message provides an explicit maintenance directive: always inspect the cause of a protective stop before unlocking. As explained in Lesson 9.2, resetting faults without identifying the root cause can conceal underlying equipment problems. 9.3 lists what to check for repeated protective stops.

05. Lab: Querying robot state with Python

In this lab exercise, you will run a Python client script that connects to a Dashboard Server stand-in. Because this course requires no physical hardware, you will run fake_dashboard_server.py on your local computer to simulate a robot that has just experienced a protective stop.

Both scripts use only Python's standard library: socket.create_server on the server side and socket.create_connection on the client side.

A real Dashboard Server sends a one-line welcome message as soon as a client connects; UR's own client library reads that line before sending any command.[4] The stand-in imitates this with the line Connected: Dashboard Server stand-in, so the client reads one line first. Wrapping the network socket with sock.makefile("rw", newline="\n") creates a buffered text stream, allowing the script to read and write lines using readline() and write().

Create the server stand-in file named fake_dashboard_server.py. This script simulates a robot controller where robotmode is RUNNING, safetystatus is PROTECTIVE_STOP, and programState is STOPPED: 

"""A stand-in for a UR robot's Dashboard Server. The robot has just had a
protective stop. Replies follow UR's Dashboard Server command table."""
import socket
import time

state = {
    "robotmode": "RUNNING",
    "safetystatus": "PROTECTIVE_STOP",
    "program": "STOPPED",
    "stop_time": time.time(),
}


def reply(cmd):
    if cmd == "robotmode":
        return "Robotmode: " + state["robotmode"]
    if cmd == "safetystatus":
        return "Safetystatus: " + state["safetystatus"]
    if cmd == "programState":
        return state["program"]
    if cmd == "running":
        return "Program running: " + ("true" if state["program"] == "PLAYING" else "false")
    if cmd == "close safety popup":
        return "closing safety popup"
    if cmd == "unlock protective stop":
        # A protective stop cannot be unlocked until 5 s after it happened
        if time.time() - state["stop_time"] < 5:
            return ("Cannot unlock protective stop until 5s after occurrence. "
                    "Always inspect cause of protective stop before unlocking")
        state["safetystatus"] = "NORMAL"
        return "Protective stop releasing"
    if cmd == "play":
        if state["safetystatus"] != "NORMAL":
            return "Failed to execute: play"
        state["program"] = "PLAYING"
        return "Starting program"
    if cmd.startswith("addToLog "):
        return "Added log message"
    if cmd == "quit":
        return "Disconnected"
    return "(this stand-in does not know that command)"


server = socket.create_server(("127.0.0.1", 29999))
print("Dashboard stand-in listening on port 29999 (Ctrl+C to stop)")
while True:
    conn, _ = server.accept()
    with conn, conn.makefile("rw", newline="\n") as f:
        f.write("Connected: Dashboard Server stand-in\n")  # welcome line
        f.flush()
        for line in f:
            answer = reply(line.strip())
            f.write(answer + "\n")
            f.flush()
            if answer == "Disconnected":
                break

Next, create the client script named health_check.py. This script opens a connection to port 29999, reads the welcome banner, queries the robot mode, safety status, and program state, and terminates the session with quit: 

"""Ask a Dashboard Server for the robot's state, like a technician's first look."""
import socket

ROBOT_IP = "127.0.0.1"  # use the robot's IP address on a real cell

sock = socket.create_connection((ROBOT_IP, 29999), timeout=5)
f = sock.makefile("rw", newline="\n")
print("Welcome:", f.readline().strip())  # the server greets first


def ask(command):
    f.write(command + "\n")  # every command ends with a newline
    f.flush()
    return f.readline().strip()


print(ask("robotmode"))
print(ask("safetystatus"))
print("Program state:", ask("programState"))
print(ask("quit"))
sock.close()

To execute the health check, follow these operational steps:

  1. Start the stand-in server: Open your first terminal window and run: 
    python fake_dashboard_server.py
    The terminal confirms: Dashboard stand-in listening on port 29999 (Ctrl+C to stop).
  2. Run the health check client: Open a second terminal window and run: 
    python health_check.py
  3. Verify output: In the second terminal window, verify the output matches: 
    Welcome: Connected: Dashboard Server stand-in
Robotmode: RUNNING
Safetystatus: PROTECTIVE_STOP
Program state: STOPPED
Disconnected

Review the reported status values:

  • Welcome greeting: Welcome: Connected: Dashboard Server stand-in confirms that the TCP socket opened and received the welcome line.
  • Robot mode: Robotmode: RUNNING confirms that the robot arm remains powered on and joint brakes remain disengaged. As established in Section 02, robot mode RUNNING reflects electrical power and brake release, not program execution.
  • Safety status: Safetystatus: PROTECTIVE_STOP indicates that the controller triggered a protective stop, such as error C153 or C157.
  • Program state: Program state: STOPPED shows that program execution ceased when the stop occurred.
  • Disconnection: Disconnected confirms that the server acknowledged the quit command and closed the TCP connection.

06. Lab: Clearing stops and resuming program execution

After the cause has been found and fixed, the stop can be cleared. In this exercise, you will run a script that performs this workflow automatically.

Create the recovery script named recover.py: 

"""Recover from a protective stop the way UR's stop-recovery guide describes."""
import socket
import time

sock = socket.create_connection(("127.0.0.1", 29999), timeout=5)
f = sock.makefile("rw", newline="\n")
f.readline()  # skip the welcome line


def ask(command):
    f.write(command + "\n")
    f.flush()
    answer = f.readline().strip()
    print(f"> {command}\n  {answer}")
    return answer


# On a real cell, find and fix the cause of the stop before unlocking (see 9.2)
ask("safetystatus")
ask("close safety popup")
if ask("unlock protective stop") != "Protective stop releasing":
    time.sleep(5)  # the stop can only be unlocked 5 s after it happened
    ask("unlock protective stop")
ask("safetystatus")
ask("play")
ask("quit")
sock.close()

The recovery script connects to the stand-in server, reads the initial greeting line, and checks safetystatus. It sends close safety popup to clear the teach pendant notification. It then issues unlock protective stop. If the command fails because less than 5 seconds have elapsed, the script pauses for 5 seconds using time.sleep(5) and issues unlock protective stop a second time. Once the safety status confirms NORMAL, it sends play to resume program execution and quit to disconnect.

To execute the recovery exercise:

  1. Verify server state: Ensure the stand-in server is running in your first terminal. If it was stopped, start it again: 
    python fake_dashboard_server.py
  2. Run recovery client: In your second terminal window, immediately run the recovery script within 5 seconds of starting the server: 
    python recover.py
  3. Verify output: Confirm that the second terminal prints the following lines: 
    > safetystatus
  Safetystatus: PROTECTIVE_STOP
> close safety popup
  closing safety popup
> unlock protective stop
  Cannot unlock protective stop until 5s after occurrence. Always inspect cause of protective stop before unlocking
> unlock protective stop
  Protective stop releasing
> safetystatus
  Safetystatus: NORMAL
> play
  Starting program
> quit
  Disconnected

Examine how each command responded during execution:

  • Safety enquiry: The initial safetystatus query confirms the active protective stop.
  • Popup dismissal: The close safety popup command returns closing safety popup, clearing the user interface popup.
  • First unlock attempt: The first unlock protective stop command is rejected because fewer than 5 seconds have passed since the stop occurred. The server returns the documented message reminding technicians to inspect the cause before unlocking.
  • Second unlock attempt: After the 5-second sleep interval expires, the second unlock protective stop command succeeds, returning Protective stop releasing.
  • Safety normalization: Querying safetystatus confirms that the safety state has returned to Safetystatus: NORMAL.
  • Program resumption: The play command returns Starting program, resuming task execution from where it stopped.
  • Disconnection: The quit command terminates the socket session.

On an active manufacturing cell, automated recovery scripts must be used with caution. The documented warning emphasizes that technicians should always inspect the cause of a protective stop before unlocking. Automatically clearing stops without diagnosing why the arm stopped can conceal mechanical interference or process drift, as highlighted in Lesson 9.2.
