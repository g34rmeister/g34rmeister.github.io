3.6 Writing Your First ROS 2 Package

Gerald Lê

01. From running examples to owning a package

In lesson 3.4 you drove Turtlesim from the keyboard and wrote two small nodes, and in lesson 3.5 you met the tools used to inspect a running system. This lesson slows down and looks closely at the thing every ROS 2 project is built from: the package. You will set up a workspace on purpose rather than by copying commands, learn what each file that ros2 pkg create writes is for, declare dependencies so that other people can build your code, and finish with a node that drives the turtle around a square.

Everything here targets ROS 2 Lyrical Luth, the twelfth release of ROS 2. It is a long-term support (LTS) release that came out in May 2026 and is supported until May 2031.[1] Its Tier 1 platforms are Ubuntu 26.04 (Resolute) on amd64 and arm64 and Windows 11 with Visual Studio 2022 on amd64, and it supports Python 3.12 to 3.14 (Ubuntu 26.04 ships Python 3.14.3).[2] A few details of package building changed in the last two releases, and many tutorials you find online were written for older distributions, so this lesson points out where Lyrical differs.

The official tutorials also moved. On Lyrical they live in a "Working with Client Libraries" section under ROS-Framework/client-libraries/ instead of the old Tutorials/Beginner-Client-Libraries/ path, and the pages carry redirects from the old addresses.[3] If a bookmark from an older course stops working, look in the new section.

02. Workspaces, underlays and overlays

The documentation defines a workspace simply: "A workspace is a directory containing ROS 2 packages."[3] The idea that matters is layering. Your ROS 2 installation in /opt/ros/lyrical is the underlay. Your own workspace is an overlay, "a secondary workspace where you can add new packages without interfering with the existing ROS 2 workspace that you're extending." The underlay must contain the dependencies of every package in the overlay, and packages in the overlay override packages with the same name in the underlay. Layers can be stacked more than two deep.[3]

On Ubuntu, first install the build tools with sudo apt update && sudo apt install ros-dev-tools.[4] Then create the workspace. The documented best practice is a new directory for every workspace, with all packages inside its src folder:[3] 

source /opt/ros/lyrical/setup.bash
mkdir -p ~/ros2_ws/src
cd ~/ros2_ws/src

When you later run colcon build from ~/ros2_ws, colcon creates three folders next to src. build holds intermediate files with one subfolder per package, install holds each installed package (by default in its own subfolder), and log "contains various logging information about each colcon invocation." Unlike the older catkin tool, there is no devel folder, and colcon builds out of the source tree.[5]

To use the overlay you source it. The tutorial is firm about where: "it is very important that you open a new terminal, separate from the one where you built the workspace. Sourcing an overlay in the same terminal where you built, or likewise building where an overlay is sourced, may create complex issues."[3] In the new terminal, source the underlay and then the overlay: 

source /opt/ros/lyrical/setup.bash
cd ~/ros2_ws
source install/local_setup.bash

There are two overlay scripts. Sourcing local_setup "will only add the packages available in the overlay to your environment," while setup sources the overlay as well as the underlay it was built against.[3] So "underlay setup, then overlay local_setup" gives the same result as "overlay setup" on its own. Underlay scripts come as setup.bash, setup.sh or setup.zsh,[4] and Lyrical adds a setup.fish script for fish shell users.[1]

The workspace tutorial proves the layering with a small experiment: change the window title in Turtlesim's turtle_frame.cpp from "TurtleSim" to "MyTurtleSim" in a cloned copy, rebuild, and run Turtlesim in a terminal that has the overlay sourced. The window shows the new title, while a terminal that sourced only the underlay still shows the original. That shows "the overlay takes precedence over the underlay."[3] A good mental model is a stack: whatever you sourced last sits on top.

Windows 11 note

The Lyrical Windows install uses pixi and conda-forge. In every Command Prompt you run pixi shell and then call C:\dev\lyrical\local_setup.bat; C++ builds need Visual Studio Build Tools 2022, run from the "x64 Native Tools Command Prompt for VS 2022".[6] On Windows you build with colcon build --merge-install and source with call install\setup.bat (or install\setup.ps1 in PowerShell).[3][5] The Lyrical workspace and colcon tutorials still mention the VS 2019 prompt and C:\dev\ros2; follow the install page where they disagree.[3][6]

03. Creating the package with ros2 pkg create

Packages are created from inside src with ros2 pkg create. The documented Python form is:[7] 

cd ~/ros2_ws/src
ros2 pkg create --build-type ament_python --license Apache-2.0 --node-name my_node my_package

--node-name "creates a simple Hello World type executable," and --license sets the package's license.[7] The one flag you must not forget is --build-type. In the Lyrical source of the command, its choices are cmake, ament_cmake, ament_cargo and ament_python, and the default is still ament_cmake.[8] Leave it out and you get a C++ package with a CMakeLists.txt instead of a Python one.

Other useful options are --dependencies (one or more packages to depend on), --description, --maintainer-name and --maintainer-email (filled in from your git config when available), --package-format (2 or 3, default 3), --destination-directory and --library-name. Passing --license ? lists the licenses that also produce a LICENSE file.[8]

For this lesson's project, create a package called turtle_square with one node called square_driver. Because our node imports rclpy, geometry_msgs and, in the stretch version, turtlesim_msgs, we can list all three at creation time: 

ros2 pkg create --build-type ament_python --license Apache-2.0 \
    --node-name square_driver turtle_square \
    --dependencies rclpy geometry_msgs turtlesim_msgs

A workspace can hold packages of different build types side by side, but packages cannot be nested inside each other.[7] The two recommended build types are ament_cmake and ament_python, and colcon reads package.xml files in format 3 (REP 149), with format 2 also supported.[5]

04. What the generator wrote

The documented output for an ament_python package lists package.xml, setup.py, setup.cfg, resource/my_package, my_package/__init__.py, the node file my_package/my_node.py, and three tests: test/test_copyright.py, test/test_flake8.py and test/test_pep257.py.[7] The Lyrical template also writes a py.typed marker file, which the documentation's sample output does not show.[8][9] Of these, the following are required for a Python package:[7]

  • package.xml: The manifest: name, version, description, maintainer, license, dependencies and the build type.[7]
  • resource/<package_name>: An empty marker file that is installed into the ament resource index so ROS tools can find the package.[7][9]
  • setup.cfg: "Required when a package has executables, so ros2 run can find them."[7]
  • setup.py: Tells setuptools how to install the package.[7]
  • <package_name>/: A Python module folder with the same name as the package, containing __init__.py. Your node files go here.[7]

Here is the shape of the setup.py that the Lyrical template generates, shown for turtle_square (maintainer fields shortened):[9] 

from setuptools import find_packages, setup

package_name = 'turtle_square'

setup(
    name=package_name,
    version='0.0.0',
    packages=find_packages(exclude=['test']),
    data_files=[
        ('share/ament_index/resource_index/packages',
            ['resource/' + package_name]),
        ('share/' + package_name, ['package.xml']),
    ],
    package_data={'': ['py.typed']},
    install_requires=['setuptools'],
    zip_safe=True,
    maintainer='...',
    maintainer_email='...',
    description='TODO: Package description',
    license='Apache-2.0',
    extras_require={'test': ['pytest']},
    entry_points={
        'console_scripts': [
            'square_driver = turtle_square.square_driver:main',
        ],
    },
)

The data_files entries install the resource marker and package.xml where ROS expects them. The package_data line for py.typed appears in the Kilted and Lyrical templates but not in Humble or Jazzy, so do not be surprised if an older project lacks it.[9] The most important part is entry_points. Each string in console_scripts reads <executable name> = <python package>.<module>:<function>, as in the tutorial's 'talker = py_pubsub.publisher_member_function:main'.[10] The name on the left is what you type after ros2 run turtle_square.

The generated setup.cfg is two short sections, [develop] script_dir=$base/lib/turtle_square and [install] install_scripts=$base/lib/turtle_square. They put the executables in lib "because ros2 run will look for them there."[9][10] Name, version, description, maintainer and license must match between package.xml and setup.py, so edit both when you fill in the TODO fields.[7]

Watch out: a typo in the official page

The setup.py listing in the Lyrical "Creating a package" tutorial uses package_name = 'my_py_pkg' and the entry point 'my_node = my_py_pkg.my_node:main', while the rest of that page uses my_package.[7] If you copy it word for word, the names will not match your package. Always check that the names in setup.py match your folder names.

05. Declaring dependencies: package.xml and rosdep

The generated Python package.xml uses format 3, has TODO placeholders for the description and license, lists the test tools ament_copyright, ament_flake8, ament_pep257 and python3-pytest as test dependencies, and ends with <export><build_type>ament_python</build_type></export>.[7] Every package your code imports should also be declared here. The tags say when each dependency is needed:[11]

  • <depend>: Needed at both build time and run time.[11]
  • <build_depend> and <build_export_depend>: Needed only for building, or for headers exported to packages that build against yours.[11]
  • <exec_depend>: "Shared libraries, executables, Python modules, launch scripts and other files required when running."[11]
  • <test_depend>: Needed only to run tests.[11]

The publisher tutorial adds its dependencies by hand as <exec_depend>rclpy</exec_depend> and <exec_depend>std_msgs</exec_depend>, one for each import in the node.[10] Using --dependencies at creation time "will automatically add the necessary dependency lines" for you, but the template writes them as <depend> tags.[12][9] The docs are not fully consistent here: the rosdep page says pure Python packages "should never use" <depend> and should use <exec_depend>, while the parameters tutorial shows <depend>rclpy</depend>.[11][13] Both build; following the rosdep page, our package declares: 

<exec_depend>rclpy</exec_depend>
<exec_depend>geometry_msgs</exec_depend>
<exec_depend>turtlesim_msgs</exec_depend>

Why bother, if the code already imports these modules? Because rosdep reads these lines. rosdep is "a meta-package manager": it looks up each key from package.xml in the rosdistro index and installs the matching system package through apt or dnf. Released ROS packages use their package name as the key.[11] Initialise it once per machine, then run it from the workspace root before every build of new code:[11][3] 

sudo rosdep init
rosdep update

cd ~/ros2_ws
rosdep install -i --from-path src --rosdistro lyrical -y

On success it prints #All required rosdeps installed successfully. The workspace tutorial explains the order: "You wouldn't want a build to fail after a long wait only to realize that you have missing dependencies."[3] Note that "rosdep only works on Linux and macOS; Windows is not supported."[11]

06. Writing the node: the Lyrical rclpy pattern

The Lyrical publisher tutorial gives the pattern every Python node in this course follows. Its main function looks like this:[10] 

import rclpy
from rclpy.executors import ExternalShutdownException
from rclpy.node import Node

from std_msgs.msg import String

# ... class MinimalPublisher(Node) defined here ...

def main(args=None):
    try:
        with rclpy.init(args=args):
            minimal_publisher = MinimalPublisher()
            rclpy.spin(minimal_publisher)
    except (KeyboardInterrupt, ExternalShutdownException):
        pass


if __name__ == '__main__':
    main()

Read it as a lifecycle. rclpy.init starts the ROS client library, and because it is used as a context manager in a with block, the library is shut down automatically when the block ends. The Lyrical tutorial therefore has no explicit destroy_node() or rclpy.shutdown() call, which you may still see in code written for older distributions.[10] Inside the block you construct the node. Its __init__ calls super().__init__('minimal_publisher') to name the node and creates its publishers, subscriptions and timers. rclpy.spin() then "spins" the node "so its callbacks are called." Pressing Ctrl+C raises KeyboardInterrupt, which the except catches so the program exits quietly.[10]

Three calls do most of the work. self.create_publisher(String, 'topic', 10) declares the message type, the topic name and a queue size of 10; "Queue size is a required Quality of Service (QoS) setting that limits the amount of queued messages if a subscriber is not receiving them fast enough." self.create_timer(0.5, self.timer_callback) runs a callback every 0.5 seconds. self.create_subscription(String, 'topic', self.listener_callback, 10) registers a callback that is called "as soon as it receives a message", so a subscriber needs no timer. The topic name and type must match on both sides.[10]

Topics are not the only tools in a node. A service server is created with create_service(Type, 'name', callback), where the callback fills in and returns a response; a client uses create_client, wait_for_service and call_async, and the docs warn: "Do not use rclpy.spin_until_future_complete in a ROS 2 callback."[12] A node can also declare a parameter with self.declare_parameter('my_parameter', 'world') (the type comes from the default value), read it with self.get_parameter('my_parameter').get_parameter_value().string_value, and have it changed at run time with ros2 param set.[13] Lesson 3.7 covers parameters in depth; for now we use topics only.

07. Turtlesim's interface on Lyrical

Before writing a controller, check exactly what the robot listens to and reports. The Lyrical Turtlesim source shows that each turtle subscribes to <name>/cmd_vel (geometry_msgs/msg/Twist) and publishes <name>/pose (turtlesim_msgs/msg/Pose) and <name>/color_sensor. Each turtle also offers the services set_pen, teleport_relative and teleport_absolute and the action rotate_absolute, while the Turtlesim node itself provides clear, reset, spawn and kill.[14] For the first turtle, the names become /turtle1/cmd_vel and /turtle1/pose.

Three details from the source shape our design:[14]

  • Only two velocity fields are used: Turtlesim reads linear.x and angular.z from the Twist. It uses linear.y only if its holonomic parameter is true.[14]
  • A one-second command timeout: If more than 1.0 s passes since the last cmd_vel message, Turtlesim sets all velocities to zero. A node that publishes once and stops will see the turtle move briefly and halt.[14]
  • Walls are hard limits: Positions are clamped to the canvas, and Turtlesim logs "Oh no! I hit the wall!" when the turtle reaches the edge.[14]

The Pose message has five float32 fields: x, y, theta, linear_velocity and angular_velocity.[15] In the published pose, y points up the screen and theta is the heading in radians.[14] The first turtle spawns at x=5.544445, y=5.544445, theta=0.0, near the centre and facing to the right.[16] Turtlesim's topics use a reliable QoS profile that keeps the last 7 messages.[14]

Old tutorials will break: turtlesim_msgs

Starting with Kilted, Turtlesim's message and service definitions moved out of the turtlesim package into a new turtlesim_msgs package. On the Kilted and Lyrical branches turtlesim_msgs/msg/Pose.msg exists and turtlesim/msg/Pose.msg does not; on Humble and Jazzy it is the other way round.[15][14] Many tutorials online still write from turtlesim.msg import Pose and <depend>turtlesim</depend>. On Lyrical, use from turtlesim_msgs.msg import Pose, from turtlesim_msgs.srv import TeleportAbsolute, and depend on turtlesim_msgs. You can confirm with ros2 interface show turtlesim_msgs/msg/Pose.

08. Designing the square driver: a timer-driven state machine

The simplest way to draw a square is open-loop: drive forward for a fixed time, turn for a fixed time, and repeat four times, without ever checking where the turtle actually is. The timeout from Section 07 decides the structure. We cannot send one "go forward" message and sleep; we must keep publishing. So the node uses a timer that fires 10 times a second (every 0.1 s, well under the 1.0 s timeout) and a small state machine with three states: FORWARD, TURN and DONE.[14][10]

The timing is simple kinematics. At 1.0 m/s, a 2.0 m side takes 2.0 s. At 1.0 rad/s, a 90° turn (π/2 rad) takes about 1.57 s. Starting near (5.54, 5.54), a 2 m square stays well clear of the walls. Replace the generated ~/ros2_ws/src/turtle_square/turtle_square/square_driver.py with the code below. It is an example written for this lesson, so test it on your own Lyrical install before relying on it. 

import math

import rclpy
from rclpy.executors import ExternalShutdownException
from rclpy.node import Node

from geometry_msgs.msg import Twist


class SquareDriver(Node):

    def __init__(self):
        super().__init__('square_driver')
        self.publisher_ = self.create_publisher(Twist, '/turtle1/cmd_vel', 10)
        self.dt = 0.1             # timer period in seconds (10 Hz)
        self.side_length = 2.0    # metres
        self.speed = 1.0          # forward speed, m/s
        self.turn_speed = 1.0     # turning rate, rad/s
        self.state = 'FORWARD'
        self.elapsed = 0.0        # time spent in the current state
        self.sides_done = 0
        self.timer = self.create_timer(self.dt, self.timer_callback)

    def timer_callback(self):
        # 1. Decide whether it is time to change state.
        if self.state == 'FORWARD' and self.elapsed >= self.side_length / self.speed:
            self.state, self.elapsed = 'TURN', 0.0
        elif self.state == 'TURN' and self.elapsed >= (math.pi / 2) / self.turn_speed:
            self.sides_done += 1
            self.get_logger().info('Finished side %d' % self.sides_done)
            self.state, self.elapsed = 'FORWARD', 0.0
            if self.sides_done == 4:
                self.state = 'DONE'

        # 2. Build the command for the current state.
        msg = Twist()             # every field starts at 0.0
        if self.state == 'FORWARD':
            msg.linear.x = self.speed
        elif self.state == 'TURN':
            msg.angular.z = self.turn_speed
        # In DONE we keep publishing zeros, so the turtle stays stopped.

        self.publisher_.publish(msg)
        self.elapsed += self.dt


def main(args=None):
    try:
        with rclpy.init(args=args):
            node = SquareDriver()
            rclpy.spin(node)
    except (KeyboardInterrupt, ExternalShutdownException):
        pass


if __name__ == '__main__':
    main()

Notice how each piece maps to the tutorial pattern: the publisher and timer are created in __init__, all the behaviour lives in the timer callback, and main uses the with rclpy.init(...) block.[10] The callback first checks for a state change and then builds the message, so the command sent on each tick always matches the current state.

Do not expect a perfect square. The timer only checks the clock every 0.1 s, so a turn that should last 1.57 s actually lasts until the next tick after that, and Turtlesim integrates the motion in its own small time steps.[14] These small errors add up from corner to corner, and the last side will not land exactly on the start point. That drift is the real lesson of open-loop control, and it motivates the feedback version in Section 10.

09. Building, running and troubleshooting

Because we used --node-name square_driver, the entry point 'square_driver = turtle_square.square_driver:main' is already in setup.py.[7][9] From the workspace root, check dependencies and build just this package:[7][3] 

cd ~/ros2_ws
rosdep install -i --from-path src --rosdistro lyrical -y
colcon build --packages-select turtle_square

A few colcon options are worth knowing. --packages-up-to builds a package plus everything it depends on. --symlink-install "saves you from having to rebuild every time you tweak python scripts" (on Windows it needs administrator rights or Developer Mode). --event-handlers console_direct+ shows build output live instead of only in log/, and --executor sequential builds one package at a time on low-resource machines such as a Raspberry Pi.[3][5] Even with a symlink install, rebuild after you change setup.py, setup.cfg or package.xml, because those files control what gets installed.

Now open a new terminal for each program and source the overlay in each one that runs your package:[3][10] 

# Terminal 1
source /opt/ros/lyrical/setup.bash
ros2 run turtlesim turtlesim_node

# Terminal 2
source /opt/ros/lyrical/setup.bash
cd ~/ros2_ws
source install/setup.bash
ros2 run turtle_square square_driver

The turtle should trace four sides and stop, and Terminal 2 should log "Finished side 1" through "Finished side 4". In a third terminal you can watch it work with ros2 topic echo /turtle1/pose, check who is connected with ros2 topic info /turtle1/cmd_vel, or open rqt_graph from lesson 3.5. To clear the drawing and put the turtle back in the centre, call ros2 service call /reset std_srvs/srv/Empty; if that type is rejected, check it with ros2 service type /reset.[14]

When something goes wrong, the message usually points to one of a small number of causes:

  • Package 'turtle_square' not found: This terminal has not sourced install/setup.bash, or the build failed. Source the overlay in a fresh terminal and check the build output.[3]
  • No executable found: ros2 run looks for the program under lib/<package>. Check that setup.cfg exists, that the console_scripts entry is spelled correctly, and that you rebuilt after editing setup.py. Community reports trace this error to a deleted setup.cfg or a forgotten source.[10][17]
  • ModuleNotFoundError for turtlesim.msg: The code was written for Jazzy or earlier. Import from turtlesim_msgs.msg instead.[15]
  • The node runs but the turtle does not move: Check the topic name with ros2 topic info /turtle1/cmd_vel, and make sure you publish repeatedly from a timer, not once, because of the one-second timeout.[14]
  • Strange build problems after sourcing: You built in a terminal where the overlay was sourced. Open a new terminal, source only the underlay, and build again.[3]

10. Stretch: closing the loop with pose feedback

A closed-loop version stops guessing from time and uses the pose Turtlesim reports. Subscribe to /turtle1/pose and store the latest message. In FORWARD, record the start point at the beginning of each side and keep driving until the straight-line distance from it reaches the side length. In TURN, aim for a target heading 90° past the previous one and turn with a speed proportional to the remaining heading error. The fields come straight from the Pose message.[15][10] The fragment below shows the new pieces; like the main example, treat it as a starting point to test, not finished code. 

from turtlesim_msgs.msg import Pose   # Lyrical: turtlesim_msgs, not turtlesim

# in __init__:
        self.pose = None
        self.pose_sub = self.create_subscription(
            Pose, '/turtle1/pose', self.pose_callback, 10)

    def pose_callback(self, msg):
        self.pose = msg

# in timer_callback (skip the tick while self.pose is None):
        # FORWARD: distance from the corner where this side started
        dist = math.hypot(self.pose.x - self.start_x, self.pose.y - self.start_y)

        # TURN: heading error wrapped to the range -pi..pi
        error = math.atan2(math.sin(self.target_theta - self.pose.theta),
                           math.cos(self.target_theta - self.pose.theta))
        msg.angular.z = max(-1.0, min(1.0, 2.0 * error))   # proportional, clamped
        # switch back to FORWARD when abs(error) < 0.01

The atan2(sin, cos) trick keeps the error between −π and π, so the turtle always turns the short way even when the target heading wraps past π. The proportional term slows the turn as the error shrinks, which is the same idea you will meet again in the control chapter. Remember to add turtlesim_msgs to package.xml (we already did) and rebuild.

Try it
  1. Create the turtle_square package with ros2 pkg create as in Section 03, open setup.py and package.xml, and find the entry point, the py.typed line and the dependency tags you asked for.
  2. Add the timer-based square_driver node from Section 08, build with colcon build --packages-select turtle_square, and run it against turtlesim_node in a fresh, sourced terminal. The code is an example to test on your install, so watch the log and the drawing carefully.
  3. Change the timer period from 0.1 to 1.5 seconds and run it again. Explain what you see using Turtlesim's one-second command timeout.
  4. Measure the drift: run ros2 topic echo /turtle1/pose and compare the final x, y and theta with the start pose.
  5. Stretch goal: build the pose-feedback version from Section 10 and compare how closely its square closes with the open-loop version.
