3.2 ROS 1 vs. ROS 2

Gerald Lê

01. Why the robotics community rebuilt ROS from scratch

ROS began life as the development environment for Willow Garage's PR2 robot, and that use case shaped its design: a single robot, workstation-class computers on board, no real-time requirements, excellent network connectivity (wired or close-range, high-bandwidth wireless), and mostly academic research applications.[1] Work on ROS started in November 2007.[1]

ROS 1 succeeded far beyond those first assumptions. By the time ROS 2 was planned, ROS was running on wheeled robots of all sizes, legged humanoids, industrial arms, self-driving cars, aerial and surface vehicles, and ROS-based products were reaching the market in manufacturing, agriculture and commercial cleaning.[1] The ROS team listed new use cases it had not planned for: teams of multiple robots, small embedded platforms, real-time systems, poor or lossy networks, and production environments.[1]

Meeting those needs required deep changes to discovery, transport and the APIs. The team considered building them into ROS 1 but concluded that changing a system so many people relied on was too risky, so ROS 2 was built as a new, parallel set of packages that is not API-compatible with ROS 1 but can interoperate with it through bridges.[1]

02. Master versus decentralized discovery

One of the biggest differences between ROS 1 and ROS 2 lies in how nodes find each other on the network.[2]

ROS 1 relied on a central coordinator, the ROS master, started with roscore.[2][3] Nodes used this master-based discovery system to find each other, and their data was carried by ROS 1's own TCPROS and UDPROS wire protocols.[2] The same roscore also held the global parameter store.[3]

This central master design brought two well-known problems:

  • Central Point of Failure: Discovery depended on one master process. DDS discovery, by contrast, is completely distributed by default, so “there is no central point of failure.”[2]
  • Multi-Robot Headaches: Multi-robot systems were possible in ROS 1, but there was no standard approach, and the ROS team described them as “all somewhat of a hack on top of the single-master structure of ROS.”[1]

How do ROS 2 nodes find each other? They discover each other automatically through DDS, with no master.[4][2] ROS 2 has no roscore.[3] Instead, it is built on the Data Distribution Service (DDS), an industry standard created by the Object Management Group (OMG) and implemented by several vendors.[2][5]

DDS implementations talk to each other with the RTPS wire protocol.[5][6] When a node starts, it advertises its presence to other nodes in the same ROS domain, and they reply with information about themselves so connections can be made. Nodes keep advertising periodically, so late arrivals are found, and they announce when they go offline.[4] This discovery traffic uses multicast,[7] and there is no central server to crash and no master that must be started first.[2]

03. The ROS Middleware (RMW) abstraction layer

ROS 2 is not tied to any single vendor's communication engine. The ROS 2 core talks to the middleware through a C interface called rmw (ROS Middleware), and each middleware has an adapter package, such as rmw_fastrtps_cpp for Fast DDS or rmw_zenoh_cpp for Zenoh, that implements that interface.[8]

The RMW layer sits below the client libraries (rclcpp for C++ and rclpy for Python).[8] Both C++ and Python nodes read an environment variable, RMW_IMPLEMENTATION, that selects which middleware to use at run time, so the same application code can run on different middlewares.[9]

The main RMW implementations for Lyrical Luth are:[5][10]

  • rmw_fastrtps_cpp: Built on eProsima Fast DDS (Apache 2 license). It is the default RMW in Lyrical Luth, is packaged with the binary releases, and has Tier 1 support.[5][10]
  • rmw_cyclonedds_cpp: Built on Eclipse Cyclone DDS (Eclipse Public License 2.0). It is fully supported, packaged with the binary releases, and Tier 1 in Lyrical.[5][10]
  • rmw_connextdds: Built on RTI Connext DDS, which uses a commercial or research license. Support is included in the ROS binaries, but Connext itself is installed separately. In Lyrical it is Tier 1 on all architectures except arm64.[5][10]
  • rmw_zenoh_cpp: Built on Eclipse Zenoh, a non-DDS protocol. It became Tier 1 in Kilted Kaiju (2025) and remains Tier 1 in Lyrical Luth.[11][10] The documentation describes Zenoh as a more lightweight alternative to DDS whose low wire overhead and flexible routing suit challenging network conditions; a Zenoh router is used to help nodes find each other.[5][12]

To switch middleware implementations on a machine, an engineer installs the corresponding RMW package and sets the environment variable in the terminal:[13] 

sudo apt install ros-lyrical-rmw-cyclonedds-cpp
export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp

04. Quality of Service (QoS) in practice

ROS 1 primarily supported only TCP, and its default transport, TCPROS, was reliable.[14] TCP guarantees that every byte arrives in order, but it does so by holding back newer data while lost packets are retransmitted.

As an illustration, imagine an autonomous vehicle whose Wi-Fi link drops a few packets of lidar data. A transport that insists on retransmitting the missing data delays the newer scans behind them, and by the time the old frames arrive they may be too stale to use for obstacle avoidance. For sensor data, the ROS documentation notes, it is usually more important to receive readings quickly than to receive every one of them.[14]

ROS 2 solves this by introducing Quality of Service (QoS) policies, which let a connection be “as reliable as TCP or as best-effort as UDP.” QoS profiles can be set independently for each publisher, subscription, service server and client.[14] The main policies are:[14]

  • History and Depth:
    • Keep Last: Only stores up to N samples, where N is the queue depth (the default profile uses a depth of 10).[14]
    • Keep All: Stores all samples, subject to the resource limits configured in the underlying middleware.[14]
  • Reliability:
    • Best Effort: Attempts to deliver samples but may lose them if the network is not robust. The predefined sensor data profile uses best effort with a small queue, because getting the latest sample quickly matters more than getting every sample.[14]
    • Reliable: Guarantees that samples are delivered, retrying several times if needed. This is the default for publishers, subscriptions and services. Even reliable delivery in ROS 2 runs over UDP.[14]
  • Durability:
    • Volatile: No attempt is made to keep old samples, so a subscriber only receives messages published after it connects. This is the default.[14]
    • Transient Local: The publisher keeps samples for “late-joining” subscriptions, such as an RViz window opened ten minutes after the robot started. Combined with a queue depth, it provides behavior similar to “latched” topics in ROS 1, which suits topics such as a static map.[14]
  • Lifespan and Deadline: Lifespan is the longest time between publishing and receiving a message before it is considered stale and silently dropped. Deadline is the expected maximum time between consecutive messages; if a publisher or subscription misses it, the application can be notified through a “deadline missed” QoS event callback.[14]

05. The QoS compatibility rule

A common source of confusion for newcomers to ROS 2 is the “silent topic”: a publisher is running and a subscriber is listening, but no messages are delivered. A frequent cause is a QoS incompatibility, because a connection is only made if the publisher and subscription have compatible QoS profiles.[14]

Compatibility follows a “Request vs Offered” model:[14]

The Rule of QoS Compatibility

A subscription requests the minimum quality it will accept, and a publisher offers the maximum quality it can provide. A connection is made only if no requested policy is more stringent than the offered one: Offered QoS ≥ Requested QoS.[14]

The documentation's compatibility tables give these results for Reliability and Durability:[14]

Publisher Offers Subscriber Requests Connection Status Technical Explanation
Reliable Reliable Compatible Both endpoints agree on delivery acknowledgments.
Reliable Best Effort Compatible Publisher offers higher quality than requested; subscriber receives data.
Best Effort Best Effort Compatible Both endpoints accept that some samples may be lost.
Best Effort Reliable INCOMPATIBLE Subscriber demands delivery guarantees that the publisher cannot provide. No connection is made.
Volatile Transient Local INCOMPATIBLE Subscriber asks for old (latched) samples, but the publisher keeps none. No communication.

If your subscriber is not receiving data, you can diagnose the issue on the command line using: 

ros2 topic info /my_topic --verbose

With --verbose, this command lists the publishers and subscribers on the topic together with their QoS profiles, so you can compare what each side offers and requests.[15]

06. Managed lifecycle nodes

An ordinary node starts working as soon as it is created. In a complex cell, that can cause startup races: a planner may begin sending commands before a motor driver is ready. Hardware drivers for cameras, lidars and motors in particular need to be started, configured and shut down in a controlled order.[16]

ROS 2 introduced managed nodes, also called lifecycle nodes, implemented in C++ by the rclcpp_lifecycle package.[16] A managed node follows a state machine with four primary states:[17]

  • Unconfigured: The state immediately after the node is created (and the state it may return to after an error). It is expected to hold no stored state.[17]
  • Inactive: The node is not doing any processing. This state lets it be configured (parameters, publishers and subscriptions) without running; it does not read topics, process data or answer functional service requests.[17]
  • Active: The main state, in which the node processes data, responds to service requests and produces output.[17]
  • Finalized: The terminal state just before the node is destroyed; it remains visible to introspection and debugging tools.[17]

Moving out of a primary state (except after an error in Active) requires an action from an external supervisory process, through transitions such as configure, activate, deactivate, cleanup and shutdown.[17] A supervisor can therefore bring every sensor driver to Inactive first and only activate the cell once each driver reports that its hardware is ready, so hardware is only used when it is ready and is released safely on shutdown.[16][17]

07. Programmable Python launch files

A ROS system usually has many nodes, and starting each one by hand quickly becomes cumbersome. The launch system starts many nodes with one command, passes them their arguments, and monitors the processes it started.[18] In ROS 1, launch files were written in XML.[19]

In ROS 2, launch files can be written in XML, YAML or Python (*.launch.py), and for most applications the choice comes down to developer preference.[18][19] Python is the most flexible option: you can use the whole language and its libraries, and the launch system itself is written in Python, so a Python launch file can reach features that XML and YAML do not expose. The trade-off is that Python launch files can be more complex and verbose.[19]

Here is an example Python launch file that starts Turtlesim and a keyboard teleoperation node: 

from launch import LaunchDescription
from launch_ros.actions import Node
from launch.actions import DeclareLaunchArgument
from launch.substitutions import LaunchConfiguration

def generate_launch_description():
    use_sim_time = LaunchConfiguration('use_sim_time', default='false')

    return LaunchDescription([
        DeclareLaunchArgument('use_sim_time', default_value='false', description='Use simulation clock'),
        Node(
            package='turtlesim',
            executable='turtlesim_node',
            name='sim',
            parameters=[{'use_sim_time': use_sim_time}]
        ),
        Node(
            package='turtlesim',
            executable='turtle_teleop_key',
            name='teleop',
            output='screen'
        )
    ])

Launch files also support event handlers, which react to process events while the system runs (for example, shutting everything down when one important node exits), as well as launch arguments, substitutions and starting composable nodes in a container.[20][18]

08. Multi-platform and security enhancements

Beyond messaging and discovery, ROS 2 expanded the core system on three fronts:

  • Cross-Platform Support: For Lyrical Luth, Ubuntu 26.04 (amd64 and arm64) and Windows 11 (amd64) are Tier 1 platforms, RHEL 10 is Tier 2, and macOS is Tier 3.[10] Windows users therefore get official binaries and can run ROS 2 directly on Windows workstations.[10][21]
  • Built-in Security (SROS 2): ROS 2 can secure communication between nodes: it can encrypt data in transit, authenticate the participants sending data, check data integrity and enforce domain-wide access controls.[22] These services come from the security plugins defined by the OMG DDS Security specification, and identities are managed with certificates signed by an identity certificate authority.[22]
  • Microcontroller Integration (micro-ROS): The ROS 2 designers wanted small computers, including bare-metal microcontrollers, to be first-class participants instead of being kept outside ROS behind a device driver.[1] The micro-ROS project “puts ROS 2 onto microcontrollers” and supports several real-time operating systems.[23]

09. Migration timeline: from Noetic to Lyrical Luth

For several years, ROS 1 and ROS 2 coexisted in the robotics community. Developers connected legacy ROS 1 nodes to ROS 2 systems with the ros1_bridge package.[24]

That transition period is now over. ROS Noetic Ninjemys, the last ROS 1 distribution, was marked End-of-Life (EOL) on May 31, 2025; after the final sync on May 29, no new Noetic changes were accepted and regressions in binary packages could no longer be fixed.[25][26] ROS 1 has reached the end of development with no new releases planned, while ROS 2 releases a new distribution every year.[26]

New robotics development therefore targets ROS 2. Long Term Support (LTS) releases have so far appeared every two years in May, each supported for five years: ROS 2 Humble Hawksbill (Ubuntu 22.04, May 2022 to May 2027), ROS 2 Jazzy Jalisco (Ubuntu 24.04, May 2024 to May 2029), and our target platform, ROS 2 Lyrical Luth, released on May 22, 2026 for Ubuntu 26.04 LTS and supported until May 2031.[27][28][29][30][10]

Try it
  1. Why is a Best Effort reliability QoS setting preferred over Reliable for high-resolution video streams from a moving mobile robot? What happens on lossy Wi-Fi if Reliable is used?
  2. You deploy a laser scanner publishing with Best Effort reliability, but your autonomous navigation node subscribes using Reliable reliability. Will the navigation node receive laser scans? Explain why or why not using the QoS compatibility rule.
  3. Explain the key difference between a Transient Local durability setting and a Volatile durability setting. Which one would you choose for a map topic that only publishes once every ten minutes?
