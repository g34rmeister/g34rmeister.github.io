3.2 ROS 1 vs. ROS 2

Gerald Lê

01. Why the robotics community rebuilt ROS from scratch

When the Robot Operating System was conceived at Willow Garage in 2007, its creators targeted a very specific hardware setup: a single PR2 mobile manipulation robot operating indoors on a dedicated, wired Gigabit Ethernet connection, running under the care of expert software engineers.[1]

ROS 1 succeeded far beyond those initial laboratory boundaries. Within five years, engineers were using ROS to run multi-vehicle aerial drone swarms over lossy Wi-Fi, industrial automotive welding arms requiring sub-millisecond determinism, and safety-critical surgical robots.[2]

Pushing ROS 1 into these demanding commercial domains revealed fundamental architectural bottlenecks that could not be solved with minor patches. Rather than maintaining backwards compatibility with flawed architectural assumptions, the robotics community undertook a comprehensive, ground-up rewrite, creating ROS 2.[2]

02. Master versus decentralized discovery

The most profound difference between ROS 1 and ROS 2 lies in how nodes find each other on the network.[2]

ROS 1 relied on a centralized master coordinator process named roscore.[1] When a node started, it called an XML-RPC service on the master to register its published and subscribed topics. The master acted as a central phonebook, introducing publisher IP addresses to subscribers so they could establish point-to-point TCP sockets (TCPROS).

This central master architecture introduced three severe operational vulnerabilities:[2]

  • Single Point of Failure: If the roscore process crashed or suffered a segmentation fault, no new nodes could discover each other. If the host machine running the master rebooted, the entire robotic computational graph disintegrated.
  • Multi-Robot Network Headaches: Coordinating multiple autonomous mobile robots in a warehouse required complex master-synchronization bridges (like multimaster_fkie) that were notoriously fragile over fluctuating industrial Wi-Fi.
  • Boot Ordering Fragility: Nodes started before roscore was completely initialized would throw fatal connection errors and crash on startup.

How do ROS 2 nodes find each other? They discover each other automatically through DDS, with no master.[2][3] ROS 2 eliminated roscore completely. Instead, it adopted the industry-standard Data Distribution Service (DDS), standardized by the Object Management Group (OMG).[3]

Under DDS, nodes use the Real-Time Publish-Subscribe (RTPS) discovery protocol over UDP multicast. When a node starts up, it broadcasts discovery announcements across the local network subnet. Peer nodes listen on defined multicast ports, parse the announcements, and negotiate peer-to-peer data links directly. There is no central server to crash, no master to boot first, and no single point of failure.[3]

03. The ROS Middleware (RMW) abstraction layer

One of the most elegant architectural designs of ROS 2 is that it is not tied to any single vendor's communication engine. Instead, the ROS 2 core defines an internal C abstraction layer known as the ROS Middleware (RMW) interface.[4]

The RMW layer sits between the higher-level client libraries (rclcpp for C++ and rclpy for Python) and the low-level communication library. As long as a middleware vendor writes a standard adapter implementing the RMW functions (such as creating publishers, registering topic callbacks, and configuring network discovery), ROS 2 can run on top of it without changing a single line of application source code.[4]

Several major RMW implementations are maintained across the ecosystem:[4]

  • rmw_fastrtps_cpp: Built on eProsima Fast DDS. Fast DDS is an open-source, high-performance C++ implementation of RTPS and DDS, serving as the default middleware in several long-term support releases.[5]
  • rmw_cyclonedds_cpp: Built on Eclipse Cyclone DDS. Cyclone DDS is a lightweight, high-performance C implementation developed by Eclipse Foundation, widely favored in multi-robot fleets and academic research for its minimal CPU and memory footprint.[6]
  • rmw_connextdds: Built on Real-Time Innovations (RTI) Connext DDS. RTI Connext is a commercial DDS suite certified for safety-critical medical devices (IEC 62304), avionics systems (DO-178C), and automotive functional safety (ISO 26262).[7]
  • rmw_zenoh_cpp: Built on Eclipse Zenoh. Beginning with the Kilted Kaiju release in 2025 and continuing into Lyrical Luth, Zenoh is supported as a Tier 1 non-DDS alternative.[8][9] Zenoh eliminates multicast discovery overhead by using lightweight routers, making it exceptionally effective across lossy Wi-Fi links, cellular 5G networks, and microcontrollers.

To switch middleware implementations on a machine, an engineer simply installs the corresponding RMW package and sets an environment variable in the terminal: 

sudo apt install ros-lyrical-rmw-cyclonedds-cpp
export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp

04. Quality of Service (QoS) in practice

In ROS 1, communication was strictly one-size-fits-all. Every topic operated over TCP sockets (TCPROS) by default. TCP guarantees that every byte arrives in order, but it does so by holding up subsequent packets and retransmitting lost data. While this is acceptable on a wired desk, it is disastrous for real-time mobile robots.

If an autonomous vehicle driving at 10 meters per second drops two Wi-Fi packets of lidar data, TCP will stall the incoming stream to retransmit the missing frames. By the time the old frames arrive, they are 300 milliseconds stale and dangerous to use for obstacle avoidance. The robot needs the newest sensor frame immediately, even if a few historical packets were lost.

ROS 2 solves this by introducing Quality of Service (QoS) policies.[10] Developers configure the communication behavior for every publisher and subscription independently:

  • History and Depth:
    • Keep Last: Only stores up to a configured queue depth N (e.g., depth = 10). If the queue fills up, the oldest unread message is discarded to make room for fresh data.
    • Keep All: Retains every message up to the resource limits of the operating system memory.
  • Reliability:
    • Best Effort: The publisher transmits data once over UDP without waiting for acknowledgments or retrying dropped packets. Prioritizes low latency and data freshness over 100% arrival guarantees. Ideal for high-rate sensor streams (cameras, lidars, IMUs).
    • Reliable: The publisher guarantees that every message arrives in order through automatic acknowledgments and retransmissions. Ideal for motor command trajectories, service requests, and emergency stop triggers.
  • Durability:
    • Volatile: Historical samples are not preserved. Subscribers only receive messages published after they successfully connect.
    • Transient Local: The publisher retains the last N samples in local memory. When a new subscriber connects late (such as an RViz visualization window opened ten minutes after the robot started), the publisher immediately sends the saved historical samples. This replaces the "latched" topic mechanism from ROS 1, making it ideal for static occupancy grid maps and robot coordinate transform trees.
  • Lifespan and Deadline: Lifespan defines how long a message remains valid before being expired from queues. Deadline defines the maximum expected interval between consecutive messages; if a sensor node fails to publish within the deadline window, the middleware triggers an alert callback.

05. The QoS compatibility rule

A common source of confusion for newcomers to ROS 2 is the "silent topic" problem: a publisher is visibly running, a subscriber is actively listening, but zero messages are delivered. In most cases, this occurs because of a QoS incompatibility.[10]

In DDS, QoS negotiation follows a strict rule:

The Rule of QoS Compatibility

A connection is established between a publisher and a subscriber if and only if the publisher offers a level of service greater than or equal to what the subscriber requests: Offered QoS ≥ Requested QoS.[10]

Let us examine how this rule applies to Reliability and Durability:

Publisher Offers Subscriber Requests Connection Status Technical Explanation
Reliable Reliable Compatible Both endpoints agree on delivery acknowledgments.
Reliable Best Effort Compatible Publisher offers higher quality than requested; subscriber receives data.
Best Effort Best Effort Compatible Both endpoints accept unacknowledged UDP packets.
Best Effort Reliable INCOMPATIBLE Subscriber demands delivery guarantees that the publisher cannot provide. Connection rejected.
Volatile Transient Local INCOMPATIBLE Subscriber demands historical latched data, but publisher retains zero history. Connection rejected.

If your subscriber is not receiving data, you can diagnose the issue on the command line using: 

ros2 topic info /my_topic --verbose

This command displays the exact Offered and Requested QoS profiles for every active publisher and subscriber on that topic.

06. Managed lifecycle nodes

In ROS 1, nodes had no formal state machine. As soon as an executable launched, its constructor ran, hardware initialized, and publishers started streaming. In complex industrial cells, this lack of lifecycle management caused race conditions: path planners began commanding arm motions before motor drivers had finished homing their encoders.

ROS 2 introduced lifecycle nodes (managed nodes via rclcpp_lifecycle).[11] A managed node follows a strict, deterministic state machine with four primary states:[11]

  • Unconfigured: The node process has started, but no memory is allocated and no hardware connections exist.
  • Inactive: The node has parsed its configuration parameters and established hardware connections, but all publishers and execution loops are held in an idle state. It processes no execution callbacks.
  • Active: The node is fully operational. Publishers actively broadcast data, subscribers process messages, and execution timers run.
  • Finalized: The node has cleanly released hardware resources and terminated, ready for process destruction.

Orchestrator launch scripts can configure and verify all sensor drivers in the Inactive state first. Once every sensor confirms physical connectivity, the orchestrator triggers an activate transition simultaneously across the cell, ensuring zero startup race conditions.

07. Programmable Python launch files

In ROS 1, launching multiple nodes required writing static XML files parsed by roslaunch. While functional, XML cannot express conditional programmatic logic, such as: "Start the real camera driver if physical hardware is connected; otherwise start a synthetic image generator."

In ROS 2, the launch system was completely re-architected.[12] While XML and YAML remain supported, the primary launch format in ROS 2 is Python (*.launch.py).[12]

Python launch files give developers full programmatic power: 

from launch import LaunchDescription
from launch_ros.actions import Node
from launch.actions import DeclareLaunchArgument
from launch.substitutions import LaunchConfiguration

def generate_launch_description():
    use_sim_time = LaunchConfiguration('use_sim_time', default='false')

    return LaunchDescription([
        DeclareLaunchArgument('use_sim_time', default_value='false', description='Use simulation clock'),
        Node(
            package='turtlesim',
            executable='turtlesim_node',
            name='sim',
            parameters=[{'use_sim_time': use_sim_time}]
        ),
        Node(
            package='turtlesim',
            executable='turtle_teleop_key',
            name='teleop',
            output='screen'
        )
    ])

Python launch files support event handlers (such as shutting down the entire robot if an emergency stop node exits), dynamic launch arguments, path substitutions, and containerized node composition.

08. Multi-platform and security enhancements

Beyond messaging and discovery, ROS 2 expanded the core system architecture across three critical engineering fronts:[2][13]

  • Cross-Platform Parity: ROS 1 was effectively tied to Ubuntu Linux. ROS 2 treats Ubuntu Linux and 64-bit Windows (Windows 10/11) as Tier 1 supported operating systems, with macOS supported via community builds (Tier 3).[14] Industrial automation teams can run ROS 2 directly on Windows workstations alongside proprietary CAD/CAM software.
  • Native Security (SROS 2): ROS 1 had zero encryption or authentication; any computer on the local network could inject rogue commands. ROS 2 integrates DDS-Security standards, providing complete cryptographic authentication via X.509 digital certificates, TLS access control, and AES-GCM message encryption.[13]
  • Microcontroller Integration (micro-ROS): ROS 1 could only bridge to microcontrollers through a fragile serial protocol called rosserial. ROS 2 provides micro-ROS, putting true ROS 2 nodes directly onto real-time embedded microcontrollers (such as STM32, ESP32, and Raspberry Pi RP2040) running FreeRTOS or Zephyr.

09. Migration timeline: from Noetic to Lyrical Luth

For several years, ROS 1 and ROS 2 coexisted in the robotics community. Developers bridged legacy ROS 1 nodes with modern ROS 2 systems using the transitional ros1_bridge package.

That transition period has now formally concluded. On May 31, 2025, the final release of ROS 1, ROS Noetic Ninjemys, officially reached its End-of-Life (EOL).[15] The ROS 1 repository servers ceased building new packages, and security patches ended.

Today, all modern robotics development takes place exclusively in ROS 2. Long Term Support (LTS) releases provide stable five-year horizons: ROS 2 Humble Hawksbill (Ubuntu 22.04 LTS), ROS 2 Jazzy Jalisco (Ubuntu 24.04 LTS), and our target platform, ROS 2 Lyrical Luth, deployed on Ubuntu 26.04 LTS.[14]

Try it
  1. Why is a Best Effort reliability QoS setting preferred over Reliable for high-resolution video streams from a moving mobile robot? What happens on lossy Wi-Fi if Reliable is used?
  2. You deploy a laser scanner publishing with Best Effort reliability, but your autonomous navigation node subscribes using Reliable reliability. Will the navigation node receive laser scans? Explain why or why not using the QoS compatibility rule.
  3. Explain the key difference between a Transient Local durability setting and a Volatile durability setting. Which one would you choose for a map topic that only publishes once every ten minutes?
