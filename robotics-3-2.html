3.2 Your First Contribution

Gerald Lê

01. Contributions beyond code

In 2.4 Intro to ROS (Vendor-Agnostic), we saw that open robotics software provides a vendor-neutral foundation for industrial and research systems. The ROS chapter (Chapter 4) comes right after this one and guides you through writing nodes and packages. Before developing complex robotics packages, however, many newcomers wonder how to take their first step as an open-source contributor.

A common misconception among newcomers is that contributing requires writing complex code. Contributing to open source does not require contributing code, as non-code parts of a project are often the most neglected or overlooked.[1]

As 3.1 said, that work is public, so even small fixes show how you work.

A study by Igor Steinmacher found that 28% of casual contributions to open source are documentation, such as typo fixes, reformatting, or writing a translation.[1] Documentation tasks are accessible entry points because they allow you to improve the project while learning its terminology and conventions.

Beyond documentation, projects need organizational help. Non-code contributions include organizing projects by linking duplicate issues, suggesting issue labels, and asking clarifying questions on opened issues.[1]

Community support is another valuable contribution path. Contributors can help communities by answering user questions on forums or issues, reviewing code on submissions, and offering to mentor other contributors.[1]

Robotics frameworks actively encourage these non-code contributions. MoveIt encourages contributions beyond code, such as enhancing documentation, answering user questions, and reviewing open pull requests.[2] (Later in 4.8 Moving an Arm with MoveIt 2, we will use MoveIt 2 for robot arm motion planning.)

Reviewing open pull requests is not limited to project maintainers. The ros2_control project encourages non-maintainers to review pull requests to increase review pace, improve code quality, and spot overlooked limitations.[3] Reviewing incoming pull requests helps newcomers see how code changes are proposed and evaluated.

02. Finding a first issue in robotics projects

When you are ready to make a contribution, selecting the right issue helps you start smoothly. Large repositories often maintain hundreds of open tickets, ranging from broad feature requests to simple fixes.

To help beginners find accessible tasks, maintainers use dedicated labels. The first-timers-only label explicitly marks issues that are easier than normal and reserved exclusively for newcomers who have never contributed to open source before.[4]

You do not need to check individual repositories manually. Aggregator websites up-for-grabs.net and goodfirstissue.dev help newcomers find issues labeled up-for-grabs, jump-in, help wanted, or Good First Issue.[4]

Open-source robotics projects follow these labeling conventions:

  • ROS 2: ROS 2 marks approachable issues for first-time contributors with the label good first issue and broader tasks with help wanted across repositories.[5] (4.1 Definition and Introduction explains what ROS is and how its software ecosystem is structured.)
  • MoveIt: MoveIt provides a dedicated section directing newcomers to tackle their first issue by browsing GitHub issues labeled Good First Issue.[2]
  • Gazebo: Gazebo maintainers triage project issues and apply the help wanted label to issues that the team thinks should be tackled by the community.[6]
  • ros2_control: The ros2_control project maintains a dedicated Contributing Board project board to help newcomers find issues suitable for first contributions.[3]

Browsing these labeled issues or project boards lets you inspect the problem description, read previous comments, and pick a manageable task.

03. The fork, clone, and branch workflow

Once you select an issue to address, you carry out your work using Git and GitHub. Because you do not have direct write permissions to the official repository, you work in a copy under your account.

When opening a pull request on GitHub, contributors fork the repository, clone locally, connect upstream as a remote, and create an edit branch.[1]

Each step in this sequence has an explicit purpose:

  • Fork: A fork is a personal copy of the repository hosted on your GitHub account. Forking lets you make changes without affecting the original project.
  • Clone: Cloning copies the files from your remote GitHub fork to your local computer so that you can edit files and run tests.
  • Upstream remote: The original project repository is called the upstream repository. Connecting upstream as a remote allows your local Git client to track and fetch changes from the original project.
  • Edit branch: Rather than modifying the main branch directly, you create a dedicated branch for your edits. A separate branch keeps your proposed changes isolated.

This workflow separates your personal experiments from the official codebase, making it straightforward to prepare clean pull requests.

04. Draft pull requests and staying in sync

Open-source repositories change constantly as other contributors merge changes. Keeping your edit branch aligned with upstream development prevents integration issues.

Pulling in upstream changes often keeps a local repository up to date and reduces the likelihood of encountering merge conflicts on a pull request.[1] A merge conflict occurs when two contributors edit the same lines in a file, requiring manual reconciliation. Frequent upstream pulls identify overlapping changes early.

When you begin preparing your submission, you do not have to wait until every detail is finished. Pull requests do not have to represent finished work and can be opened early as a draft or marked WIP to get early feedback from reviewers.[1]

Opening a draft pull request (or marking it with WIP, meaning Work In Progress) signals to maintainers that your work is still evolving. Reviewers can check your overall direction and suggest improvements before you invest time completing every detail.

05. Communication norms: public collaboration and reproduction

Open-source development relies on transparent communication among people distributed across the world. Following standard community norms makes your interactions effective and polite.

Communication in open source should remain public rather than via private messages to maintainers, allowing the wider community to learn from discussions.[1] When discussions occur in public issue trackers or forums, other contributors encountering similar problems can read the explanations and benefit from past solutions.

When reporting a bug or asking for technical guidance, clarity is required. Effective communication requires providing context and reproduction steps when reporting errors, and checking existing documentation and issues beforehand.[1] Providing exact error messages and the sequence of steps needed to reproduce an error allows maintainers to diagnose the problem quickly without guessing.

Coordinating on open issues prevents wasted effort. Commenting on an open issue alerts others that a contributor is working on it to prevent duplicate effort, and documenting self-resolved solutions benefits others.[1] If you find the solution to an issue yourself after asking, writing a brief explanation of how you solved it before closing the issue creates a permanent resource for the community.

When proposing new features or major modifications, community discussion comes first. If unsure about a proposed feature, MoveIt contributors are encouraged to open an issue or post on Discourse first to request community feedback.[2] Discussing design ideas on Discourse or an issue tracker confirms that maintainers support the concept before anyone writes code.
