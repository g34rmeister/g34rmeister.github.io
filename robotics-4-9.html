      4.9 ROS-Industrial and Vendor Drivers

      Gerald Lê
      Chapter 4, lesson 9 of 10 ← Previous: 4.8 Moving an Arm with MoveIt 2 Next: 4.10 Lab: From a Failing Test to a Bug Report →

      01. Why ROS needs a driver for every robot brand

      Suppose you plan a smooth arm move on your Linux personal computer (PC) using MoveIt 2. When you try to send that plan to a real factory arm, like a Universal Robots (UR) or KUKA robot, the arm cannot read it directly. Every robot brand runs its own software inside its control cabinet, and none of them understand the Robot Operating System (ROS) out of the box.

      In lesson 2.3, you met four vendor languages: RAPID for ABB, URScript for Universal Robots, KRL for KUKA, and TP for FANUC. Each language runs inside the maker's own robot controller. That cabinet drives the motors, reads the encoders, and runs the certified safety functions.

      In lesson 4.8, you planned arm motions with MoveIt 2 on an ordinary Linux PC. How does a motion path computed on a PC reach a controller that only speaks its own language?

      The answer is a vendor driver. It is a pair of programs, one on the robot controller and one on the ROS 2 PC. Together, they pass motion commands and robot state back and forth. Drivers differ in three main ways: who maintains them, which ROS 2 distributions they support, and what they can do. First, you will meet the community behind industrial ROS and the pattern all drivers share. Then you will compare five robot brands and learn when a factory should use ROS at all.

      02. ROS-Industrial: a community, not a single program

      Before you download a driver for a factory robot, you will often hear the name ROS-Industrial. It is not a single piece of software you install once. Instead, it is an open-source community where robot makers, researchers, and factories build shared tools for manufacturing.

      ROS-Industrial (ROS-I) applies ROS to factory automation. Its code repositories hold interfaces for common industrial robot arms (manipulators), grippers, sensors, and device networks.[1] The project grew out of a partnership between Yaskawa Motoman, Southwest Research Institute (SwRI), and Willow Garage.[2] Today, its community includes robot manufacturers, system integrators, researchers, and industrial end users.[2] Regional consortia share the cost of applied research around the world.[2]

      Alongside hardware drivers, ROS-I builds application tools that vendor robot languages do not provide. Here are three examples:

      • Tesseract: a lightweight motion-planning framework. In plain words, its core works in Python without needing ROS. Its README calls those core packages "ROS agnostic and have full python support", and the project holds a monthly public meeting.[3]
      • Scan-N-Plan: a set of tools that plans robot paths from 3D scan data. It targets painting, sanding, deburring, and inspection on high-mix parts, flexible parts, and parts without a computer-aided design (CAD) model.[4]
      • ros2_canopen: a ROS 2 stack for CANopen industrial devices, released for ROS 2 Lyrical. Its README still warns that it is "not yet ready for production use".[5][6]

      Support level is the first thing you should check on any ROS-I package. Older ROS 1 drivers were often maintained by volunteers on a best-effort basis, with no direct backing from a robot maker. By contrast, Yaskawa's MotoROS2 carries a "consortium / vendor" badge.[7]

      In ROS 2, drivers have mostly moved out of community repositories and into repositories owned by the robot makers. Universal Robots, KUKA, Yaskawa, and FANUC all publish their own drivers. For a factory, that difference matters. A vendor-owned driver gives you someone to call when something breaks.

      For the curious: regional consortia and ROS 1 community support badges

      Three regional groups lead ROS-Industrial. SwRI leads the Americas, Fraunhofer IPA in Stuttgart leads Europe, and ARTC (A*STAR) with Nanyang Technological University leads Asia-Pacific.[8][2]

      In ROS 1, the core communication packages, industrial_core, are labeled "community supported". Neither a robot maker nor the consortia support them directly, and volunteers maintain them on a best-effort basis.[9] The older ROS 1 driver repositories abb_driver and kuka_experimental carry the same "community" badge. The kuka_experimental repository warns that its application programming interfaces (APIs) "are to be considered unstable and are not guaranteed to be complete and / or functional".[10][11]

      03. How every driver works: three layers

      Each robot brand has its own language and network setup, so their drivers look different at first glance. Underneath, though, every driver in this lesson follows the same three-layer pattern. Because the top layer stays the same, swapping a UR arm for a KUKA arm only changes the bottom two layers.

      Here are the three layers from the robot up to MoveIt 2:

      1. 1. A small program on the controller, written in the vendor's language. It opens a network link using Transmission Control Protocol (TCP) or User Datagram Protocol (UDP). It accepts target positions or whole trajectories, and sends back joint positions and status. Examples include a URScript program started by a URCap, a RAPID module using Externally Guided Motion (EGM), or a KUKA program using Robot Sensor Interface (RSI). Other examples are a FANUC TP program using Stream Motion, or a MotoPlus application on a Yaskawa controller.[12][13][14][15][7]
      2. 2. A ros2_control hardware interface on the PC. This C++ plugin wraps that network link. To the rest of ROS, the arm looks like any other robot: a set of joints with position, velocity, or effort interfaces. It takes the place of the mock hardware you used in lesson 4.8.
      3. 3. Standard ROS 2 controllers on top. The usual one is joint_trajectory_controller, which offers a control_msgs/FollowJointTrajectory action. MoveIt 2 sends its planned motions to that action.[16]

      Because layer 3 is the same for every brand, your MoveIt 2 planner can talk to different robots the same way.

      The FollowJointTrajectory action is the shared language at the top. Recall from lesson 4.1 that an action is a long-running request with live feedback and a final result. That matches how moving a robot arm works.

      In plain words, the goal lists the joint names, the target positions, and the arrival time for each point. While the arm moves, feedback reports where the joints should be, where they are, and the gap between them. When the move finishes, the result returns an error_code: 0 means it succeeded, and negative numbers mean the move failed.[17]

      Drivers move arms in one of two styles. In a streaming driver, the PC splits the path into tiny steps and sends a new target every few milliseconds. In a trajectory-forwarding driver, the PC sends the whole path once, and the controller splits up the steps itself. Forwarding demands much less precise timing from your PC.

      For the curious: FollowJointTrajectory message fields and error codes

      The action goal holds a trajectory (a list of joint names and points, each with positions and a time_from_start), along with path_tolerance, goal_tolerance, and goal_time_tolerance. Feedback reports desired, actual, and error values. In the result's error_code, 0 means SUCCESSFUL, and negative values flag failures: INVALID_GOAL (-1), INVALID_JOINTS (-2), OLD_HEADER_TIMESTAMP (-3), PATH_TOLERANCE_VIOLATED (-4), and GOAL_TOLERANCE_VIOLATED (-5).[17]

      04. Universal Robots: the official driver

      If you are starting out with industrial arms in ROS 2, Universal Robots arms like the UR5e are a common starting point. Universal Robots writes and maintains its own official ROS 2 driver. You can start it with a single launch command and connect it to the robot's touchscreen over your network.

      The driver is built on the Universal_Robots_Client_Library. It works with all UR robots from 3 kg to 30 kg payload on PolyScope X, PolyScope 5, and CB3 controllers.[18] Its release table lists Humble, Jazzy, Kilted, Lyrical, and Rolling. In plain words, you need a Linux PC to run it; the README states that "a fundamental requirement for the driver is using Linux".[18]

      Safety stops and speed limits stay active while the driver runs. It supports pausing at an emergency stop or safeguard stop, "automatic speed scaling to avoid violate the safety setting", and manual speed scaling from the teach pendant.[18]

      You start the driver with one launch command, passing the robot model and its Internet Protocol (IP) address:[18] 

      ros2 launch ur_robot_driver ur_control.launch.py ur_type:=ur5e robot_ip:=192.168.56.101

      On the robot side, the driver uses URScript. In the default teach pendant mode, you install the External Control URCap plugin on the robot. Next, you enter the ROS PC's IP address and port, add the External Control node to a pendant program, and press play.[12][19]

      In everyday words, reaching that node tells the robot to fetch its control program from your PC. The docs put it this way: "the URCap will request script code from the ROS driver and execute it".[12] On your PC, a component called ScriptSender listens on a TCP socket and sends back external_control.urscript.[20] That script runs servoj or speedj at every control step, so the code on the robot is itself URScript.[21]

      Motion commands travel over a reverse interface, a custom TCP connection that carries the target values and control mode.[22] Robot state comes back through UR's Real-Time Data Exchange (RTDE) interface.[23]

      The driver also offers a headless mode, which is off by default. In headless mode, the PC sends the URScript directly to the controller without a pendant program.[24][12] On e-Series arms, this requires remote control mode, which locks the pendant so it cannot start motion or freedrive. Pressing a pendant motion button or starting another program stops the driver's script until you restart it.[12]

      Timing. On e-Series arms, the controller manager runs at 500 Hz (500 times per second), giving the PC just 2 ms per step. On older CB3 arms, it runs at 125 Hz.[25][26]

      Speed scaling. The arm may move slower than your PC asked if you turn down the pendant speed slider, or if the controller slows down to obey safety limits. The driver multiplies both slowdown factors and publishes a number from 0 to 1 through speed_scaling_state_broadcaster.[27] The trajectory controller uses that number to stretch out time so the robot stays on its planned path.

      Two things to watch for. First, the action name changes depending on your ROS 2 release. On Humble, Jazzy, and Kilted, you send goals to /scaled_joint_trajectory_controller/follow_joint_trajectory, whereas on Lyrical you send them to /joint_trajectory_controller/follow_joint_trajectory.[28][29][24] Second, UR's MoveIt setup turns off Trajectory Execution Monitoring so a scaled-down, slower move does not get canceled by mistake.[16]

      Finally, the passthrough trajectory controller hands the whole trajectory to the robot so the controller interpolates it. In plain words, this lets a slower PC run smooth moves, though it cannot replace a trajectory that is already running. UR's docs say "the realtime requirements for the control PC can be massively decreased".[27]

      For the curious: UR package versions, protocol details, and distro branch changes

      In ROS 2 Lyrical, the distribution file lists ur_robot_driver version 6.2.0-1 along with its calibration, controller, dashboard, MoveIt configuration, and driver packages.[6]

      In teach pendant mode, the port you enter on the robot must match script_sender_port (default 50002), and PolyScope X uses a URCapX instead of a URCap.[12][19][20] In headless mode, if a pendant button stops the driver's program, you restart it with the /io_and_status_controller/resend_robot_program service.[12]

      Each reverse-interface TCP packet holds eight 32-bit integers: a read timeout, six motion-target values, and a control mode. Available modes are SERVOJ (high-rate joint positions), SPEEDJ (joint velocities), FORWARD (a whole trajectory interpolated on the robot, used by the passthrough controller), FREEDRIVE, and, since PolyScope 5.23.0 and 10.10.0, TORQUE.[22][27]

      For speed scaling, the driver multiplies the RTDE values speed_scaling (the slider) and target_speed_fraction (the controller's own slowdown).[27] On Humble, Jazzy, and Kilted branches, the driver defines scaled_joint_trajectory_controller (type ur_controllers/ScaledJointTrajectoryController).[28] On Lyrical and main branches, that entry is removed. The stock joint_trajectory_controller instead takes a speed_scaling parameter pointing at speed_scaling/speed_scaling_factor, and the launch file starts it by default.[29][24] UR turns off MoveIt's Trajectory Execution Monitoring because the monitor "will in most cases unnecessarily (and unexpectedly) abort goals".[16]

      05. ABB: a community driver built on EGM

      Unlike Universal Robots, ABB did not have an official ROS 2 driver found for this lesson. Instead, most ROS 2 projects use a community driver maintained by PickNik Robotics called abb_ros2. Because it is not packaged for standard ROS 2 releases, you have to build it from source code and pair it with a paid feature on the ABB controller.

      The abb_ros2 repository provides a ros2_control hardware interface built on abb_libegm. It also includes a client for ABB's Robot Web Services (RWS), launch files, robot descriptions, and RobotStudio files.[30] Because it is not released into Humble, Jazzy, Kilted, or Lyrical, you must build it from source.[30][6]

      The driver talks to the ABB cabinet over two channels:

      • Robot Web Services (RWS): reads robot status over Hypertext Transfer Protocol (HTTP). Only RWS 1.0 works today. The docs state that "RobotWare 7.0 and higher use RWS 2.0 and are not currently supported".[31]
      • Externally Guided Motion (EGM): carries robot motion over UDP, commonly at about 250 Hz (a 4 ms cycle).[13][32] It is a paid RobotWare option (689-1) that requires RobotWare 6.07.01 or later.[13]

      In everyday words, the ABB controller sets the timing and pulls new targets from your PC. The README puts it this way: "the robot controller requests new references over a UDP channel, at the rate specified with RAPID EGMAct instructions".[13]

      ABB's vendor language stays in the loop. The supplied RAPID module moves the arm home with MoveAbsJ, sets up EGM, and loops on EGMRunJoint while watching for UDP communication faults:[33] 

      EGMGetId egm_id;
EGMSetupUC ROB_1, egm_id, "default", "ROB_1", \Joint;
EGMActJoint egm_id \J1:=egm_condition ... \MaxSpeedDeviation:=20.0;
WHILE TRUE DO
  EGMRunJoint egm_id, EGM_STOP_HOLD, \J1 \J2 \J3 \J4 \J5 \J6 \CondTime:=5 \RampOutTime:=5;
ENDWHILE

      The abb_libegm library itself "has not been productized" and comes as-is. Its README advises testing in RobotStudio before running a real arm, and thinking about cyber security before connecting controllers to networks.[13]

      For the curious: abb_ros2 branches, ports, and RobotStudio setup

      The default branch of abb_ros2 is rolling, and older humble, iron, and foxy branches also exist.[30]

      The library uses EGM's UDP variant in joint and pose modes.[13] In RobotStudio, you add the EGM option, set up a UDPUC transmission protocol, and load the RAPID module into task T_ROB1.[34] By default, EGM uses UDP port 6511 and RWS uses port 80. Simulating with RobotStudio requires two computers: one running Windows and one running Linux.[31]

      06. FANUC and KUKA: drivers from the robot makers

      For a long time, teams running FANUC or KUKA arms had to rely on community drivers. Today, both robot makers publish official ROS 2 drivers of their own. If you are setting up a FANUC or KUKA cell, knowing which interface and Linux kernel your controller needs will save hours of setup.

      FANUC. FANUC published its official driver, fanuc_driver, in 2025 under the Apache-2.0 license.[35] In plain words, it streams rapid motion updates to real or simulated FANUC arms. Its README calls it "a ros2_control high-bandwidth streaming driver".[35] It covers CRX and other models with payloads from 3 to 2,300 kg.[36]

      The FANUC driver uses two channels on the controller: Stream Motion (a UDP stream run by a TP program) and the Remote Motion Interface (RMI).[14][37] You cannot run the RMI controller at the same time as a streaming controller such as the joint trajectory controller.[37] Its controller manager runs at 500 Hz, and like UR it ships its own scaled joint trajectory controller.[38]

      KUKA. KUKA's official repository, kuka-ros/kuka_drivers, "contains ROS2 drivers for all KUKA operating systems".[39] You can install it with sudo apt install ros-jazzy-kuka-drivers. KUKA recommends a real-time Linux kernel "as all three drivers require cyclic, real-time communication", and does not recommend Windows.[39]

      KUKA builds several controller operating systems, each with its own real-time link. The driver wraps all three behind one common ROS application programming interface (API):[15]

      • KSS (KUKA System Software for industrial robots) and iiQKA.OS2 (different generations of KUKA controller operating systems): the Robot Sensor Interface (RSI).[15][40] RSI cycles every 12 ms (normal) or 4 ms (fast), and drops the link if the PC misses too many answers.[41][42]
      • Sunrise (LBR iiwa cobots): the Fast Robot Interface (FRI), with a cycle time settable from 1 to 10 ms.[15][43]
      • iiQKA (LBR iisy): ExternalAPI.Control (EAC).[15]

      In plain words, KUKA's controller drives the clock, so the PC waits for each update. The docs state that "All 3 of the KUKA real-time interfaces handle the timing on the controller side".[15] Because the read call blocks until an update arrives, KUKA wrote its own control node instead of using the default ros2_control_node. Startup uses a lifecycle node (from lesson 4.2) called robot_manager so external motion cannot start until the controllers are active.[15]

      For the curious: FANUC and KUKA branches, legacy repos, and lifecycle startup

      FANUC's fanuc_driver is licensed by FANUC America and FANUC CORPORATION. Its main branch targets ROS 2 Jazzy on Ubuntu 24.04, and a humble branch covers Humble.[35] Its December 2025 announcement covered CRX and other models from 3 to 2,300 kg.[36] The older community ros-industrial/fanuc repository is a ROS 1 project whose default branch is noetic-devel.[44]

      KUKA's kuka-ros/kuka_drivers has a Jazzy branch (master) and a Humble branch. It is released in the Humble and Jazzy distributions, but not in Kilted or Lyrical.[39][45][6] The kroshu/kuka_drivers repository combines this official code with community code for older KUKA systems.[40] At startup, you step the lifecycle node through ros2 lifecycle set robot_manager configure, then activate.[15]

      07. Yaskawa MotoROS2 and a side-by-side comparison

      The four drivers above all run ROS 2 on a separate PC and send targets across a network cable. Yaskawa's MotoROS2 flips that design around by running ROS 2 directly on the robot controller itself. Comparing all five brands side by side shows what software runs on each controller and which ROS 2 version you need.

      MotoROS2 is a MotoPlus application loaded onto the controller in Maintenance mode. MotoPlus is Yaskawa's C/C++ runtime environment that lets custom real-time software run directly on the robot controller. Because MotoROS2 is built on micro-ROS, a micro-ROS Agent on your PC bridges it to the rest of ROS 2 and "must always be running".[7]

      MotoROS2 offers a follow_joint_trajectory action, so it still fits the three-layer pattern. However, it is a trajectory-forwarding driver with strict rules. Before you send a move, your trajectory must start at the robot's current position. The README warns that "MotoROS2 will reject any trajectory which does not start at the current state".[7] You also cannot replace a trajectory while it is running.[7]

      The table below sums up the five brands as of October 2026. Driver support changes quickly, so check each README before starting a project.

      Brand Program on the controller Link to the PC ROS 2 distros Maintained by
      Universal Robots URScript via External Control URCap (or headless) RTDE plus TCP script and reverse-interface sockets Humble, Jazzy, Kilted, Lyrical, Rolling Vendor
      ABB RAPID module with EGM instructions EGM over UDP, RWS 1.0 over HTTP Rolling branch, source build only Community (PickNik)
      FANUC TP program with Stream Motion; RMI Stream Motion over UDP Jazzy, Humble Vendor (since 2025)
      KUKA RSI, FRI or EAC, depending on the controller OS Controller-timed real-time link Jazzy, Humble Vendor, plus community legacy code
      Yaskawa MotoROS2 MotoPlus application micro-ROS Agent on the PC Humble, Jazzy Vendor

      For a course built on Lyrical, only the UR driver was confirmed as released for Lyrical. The others need a Jazzy or Humble machine, or a source build.

      For the curious: MotoROS2 supported controllers, middleware, and trajectory limits

      MotoROS2 supports the DX200, YRC1000, and YRC1000micro controllers, with binaries for Humble and Jazzy (no Kilted or Lyrical support is stated). It works only with the Fast DDS middleware.[7]

      Before sending a goal, a client must check robot_status, make sure the trajectory starts at the robot's current state, and call start_traj_mode. A single trajectory may hold at most 200 points, and state publishing is capped at about 100 Hz. MotoROS2 does not support Cartesian motion, asynchronous multi-group motion, or replacing a trajectory while it runs.[7]

      08. Real time and safety: the controller stays in charge

      When your PC streams motion targets to a factory arm every few milliseconds, two questions come up right away. What happens if the PC falls behind, and what keeps people safe if ROS 2 sends a bad command? The short answer is that the robot controller enforces strict timing and keeps full control of safety.

      Every streaming driver above runs at a fixed pace set by the robot controller:

      • UR e-Series and FANUC: 500 Hz (every 2 ms).[25][38]
      • ABB EGM: about 4 ms.[32]
      • KUKA RSI and FRI: 4 or 12 ms for RSI, and 1 to 10 ms for FRI.[41][42][43]

      If your PC misses its deadlines, the controller drops the network link.[42] In plain words, the PC must read incoming robot data before the next update arrives. UR's client library warns that "it is quite critical that arriving RTDE messages are read before the next message arrives". It runs its receive thread at real-time priority and shuts down RTDE communication if data is not read fast enough.[23][46]

      To meet those deadlines, UR recommends a PREEMPT_RT kernel. This is a real-time patch for the Linux kernel. It is designed so that tasks for hardware control loops run on time, predictably. It notes that a low-latency kernel (sudo apt install linux-lowlatency) "has shown to be sufficient in many situations". It also warns that e-Series robots may move unevenly without a real-time-enabled system.[47] Trajectory-forwarding modes, such as UR's passthrough controller and MotoROS2, avoid much of this problem because the controller does the fine-grained interpolation.[27]

      Even more important than timing is knowing which machine protects people in the work cell. ROS 2 is not the robot's safety system. The certified safety functions, such as the safety configuration, emergency stops, protective stops, speed limits and zone limits, live in the vendor's controller and keep working whatever the PC sends. ROS only sends requests, and the robot may slow down or stop at any time. The drivers make this visible:

      • UR: the driver pauses at emergency and safeguard stops and scales speed to respect the safety settings.[18] The io_and_status_controller publishes the safety mode (for example PROTECTIVE_STOP or ROBOT_EMERGENCY_STOP) and whether the robot program is running. If it is not, "no commands can be sent to the robot".[27]
      • KUKA: stopping the ROS side is "a non-realtime process", and "in cases where an abrupt stop is needed, the safety stop of the Teach Pendant should be used!"[48]
      • Yaskawa: the Functional Safety Unit (FSU) can reduce speed, restrict the workspace or stop motion. Trajectories continue at reduced speed, but MotoROS2 "does not currently publish speed reduction ratios imposed by an FSU", so your planner must tolerate slowdowns it cannot see.[7]

      Your ROS application must cope with the safety system, not fight it. Turning off MoveIt's execution monitor on UR robots (section 04) is one example. As a general rule, your risk assessment should assume that ROS commands can be wrong, and rely on the controller's safety functions and the cell safeguards from lesson 5.4 to keep people safe.

      09. ROS or the vendor language?

      After seeing drivers, real-time kernels, and safety boundaries, you might ask why factories still use vendor languages like RAPID or URScript. On a repetitive assembly line, vendor code is simpler, faster to validate, and supported directly by the maker. Most factories do not choose one tool for everything. Instead, they run vendor code for reliable work and call ROS only for smart, sensor-driven tasks.

      Vendor robot languages are still the most common way to program industrial robots. Each maker created its own language, incompatible with the others. Programmers tend to specialize in a few brands, which makes them slow to adopt new tools.[49]

      For a fixed path in a validated cell, the vendor language is usually the practical choice. It is what the maker supports and what plant staff already know. ROS-I's own representatives describe its focus as tasks with no off-the-shelf vendor solution, such as perception-driven work where the path is not known in advance. They also describe it as running alongside vendor software rather than replacing it.[50]

      The drivers are built for that kind of teamwork. A UR pendant program can do its normal steps, hit the External Control node to let ROS take over, and then resume once the driver calls hand_back_control.[12][27] ABB's RAPID template likewise moves the arm home with a normal RAPID command before handing motion to EGM.[33]

      Each driver project also states clear limits. For example, abb_libegm offers "only limited support", and MotoROS2 has no Cartesian motion. The legacy abb_driver supports joint motion only, with no input and output (I/O).[13][7][11]

      Here is a simple rule of thumb:

      • Use the vendor language when the path is fixed, cycle time and uptime matter most, the cell must be validated, and the plant staff support that brand.
      • Use ROS 2 when motion depends on sensing, such as scan-then-plan or bin picking, or when the cell mixes brands or mobile bases. It also fits when you need planners like MoveIt 2 or Tesseract, or when you are prototyping and researching.
      • Use both: let the vendor program own safety, I/O, and the process sequence, and call into ROS only for the "smart" segment.

      10. Hands-on: one move, two languages

      Seeing the same robot motion written both ways makes the difference between vendor code and ROS 2 easy to spot. Below, you will send a UR arm through two poses: first in URScript, and then as a ROS 2 action goal. Notice that URScript asks for speed and acceleration, while ROS 2 asks for the arrival time at each pose.

      The first pose is the home pose used by UR's own test client: [0, -1.57, 0, -1.57, 0, 0] radians. The six joints are named shoulder_pan_joint, shoulder_lift_joint, elbow_joint, wrist_1_joint, wrist_2_joint, and wrist_3_joint.[16] Both examples are this lesson's own and have not been run on a robot, so test them in URSim first.

      In URScript, using movej from lesson 2.3, you give each move a joint acceleration and speed: 

      def move_two_poses():
  movej([0, -1.57, 0, -1.57, 0, 0], a=1.0, v=0.5)
  movej([0.5, -1.2, 0.8, -1.57, 0, 0], a=1.0, v=0.5)
end

      In ROS 2, start the driver and play the External Control program on the pendant (or use headless mode). Then send one FollowJointTrajectory goal from the command line. On Lyrical, the action server is /joint_trajectory_controller/follow_joint_trajectory:[29][17] 

      ros2 action send_goal /joint_trajectory_controller/follow_joint_trajectory \
  control_msgs/action/FollowJointTrajectory "{trajectory: {
    joint_names: [shoulder_pan_joint, shoulder_lift_joint, elbow_joint,
                  wrist_1_joint, wrist_2_joint, wrist_3_joint],
    points: [
      {positions: [0, -1.57, 0, -1.57, 0, 0], time_from_start: {sec: 4}},
      {positions: [0.5, -1.2, 0.8, -1.57, 0, 0], time_from_start: {sec: 8}} ]}}"

      On Jazzy or Humble, change the action name to /scaled_joint_trajectory_controller/follow_joint_trajectory.[28] UR's docs also include a ready-made test, ros2 launch ur_robot_driver test_joint_trajectory_controller.launch.py, which checks that the arm starts near the home pose.[16] Compare the two versions:

      • Speed versus time: URScript states a speed and acceleration for each move. The ROS goal states a time for each waypoint. The joint trajectory controller interpolates on the PC (at 500 Hz on e-Series) and streams setpoints to the robot.[25]
      • Who interpolates: with the passthrough controller, the whole trajectory would go to the robot and be interpolated there instead.[27]
      • Slowdowns: turning down the pendant speed slider stretches the ROS trajectory through speed scaling, so the 8 s motion takes longer.[27]
      • Errors: instead of a pendant pop-up, a failure comes back as an error_code, such as -4 for PATH_TOLERANCE_VIOLATED.[17]
      • Portability: on a Yaskawa robot, MotoROS2 would reject this same goal unless its first point matched the robot's current position.[7]
      Try it
      1. Start URSim, install the External Control URCap, and launch ur_control.launch.py against it. Run the URScript version from the pendant, then run the ros2 action send_goal version. Time both with the speed slider at 100% and at 50%.
      2. Run ros2 control list_controllers while the driver is up. Which trajectory controller is active on your distribution, and what is its action name?
      3. Pick one of ABB, FANUC, KUKA, or Yaskawa. From its README, write down the controller program, network link, supported ROS 2 distributions, and maintainer. Would you use it in a production cell today? Give one reason for and one against.
