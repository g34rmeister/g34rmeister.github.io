4.5 ROS Tools

Gerald Lê

01. The ROS developer toolchain

Writing code for robots brings debugging problems that ordinary web or desktop programs do not have. A mobile robot or robot arm combines many processes running at once, moving mechanical parts, several sensors and many 3D coordinate frames. If a robot drives the wrong way or misses a doorway, scrolling through terminal text is rarely enough to find out why.

To make robotic systems easier to see into and debug, the ROS ecosystem provides a set of developer tools:

  • RViz2: A 3D visualizer for ROS that draws the data flowing through the system, such as sensor readings, maps and the robot model.[1]
  • rqt and rqt_graph: rqt is a graphical framework whose tools are plugins; rqt_graph is the plugin that shows which nodes are connected over which topics.[2][3]
  • ros2 bag: A command-line tool that records data published on topics (and services and actions) so it can be replayed later.[4]
  • Gazebo: A robot simulator with physics engines and simulated sensors such as cameras, lidars and IMUs.[5]

02. RViz2: visualizing robot perception in 3D

RViz (run in ROS 2 as the rviz2 package) is the 3D visualizer of the ROS framework.[1] What is the difference between RViz and Gazebo? RViz displays data already flowing through ROS; Gazebo simulates the robot and its world with physics.[1][5]

RViz2 simulates nothing: it has no physics engine. It draws what arrives on ROS topics. Each thing it draws is called a display, and you add displays from a list of built-in types, including:[1]

  • RobotModel: Shows the robot in its current pose, as defined by the current TF transforms.[1] Those transforms usually come from robot_state_publisher, which reads the robot's URDF (Unified Robot Description Format, an XML file describing links and joints) description and joint positions (sensor_msgs/msg/JointState messages) and calculates the transforms between all of the robot's parts.[6]
  • Laser Scan and Point Cloud(2): Show data from a laser scanner (sensor_msgs/msg/LaserScan) or a point cloud (sensor_msgs/msg/PointCloud2), with options for rendering modes and accumulation.[1]
  • Map and Grid Cells: Map draws an occupancy grid (nav_msgs/msg/OccupancyGrid) on the ground plane; Grid Cells draws cells from a grid, usually obstacles from a navigation costmap.[1]
  • InteractiveMarker: Shows 3D objects from interactive marker servers and lets you move them with the mouse.[1]

To start RViz2 from your terminal, run:[1] 

ros2 run rviz2 rviz2

03. The tf2 transform library and the Fixed Frame

To draw data from several sensors in the same 3D view, RViz2 uses the tf transform system to convert each piece of data from the coordinate frame it arrived in into a common reference frame.[1] In ROS 2 this is the tf2 library, which keeps track of multiple coordinate frames over time.[7]

On a real robot, sensors are mounted in different places. As an example of our own: a front lidar might sit 30 cm ahead of and 15 cm above the robot's wheel centre, while a depth camera sits on a mast. When the lidar reports an obstacle at (x = 1.2 m, y = 0.5 m) in its own frame, the navigation software needs to know where that obstacle is relative to the robot's base or to the map.

tf2 stores the relationships between frames as a tree, buffered in time, and can transform points and vectors between any two frames at any desired time.[7] In RViz the most important setting is the Fixed Frame, the frame treated as the "world": usually map or world, though it can also be the odometry frame. For correct results, the fixed frame should not move relative to the world. If you set it to a moving frame such as the robot's base, everything the robot has seen will appear in front of the robot instead of where it really is.[1] Each display also shows a status (OK, Warning, Error or Disabled), which is the first place to look when data does not appear.[1]

04. rqt and rqt_graph: computational graph inspection

rqt is a graphical user interface framework that implements its tools as plugins. You can run the tools as dockable windows inside one rqt window, or on their own.[2]

One of the most useful plugins is rqt_graph, a GUI plugin for visualising the ROS computation graph: it shows the running nodes and the topics that connect them.[3][8]

Start it from the terminal while Turtlesim and the teleop node are running (or open rqt and choose Plugins > Introspection > Node Graph):[3] 

ros2 run rqt_graph rqt_graph

In rqt_graph, running nodes are drawn as ovals (here /teleop_turtle and /turtlesim) and topics as boxes (/turtle1/cmd_vel), with arrows showing which way messages flow.[3][8] In this graph, /teleop_turtle publishes your keystrokes on /turtle1/cmd_vel and /turtlesim subscribes to it.[3] If a new sensor driver is not reaching your planner, rqt_graph quickly shows whether the two nodes are really joined by the same topic or whether a typo in a topic name has left one of them disconnected. Recent versions also flag topics whose publishers and subscribers have incompatible message types or QoS settings.[8]

05. Specialized rqt plugins

Besides rqt_graph, rqt comes with other plugins that are useful for debugging:[2]

  • rqt_plot: A GUI plugin that plots numeric values in a 2D graph.[9] You enter a topic field (for example /turtle1/pose/x) and watch it change over time, which helps when tuning controllers or looking at sensor noise.
  • rqt_console: A log viewer that collects log messages over time and lets you view, filter, save and reload them.[10] ROS 2 nodes send their log messages to the /rosout topic by default, and each message has a severity level: DEBUG, INFO, WARN, ERROR or FATAL.[11]
  • rqt_service_caller: A GUI plugin for calling services.[12] In rqt it is under Plugins > Services > Service Caller; you pick a service such as /spawn, fill in the request fields and click Call.[13]

06. ros2 bag: telemetry recording and playback

Field tests with real robots are expensive and hard to repeat. If a rover fails at a tricky spot outdoors, an engineer back at the lab cannot easily recreate exactly the same situation to debug the code.

The solution is ros2 bag. Which tool records messages on chosen topics so you can replay them later without the robot? The answer is ros2 bag.[4]

ros2 bag is a command-line tool that records the data published on any number of topics (and, in recent releases, services and actions) and saves it to disk. You can then replay the data to reproduce your tests and experiments, or share it so others can recreate your work.[4]

With Turtlesim and the teleop node running, record a session. The -o option names the bag directory, and the topics to record are listed after --topics:[4] 

ros2 bag record -o my_turtle_session --topics /turtle1/cmd_vel /turtle1/pose

While recording, drive the turtle around with the keyboard teleop for about twenty seconds, then press Ctrl+C. ros2 bag creates a directory named my_turtle_session containing a metadata.yaml file and the recorded data file.[4]

To inspect the recording, run:[4] 

ros2 bag info my_turtle_session

The terminal prints the files, bag size, storage format (mcap by default), ROS distribution, duration, start and end times, total message count, and for each topic its message type, message count and serialization format.[4] In the official example, /turtle1/cmd_vel had only 9 messages (one per key press) while /turtle1/pose had over 3000, because Turtlesim publishes the pose at regular intervals the whole time it runs.[4]

Before replaying, stop the teleop node with Ctrl+C. You can also put the turtle back in its starting position with Turtlesim's /reset service, whose type is std_srvs/srv/Empty:[4][14] 

ros2 service call /reset std_srvs/srv/Empty

Now replay the bag:[4] 

ros2 bag play my_turtle_session

ros2 bag play publishes the recorded messages again, and the turtle follows the path you drove while recording, though not 100% exactly, because Turtlesim is sensitive to small changes in timing.[4] Because this bag also contains /turtle1/pose, playback keeps going for as long as Turtlesim was running during the recording, even if the turtle was standing still.[4]

07. Storage backends: sqlite3 and MCAP

In early ROS 2 releases, ros2 bag recorded into sqlite3 databases by default. Testing showed that in many cases this was not fast enough and lacked features wanted for offline processing.[15]

Starting with ROS 2 Iron, the default format for new bags is MCAP, and this is still the default in Jazzy and Lyrical. The older sqlite3 format can still be chosen for recording, and bags in either format can be played back.[4][15] MCAP is an open-source container file format for multimodal log data, maintained as a Foxglove project. Its documentation highlights:[16]

  • Append-only writing: MCAP uses a row-oriented, append-only design to minimise disk I/O while recording.[16]
  • Built-in indexing: Files can contain an optional index for fast, efficient reading, so tools can jump to a point in a recording without reading the whole file.[16]
  • Self-describing schemas: MCAP stores message schemas alongside the data, so files stay readable in the future even as your code changes.[16]

08. Gazebo: multi-physics simulation

While RViz2 visualizes data, Gazebo creates the virtual world the robot lives in.[5]

Gazebo is an open-source robot simulator. Current Gazebo (Gazebo Sim) ships physics engine plugins for DART and Bullet, plus its own simple TPE engine; the ODE and Simbody engines used by Gazebo Classic are not supported in the new Gazebo.[5] In Gazebo:

  • Wheeled robots can be given wheel slip with the WheelSlip plugin.[5]
  • Simulated sensors include cameras, depth and RGBD cameras, GPU lidars, IMUs, contact sensors, air pressure and thermal cameras.[5]
  • Sensor readings can include Gaussian noise, so algorithms are tested on imperfect data, as on a real robot.[5]

An important milestone came on January 31, 2025, when Gazebo Classic (Gazebo 11, the last Classic release) officially reached end of life.[17] New work uses the current Gazebo, which was called Ignition Gazebo until the Ignition name was retired in 2022.[18] Each ROS 2 release has a recommended Gazebo release: ROS 2 Jazzy pairs with Gazebo Harmonic, and ROS 2 Lyrical Luth pairs with Gazebo Jetty.[19][20]

09. Bridging worlds: the ros_gz architecture

Gazebo does not talk to other programs through ROS itself. It has its own messaging system, called Gazebo Transport, with its own message types (such as gz.msgs.LaserScan).[21]

To connect Gazebo to ROS 2, you use the ros_gz packages (installed with sudo apt-get install ros-${ROS_DISTRO}-ros-gz). Its ros_gz_bridge provides a network bridge that exchanges messages between ROS 2 and Gazebo Transport.[19][21] For example:[21] 

ros2 run ros_gz_bridge parameter_bridge /scan@sensor_msgs/msg/LaserScan[gz.msgs.LaserScan

The argument gives the topic name, the ROS message type and the Gazebo message type. The symbol between the two types sets the direction: @ is a two-way bridge, [ bridges from Gazebo to ROS, and ] bridges from ROS to Gazebo.[21] Here the simulated lidar's gz.msgs.LaserScan messages are converted into ROS sensor_msgs/msg/LaserScan messages on /scan. Any ROS node subscribed to /scan (for example a navigation stack) receives them just as it would from a real lidar driver, which is what lets you test the same code in simulation first.

10. Essential community packages

Robotics engineers rarely write core autonomy algorithms from scratch. Instead, they build on well-tested community packages such as these:

Package Domain Primary Capability
Nav2[22] Mobile Navigation Successor of the ROS Navigation Stack: perception, planning, control, localization and behaviors, with navigation logic built from behavior trees.
MoveIt 2[23] Arm Manipulation The robotic manipulation platform for ROS 2: kinematics, motion planning and planning around objects.
slam_toolbox[24] Mapping & Localization 2D Simultaneous Localization and Mapping (SLAM) with pose-graph optimization, a localization mode, lifelong mapping and map serialization.
ros2_control[25] Robot Control A framework for (real-time) control of robots using ROS 2, with hardware interfaces and ready-made controllers such as joint trajectory and differential drive controllers.

Together, RViz2, rqt, ros2 bag, Gazebo and these community packages give a single developer or a small team a complete workbench for building, testing and debugging robot software.

Try it
  1. Launch Turtlesim and keyboard teleop, then open rqt_graph. Experiment with the graph filters: uncheck "Debug" under Hide, refresh, and note which extra nodes and topics appear.
  2. Record a 15-second bag file while teleoperating the turtle in a figure-eight pattern. Inspect the resulting dataset with ros2 bag info, then divide the message count on /turtle1/pose by the duration to estimate its publishing rate. Compare your answer with ros2 topic hz /turtle1/pose.
  3. Explain in your own words why an engineer testing an autonomous driving algorithm prefers testing against a recorded ros2 bag file before testing on real hardware on public roads.
