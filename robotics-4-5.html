      4.5 ROS Tools

      Gerald Lê
      Chapter 4, lesson 5 of 10 ← Previous: 4.4 Running Your First Example (Turtlesim) Next: 4.6 Writing Your First ROS 2 Package →

      01. Tools for seeing inside a robot

      When a website breaks, you can read an error message in your terminal. When a mobile robot drives the wrong way or misses a doorway, text logs rarely tell you why. You need to see what your robot is sensing, how its parts are connected, and what it tried to do. The Robot Operating System (ROS) gives you four tools to look inside a running robot and test your code.

      A robot arm or mobile robot runs many programs at once. It moves physical parts and combines sensors in three-dimensional (3D) space. These four developer tools help you inspect and test every piece:

      • RViz2: A 3D visualizer for ROS. It draws live data flowing through the system, such as sensor readings, maps, and the robot model.[1]
      • rqt and rqt_graph: rqt is a graphical framework made of plugins.[2] One plugin, rqt_graph, shows which nodes are connected over which topics.[3]
      • ros2 bag: A command-line tool that records data published on topics, services, and actions so you can replay it later.[4]
      • Gazebo: A robot simulator with physics engines and simulated sensors such as cameras, lidars, and inertial measurement units (IMUs).[5]

      02. RViz2: seeing what your robot sees in 3D

      Imagine your mobile robot stops in front of an open doorway and refuses to drive through. Looking at the robot will not tell you whether its scanner sees a clear path or an obstacle. You need a window that draws the robot’s view of the world in real time.

      RViz (run in ROS 2 as the rviz2 package) is the 3D visualizer of the ROS framework.[1] RViz is different from Gazebo, a robot simulator. RViz only displays data already flowing through ROS, whereas Gazebo simulates the robot and its world with physics.[1][5]

      RViz2 simulates nothing and has no physics engine. It simply draws whatever arrives on ROS topics. Each visual layer you turn on is called a display. You add displays from a list of built-in types, including:[1]

      • RobotModel: Draws the robot in its current pose using its active coordinate transforms (TF).[1] Those transforms usually come from the robot_state_publisher node. It reads the robot’s Unified Robot Description Format (URDF), an Extensible Markup Language (XML) file describing links and joints. Using that file and incoming joint positions (sensor_msgs/msg/JointState), it calculates the transforms between all the robot’s parts.[6]
      • Laser Scan and Point Cloud(2): Show readings from a laser scanner (sensor_msgs/msg/LaserScan) or a point cloud (sensor_msgs/msg/PointCloud2). You can adjust rendering modes and how scans accumulate over time.[1]
      • Map and Grid Cells: Map draws an occupancy grid (nav_msgs/msg/OccupancyGrid) on the ground plane. Grid Cells draws cells from a grid, usually obstacles from a navigation costmap.[1]
      • InteractiveMarker: Shows 3D objects from interactive marker servers and lets you move them with your mouse.[1]

      To start RViz2 from your terminal, run this command:[1] 

      ros2 run rviz2 rviz2

      03. Lining up sensor data with tf2

      Every sensor on a robot measures the world from where it is mounted, not from the robot’s center. A front lidar measures from its own spot, while a camera on a mast sees from higher up. To draw both readings in one 3D view, ROS 2 needs a way to line up all those viewpoints.

      On a real robot, sensors sit in different places. Take an example of our own. A front lidar might sit 30 cm ahead of and 15 cm above the robot’s wheel center. A depth camera sits on a mast. Suppose the lidar reports an obstacle at (x = 1.2 m, y = 0.5 m) in its own frame. Your navigation software needs to know where that obstacle is relative to the robot’s base or to the map.

      To draw data from several sensors in the same 3D view, RViz2 uses the tf transform system. It converts each reading from the coordinate frame it arrived in into a common reference frame.[1] In ROS 2, the tf2 library handles this job and tracks multiple coordinate frames over time.[7] tf2 stores the relationships between frames as a tree, buffered in time. It can transform points and vectors between any two frames at any desired time.[7]

      In RViz, the most important setting is the Fixed Frame, which is the frame treated as the “world.” You usually set it to map or world, though you can also use the odometry frame. For correct results, the fixed frame should not move relative to the world. Avoid setting it to a moving frame such as the robot’s base. Otherwise, everything the robot has seen will appear in front of the robot instead of where it really is.[1] Each display also shows a status (OK, Warning, Error, or Disabled). Check that status first whenever data does not appear.[1]

      04. rqt_graph: seeing how nodes connect

      Suppose you start a sensor driver and a planner, or launch Turtlesim with keyboard control, and nothing moves. Often the problem is a simple typo in a topic name that keeps two programs from talking. Instead of guessing, you can view a live diagram of your running nodes and how they connect.

      rqt is a graphical user interface (GUI) framework that implements its tools as plugins. You can run them as dockable windows inside one rqt window, or on their own.[2] One of the most useful plugins is rqt_graph. It visualizes the ROS computation graph, showing running nodes and the topics that connect them.[3][8]

      Start it from your terminal while Turtlesim and the teleop node are running. You can also open rqt and choose Plugins > Introspection > Node Graph:[3] 

      ros2 run rqt_graph rqt_graph

      In rqt_graph, running nodes appear as ovals (here /teleop_turtle and /turtlesim). Topics appear as boxes (/turtle1/cmd_vel), and arrows show which way messages flow.[3][8] Here, /teleop_turtle publishes your keystrokes on /turtle1/cmd_vel, and /turtlesim subscribes to it.[3]

      If a new sensor driver is not reaching your planner, rqt_graph helps you debug quickly. You can see whether the two nodes share the same topic, or whether a topic typo left one disconnected. Recent versions also flag topics whose publishers and subscribers have incompatible message types or Quality of Service (QoS) settings.[8]

      05. More rqt tools: plots, logs, and services

      Once you know your nodes are connected, you often need to inspect what they are doing. You might want to watch a sensor value change, filter error logs, or trigger a service with a click. Besides rqt_graph, rqt gives you three built-in plugins for these debugging jobs:[2]

      • rqt_plot: A GUI plugin that plots numeric values on a two-dimensional (2D) graph.[9] You enter a topic field, such as /turtle1/pose/x, and watch it change over time. This helps when tuning controllers or looking at sensor noise.
      • rqt_console: A log viewer that collects log messages over time and lets you view, filter, save, and reload them.[10] By default, ROS 2 nodes send their log messages to the /rosout topic. Each message has a severity level: DEBUG, INFO, WARN, ERROR, or FATAL.[11]
      • rqt_service_caller: A GUI plugin for calling services.[12] Open it in rqt under Plugins > Services > Service Caller. Pick a service such as /spawn, fill in the request fields, and click Call.[13]

      06. ros2 bag: recording and replaying robot data

      Field tests with real robots are expensive and hard to repeat. If a rover fails at a tricky spot outdoors, you cannot easily recreate that exact situation back in the lab. Instead, you can record what your robot’s topics published during the run and replay it later without the robot.

      That is what ros2 bag does. It is a command-line tool that records data published on any number of topics and saves it to disk.[4] In recent releases, it can also record services and actions. You can replay the data to reproduce tests and experiments, or share it so others can recreate your work.[4]

      Try recording a session while Turtlesim and the teleop node are running. The -o option names the bag directory, and --topics lists the topics to record:[4] 

      ros2 bag record -o my_turtle_session --topics /turtle1/cmd_vel /turtle1/pose

      Drive the turtle around with the keyboard teleop for about twenty seconds, then press Ctrl+C. ros2 bag creates a directory named my_turtle_session. Inside, it saves a metadata.yaml file and the recorded data file.[4]

      To inspect the recording, run:[4] 

      ros2 bag info my_turtle_session

      The terminal prints the files, bag size, storage format (mcap by default), ROS distribution, duration, and start and end times. It also shows the total message count and lists each topic’s message type, message count, and serialization format.[4] In the official example, /turtle1/cmd_vel had only 9 messages, one per key press. In contrast, /turtle1/pose had over 3000 messages, because Turtlesim publishes the pose at regular intervals the whole time it runs.[4]

      Before replaying, stop the teleop node with Ctrl+C. You can also return the turtle to its starting position with Turtlesim’s /reset service, whose type is std_srvs/srv/Empty:[4][14] 

      ros2 service call /reset std_srvs/srv/Empty

      Now replay the bag:[4] 

      ros2 bag play my_turtle_session

      ros2 bag play publishes the recorded messages again, and the turtle follows the path you drove while recording. It will not match 100% exactly, because Turtlesim is sensitive to small changes in timing.[4] Because this bag also contains /turtle1/pose, playback keeps going for as long as Turtlesim was running during the recording. It continues even when the turtle was standing still.[4]

      07. How ros2 bag stores your recordings

      When you record a robot run with ros2 bag, messages need to reach your disk fast. Later, you want to jump to one moment in a run and still read files after your code changes. To make that easy, modern ROS 2 saves new bags in the MCAP format by default.

      Earlier ROS 2 versions stored bags in sqlite3 databases. Testing showed sqlite3 was often not fast enough and lacked features wanted for offline processing.[15] Today, ros2 bag defaults to MCAP, though you can still choose sqlite3 and play back bags in either format.[4][15]

      MCAP is an open-source container file format for multimodal log data, maintained as a Foxglove project. Its documentation highlights three strengths:[16]

      • Append-only writing: MCAP uses a row-oriented, append-only design to minimize disk input/output (I/O) while recording.[16]
      • Built-in indexing: Files can contain an optional index for fast, efficient reading. Tools can jump to a point in a recording without reading the whole file.[16]
      • Self-describing schemas: MCAP stores message schemas alongside the data. Your files stay readable in the future even as your code changes.[16]
      For the curious: ROS 2 release history for sqlite3 and MCAP

      In early ROS 2 releases, ros2 bag recorded into sqlite3 databases by default.[15] Starting with ROS 2 Iron, the default format for new bags switched to MCAP, and this is still the default in Jazzy and Lyrical.[4][15]

      08. Gazebo: testing robots in a virtual world

      Running tests on a real robot takes effort and can be expensive. You can test your algorithms in a virtual world with simulated physics and sensors first. While RViz2 visualizes data, Gazebo is an open-source simulator that creates the virtual world the robot lives in.[5]

      In Gazebo, you can test realistic robot conditions before using real hardware:

      • Wheeled robots can be given wheel slip with the WheelSlip plugin.[5]
      • Simulated sensors include cameras, depth and red-green-blue-depth (RGBD) cameras, graphics processing unit (GPU) lidars, IMUs, contact sensors, air pressure, and thermal cameras.[5]
      • Sensor readings can include Gaussian noise. That lets you test algorithms on imperfect data, as on a real robot.[5]
      For the curious: Gazebo physics engines, naming history, and ROS 2 pairings

      Current Gazebo (Gazebo Sim) ships physics engine plugins for DART and Bullet, plus its own simple TPE engine. The ODE and Simbody engines used by Gazebo Classic are not supported in the new Gazebo.[5]

      On January 31, 2025, Gazebo Classic (Gazebo 11, the last Classic release) officially reached end of life.[17] New work uses the current Gazebo, which was called Ignition Gazebo until the Ignition name was retired in 2022.[18] Each ROS 2 release has a recommended Gazebo release: ROS 2 Jazzy pairs with Gazebo Harmonic, and ROS 2 Lyrical Luth pairs with Gazebo Jetty.[19][20]

      09. Connecting Gazebo to ROS 2

      Gazebo is a separate program from ROS 2, so the two do not speak the same message format by default. Gazebo uses its own messaging system, called Gazebo Transport, with its own message types such as gz.msgs.LaserScan.[21] To let your ROS 2 code interact with a simulated robot, you need a translator between them.

      You connect Gazebo to ROS 2 with the ros_gz packages (installed with sudo apt-get install ros-${ROS_DISTRO}-ros-gz). Its ros_gz_bridge provides a network bridge that exchanges messages between ROS 2 and Gazebo Transport.[19][21] For example:[21] 

      ros2 run ros_gz_bridge parameter_bridge /scan@sensor_msgs/msg/LaserScan[gz.msgs.LaserScan

      The argument gives the topic name, the ROS message type, and the Gazebo message type. The symbol between the two types sets the direction. An @ is a two-way bridge, [ bridges from Gazebo to ROS, and ] bridges from ROS to Gazebo.[21]

      Here, the bridge converts the simulated lidar’s gz.msgs.LaserScan messages into ROS sensor_msgs/msg/LaserScan messages on /scan. Any ROS node subscribed to /scan receives them just as it would from a real lidar driver. A navigation stack, for example, sees no difference. This is what lets you test the same code in simulation first.

      10. Ready-made packages you can build on

      You do not have to write core autonomy algorithms from scratch. Robotics engineers save time by building on well-tested community packages. You can use the tools in this lesson to inspect, record, and simulate packages such as these:

      Package Domain Primary Capability
      Nav2[22] Mobile Navigation Successor of the ROS Navigation Stack: perception, planning, control, localization and behaviors, with navigation logic built from behavior trees.
      MoveIt 2[23] Arm Manipulation The robotic manipulation platform for ROS 2: kinematics, motion planning and planning around objects.
      slam_toolbox[24] Mapping & Localization 2D Simultaneous Localization and Mapping (SLAM) with pose-graph optimization, a localization mode, lifelong mapping and map serialization.
      ros2_control[25] Robot Control A framework for (real-time) control of robots using ROS 2, with hardware interfaces and ready-made controllers such as joint trajectory and differential drive controllers.

      Together, RViz2, rqt, ros2 bag, Gazebo, and these community packages equip a single developer or a small team. They give you the tools for building, testing, and debugging robot software.

      Try it
      1. Launch Turtlesim and keyboard teleop, then open rqt_graph. Experiment with the graph filters: uncheck "Debug" under Hide, refresh, and note which extra nodes and topics appear.
      2. Record a 15-second bag file while teleoperating the turtle in a figure-eight pattern. Inspect the resulting dataset with ros2 bag info. Divide the message count on /turtle1/pose by the duration to estimate its publishing rate, then compare your answer with ros2 topic hz /turtle1/pose.
      3. Suppose an engineer is testing an autonomous driving algorithm. Explain in your own words why they prefer testing against a recorded ros2 bag file before testing on real hardware on public roads.
