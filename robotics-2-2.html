      2.2 Common Programming Environments

      Gerald Lê
      Chapter 2, lesson 2 of 8 ← Previous: 2.1 Types of Programming Next: 2.3 Common Programming Languages →
      Start here

      This lesson contrasts PC-based 3D simulation suites with touchscreen teach-pendant environments used directly on the shop floor. You do not need to memorize every vendor product name; focus on how virtual controllers mirror real hardware and how plugin ecosystems extend them.

      • You will learn how ABB RobotStudio runs a Virtual Controller copy of real RobotWare software.
      • You will learn how Universal Robots PolyScope organizes programs in a tree with safety boundaries and URCaps plugins.
      • You will learn how virtual commissioning tests PLC interlocks before touching real hardware.

      01. Why robots need special programming tools

      Writing code for an app is very different from programming a factory robot. Normal software runs on a screen, while a robot program moves heavy arms and grippers in the real world. Your program also has to coordinate with safety switches and other machines in the work cell. Learning how robot programming tools work shows you how engineers test moves before a robot ever powers on.

      General software developers write source code in text editors, compile it, and test it on a computer. In robotics, the software must also coordinate physical arms, grippers, and safety interlocks. It must also work with programmable logic controllers (PLCs). In a modern robotic cell, the PLCs and robot controllers must be integrated with each other.[1]

      Because of these needs, robot programming environments have split into two main kinds. First, three-dimensional (3D) offline simulation suites run on a personal computer (PC). They let engineers build a virtual copy of a work cell and test real robot programs in it.[2] Second, graphical teach pendant environments run directly on the robot controller. They let shop-floor staff teach positions and build programs without traditional coding.[3]

      Two widely used tools show this contrast. One is ABB RobotStudio, which ABB describes as the world’s most used offline programming tool for robotics.[2] The other is Universal Robots (UR) PolyScope. It is a graphical interface for UR collaborative robots that is designed for users without coding experience.[3]

      02. Simulating a robot on a PC: ABB RobotStudio

      Stopping a busy factory robot just to write or test new code interrupts production. Offline programming lets you build and test the whole robot cell on a computer screen instead. You can check moves and debug programs while the real cell keeps running on the shop floor.

      ABB RobotStudio is an offline programming and 3D simulation platform for ABB robots.[2] It lets automation engineers model, program, simulate, and debug robot cells on a Windows PC without disturbing live production.[2][4]

      At the center of RobotStudio is ABB’s Virtual Controller. In everyday words, it runs the same controller software on your PC that runs the real robot in the factory; ABB states that the tool is built on the Virtual Controller, “an exact copy of the real software that runs your robots in production.”[2][5] That production software is RobotWare, the controller software of ABB robots.[6]

      Because the simulated robot runs the same controller software as the real machine, simulations can use real robot programs and configuration files. Those files are identical to the ones used on the shop floor.[2] This is why you can usually transfer RobotStudio programs to a physical robot with little adjustment. You only need to calibrate the real cell (see Lesson 2.1).

      03. How simulation matches real robot motion

      When you plan a two-robot packaging cell on a PC, you want to know how fast it will really run. A simulation only helps if the virtual arm follows the same path and acceleration rules as the real robot. You also need to know that simulated cycle times are close to reality.

      Two motion control features in ABB’s RobotWare software shape how ABB robots move. Because the Virtual Controller copies the real controller software, both features run in simulation too:[6][5]

      • TrueMove: In everyday words, TrueMove keeps the robot on the path you programmed even when you change its speed; ABB states that TrueMove “ensures that the motion path followed by the robot is the same as the programmed path,” and describes the result as a speed-independent path that does not require tuning.[6] If an operator lowers program speed during testing, the tool should trace the same geometric path.
      • QuickMove: In everyday words, QuickMove accelerates and slows down as quickly as the robot can to shorten each cycle; ABB describes QuickMove as a self-optimizing motion control feature that “keeps cycle times to a minimum by ensuring maximum acceleration at every moment.”[6]

      Because the simulation runs this real motion software, engineers use it to estimate cycle times before hardware is installed. For example, you can check whether a proposed two-robot packaging cell can meet a required cycle time. Keep in mind that simulated times are still estimates rather than exact shop-floor measurements.

      For the curious: simulated cycle-time caveats in an early RobotStudio specification

      Simulated times are still estimates: an early RobotStudio product specification noted that motion time in the Virtual Controller was 0.1 s too fast per program cycle and that non-motion time such as wait instructions was not included.[4]

      04. Creating robot paths from 3D models and add-ins

      Teaching a robot to follow the curved edge of a sheet metal part by hand could take hundreds of separate points. Instead, you can import a 3D model of the part straight into your virtual cell. The software then turns edges and curves on that model into a robot path for you.

      RobotStudio can import major computer-aided design (CAD) formats into the simulation.[7] Once a part model is imported, you do not need to jog a robot to teach hundreds of discrete points. Instead, you select curves on the part model, such as the edge of a sheet metal part. RobotStudio then creates robot targets and paths along them. You control how closely the path follows the geometry and whether segments are linear or circular.[4][5]

      For specialized processes, ABB also offers add-in packages for RobotStudio called PowerPacs:

      PowerPac Add-In Primary Industrial Purpose Key Automated Capabilities
      ArcWeld PowerPac Arc welding Offline programming and simulation of arc welding stations.[4]
      Machining PowerPac Machining, deburring, grinding, polishing, and deflashing Several strategies for creating paths on freeform surfaces, an integrated postprocessor that converts computer-aided manufacturing (CAM) output into robot paths, and tools to optimize paths for collisions, speed, and reach.[8]
      Palletizing PowerPac End-of-line palletizing Configuration and simulation of palletizing applications, including pallet patterns that stack products in layers and slip sheets between layers.[9]
      Cutting PowerPac Robotic laser cutting Generating and editing cutting paths from part shape data and CAD files, optimizing cutting programs, and configuring interface signals.[10]
      For the curious: RobotStudio’s 3D geometry kernel and supported CAD formats

      RobotStudio has used Spatial’s ACIS 3D geometry kernel since the beginning, and Spatial’s InterOp translators let it import major CAD formats.[7] An early ABB product specification lists IGES and STEP import as standard, with VDAFS, CATIA, STL, and VRML available as options.[4]

      05. Virtual commissioning: testing signals before power-on

      A robot arm rarely works by itself. On a factory floor, it has to coordinate with conveyors, grippers, safety doors, and operator panels. If a signal between the robot and the rest of the cell fires out of order, the cell cannot run properly. Virtual commissioning lets you test those signals in software before powering on hardware.

      In an automated cell, manipulators must communicate with PLCs, safety devices, sensors, operator panels, and part fixtures.[1] In everyday words, virtual commissioning means checking your cell’s control software against a simulation model early in the project; Raffaeli et al. define it as “a technique that aims to validate the control software of a manufacturing system with a simulation model,” carried out early in the commissioning process.[1]

      Using a virtual cell, controls engineers can test PLC logic, safety interlocks, and handshakes between conveyors and robot grippers before hardware is powered on. In Raffaeli et al.’s case study, using the virtual cell to improve the sequence of operations reduced the overall cycle time by 30%.[1]

      For the curious: how Raffaeli et al. linked RobotStudio to a PLC

      Raffaeli et al. used ABB RobotStudio as the virtual prototyping platform for a robotic assembly cell. They developed a “PLC Smart Component” that extends RobotStudio so the simulated robots can exchange signals with a Beckhoff TwinCAT PLC environment. Their paper also discusses coupling simulation models to control software through the open platform communications (OPC) protocol.[1]

      06. Programming on a touchscreen: Universal Robots PolyScope

      Not every robot job needs a full 3D simulation suite on a separate desktop computer. Small workshops often want shop-floor staff to set up a robot directly at the machine. Touchscreen teach pendants make this easier by replacing typed code with menus and buttons.

      While RobotStudio is a desktop engineering suite, Universal Robots took a different approach with PolyScope for its collaborative robots (cobots). PolyScope runs on the robot’s teach pendant and works with all UR cobots.[3] In everyday words, it is built so people can program a robot without coding experience; Universal Robots says it offers a graphical interface intended to work “without requiring program expertise.”[3]

      In PolyScope 5 on e-Series robots, the screen header gives you access to four main tabs:[11]

      • Run Tab: A simple way of operating the robot using pre-written programs.[11]
      • Program Tab: Where robot programs are created and modified.[11]
      • Installation Tab: Configures robot arm settings and external equipment, such as mounting, safety, and tool input/output (I/O).[11][12]
      • Move Tab: Controls robot movement, for example with tool center point (TCP) arrows that move the tool in straight lines or joint position values for individual joints.[11]

      Universal Robots also offers the newer PolyScope X platform. It includes its own software development kit (SDK) for adding extensions.[13]

      07. Building a program tree and teaching by hand

      Suppose you want a cobot to pick up a part, check a sensor, and drop it into a good bin or a reject bin. Instead of asking you to write lines of text code, PolyScope lets you snap steps together in an outline. You can also guide the arm by hand to show it where each target sits.

      PolyScope displays a robot routine as a program tree. The tree grows as you add steps called nodes, and you configure each selected node in the Command tab. Nodes that are not configured correctly are highlighted in yellow, so the program cannot run until they are fixed.[11] Here is a simplified example of a pick-and-sort routine: 

      Robot Program
  MoveJ
    Waypoint_Home
  MoveL
    Waypoint_Approach
    Waypoint_Pick
    Set DO[0] = On
    Wait: 0.5 s
    Waypoint_Retract
  If DI[2] == True Then
    MoveL
      Waypoint_DropGood
  Else
    MoveL
      Waypoint_DropReject
  EndIf

      You can read this program tree from top to bottom. First, the robot moves from Waypoint_Home through Waypoint_Approach to Waypoint_Pick. There it switches on digital output 0 (DO[0]), waits 0.5 s, and retracts. Next, it checks digital input 2 (DI[2]) to choose between Waypoint_DropGood and Waypoint_DropReject.

      To teach a fixed waypoint, you physically move the robot arm to the spot and save it in the program. For example, you can hold the Freedrive button on the teach pendant or on the robot itself.[11] In Freedrive, the brakes are released and the joints move with little resistance.[11][12]

      Behind this graphical layer, the robot is controlled by URScript, the Universal Robots scripting language. PolyScope generates program code in URScript automatically.[14] Advanced users can also add a Script node to the tree to run their own URScript.[11] That gives access to features such as threads and socket communication.[14]

      08. Virtual safety walls and speed limits

      When a cobot shares a workspace with people, software limits help keep the arm out of danger zones and slow it down when someone comes near. You can set invisible walls in space and lock those limits behind a password so nobody changes them by mistake.

      Collaborative robots are often used in shared work areas, which requires dependable software control of speed and working space. Universal Robots states that PolyScope for e-Series includes 17 certified safety features.[3] Safety settings are password protected and can only be changed once a safety password is set.[11]

      Operators configure safety planes: virtual walls defined in cell space. Restricting the tool flange prevents the tool flange and attached tool from crossing a safety plane, and the Restrict Elbow option keeps the elbow joint from passing through a plane. Separate limits cap stopping time and the distance the tool or elbow can travel while stopping.[11]

      PolyScope also supports two safety configurations. Slowing the robot when a person comes near resembles speed and separation monitoring, one of the four collaborative techniques described in ISO/TS 15066, an international technical specification for collaborative robot safety:[11][15]

      • Normal Mode: The safety configuration that is active by default, with the limits used for normal production.[11]
      • Reduced Mode: Becomes active when the TCP moves beyond a Trigger Reduced plane or when a configured safety input is triggered, for example by a laser area scanner that detects a person. The robot must decelerate to meet the lower reduced limits, which the integrator sets from the risk assessment.[11][12]

      09. Adding new tools with URCaps plugins

      Sooner or later you will attach a new electric gripper, screw feeder, or camera to your robot. Traditionally, making that device talk to the robot meant writing custom communication code and wiring it into your program by hand. Plugins let you install the tool once and control it with ready-made screens inside PolyScope.

      Universal Robots handles this with plugins called URCaps. In everyday words, a URCap is an add-on that plugs directly into PolyScope; Universal Robots states that in PolyScope 5, “a URCap is a Java-based plugin, that integrates in to PolyScope.”[16]

      A URCap can add two kinds of items. Installation nodes configure general settings and the application environment, while program nodes run commands in the program sequence.[16] When you install a gripper URCap, its program nodes appear in the PolyScope program tree beside the built-in nodes. You can then operate the gripper through a simple user interface instead of writing low-level communication code.[16]

      For the curious: background daemons and PolyScope X URCap packaging

      In PolyScope 5, a URCap can also install a daemon (a background process that runs continuously without user intervention to provide services), such as a Python script that runs on the UR controller in the background.[16]

      For PolyScope X, URCaps are packaged as single .urcapx files. The SDK supports custom program nodes, application nodes, and Docker container contributions, with web contributions written against a TypeScript application programming interface (API).[13]

      10. Other robot programming suites: ROBOGUIDE, MotoSim, and RoboDK

      ABB and Universal Robots are not the only options on the factory floor. Most major robot makers offer their own offline simulation software, and third-party tools let you program many brands in one place. Knowing these tools helps you recognize what different shops and factories use.

      Beyond RobotStudio and PolyScope, three other programming suites are widely used:

      • FANUC ROBOGUIDE: ROBOGUIDE is FANUC’s 3D robot simulation suite. Its virtual controller calculates, validates, and optimizes cycle times.[17] You can also display virtual teach pendants for each controller and use specialized application packages.[18]
      • Yaskawa MotoSim EG-VRC: MotoSim EG-VRC is PC-based offline programming software for several Yaskawa Motoman robot controllers. Its Collision Detection feature turns robots red in the simulation to signal a potential interference, which helps when several robots work close together as a team.[19]
      • RoboDK: Unlike vendor tools, RoboDK is an independent offline programming environment. RoboDK states that it includes over 100 post processors to generate programs for more than 1400 robots from 80 manufacturers. Its application programming interface (API) is available for Python, C#/.NET, C++, and Matlab.[20]
      For the curious: FANUC ROBOGUIDE packages and Yaskawa controller models

      FANUC ROBOGUIDE’s application packages include iRPickPRO, HandlingPRO, PaintPRO, PalletPRO, and WeldPRO.[18]

      Yaskawa MotoSim EG-VRC supports Yaskawa Motoman robots that use NX100, DX100, DX200, FS100, YRC1000, or YRC1000micro controllers.[19]

      11. Choosing the right programming environment

      With several environments to pick from, how do you decide which one fits a job? The right tool depends on which robots you use, how often your parts change, and who will program the cell. Comparing three main options side by side makes the trade-offs clear.

      Feature ABB RobotStudio UR PolyScope RoboDK
      Target Hardware ABB robots[2] Universal Robots cobots[3] More than 1400 robots from 80 manufacturers[20]
      Interface Location Windows PC[4] Robot teach pendant[3] Windows, Mac, and Ubuntu PCs, plus a web version[21]
      Simulation Parity Virtual Controller, a copy of the real controller software[2] Program runs on the real robot controller Generic simulation with brand-specific post processors[20]
      CAD Automation Automatic paths from CAD curves[4] Waypoints taught by moving the arm[11] Converts CAM programs (APT, G-code and others) into robot programs[22]
      Underlying Language ABB RAPID[23] Universal Robots URScript[14] Output in each vendor's language through post processors; API in Python and other languages[20]

      Your factory workflow usually points to one clear choice. High-volume production lines often use proprietary suites like RobotStudio or ROBOGUIDE for cycle-time estimation and virtual commissioning.[17][1] For high-mix, small-batch work or assembly benches, pendant-based cobot tools like PolyScope are a better fit. They let floor technicians deploy and adjust robots quickly without coding expertise.[3]

      Try it
      1. Compare how ABB RobotStudio and UR PolyScope are designed to be used. Which one targets engineering design offices, and which one targets factory-floor operators?
      2. A manufacturing cell uses a laser area scanner to detect people. Outline how you would set up Normal Mode and Reduced Mode in PolyScope to balance worker safety and productivity.
      3. Why is virtual commissioning especially helpful when connecting a robot to a third-party programmable logic controller (PLC)? What problems does it catch before you power on the hardware?
