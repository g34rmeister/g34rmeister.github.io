2.2 Common Programming Environments

Gerald Lê

01. The role of dedicated programming environments

Programming an industrial robot requires tools that connect high-level task logic with real-time mechanical motion. General software developers write source code in text editors, compile it, and test it on a computer. In robotics, the software must also coordinate physical arms, grippers, safety interlocks, and programmable logic controllers (PLCs); in a modern robotic cell, PLCs and robot controllers must be coordinated and integrated.[1]

Robot programming environments have therefore split into two main kinds. First, 3D offline simulation suites let engineers build a virtual copy of a work cell on a PC and test real robot programs in it.[2] Second, graphical teach pendant environments running on the robot controller let shop-floor staff teach positions and build programs without traditional coding.[3]

Two widely used environments illustrate this contrast: ABB RobotStudio, which ABB describes as the world's most used offline programming tool for robotics,[2] and Universal Robots PolyScope, a graphical interface for UR collaborative robots that is designed for users without coding experience.[3]

02. ABB RobotStudio and the Virtual Controller

ABB RobotStudio is an offline programming and 3D simulation platform for ABB robots.[2] It lets automation engineers model, program, simulate, and debug robot cells on a Windows PC without disturbing live production.[2][4]

The core of RobotStudio is ABB's Virtual Controller. ABB states that the tool is built on the Virtual Controller, “an exact copy of the real software that runs your robots in production.”[2][5] That production software is RobotWare, the controller software of ABB robots.[6]

Because the simulated robot runs the same controller software as the real machine, simulations can use real robot programs and configuration files identical to those used on the shop floor.[2] This is why RobotStudio programs can usually be transferred to a physical robot with little adjustment, apart from calibrating the real cell (see Lesson 2.1).

03. Motion fidelity: TrueMove and QuickMove

Two motion control features of ABB's RobotWare controller software shape how ABB robots move, and because the Virtual Controller is a copy of the real controller software, they are also present in simulation:[6][5]

  • TrueMove: ABB states that TrueMove “ensures that the motion path followed by the robot is the same as the programmed path,” and describes the result as a speed-independent path that does not require tuning.[6] If an operator lowers program speed during testing, the tool should trace the same geometric path.
  • QuickMove: ABB describes QuickMove as a self-optimizing motion control feature that “keeps cycle times to a minimum by ensuring maximum acceleration at every moment.”[6]

Because the simulation uses the real motion software, engineers use it to estimate cycle times before hardware is installed, for example to check whether a proposed two-robot packaging cell can meet a required cycle time. Simulated times are still estimates: an early RobotStudio product specification noted that motion time in the Virtual Controller was 0.1 s too fast per program cycle and that non-motion time such as wait instructions was not included.[4]

04. 3D CAD integration and PowerPac extensions

RobotStudio uses the ACIS 3D geometry kernel from Spatial, which has been part of RobotStudio since the beginning, and Spatial's InterOp translators let it import major CAD formats.[7] An early ABB product specification lists IGES and STEP import as standard, with VDAFS, CATIA, STL, and VRML available as options.[4]

Once a part model is imported, engineers can generate robot paths automatically. Instead of jogging a robot to teach hundreds of discrete points, the programmer selects curves on the part model, such as the edge of a sheet metal part, and RobotStudio creates robot targets and paths along them. The user controls how closely the path follows the geometry and whether segments are linear or circular.[4][5]

For specialized processes, ABB offers add-in packages for RobotStudio called PowerPacs:

PowerPac Add-In Primary Industrial Purpose Key Automated Capabilities
ArcWeld PowerPac Arc welding Offline programming and simulation of arc welding stations.[4]
Machining PowerPac Machining, deburring, grinding, polishing, and deflashing Several strategies for creating paths on freeform surfaces, an integrated postprocessor that converts CAM output into robot paths, and tools to optimize paths for collisions, speed, and reach.[8]
Palletizing PowerPac End-of-line palletizing Configuration and simulation of palletizing applications, including pallet patterns that stack products in layers and slip sheets between layers.[9]
Cutting PowerPac Robotic laser cutting Generating and editing cutting paths from part shape data and CAD files, optimizing cutting programs, and configuring interface signals.[10]

05. Virtual commissioning and fieldbus integration

Modern automated cells do not run robots in isolation. Manipulators must communicate with PLCs, safety devices, sensors, operator panels, and part fixtures.[1]

Virtual commissioning is “a technique that aims to validate the control software of a manufacturing system with a simulation model,” carried out early in the commissioning process.[1] Raffaeli et al. used ABB RobotStudio as the virtual prototyping platform for a robotic assembly cell and developed a “PLC Smart Component” that extends RobotStudio so the simulated robots can exchange signals with a Beckhoff TwinCAT PLC environment. Their paper also discusses coupling simulation models to control software through the open platform communications (OPC) protocol.[1]

In this way, controls engineers can test PLC logic, interlocks, and the handshakes between conveyors and robot grippers in software, before hardware is powered on. In Raffaeli et al.'s case study, using the virtual cell to improve the sequence of operations reduced the overall cycle time by 30%.[1]

06. Universal Robots PolyScope: a touch-first paradigm

While RobotStudio is a desktop engineering suite, Universal Robots took a different approach with PolyScope for its collaborative robots (cobots). PolyScope runs on the robot's teach pendant and offers a graphical interface intended to work “without requiring program expertise,” and it is compatible with all UR cobots.[3]

In PolyScope 5 on e-Series robots, the screen header gives access to four main tabs:[11]

  • Run Tab: A simple way of operating the robot using pre-written programs.[11]
  • Program Tab: Where robot programs are created and modified.[11]
  • Installation Tab: Configures robot arm settings and external equipment, such as mounting, safety, and tool I/O.[11][12]
  • Move Tab: Controls robot movement, for example with TCP arrows that move the tool in straight lines or joint position values for individual joints.[11]

Universal Robots also offers the newer PolyScope X platform, which has its own software development kit for extensions.[13]

07. PolyScope program tree and freedrive navigation

Rather than asking operators to write text code, PolyScope shows a robot routine as a program tree. The tree grows as nodes are added, each selected node is configured in the Command tab, and nodes that are not configured correctly are highlighted in yellow so the program cannot run until they are fixed.[11] A simplified example of a pick-and-sort routine: 

Robot Program
  MoveJ
    Waypoint_Home
  MoveL
    Waypoint_Approach
    Waypoint_Pick
    Set DO[0] = On
    Wait: 0.5 s
    Waypoint_Retract
  If DI[2] == True Then
    MoveL
      Waypoint_DropGood
  Else
    MoveL
      Waypoint_DropReject
  EndIf

To teach a fixed waypoint, the operator physically moves the robot arm to the position, for example by holding the Freedrive button, and then sets the waypoint in the program.[11] Freedrive can be enabled from the teach pendant or from a Freedrive button on the robot; in Freedrive the brakes are released and the joints move with little resistance.[11][12]

Behind this graphical layer, the robot is controlled by URScript, the Universal Robots scripting language, and PolyScope generates program code in it.[14] Advanced users can add a Script node to the tree to run their own URScript,[11] which supports features such as threads and socket communication.[14]

08. Safety boundary configuration and dual modes

Collaborative robots are often used in shared work areas, which requires dependable software control of speed and working space. Universal Robots states that PolyScope for e-Series includes 17 certified safety features.[3] Safety settings are password protected and can only be changed once a safety password is set.[11]

Operators configure safety planes: virtual walls defined in cell space. Restricting the tool flange prevents the tool flange and attached tool from crossing a safety plane, and the Restrict Elbow option keeps the elbow joint from passing through a plane. Separate limits cap stopping time and the distance the tool or elbow can travel while stopping.[11]

PolyScope also supports two safety configurations. Slowing the robot when a person comes near resembles speed and separation monitoring, one of the four collaborative techniques described in ISO/TS 15066:[11][15]

  • Normal Mode: The safety configuration that is active by default, with the limits used for normal production.[11]
  • Reduced Mode: Becomes active when the TCP moves beyond a Trigger Reduced plane or when a configured safety input is triggered, for example by a laser area scanner that detects a person. The robot must decelerate to meet the lower reduced limits, which the integrator sets from the risk assessment.[11][12]

09. The URCaps plugin ecosystem

Integrating a new electric gripper, screw feeder, or camera with a robot has traditionally meant writing custom communication code and then integrating it by hand into the robot program.

Universal Robots addresses this with URCaps. In PolyScope 5, “a URCap is a Java-based plugin, that integrates in to PolyScope.” A URCap can add installation nodes, which configure general settings and the application environment, and program nodes, which carry out particular commands in the program sequence. A URCap can also install a daemon (a background process that runs continuously without user intervention to provide services), such as a Python script that runs on the UR controller in the background.[16] For PolyScope X, URCaps are packaged as single .urcapx files. The SDK supports custom program nodes, application nodes, and Docker container contributions, with web contributions written against a TypeScript API.[13]

When a gripper URCap is installed, its program nodes appear in the PolyScope program tree next to the built-in nodes, so the operator can operate the gripper through a simple user interface instead of writing low-level communication code.[16]

10. The competitive landscape: ROBOGUIDE, MotoSim, and RoboDK

Beyond RobotStudio and PolyScope, several other programming suites are widely used:

  • FANUC ROBOGUIDE: ROBOGUIDE is FANUC's 3D robot simulation suite. Its virtual controller calculates, validates, and optimizes cycle times,[17] and virtual teach pendants can be displayed for each controller.[18] Its application packages include iRPickPRO, HandlingPRO, PaintPRO, PalletPRO, and WeldPRO.[18]
  • Yaskawa MotoSim EG-VRC: MotoSim EG-VRC is PC-based offline programming software for Yaskawa Motoman robots that use NX100, DX100, DX200, FS100, YRC1000, or YRC1000micro controllers. Its Collision Detection feature turns robots red in the simulation to signal a potential interference, which helps when several robots must work close together as a team.[19]
  • RoboDK: Unlike vendor tools, RoboDK is an independent offline programming environment. RoboDK states that it includes over 100 post processors to generate programs for more than 1400 robots from 80 robot manufacturers, and its API is available for Python, C#/.NET, C++, and Matlab.[20]

11. Selecting an environment: cost and complexity

Choosing a robot programming environment depends on operational constraints:

Feature ABB RobotStudio UR PolyScope RoboDK
Target Hardware ABB robots[2] Universal Robots cobots[3] More than 1400 robots from 80 manufacturers[20]
Interface Location Windows PC[4] Robot teach pendant[3] Windows, Mac, and Ubuntu PCs, plus a web version[21]
Simulation Parity Virtual Controller, a copy of the real controller software[2] Program runs on the real robot controller Generic simulation with brand-specific post processors[20]
CAD Automation Automatic paths from CAD curves[4] Waypoints taught by moving the arm[11] Converts CAM programs (APT, G-code and others) into robot programs[22]
Underlying Language ABB RAPID[23] Universal Robots URScript[14] Output in each vendor's language through post processors; API in Python and other languages[20]

For high-volume production lines, proprietary suites like RobotStudio or ROBOGUIDE are valuable for cycle-time estimation and virtual commissioning.[17][1] For high-mix, small-batch work or assembly benches, pendant-based cobot environments like PolyScope let floor technicians deploy and adjust robots quickly without coding expertise.[3]

Try it
  1. Compare the architectural philosophy of ABB RobotStudio and UR PolyScope. Which one targets engineering design offices, and which one targets factory-floor operators?
  2. A manufacturing cell uses a laser scanner to detect humans. Outline how you would set up Normal Mode and Reduced Mode in PolyScope to balance worker safety and productivity.
  3. Why is virtual commissioning especially valuable when integrating a robot with a third-party programmable logic controller (PLC)? What failures does it catch before physical power-on?
