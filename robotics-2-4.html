2.4 Intro to ROS (Vendor-Agnostic)

Gerald Lê

01. The fragmentation of industrial robotics

In lesson 2.3, we saw that every industrial robot manufacturer maintains its own proprietary programming language and controller architecture. A motion program written in ABB RAPID cannot run on a KUKA or FANUC arm. A technician who spends five years mastering Universal Robots URScript cannot transfer those exact syntax rules to a Yaskawa Motoman cell.

This walled-garden approach creates engineering bottlenecks. Picture an automated cell with an ABB arm, a mobile robot from another company, a 3D depth camera, and a six-axis force sensor. Without a common software layer, the engineering team must write and maintain custom communication code to connect every pair of devices.

The same problem slows research. The original ROS paper observed that robot software projects often tangle drivers and algorithms that could be reused elsewhere with the project's own middleware, so a new algorithm for path planning, object detection, or simultaneous localization and mapping (SLAM) gets rewritten again and again for each platform.[1]

What the robotics community needed was a vendor-neutral layer: a common software platform that lets sensors, algorithms, and robots of any brand exchange data in the same way. That open-source layer is ROS, the Robot Operating System.[1]

02. What problem does ROS solve?

Despite its name, ROS is not an operating system like Linux or Windows. Its authors wrote that ROS “is not an operating system in the traditional sense of process management and scheduling”; instead, it provides a structured communications layer above the host operating system.[1] This kind of software is called middleware. For ROS 2, the main (Tier 1) host platform is Ubuntu Linux.[2]

What problem does ROS solve that vendor languages do not? It gives a common layer so skills and code carry over between robot brands.[1]

Under the ROS model, the physical robot hardware is hidden behind standard interfaces:[3]

  • Hardware Abstraction: ROS provides the sensor_msgs package, which defines common sensor message formats, so any vendor's sensor can be used as long as its driver publishes those standard messages. A planar lidar, for example, publishes sensor_msgs/msg/LaserScan messages, which navigation and mapping packages read directly.[3] In the other direction, the Nav2 controller publishes velocity commands as geometry_msgs Twist messages on the cmd_vel topic, and a driver for the particular robot base turns those commands into motor signals.[4]
  • Algorithm Reuse: Large community libraries, such as MoveIt 2 for robot arms and Nav2 for mobile robots, are built as collections of plugins that can be configured for many different robots, so an improvement to the library can benefit every robot that uses it.[5][6]
  • Toolchain Standardization: ROS is built from many small tools rather than one large program; from the start these included the 3D visualizer rviz.[1] Developers today share the same visualization tool (RViz2), data recording tool (ros2 bag, part of rosbag2), and Gazebo simulator across robot brands.[7][8]

03. The origins of ROS: Stanford and Willow Garage

ROS grew out of two groups. At Stanford University, the STAIR project, which Andrew Ng had started, and the Personal Robotics Program, run by Eric Berger and Keenan Wyrobek in Ken Salisbury's lab, were both trying to build capable robots on top of reusable software.[9][1] Wyrobek later described the problem they wanted to fix as a cycle of researchers “90 percent duplicating what someone else has already done”.[9]

The work continued at Willow Garage, a robotics research lab in Menlo Park, California, funded by Scott Hassan, who saw building the “Linux of robots” as a way of giving back; Steve Cousins served as its CEO.[9] The name “ROS” was first used publicly when Ken Conley set up the code repository on 7 November 2007.[9] Willow Garage also built the PR2 (Personal Robot 2), a hardware platform whose capabilities, in Berger's words, “way outstripped the current software,” and ROS was developed for its Personal Robots Program.[9][1]

In 2012, the non-profit Open Source Robotics Foundation (OSRF) was founded as one of Willow Garage's spin-offs, and it came to work under the name Open Robotics. In December 2022, Intrinsic (an Alphabet company) acquired Open Robotics' for-profit arm, the Open Source Robotics Corporation, while the OSRF kept stewardship of ROS, Gazebo, and Open-RMF.[10] In March 2024, the OSRF launched the Open Source Robotics Alliance (OSRA) to support the development and maintenance of ROS, Gazebo, and Open-RMF.[7]

04. The limits of ROS 1: the roscore bottleneck

ROS 1 was widely adopted in research labs. However, as people tried to use it in products, multi-robot teams, and factories, its design showed several limitations:[11]

  • A central master (roscore): In ROS 1, nodes connect to each other directly, but they find each other through a name service called the master (started by roscore), and connection set-up is negotiated over XML-RPC.[1] Every node therefore depends on that one master. The ROS 2 design team noted that multi-robot systems had no standard approach and were “somewhat of a hack on top of the single-master structure of ROS.”[11]
  • No direct real-time support: ROS 1 moved messages with its own TCPROS and UDPROS transports.[12] One goal of ROS 2 was to support real-time control directly in ROS, which ROS 1 did not do.[11]
  • Unreliable networks: ROS 2 set out to “behave as well as is possible when network connectivity degrades due to loss and/or delay,” a situation common for mobile robots on Wi-Fi.[11]
  • Security as an afterthought: As the SROS2 authors put it, ROS “was not designed initially with security in mind.”[13]

05. The ROS 2 revolution: DDS and decentralization

The changes needed were too intrusive, and too risky for the many people relying on ROS 1, to make inside the existing system. So the community built ROS 2 as a new, parallel set of packages that can talk to ROS 1 through bridges.[11]

The defining decision of ROS 2 was to build its communication on an existing industry standard: the Data Distribution Service (DDS) from the Object Management Group (OMG), whose current version is 1.4 (2015).[14][12]

DDS is a publish-subscribe standard with several vendor implementations and mission-critical deployments in defense, utilities, finance, space, and flight systems.[12] Adopting it addressed the main ROS 1 limitations:[12][13]

  • No central master: DDS discovery is distributed, so “any two DDS programs” can communicate without a tool like the ROS master. Data travels using the DDSI-RTPS wire protocol, by default over UDP, replacing TCPROS and UDPROS.[12]
  • Configurable Quality of Service (QoS): DDS QoS settings control reliability and latency per data stream, from behavior close to raw UDP (good for soft real-time data) to TCP-like reliable delivery.[12] In ROS 2 terms, a high-bandwidth camera or lidar stream can use “best effort” delivery and simply drop late data, while a command that must arrive uses “reliable” delivery.
  • Real-time capable: The DDS wire specification supports real-time applications, including on embedded devices, which fits the ROS 2 goal of supporting real-time control directly.[12][11]
  • Security (SROS 2): DDS-Security gives each participant an identity from a public key infrastructure with mutual authentication, encrypts traffic (AES-GCM), and enforces access-control policies. SROS 2 is the set of ROS 2 tools that creates the certificates, keystores, and permission files needed to switch this on.[13]

06. Target releases and the LTS lifecycle: Lyrical Luth

New ROS 2 releases are published on a time-based schedule every 12 months. In even years, the release comes one month after the new Ubuntu LTS (long-term support) release and is itself an LTS release supported for five years; releases in odd years are supported for 1.5 years.[2]

Recent LTS releases include ROS 2 Humble Hawksbill (May 2022 to May 2027, on Ubuntu 22.04) and ROS 2 Jazzy Jalisco (May 2024 to May 2029, on Ubuntu 24.04).[2]

In this curriculum, our target release is ROS 2 Lyrical Luth, the twelfth ROS 2 release, announced on 22 May 2026. It is an LTS release supported until May 2031, with Ubuntu 26.04 as its Tier 1 Linux platform.[8] Its release notes highlight a new events-based executor for C++ nodes, an AsyncNode that lets Python nodes use asyncio, zero-copy buffer support for moving large data to GPUs, and rosbag2 and command-line improvements.[8]

07. The four pillars of ROS

ROS is often described as four things at once: plumbing (message passing between nodes), tools (launch, introspection, debugging, visualization, plotting, logging, and playback), capabilities (ready-made software so you can focus on your application), and a community ecosystem.[15] The table gives ROS 2 examples of each:

Pillar Core Technical Function Primary Examples
1. Plumbing Inter-process communication and distributed messaging DDS middleware, Topics (publish/subscribe), Services (request/reply), and Actions (goal/feedback/result).[12][6]
2. Tools Visualization, inspection, debugging, and data logging rviz2 (3D visualization) and ros2 bag (recording and playback), plus launch and command-line introspection tools.[1][8]
3. Capabilities Reusable algorithm libraries Nav2 (mobile robot navigation), MoveIt 2 (arm kinematics and motion planning), and slam_toolbox (mapping).[6][5][3]
4. Ecosystem Open-source packages and a global community Community-maintained packages, shared standard message definitions, vendor-supported drivers, and the ROSCon conference.[15][3][10]

08. Community stacks: Nav2 and MoveIt 2

Much of the value of ROS lies in the community software stacks built on top of its plumbing. Building an autonomous mobile robot or a vision-guided manipulation cell from scratch requires a great deal of hard mathematics. With ROS 2, many of these capabilities are available as modular open-source libraries:

Navigation 2 (Nav2): Nav2 is the professionally supported successor of the original ROS Navigation Stack.[6] It uses a behavior tree to orchestrate its navigation tasks,[16] and its task servers load plugins for planners, controllers, and behaviors; the documentation covers planners such as NavFn and Smac and controllers such as DWB, MPPI, and Regulated Pure Pursuit.[6] Nav2 builds a model of the environment from sensor data and plans around obstacles in it.[6] Its developers tested it by having a robot navigate safely alongside students on a university campus over a marathon-length distance.[16]

MoveIt 2: MoveIt 2 is the main motion planning framework for robot arms in ROS 2.[5] It keeps a planning scene, a model of the world and the robot's current state. It uses FCL (the Flexible Collision Library) as its primary collision checker, a KDL numerical solver as its default inverse kinematics plugin, and OMPL (the Open Motion Planning Library) for its default planners, with the Pilz industrial motion planner and CHOMP also available.[5] Instead of coding every joint waypoint by hand, a programmer can ask MoveIt to move the tool to a target pose without hitting the table, and MoveIt plans a collision-free joint trajectory.[5]

09. ROS-Industrial: open source on the factory floor

Manufacturing companies need software with long-term support and robust interfaces to industrial hardware, which early ROS, built for research robots, did not focus on. ROS-Industrial (ROS-I) was created to fill that gap.[17]

ROS-Industrial began as a collaboration between Yaskawa Motoman, Southwest Research Institute (SwRI), and Willow Garage, and its code repository was started in January 2012 by Shaun Edwards at SwRI. The project focused on common interfaces for industrial robot arms, sensors, grippers, and automation equipment.[17]

To support long-term development, industry members formed regional consortia:[17]

  • ROS-Industrial Consortium Americas: Launched in March 2013 and led by Southwest Research Institute (SwRI).
  • ROS-Industrial Consortium Europe: Led by Fraunhofer IPA in Germany.
  • ROS-Industrial Consortium Asia Pacific: Led by the Advanced Remanufacturing and Technology Centre (ARTC) and Nanyang Technological University (NTU) in Singapore.

Beyond drivers and interfaces, ROS-Industrial supports advanced capabilities in perception, calibration, motion planning, and process automation for manufacturing tasks.[17]

10. Deep dive: Universal Robots ROS 2 driver

How does a vendor driver connect a ROS 2 computer to a proprietary robot controller? Universal Robots officially provides and supports drivers for ROS and ROS 2, which makes its Universal Robots ROS 2 Driver (Universal_Robots_ROS2_Driver) a good case study.[18] The driver is built on top of UR's Universal_Robots_Client_Library and works across the UR range, including robots with PolyScope X, PolyScope 5, or CB3 controllers.[19]

The driver runs on an external computer connected to the UR controller over the network. Its main parts are:[20]

  • Real-time communication: UR describes the driver's communication as real-time enabled with a 2 ms cycle time.[18]
  • ros2_control hardware interface: The hardware interface is implemented with the ros2_control framework. It does not decide how the robot moves by itself; standard controllers such as the JointTrajectoryController (used with MoveIt 2) or a force-mode controller do that, and the interface also exposes force-torque sensor data, speed scaling, and I/O.[20][18]
  • Factory calibration extraction: Every UR arm is calibrated individually at the factory. The separate ur_calibration tool extracts that calibration from the real robot and converts it for the ROS robot description (URDF). The documentation warns that without this step, end-effector positions in ROS might be off by centimeters.[20][19]
  • Dashboard client: A dashboard client talks to the robot's dashboard server and exposes ROS 2 services such as power_on, brake_release, load_program, play, and unlock_protective_stop, so a ROS program can start the robot and clear a protective stop (after its cause is fixed) without using the teach pendant.[20]

11. When to use ROS vs. proprietary vendor languages

Despite the power of ROS 2, it does not replace vendor languages like RAPID or PolyScope in every situation. The guidance below is this lesson's rule of thumb, drawn from the strengths and limits described above, rather than a formal standard:

Use proprietary vendor environments when:

  • Standalone repetitive cells: The application is a standalone, repetitive task (such as spot welding, machine tending, or palletizing) inside a fixed, guarded cell. The vendor's own language runs inside the controller's real-time loop and comes with the vendor's support.
  • Shop floor maintainability: The factory relies on maintenance technicians rather than software engineers. Technicians can jog arms and adjust taught points on the teach pendant without knowing Linux, Git, or C++.

Use ROS 2 when:

  • Multi-vendor integration: The cell combines equipment from several manufacturers, such as a robot arm mounted on a mobile base with a third-party camera.
  • Sensor-guided autonomy: The robot depends on 3D perception (depth cameras or lidars), dynamic obstacle avoidance, bin picking, or machine-learning inference.
  • Fleet and digital twin unification: Software must run the same way in a physics simulator such as Gazebo (a digital twin of the cell) and on a varied fleet of physical robots.
