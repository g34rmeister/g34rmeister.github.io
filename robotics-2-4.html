      2.4 Intro to ROS (Vendor-Agnostic)

      Gerald Lê
      Chapter 2, lesson 4 of 8 ← Previous: 2.3 Common Programming Languages Next: 2.5 End-of-Arm Tooling and I/O →
      Start here

      Vendor languages lock code to one robot brand. This lesson introduces ROS (Robot Operating System) as an open-source, vendor-neutral middleware layer that connects sensors, arms, and algorithms across brands—and explains when factory teams still choose proprietary vendor controllers instead.

      • You will learn how ROS 2 replaces ROS 1's single roscore bottleneck with decentralized DDS and Quality of Service settings.
      • You will learn the four pillars of ROS: plumbing (message passing), tools, capabilities such as Nav2 and MoveIt 2, and the ecosystem of community packages.
      • You will learn how ROS-Industrial and vendor drivers bring open-source software onto factory floors.

      01. Why robot brands do not speak the same language

      Imagine building a factory workcell with parts from different companies. You might pair an ABB robot arm with a mobile robot from another maker, a 3D depth camera, and a force sensor. Each brand uses its own software rules, so the machines cannot talk to one another out of the box. Sharing one common software layer saves teams from rewriting the same code over and over.

      In lesson 2.3, you saw that each industrial robot maker keeps its own programming language and controller design. A motion program written in ABB RAPID cannot run on a KUKA or FANUC arm. A technician who spends five years learning Universal Robots URScript cannot reuse those exact syntax rules on a Yaskawa Motoman cell.

      This brand lock-in creates bottlenecks on real projects. Think back to that mixed cell with an ABB arm, a mobile robot, a 3D depth camera, and a six-axis force sensor. Without a common software layer, your team must write and maintain custom communication code to connect every pair of devices.

      The same problem slows down robotics research. The original ROS paper noted that robot projects often tangle reusable drivers and algorithms with their own messaging code. Because of that, engineers rewrite algorithms for path planning, object detection, or simultaneous localization and mapping (SLAM) again and again for each robot.[1]

      The robotics community needed a vendor-neutral layer that works across brands. It needed one common software platform where sensors, algorithms, and robots of any brand exchange data the same way. That open-source layer is ROS, the Robot Operating System.[1]

      02. What problem does ROS solve?

      Think of ROS as a universal translator and toolkit for robot software. If you swap one brand of laser scanner for another, you should not have to rewrite your navigation code. ROS gives every part of your robot a standard way to share data, reuse proven programs, and share debugging tools.

      Even with “Operating System” in its name, ROS is not an operating system like Linux or Windows. In everyday words, it sits on top of your computer’s operating system and helps programs talk to one another. Its authors wrote that ROS “is not an operating system in the traditional sense of process management and scheduling”.[1] Instead, it provides a structured communications layer above the host operating system. Software that sits between the operating system and your applications is called middleware. For ROS 2, the main host platform is Ubuntu Linux.[2]

      Unlike a vendor language, ROS provides one common layer. That means your skills and code carry over between robot brands.[1]

      Under the ROS model, your program does not have to care about the exact wiring of one machine. Standard interfaces hide the physical robot hardware behind shared message types:[3]

      • Hardware Abstraction: Any maker’s sensor works with ROS as long as its driver publishes standard messages. For example, a flat laser scanner (planar lidar) publishes scan messages that navigation and mapping packages read directly.[3] In the other direction, the Navigation 2 (Nav2) controller sends velocity commands, and a driver for the robot base turns them into motor signals.[4]
      • Algorithm Reuse: Large community libraries work across many different machines. Examples include MoveIt 2 for robot arms and Nav2 for mobile robots. Both are built from configurable plugins, so an improvement to the library can benefit every robot that uses it.[5][6]
      • Toolchain Standardization: ROS is built from many small tools rather than one giant program.[1] Today, developers share the same 3D viewer (RViz2), data recorder (ros2 bag), and Gazebo simulator across robot brands.[7][8]
      For the curious: exact ROS message names, Tier 1 platform, and tool origins

      Ubuntu Linux is listed as the Tier 1 (main) host platform for ROS 2.[2]

      Standard sensor messages live in the sensor_msgs package, where a planar lidar publishes sensor_msgs/msg/LaserScan messages.[3] In the reverse direction, the Nav2 controller publishes velocity commands as geometry_msgs/msg/Twist messages on the cmd_vel topic.[4]

      From the start, ROS’s small-tools design included the 3D visualizer rviz.[1] Today’s ros2 bag recording tool is part of rosbag2.[8]

      03. How ROS got its start

      ROS started because early researchers were tired of rebuilding basic robot software from scratch. Before a lab could test a new idea, it often spent months writing motor drivers and camera tools. A small group of engineers decided to share one open toolkit so everyone could build on each other’s work.

      ROS grew out of two teams at Stanford University. Andrew Ng had started the STAIR project, while Eric Berger and Keenan Wyrobek ran the Personal Robotics Program in Ken Salisbury’s lab. Both groups wanted to build capable robots on top of reusable software.[9][1] In plain words, labs were wasting most of their effort solving the same starter problems. Wyrobek described it as researchers “90 percent duplicating what someone else has already done”.[9]

      The work continued at Willow Garage, a robotics research lab in Menlo Park, California. Scott Hassan funded it because he saw building the “Linux of robots” as a way of giving back, and Steve Cousins served as its chief executive officer (CEO).[9] Willow Garage also built the PR2 (Personal Robot 2). In Berger’s words, its hardware capabilities “way outstripped the current software,” so the team built ROS for its Personal Robots Program.[9][1]

      In 2012, a non-profit spin-off called the Open Source Robotics Foundation (OSRF) formed to guide the project, working under the name Open Robotics.[10] Later, the foundation launched the Open Source Robotics Alliance (OSRA) so companies and maintainers could support ROS, Gazebo, and Open-RMF together.[7]

      For the curious: key dates and Open Robotics governance history

      The name “ROS” was first used publicly when Ken Conley set up the code repository on 7 November 2007.[9]

      In December 2022, Intrinsic (an Alphabet company) acquired Open Robotics’ for-profit arm, the Open Source Robotics Corporation. Meanwhile, the non-profit OSRF kept stewardship of ROS, Gazebo, and Open-RMF.[10] In March 2024, the OSRF launched the Open Source Robotics Alliance (OSRA) to support their development and maintenance.[7]

      04. Why ROS 1 struggled in factories

      ROS 1 became a hit in university labs, where a few robots ran on a quiet local network. Moving onto real products and busy factory floors was much harder. If one central lookup program stopped, or if a warehouse robot lost Wi-Fi for a moment, the setup could stall. Those pain points showed engineers what needed fixing.

      As people tried to use ROS 1 in products, multi-robot teams, and factories, four design limits stood out:[11]

      • One central master (roscore): In ROS 1, separate programs (nodes) connect directly, but they find each other through one central name service called the master (started by roscore). Every node depends on that single master. In plain words, running multiple robots had no standard plan. The ROS 2 design team called it “somewhat of a hack on top of the single-master structure of ROS.”[11]
      • No direct real-time control: Factory arms need tight, predictable timing. ROS 1 moved messages with its own TCPROS and UDPROS transports,[12] and did not support real-time control directly. Adding direct real-time support became a core goal for ROS 2.[11]
      • Unreliable networks: Mobile robots on Wi-Fi often hit weak signals and dropped packets. ROS 2 set out to handle spotty connections cleanly. In the design team’s words, it needed to “behave as well as is possible when network connectivity degrades due to loss and/or delay.”[11]
      • Security as an afterthought: Early ROS assumed a trusted lab network. As the authors of SROS2 (the ROS 2 security tools) put it, ROS “was not designed initially with security in mind.”[13]
      For the curious: how ROS 1 nodes set up connections

      In ROS 1, once nodes look up each other’s addresses through the master started by roscore, their connection set-up is negotiated over XML-RPC.[1] After that handshake, messages travel over ROS 1’s custom TCPROS and UDPROS transports.[12]

      05. How ROS 2 fixes those limits with DDS

      Rather than patching an old foundation, the ROS community built a fresh version called ROS 2. Now, a camera program and a wheel controller can find each other directly on the network, with no central master in the middle. You can also tune each data stream separately, choosing speed for live camera frames and guaranteed delivery for stop commands.

      Changing ROS 1 from the inside was too risky for teams already relying on it. So the community built ROS 2 as a new, parallel set of packages. Existing ROS 1 programs can still talk to ROS 2 through software bridges.[11]

      Instead of inventing another custom messaging protocol, ROS 2 builds on an existing industry standard. That standard is the Data Distribution Service (DDS), maintained by the Object Management Group (OMG).[14][12]

      DDS is a publish-subscribe standard with several vendor implementations. It already powers mission-critical systems in defense, utilities, finance, space, and flight.[12] Adopting DDS solved the main limits of ROS 1:[12][13]

      • No central master: Discovery is spread across the network instead of sitting in one program. In plain words, there is no single bottleneck. The ROS 2 design notes state that “any two DDS programs” can communicate without a ROS master.[12]
      • Configurable Quality of Service (QoS): You can choose speed or reliability per data stream.[12] In ROS 2, a busy camera or lidar stream can use “best effort” delivery and drop late data. A motion command that must arrive uses “reliable” delivery.
      • Real-time capable: The DDS specification supports real-time applications, including on embedded boards. That matches ROS 2’s goal of supporting real-time control directly.[12][11]
      • Security (SROS 2): DDS-Security checks each node’s identity, encrypts traffic, and enforces access rules. SROS 2 is the set of ROS 2 tools that generates the security files needed to turn those protections on.[13]
      For the curious: DDS version, wire protocols, and SROS 2 cryptography

      The Object Management Group (OMG) DDS standard used here is version 1.4, published in 2015.[14]

      Under the hood, DDS sends data using the DDSI-RTPS wire protocol, by default over UDP, replacing ROS 1’s TCPROS and UDPROS transports. Its Quality of Service (QoS) settings span from behavior close to raw UDP (good for soft real-time data) to TCP-like reliable delivery.[12]

      For security, DDS-Security gives each participant an identity from a public key infrastructure with mutual authentication, encrypts traffic (AES-GCM), and enforces access-control policies. SROS 2 creates the certificates, keystores, and permission files needed to switch this on.[13]

      06. Which ROS 2 version this course uses: Lyrical Luth

      Just like Ubuntu or Python, ROS 2 puts out a new release every year. Picking the right version keeps your projects from breaking on expired software. In this course, we stick to one long-lasting release so every example works together smoothly.

      New ROS 2 releases follow a fixed 12-month schedule. In even years, a release comes one month after the new Ubuntu long-term support (LTS) release and gets five years of support. Odd-year releases are supported for 1.5 years.[2]

      Our target release in this curriculum is ROS 2 Lyrical Luth, announced on 22 May 2026. It is an LTS release supported until May 2031, with Ubuntu 26.04 as its main Linux platform.[8] If you work with older lab robots, you may also meet earlier LTS versions such as Humble Hawksbill and Jazzy Jalisco.[2]

      For the curious: past LTS dates and new features in Lyrical Luth

      Recent LTS releases include ROS 2 Humble Hawksbill (May 2022 to May 2027, on Ubuntu 22.04) and ROS 2 Jazzy Jalisco (May 2024 to May 2029, on Ubuntu 24.04).[2]

      ROS 2 Lyrical Luth is the twelfth ROS 2 release, with Ubuntu 26.04 as its Tier 1 Linux platform. Its release notes highlight a new events-based executor for C++ nodes, an AsyncNode that lets Python nodes use asyncio, zero-copy buffer support for moving large data to graphics processors (GPUs), and rosbag2 and command-line improvements.[8]

      07. The four pillars of ROS

      Beginners often wonder whether ROS is a messaging tool, a simulator, or a library of robot algorithms. The short answer is that it is all of those working together. Think of building a car: you need wiring, dashboard gauges, an engine, and a parts network.

      ROS is often described as four pillars at once: plumbing (message passing between nodes), tools (for launch, inspection, debugging, visualization, plotting, logging, and playback), capabilities (ready-made software so you can focus on your job), and a community ecosystem.[15] The table gives ROS 2 examples of each:

      Pillar Core Technical Function Primary Examples
      1. Plumbing Inter-process communication and distributed messaging DDS middleware, Topics (publish/subscribe), Services (request/reply), and Actions (goal/feedback/result).[12][6]
      2. Tools Visualization, inspection, debugging, and data logging rviz2 (3D visualization) and ros2 bag (recording and playback), plus launch and command-line introspection tools.[1][8]
      3. Capabilities Reusable algorithm libraries Nav2 (mobile robot navigation), MoveIt 2 (arm kinematics and motion planning), and slam_toolbox (mapping).[6][5][3]
      4. Ecosystem Open-source packages and a global community Community-maintained packages, shared standard message definitions, vendor-supported drivers, and the ROSCon conference.[15][3][10]

      08. Ready-made software for driving and robot arms

      Once your robot programs can talk to each other, you still need your machine to move smartly without crashing. Writing obstacle-avoidance or arm-steering math from scratch can take months. Instead, ROS 2 gives you modular open-source toolkits that handle path planning, collision checking, and inverse kinematics for you:

      Navigation 2 (Nav2): Nav2 helps mobile robots drive safely from one spot to another.[6] It builds a model of the room from sensor data and plans routes around obstacles.[6] Under the hood, it uses a behavior tree to coordinate its navigation tasks and lets you plug in different planners, controllers, and behaviors.[16][6] Its developers proved it by having a robot navigate safely alongside students on a university campus over a marathon-length distance.[16]

      MoveIt 2: MoveIt 2 is the main motion-planning framework for robot arms in ROS 2.[5] It tracks a planning scene, which is a model of the world and the robot’s current state. Instead of coding every joint waypoint by hand, you ask MoveIt 2 to move the tool to a target pose without hitting the table. MoveIt 2 then plans a collision-free path for the arm’s joints.[5]

      For the curious: Nav2 and MoveIt 2 planners, solvers, and libraries

      Nav2 is the professionally supported successor to the original ROS Navigation Stack. Its task servers load plugins for planners, controllers, and behaviors. The documentation covers planners such as NavFn and Smac, and controllers such as DWB, MPPI, and Regulated Pure Pursuit.[6]

      MoveIt 2 uses FCL (the Flexible Collision Library) as its primary collision checker, a KDL numerical solver as its default inverse kinematics plugin, and OMPL (the Open Motion Planning Library) for its default planners, with the Pilz industrial motion planner and CHOMP also available.[5]

      09. ROS-Industrial: open source on the factory floor

      Factory teams need software with long-term support and sturdy links to industrial hardware. Early ROS, built for research robots in university labs, did not focus on those needs. A dedicated project stepped in to adapt open-source tools for real manufacturing equipment.

      ROS-Industrial (ROS-I) was created to fill that factory gap.[17] It focuses on common interfaces for industrial robot arms, sensors, grippers, and automation equipment.[17] Regional industry groups now support its long-term development in the Americas, Europe, and Asia Pacific.[17] Beyond basic drivers and interfaces, ROS-Industrial also supports perception, calibration, motion planning, and process automation for manufacturing jobs.[17]

      For the curious: ROS-Industrial founding history and regional consortia

      ROS-Industrial began as a collaboration between Yaskawa Motoman, Southwest Research Institute (SwRI), and Willow Garage. Shaun Edwards started its code repository at SwRI in January 2012.[17]

      Industry members formed three regional consortia to support long-term development:[17]

      • ROS-Industrial Consortium Americas: Launched in March 2013 and led by Southwest Research Institute (SwRI).
      • ROS-Industrial Consortium Europe: Led by Fraunhofer IPA in Germany.
      • ROS-Industrial Consortium Asia Pacific: Led by the Advanced Remanufacturing and Technology Centre (ARTC) and Nanyang Technological University (NTU) in Singapore.

      10. Example: how a ROS 2 driver controls a factory arm

      How does a Linux computer running ROS 2 actually move a real factory robot arm? The arm still uses its own built-in controller box, so you need a bridge program called a driver. Looking at one official manufacturer driver shows how ROS 2 commands turn into safe, accurate arm motion.

      Universal Robots (UR) officially provides and supports drivers for ROS and ROS 2. Its Universal Robots ROS 2 Driver (Universal_Robots_ROS2_Driver) is a clear real-world case study.[18] It runs across the UR product range on an external computer connected to the UR controller over the network.[19][20] Its main parts are:[20]

      • Real-time communication: UR describes the driver’s communication as real-time enabled with a 2 ms cycle time.[18]
      • Standard hardware interface (ros2_control): This layer connects the arm to standard ROS 2 motion controllers, such as the ones used with MoveIt 2. It also exposes force-torque sensor data, speed scaling, and inputs and outputs (I/O).[20][18]
      • Factory calibration extraction (ur_calibration): Every UR arm is calibrated individually at the factory. This separate tool pulls that calibration from the real robot into the ROS robot description (URDF). Without this step, end-effector positions in ROS might be off by centimeters.[20][19]
      • Dashboard client: This tool lets a ROS 2 program power on the arm, release brakes, load or start programs, and clear a protective stop (after its cause is fixed) without using the teach pendant.[20]
      For the curious: supported UR controllers, client library, and exact ROS 2 names

      The Universal_Robots_ROS2_Driver is built on top of UR’s Universal_Robots_Client_Library and works with PolyScope X, PolyScope 5, or CB3 controllers.[19]

      Inside the ros2_control framework, the hardware interface does not decide how the robot moves on its own. Standard controllers such as the JointTrajectoryController (used with MoveIt 2) or a force-mode controller do that.[20][18]

      The dashboard client talks to the robot’s dashboard server and exposes ROS 2 services such as power_on, brake_release, load_program, play, and unlock_protective_stop.[20]

      11. Should you use ROS 2 or a vendor language?

      After seeing everything ROS 2 can do, it is tempting to use it for every robot project. On a real factory floor, though, simpler vendor tools are often the smarter pick. The right choice depends on what your robot does and who will maintain it.

      ROS 2 does not replace vendor languages like RAPID or PolyScope in every situation. The guidance below is this lesson’s rule of thumb, drawn from the strengths and limits above, rather than a formal standard:

      Use proprietary vendor environments when:

      • Standalone repetitive cells: Pick a vendor tool for repetitive tasks (like spot welding, machine tending, or palletizing) inside a fixed, guarded cell. The vendor’s language runs inside the controller’s real-time loop and comes with vendor support.
      • Shop floor maintainability: Pick a vendor tool when maintenance technicians run the line instead of software engineers. Technicians can jog arms and adjust taught points on the teach pendant without knowing Linux, Git, or C++.

      Use ROS 2 when:

      • Multi-vendor integration: Pick ROS 2 when your cell combines gear from several brands, such as a robot arm mounted on a mobile base with a third-party camera.
      • Sensor-guided autonomy: Pick ROS 2 when the robot depends on 3D perception (depth cameras or lidars), dynamic obstacle avoidance, bin picking, or machine-learning inference.
      • Fleet and digital twin unification: Pick ROS 2 when software must run the same way in a physics simulator like Gazebo (a digital twin of the cell) and on a varied fleet of physical robots.
