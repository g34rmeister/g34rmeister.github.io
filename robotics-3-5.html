3.5 Case Study: Contributing to Nav2

Gerald Lê

01. What Nav2 is

Nav2 is the navigation project for mobile robots in ROS 2. The project works to make autonomous navigation accessible to everyone in robotics.[1] Alongside MoveIt, Nav2 serves as a flagship application framework for the ROS ecosystem.[1]

Before ROS 2, mobile robots relied on the ROS 1 Navigation Stack.[1] Nav2 redesigns that earlier system to be more flexible, incorporating a decade of community experience and feedback.[1] Like all open-source projects, Nav2 thrives through the collective effort of developers, maintainers, users, and collaborators.[1]

Open Navigation LLC provides professional stewardship, leading project maintenance, development, and support services across the Nav2 and ROS community.[2]

02. How a mobile robot navigates

Nav2 relies on ROS 2 middleware for communication and lifecycle management.[3] Before exploring code, newcomers should understand how coordinates, maps, and algorithms interact to steer a robot.

Autonomous movement requires tracking coordinate frames. Standards call for two primary transformations: global positioning links map to odom, while odometry calculates odom to base_link.[4] Nav2 manages these changing relationships using TF2, ROS 2's time-variant transform library.[4]

Global positioning estimates robot coordinates on a map. Nav2 includes amcl, which implements Adaptive Monte-Carlo Localization via particle filtering.[4] For mapping while driving, Nav2 supplies SLAM Toolbox as the default algorithm to position the vehicle and build static maps.[4]

Odometry establishes the local odom to base_link transformation.[4] Measurements can originate from wheel encoders, inertial measurement units (IMUs), visual-inertial odometry (VIO), radar, or lidar.[4] Odometry aims to create a smooth, continuous local frame that tracks vehicle motion.[4]

Robots perceive obstacles through an environmental representation, which Nav2 implements as a costmap.[5] In Nav2, a costmap is a regular two-dimensional cell grid, assigning values that represent unknown, free, occupied, or inflated obstacle regions.[5] Planners search this grid to compute a global plan, and controllers sample it to compute local control efforts.[5] Costmap layers, written as plugins, feed information into the costmap.[5]

Planning and control algorithms drive navigation tasks.[6] Nav2 groups algorithms into action servers, including the planner, controller, behavior, smoother, and route servers, each hosting swappable algorithm plugins.[6] The planner calculates a path to satisfy an objective function, usually a valid, and potentially optimal, path from the current pose to a goal pose.[6]

Controllers (local planners in ROS 1) compute control efforts to follow the global plan or execute local maneuvers.[6] Recovery behaviors make the system fault tolerant: they handle unknown or failure conditions on their own.[6]

Nav2 coordinates these planning, control, and recovery steps through behavior trees.[7] Behavior trees arrange tasks into a hierarchy, creating a scalable, human-understandable framework for multi-step applications.[7] This formal structure organizes navigation logic so it can be formally verified and validated as correct.[7] Inside the BT Navigator, custom node plugins assemble into complete trees.[7]

03. How the project is organised

Nav2 relies on a modular architecture divided into packages and plugin interfaces.[8] The project defines plugin interfaces for costmap layers, planners, controllers, behavior trees, and recovery behaviors so developers can insert custom navigation algorithms.[8]

Examples of existing plugins include voxel layers, DWB controllers and Smac planners.[8] Nav2 lists documented plugins in docs/configuration_and_development/navigation_plugins/index.md.[8] Anyone who designs or discovers an unlisted plugin is invited to submit a pull request adding it to that index.[8]

The project documentation lives in its own dedicated repository at docs.nav2.org.

04. Licensing and sign-off

Nav2 defines licensing rules across two documents: the repository LICENSE file and the CONTRIBUTING.md guide.

In the repository LICENSE, the project states: “Portions of this repository are available under one of the following licenses * Apache-2.0 * BSD-3-Clause * Apache-2.0 AND BSD-3-Clause.”[9] For modifications, it specifies: “Contributions to existing files should be made under the license of that file.”[9] Because several packages originated in ROS 1, each package carries its own license history. Modifications should follow the predominant license of that package, while entirely new packages belong under Apache 2.0.[10]

Meanwhile, the repository CONTRIBUTING.md file states: “Any contribution that you make to this repository will be under the Apache 2 License, as dictated by that license”.[11]

Contributors must also certify code origin through the Developer Certificate of Origin (DCO).[11] Developers certify they have the right to submit code by adding a Signed-off-by line to each commit message.[11] Running git commit -s -m "..." automatically appends this sign-off line, confirming agreement with the DCO.[10]

05. How to get involved

Nav2 welcomes developers to engage through its community platforms. All ROS 2 Technical Steering Committee working group meetings are published on the ROS working group calendar, where contributors can check scheduled dates and times for Nav2 working group sessions.[10] The project also hosts a Community Slack where contributors discuss topics in public channels or send direct messages to maintainers.[10]

Nav2 structures contributions through a three-step workflow. First, open an issue ticket for any defect or enhancement; fixing it immediately is optional, as reporting bugs is already valuable.[10] Second, claim an issue by commenting on the ticket, ideally providing an implementation strategy and timeline so others can coordinate.[10] Third, submit a pull request with the PR template completed.[10] Submissions undergo review by one to two reviewers. While a single maintainer can merge trivial fixes, substantial changes require approval from at least one maintainer and one other community member.[10]

06. A first contribution path

Lessons 3.2 and 3.4 introduced GitHub workflows for branching, making commits, and opening pull requests. Those mechanics apply directly to Nav2.

If your changes mean that documentation must be updated, the contribution rules say that update belongs in the same pull request.[10] For learners not yet writing C++ navigation code, reporting bugs is explicitly recognized as a valuable contribution.[10]

Another accessible path is expanding the navigation plugins list. The plugin catalog is stored at docs/configuration_and_development/navigation_plugins/index.md in the documentation repository.[8] If you develop a new plugin or find one built by the community, the project invites a pull request that adds it to the list.[8]
