3.5 ROS Tools

Gerald Lê

01. The ROS developer toolchain

Writing code for robots presents debugging challenges that do not exist in conventional web or desktop development. A mobile robot or articulated arm combines asynchronous processes, mechanical dynamics, multi-sensor telemetry, and complex 3D coordinate frame transformations. If a robot begins driving in the wrong direction or fails to detect a doorway, looking at raw terminal text logs is rarely sufficient to understand why.

To make complex robotic systems transparent and debuggable, the ROS ecosystem provides a specialized suite of developer utilities:[1]

  • RViz2: A 3D visualizer that displays what the robot "sees" and "thinks" by rendering live topic streams in space.[1]
  • rqt & rqt_graph: A modular graphical user interface framework for introspecting active computational graphs and monitoring signals.[2]
  • ros2 bag: A high-throughput telemetry recorder that saves message streams to disk for offline playback and algorithm verification.[3]
  • Gazebo: A 3D multi-physics simulator that models rigid-body dynamics, friction, lighting, and synthetic sensors in virtual worlds.[4]

02. RViz2: visualizing robot perception in 3D

RViz2 (ROS Visualization 2) is the primary 3D visualization tool in the ROS 2 ecosystem.[1] What is the difference between RViz and Gazebo? RViz displays data already flowing through ROS; Gazebo simulates the robot and its world with physics.[1][4]

RViz2 simulates nothing. It has no physics engine, no gravity, and no collision dynamics. Instead, RViz2 acts as an interactive 3D rendering canvas. It listens to active ROS 2 topics and displays sensor telemetry, planned navigation paths, costmaps, and robot geometric models directly in 3D space:[1]

  • RobotModel Display: Parses the robot's Unified Robot Description Format (URDF) XML model and renders the 3D visual mesh files (such as STL or Collada files) of every link, animated in real time using joint positions from /joint_states.
  • LaserScan & PointCloud2 Displays: Renders 2D planar lidar sweeps and 3D RGB-D depth camera point clouds. Points can be colored dynamically by height, distance, or laser reflection intensity.
  • Map & Costmap Displays: Visualizes 2D occupancy grids produced by SLAM or navigation algorithms, displaying free space as light gray, occupied obstacles as black, and safety inflation margins as colored gradients.
  • Interactive Markers: Lets human operators drag 3D directional arrows inside the viewport to set target navigation destinations or position a robotic gripper in Cartesian space.

To launch RViz2 from your terminal, run: 

ros2 run rviz2 rviz2

03. The tf2 transform library and the Fixed Frame

To render multiple sensors in the same 3D viewport, RViz2 relies on tf2, the spatial transform library of ROS.[5]

On a real robot, sensors are mounted at different physical locations. The front lidar might sit 30 cm forward and 15 cm above the robot's wheel center, while a depth camera is mounted on a tilting mast. When the lidar reports an obstacle at distance (x = 1.2 m, y = 0.5 m) in its own sensor coordinates, navigation algorithms must know where that obstacle is located relative to the map or the robot's base.

tf2 maintains a spatial relationship tree over time.[5] At the top left of the RViz2 interface sits the Fixed Frame dropdown. The Fixed Frame represents the static reference anchor (typically map or odom) against which all other coordinates are rendered. If tf2 cannot calculate a mathematical transform between a sensor's frame and the selected Fixed Frame, RViz2 displays a red warning and refuses to render the data.

04. rqt and rqt_graph: computational graph inspection

rqt is a modular, Qt-based graphical user interface framework that hosts dozens of debugging plugins inside a single customizable dashboard.[2]

The most widely used plugin is rqt_graph.[2] rqt_graph queries active DDS discovery traffic on the network to generate an interactive, real-time directed graph illustrating every active node and topic connection.

Launch it directly from the terminal while Turtlesim is running:[2] 

ros2 run rqt_graph rqt_graph

In the diagram above, rqt_graph renders running nodes as ovals (/teleop_turtle and /turtlesim) and active topics as rectangular boxes (/turtle1/cmd_vel). Directed arrows indicate the flow of published messages. If a newly developed sensor driver is failing to talk to your path planner, opening rqt_graph immediately reveals whether the topic name matches or if a typo isolated the node.

05. Specialized rqt plugins

Beyond graph inspection, the rqt suite provides several powerful specialized tools:[2]

  • rqt_plot: A 2D oscilloscope utility. You type in a topic name and field (such as /turtle1/pose/x or /motor/current), and rqt_plot generates a real-time scrolling strip-chart graph of the numerical values over time. It is invaluable for tuning motor PID controllers and observing sensor noise.
  • rqt_console: A centralized log viewer that subscribes to the /rosout system topic. It aggregates log messages across every running node, allowing engineers to filter messages by severity level (DEBUG, INFO, WARN, ERROR, FATAL) and search by node name or keyword.
  • rqt_service_caller: A graphical tool that queries all advertised services and generates input form fields matching the service request structure, letting you test hardware actions with custom numbers via click.

06. ros2 bag: telemetry recording and playback

In experimental robotics, physical field tests are expensive and difficult to reproduce. If an autonomous rover encounters an edge-case navigation failure while mapping an outdoor quarry, an engineer cannot easily re-stage the exact physical event to debug code back at the laboratory bench.

The solution is ros2 bag.[3] Which tool records messages on chosen topics so you can replay them later without the robot? The answer is ros2 bag.[3]

ros2 bag intercepts serialized DDS messages directly from the network transport and writes them losslessly to disk along with high-precision nanosecond timestamps.[3]

With Turtlesim running, you can record a telemetry session: 

ros2 bag record -o my_turtle_session --topics /turtle1/cmd_vel /turtle1/pose

While recording, drive the turtle around with the keyboard teleop for twenty seconds, then press Ctrl+C. ros2 bag creates a folder named my_turtle_session containing metadata and serialized data files.

To inspect the recorded dataset, query its metadata:[3] 

ros2 bag info my_turtle_session

The terminal prints the recording duration, start and end timestamps, total message count, serialization format, and a list of recorded topics with their exact message types and sample frequencies.

Now, reset the simulator: 

ros2 service call /reset std_srvs/srv/Empty "{}"

The turtle jumps back to the center of the screen. Now replay your recorded bag file:[3] 

ros2 bag play my_turtle_session

The ros2 bag play process begins publishing the recorded messages back onto /turtle1/cmd_vel with the exact microsecond timing of the original run. The turtle moves autonomously across the screen, retracing its previous path perfectly.

07. Storage backends: sqlite3 and MCAP

In early ROS 2 releases, ros2 bag stored data inside SQLite databases (.db3 files). While SQLite is universal, its write throughput and file locking mechanisms struggled to keep up with modern multi-gigabyte robotics data streams, such as high-frequency 4K stereo vision and 128-beam 3D lidars.

Modern ROS 2 distributions (including Jazzy and Lyrical) support the MCAP storage container format as a primary backend.[6] MCAP (developed by Foxglove) is a modern, modular container format engineered specifically for robotics telemetry:[6]

  • Zero-Copy Streaming: MCAP structures data sequentially, allowing logging nodes to stream sensor frames to NVMe drives at memory bus speeds without database transaction locks.
  • Built-in Indexing: High-speed chunk indexing lets visualization tools jump to any point in an 80 GB recording instantly without scanning through the entire file.
  • Self-Describing Schemas: Message definition schemas are embedded directly inside the MCAP file header, ensuring the data can still be decoded years later even if message definitions change.

08. Gazebo: multi-physics simulation

While RViz2 visualizes data, Gazebo creates the virtual reality where robots live.[4]

Gazebo is an open-source, multi-robot 3D physics simulator. It incorporates advanced physics engines (including ODE, Bullet, DART, and Simbody) to calculate rigid-body dynamics, joint constraints, friction, mass inertia, and surface contact forces.[4] In Gazebo:

  • A four-wheeled mobile robot sliding on wet concrete experiences realistic wheel slip governed by friction coefficients.
  • A six-axis articulated arm lifting a heavy payload deflects slightly due to gravitational torques.
  • Simulated sensors (lidars, depth cameras, IMUs, ultrasonic sensors) produce synthetic measurements with realistic Gaussian noise and optical occlusions.

An important historical milestone occurred on January 31, 2025, when the older simulator, Gazebo Classic (versions 1 through 11), officially reached End-of-Life (EOL).[7] All modern robotics engineering has transitioned to modern Gazebo (formerly known as Ignition Gazebo). Modern Gazebo releases are synchronized with ROS 2 LTS distributions: ROS 2 Jazzy is paired with Gazebo Harmonic, and ROS 2 Lyrical Luth is paired with Gazebo Jetty.[4][7]

09. Bridging worlds: the ros_gz architecture

Gazebo does not use DDS internally. Instead, Gazebo operates its own lightweight, inter-process transport protocol optimized for fast simulation stepping.

To connect Gazebo to ROS 2, developers use the ros_gz bridge suite.[8] The bridge node acts as an automated protocol translator: 

ros2 run ros_gz_bridge parameter_bridge /scan@sensor_msgs/msg/LaserScan[gz.msgs.LaserScan

When the simulated lidar sensor in Gazebo casts rays in its virtual 3D world, it publishes a gz.msgs.LaserScan packet. The bridge receives this packet, converts it into a standard ROS sensor_msgs/msg/LaserScan, and republishes it across DDS. The autonomous navigation stack (Nav2) subscribes to /scan, completely unaware that the laser points originate from simulated software rays rather than a physical glass sensor.

10. Essential community packages

Modern robotics engineering rarely builds foundational autonomy algorithms from scratch. Instead, engineers combine well-tested community packages:[9][10][11]

Package Domain Primary Capability
Nav2 Mobile Navigation Behavior-tree path planning, dynamic costmap inflation, obstacle avoidance, and recovery behaviors.
MoveIt 2 Arm Manipulation 3D inverse kinematics, collision checking with environment meshes, and trajectory planning for multi-axis arms.
slam_toolbox Mapping & Localization 2D laser-based Simultaneous Localization and Mapping, graph optimization, and map serialization.
ros2_control Hardware Abstraction Real-time motor drive interfaces, transmission modeling, and closed-loop trajectory controllers.

Together, RViz2, rqt, ros2 bag, Gazebo, and these community packages provide an end-to-end engineering workbench, empowering a single developer to build systems that once required fifty-person corporate teams.

Try it
  1. Launch Turtlesim and keyboard teleop, then open rqt_graph. Experiment with the graph filters: check "Hide Debug" and note which topics disappear.
  2. Record a 15-second bag file while teleoperating the turtle in a figure-eight pattern. Inspect the resulting dataset with ros2 bag info and verify message frequency on /turtle1/pose.
  3. Explain in your own words why an engineer testing an autonomous driving algorithm prefers testing against a recorded ros2 bag file before testing on real hardware on public roads.
