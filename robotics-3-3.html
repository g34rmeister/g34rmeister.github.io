3.3 How Robotics Projects Work

Gerald Lê

01. ROS 2 distributions and release branches

In 2.4 Intro to ROS (Vendor-Agnostic), we were introduced to ROS. The ROS chapter (Chapter 4) comes right after this one; 4.1 Definition and Introduction defines what ROS is. Because robots interact with physical machinery in factory and lab environments, unexpected software changes can cause physical damage or cell downtime. The open-source robotics ecosystem uses structured branching policies to maintain stability.

In ROS, software is released in named distributions. A distribution is a versioned collection of ROS packages released together. In ROS 2, packages maintain separate branches in their source repository for each ROS distribution they target, named after that distribution.[1] Maintaining distribution-specific branches allows developers to install and target a specific ROS release without receiving untested code from newer versions.

Once a distribution is published, its interfaces remain fixed. Major version increments and breaking API changes are prohibited within an already released ROS distribution.[1] An Application Programming Interface (API) is the contract of functions, classes, and message definitions that other programs use to communicate with a library. A breaking API change alters these interfaces and causes existing user code to fail to build or run. Prohibiting breaking changes ensures that a running robot system does not fail after updating packages.

Active development continues on a separate branch. In ROS 2 development, features or fixes must be accepted and merged into the rolling branch before opening a pull request to backport them to older releases.[1] The rolling branch is the unreleased, continuously updated version of ROS 2 where new capabilities land first. Backporting means copying a fix or non-breaking feature that was already merged into the rolling branch back into an older, supported distribution branch. This rule guarantees that improvements are validated in current development before being backported.

02. Package quality categories and the build farm

Robotics software must maintain high standards because programming faults can cause physical damage. To set clear expectations, ROS 2 packages ascribe to quality categories defined in REP 2004, which sets differentiated standards for versioning, testing, and documentation.[1]

A ROS Enhancement Proposal (REP) is a design document describing community processes, standards, and conventions. REP 2004 classifies packages into quality levels based on test coverage, documentation completeness, and interface policies.

Testing across different operating systems and hardware platforms requires continuous integration (CI). The ROS 2 build farm at ci.ros2.org runs nightly jobs that build code and execute automated tests across platforms and architectures.[1] A build farm is a network of automated servers that compile code, execute tests, and create binary packages. Nightly testing catches regressions before changes reach users.

03. ROS 2 pull request requirements

Submitting changes to ROS 2 requires opening a pull request (PR), which is a proposal to merge code from a contributor branch into upstream. To establish clean licensing, ROS 2 enforces the Developer Certificate of Origin on ROSCore pull requests, requiring every commit message to include a Signed-off-by line.[1] The Developer Certificate of Origin (DCO) is a declaration that the contributor wrote the code or has legal authority to submit it under an open-source license.

For small edits, this administrative requirement is lifted. DCO sign-off in ROS 2 is not required for pull requests that only perform trivial changes such as whitespace removal or typo corrections.[1] Contributors can fix obvious documentation typos without setting up commit sign-offs.

Every non-trivial submission must be verified. In ROS 2, merging a pull request requires a minimum of one approval from a developer who did not author the contribution.[1] Peer review ensures that an independent engineer checks code logic, test results, and documentation.

Once a ROS 2 pull request is approved, it is typically merged using Squash and Merge to keep a clean history, and the branch is deleted.[1] Squash and merge combines all commits from a pull request into a single commit on the main branch. This keeps the project history readable and removes temporary checkpoint commits.

04. MoveIt 2: branches, chunked PRs, and community feedback

MoveIt 2 is the primary manipulation and motion planning framework in ROS 2, introduced in 4.8 Moving an Arm with MoveIt 2. MoveIt 2 balances research innovation against production arm reliability.

MoveIt 2 uses the main branch for active development allowing breaking changes, while stable branches like humble and jazzy only accept bug fix backports.[2] Developers building production systems can rely on stable branches like humble or jazzy, while developers working on new algorithms contribute to main.

Because motion planning pipelines are complex, large pull requests are difficult to review. MoveIt asks contributors to submit pull requests in small digestible chunks rather than thousands of lines of code to maintain stability and review quality.[3] Small PRs allow maintainers to review logic thoroughly and merge fixes promptly.

Before writing code for major changes, contributors should discuss their ideas with the community. If unsure about a proposed feature, MoveIt contributors are encouraged to open an issue or post on Discourse first to request community feedback.[3] Discourse is an online forum used for ROS community discussions. MoveIt also encourages contributions beyond code, such as enhancing documentation, answering user questions, and reviewing open pull requests.[3]

05. ros2_control: approvals and review hygiene

The ros2_control framework provides real-time hardware interfaces and controller loops, which 8.5 From the Plant Floor to IT introduces. Because controller code directly commands physical motors, review rules are strict.

Pull requests in ros2_control must be explicitly approved by two maintainers before merging, with an exception for maintainer PRs needing one approval.[4] Two independent maintainer reviews ensure that safety-critical control loops are examined thoroughly.

Maintainer time is limited, so community participation is welcomed. The ros2_control project encourages non-maintainers to review pull requests to increase review pace, improve code quality, and spot overlooked limitations.[4] Anyone can review PRs, test branches locally, and point out edge cases.

To keep the review process smooth, contributors must follow Git review rules. In ros2_control, contributors must not force-push after a PR has been reviewed because force-pushing breaks the GitHub review UI.[4] A force-push rewrites commit history on the branch. This wipes out GitHub's inter-commit diff views, forcing reviewers to re-read everything from scratch.

Pull requests to ros2_control should maintain a limited scope that accomplishes one thing, placing unrelated fixes into separate PRs.[4] Contributions submitted to ros2_control are licensed under the Apache 2 License according to Section 5 of that license.[4] The ros2_control project maintains a dedicated Contributing Board project board to help newcomers find issues suitable for first contributions.[4]

06. Gazebo and Nav2: governance and project leadership

Simulation and mobile robot navigation are two other major areas of open-source robotics. Gazebo simulates multi-robot physics and sensors, while Nav2 is the navigation framework for mobile robots.

In Gazebo, pull requests must clear explicit quality checks. Gazebo pull requests can be merged once they have at least one approval from the core team, zero unresolved comments, passing CI, and a passing DCO check.[5]

To satisfy DCO sign-offs easily, developers use standard Git options. In Gazebo, developers can satisfy the DCO requirement by running git commit -s to automatically append their signature to commit messages.[5] The -s option appends a Signed-off-by: line with the author's configured Git name and email.

To guide new contributors, Gazebo maintainers triage project issues and apply the help wanted label to issues that the team thinks should be tackled by the community.[5] Everyone participating in Gazebo is governed by the Gazebo Code of Conduct, with unacceptable behavior reported through Gazebo support.[5]

Nav2 demonstrates how dedicated stewardship manages open-source infrastructure. Open Navigation LLC provides project leadership, maintenance, development, and support services for the Nav2 robotics navigation framework.[6] This leadership model provides continuous engineering, bug triage, and long-term maintenance for autonomous navigation.
