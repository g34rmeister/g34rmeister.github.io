2.3 Common Programming Languages

Gerald Lê

01. Why proprietary vendor languages persist

When software engineers first encounter industrial robotics, their immediate question is almost always: why does every robot manufacturer invent its own programming language? In web, cloud, and embedded systems, developers converge around universal languages like Python, C++, Rust, and Java. In the industrial robot sector, however, ABB robots are programmed in RAPID, KUKA arms in KRL, Universal Robots in URScript, and FANUC arms in TP or KAREL.[1][2][3][4]

The reason stems from real-time determinism and mechanical safety. An industrial robot controller is not a desktop operating system running user-space processes. It is a certified hard real-time motion system that evaluates inverse kinematics, gravity compensation, acceleration profiles, and emergency stop circuits every single millisecond.[1]

Proprietary vendor languages were designed specifically around the physics of spatial manipulators. Their fundamental primitives are not strings or integers, but Cartesian poses, tool center point (TCP) frames, velocity profiles, and corner blending zones. While graphical interfaces like PolyScope or RobotStudio handle routine setups, text-based vendor languages expose the raw, unconstrained power of the robot controller.[1][2]

02. ABB RAPID: architecture and routines

RAPID is ABB's strongly typed, multitasking procedural language, introduced in the mid-1990s with the S4 controller and refined through the IRC5 and current OmniCore platforms.[1] It is an imperative language with syntax reminiscent of Ada and Pascal.

A RAPID program is structured in a clear execution hierarchy:[1]

  • Tasks: Independent threads of execution. A controller can execute a motion task controlling physical arm joints alongside several non-motion background tasks handling sensor communications or safety monitoring.
  • Modules: Within each task, code and data are organized into modules (declared with MODULE ... ENDMODULE). System modules store permanent tool definitions and cell coordinate frames, while program modules hold user logic.
  • Routines: Executable blocks within modules. RAPID recognizes three distinct routine types:
    • Procedures (PROC): Execute a sequence of instructions without returning a value (e.g., PROC main() ... ENDPROC).
    • Functions (FUNC): Compute and return a typed value, such as a calculated Cartesian distance or mathematical transformation.
    • Trap Routines (TRAP): Asynchronous interrupt handlers. When a digital input fires (such as a part-drop optical sensor), the controller pauses main execution and jumps immediately to the assigned TRAP routine.

03. RAPID data types: robtarget, speed, and zones

To control spatial motion, RAPID relies on heavily structured composite data types:[1]

  • robtarget: Defines a full spatial destination: 
    [[500, 0, 600], [0, 0, 1, 0], [0, -1, 1, 0], [9E9, 9E9, 9E9, 9E9, 9E9, 9E9]]
    The first array contains X, Y, Z coordinates in millimeters. The second array defines orientation as a four-component unit quaternion [q1, q2, q3, q4]. Quaternions eliminate mathematical gimbal lock, which plagues Euler angle systems.[5] The third array defines axis configuration flags [cf1, cf4, cf6, cfx], which instruct the controller which quadrant each joint should assume, resolving the ambiguity where multiple distinct arm postures reach the exact same Cartesian coordinate.[1] The fourth array reserves positions for external auxiliary axes (such as linear track gantries or rotating positioner tables).
  • speeddata: Specifies the speed profile: [v_tcp, v_ori, v_leax, v_reax]. v_tcp defines the linear velocity of the tool center point in mm/s (e.g., v1000 or v200), while v_ori defines the tool reorientation velocity in degrees per second.
  • zonedata: Governs path corner blending: [finep, pebax, pex, pez, peori, peax]. If set to fine, the robot comes to a complete physical standstill at the waypoint before reading the next line. If set to a zone like z50, the controller blends the corner, allowing the tool to curve smoothly within a 50 mm radius sphere around the point, maintaining constant tool momentum and reducing cycle time.

04. Real-world RAPID program walkthrough

The following complete RAPID module demonstrates industrial pick-and-place logic, illustrating joint motion, linear motion, digital input validation, and zone blending:[1] 

MODULE PickAndPlaceModule
    ! Predefined Cartesian targets: position (mm), quaternion, config, external axes
    CONST robtarget pHome := [[600, 0, 750], [0, 0, 1, 0], [0, 0, 0, 0], [9E9, 9E9, 9E9, 9E9, 9E9, 9E9]];
    CONST robtarget pPick := [[450, 200, 120], [0, 0, 1, 0], [0, -1, 1, 0], [9E9, 9E9, 9E9, 9E9, 9E9, 9E9]];
    CONST robtarget pDrop := [[450, -200, 120], [0, 0, 1, 0], [0, 1, -1, 0], [9E9, 9E9, 9E9, 9E9, 9E9, 9E9]];

    ! Tool definition: mass 2.5 kg, TCP offset 150 mm along tool Z-axis
    PERS tooldata tGripper := [TRUE, [[0, 0, 150], [1, 0, 0, 0]], [2.5, [0, 0, 50], [1, 0, 0, 0], 0, 0, 0]];

    PROC main()
        ! Move to safe home position using joint interpolation at 1000 mm/s with 50 mm zone
        MoveJ pHome, v1000, z50, tGripper;

        ! Wait for conveyor part sensor (Digital Input 1) to go HIGH
        WaitDI diPartInPosition, 1;

        ! Approach 100 mm above pick point linearly, then descend
        MoveL Offs(pPick, 0, 0, 100), v500, z10, tGripper;
        MoveL pPick, v100, fine, tGripper;

        ! Actuate pneumatic gripper (Digital Output 1) and confirm grip switch
        SetDO doGripClose, 1;
        WaitTime 0.3;
        IF diGripConfirmed = 0 THEN
            ! If part missing, branch to fault recovery
            SetDO doAlarmLight, 1;
            Stop;
        ENDIF

        ! Retract vertically, transfer across cell, and lower to drop target
        MoveL Offs(pPick, 0, 0, 100), v300, z20, tGripper;
        MoveJ Offs(pDrop, 0, 0, 100), v800, z30, tGripper;
        MoveL pDrop, v100, fine, tGripper;

        ! Release gripper and return to home
        SetDO doGripClose, 0;
        WaitTime 0.2;
        MoveL Offs(pDrop, 0, 0, 100), v300, z10, tGripper;
        MoveJ pHome, v1000, fine, tGripper;
    ENDPROC
ENDMODULE

05. Universal Robots URScript: syntax and execution

Universal Robots chose an accessible design for its collaborative robot script language, URScript.[2] Rather than compiling to binary or requiring complex type declarations, URScript is an interpreted, Python-like language with dynamic variable typing and clean indentation syntax.

Programs execute in the controller's real-time URControl process. On the older CB-series robots, the motion cycle operates at 125 Hz (8 ms loop). On the modern e-Series and heavy-payload UR20 and UR30 cobots, the controller executes at 500 Hz (2 ms loop).[2] Every two milliseconds, the URScript engine computes forward kinematics, checks safety boundaries, and computes motor torques.

URScript supports native multi-threading. A developer can spawn lightweight background threads with the thread ... end block. A thread can continuously poll an analog laser distance sensor or watch an emergency stop relay while the main arm trajectory proceeds without pausing.[2]

06. URScript motion and rotation vectors

In URScript, spatial points are represented by the composite pose type, written with the prefix p:[2] 

p[x, y, z, rx, ry, rz]

Unlike RAPID, which records Cartesian position in millimeters, URScript adheres strictly to standard SI units: positions x, y, z are in meters. Furthermore, orientation is not specified by quaternions or Euler angles, but as a three-dimensional rotation vector (an axis-angle representation).[2]

In a rotation vector [rx, ry, rz], the directional unit vector defines the spatial axis around which the tool rotates. The total mathematical length (Euclidean norm) of the vector, \(\theta = \sqrt{rx^2 + ry^2 + rz^2}\), defines the rotation angle in radians. For example, a pure 180-degree rotation (\(\pi\) radians) around the tool's Y axis is represented compactly as p[0, 0, 0, 0, 3.14159, 0].

URScript defines three fundamental motion instructions:[2]

  • movej(q, a=1.4, v=1.05, t=0, r=0): Moves the robot in joint space to a list of target joint angles q (in radians) or to a pose. All joints accelerate and decelerate synchronously, reaching the target at the same time. The tool tip follows a curved arc through Cartesian space.
  • movel(pose, a=1.2, v=0.25, t=0, r=0): Moves the tool center point along a straight line in Cartesian space from its current position to the target pose. Joint motors vary their speeds dynamically to maintain linear tool travel.
  • movep(pose, a=1.2, v=0.25, r=0): Process move. Unlike movel, which varies speed near blended waypoints, movep maintains a constant linear velocity throughout blended paths, which is critical for dispensing adhesive beads, applying paint, or arc welding.

07. Real-world URScript program walkthrough

The following script demonstrates a complete URScript routine, showcasing pose manipulation, digital I/O control, sleep timers, and linear tool moves:[2] 

def pick_and_place_demo():
  # Define base positions (x, y, z in meters; rx, ry, rz in radians)
  p_home = p[0.400, 0.000, 0.500, 0.0, 3.14159, 0.0]
  p_pick = p[0.350, 0.250, 0.150, 0.0, 3.14159, 0.0]
  p_drop = p[0.350, -0.250, 0.150, 0.0, 3.14159, 0.0]

  # Move to home position in joint space (a = joint acceleration, v = joint velocity)
  movej(p_home, a=1.4, v=1.05)

  # Check part presence sensor on digital input 0
  if (get_digital_in(0) == True):
    # Approach 8 cm above pick point with 2 cm blend radius (r=0.02)
    p_approach = pose_add(p_pick, p[0, 0, 0.080, 0, 0, 0])
    movel(p_approach, a=0.8, v=0.4, r=0.02)

    # Descend to pick location in a straight line and stop exactly (r=0)
    movel(p_pick, a=0.4, v=0.1, r=0.0)

    # Trigger pneumatic gripper on digital output 0
    set_digital_out(0, True)
    sleep(0.3)

    # Lift vertically to clear fixture
    movel(p_approach, a=0.8, v=0.3, r=0.02)

    # Transfer linearly across cell to drop location
    p_drop_approach = pose_add(p_drop, p[0, 0, 0.080, 0, 0, 0])
    movel(p_drop_approach, a=0.8, v=0.5, r=0.02)
    movel(p_drop, a=0.4, v=0.1, r=0.0)

    # Open gripper and retract
    set_digital_out(0, False)
    sleep(0.2)
    movel(p_drop_approach, a=0.8, v=0.3)
  end

  # Return safely to home
  movej(p_home, a=1.4, v=1.05)
end

08. KUKA Robot Language (KRL)

KUKA Robot Language (KRL) is the proprietary language running on KUKA industrial controllers.[3] KRL is structured around Pascal-like syntax with strict compile-time type verification.

A unique architectural feature of KRL is its dual-file program structure.[3] Every KRL program consists of two separate files sharing the same name:

  • Source File (.src): Contains procedural execution code, logic loops, I/O instructions, and motion calls (such as PTP for point-to-point joint motion, LIN for linear motion, and CIRC for circular paths).
  • Data File (.dat): Contains persistent variables, tool definitions, coordinate frames, and target position coordinates. In KUKA controllers, when an operator touches up a point using the teach pendant, the numerical values in the .dat file are updated automatically without modifying the logic statements in the .src file.

KRL represents spatial targets as E6POS or FRAME structures. An E6POS defines Cartesian coordinates X, Y, Z (in mm), Z-Y-X Euler angles A, B, C (in degrees), external axis values E1 through E6, and two integer bitmasks: Status (S) and Turn (T). Status and Turn uniquely resolve robot arm configuration flags and joint wrap-around ambiguity.[3]

09. FANUC TP and KAREL

FANUC manipulators utilize two distinct programming languages operating at different system levels:[4]

  • Teach Pendant (TP) Language: The standard programming language used on the shop floor. TP is a tokenized, line-numbered language written and edited using menu-driven softkeys on the FANUC iPendant.[4] A typical motion instruction reads: 
    1: J P[1:Home] 100% FINE
2: L P[2:Pick] 500mm/sec CNT50
    Targets are stored in numbered Position Registers (PR[i]) or local Positions (P[i]). Because TP programs are tokenized rather than plain text, syntax errors cannot be typed into the pendant: every command is generated through guided menus.
  • KAREL: A compiled, high-level programming language named in honor of Karel Čapek.[4] Derived from Pascal, KAREL is used for complex algorithmic calculations, string parsing, TCP/IP socket communications, and vision guidance routines. Because KAREL runs as a background task, industrial best practice uses KAREL to handle data and communication while delegating actual robot arm motion to TP programs for safety compliance.[4]

10. RRL and historical standardization

Unlike URScript and RAPID, RRL is not a language you will find on today’s commercial robots. The only documented robot language by that name is RRL, “an integrated environment of robot programming” built at the Jožef Stefan Institute in Ljubljana, Slovenia, and published by Bojan Nemec, Anton Ružić and Vinko Ilc in 1992.[6] It was an academic research system designed to integrate sensor feedback and trajectory generation, but it was never adopted by commercial robot manufacturers.

The robotics community has long recognized the inefficiency of proprietary language fragmentation. In 1992, the German national standards body published DIN 66312: Industrial Robot Language (IRL).[7] DIN 66312 defined a standardized, high-level robot language intended to allow robot programs to execute across any vendor's arm.

While DIN 66312 influenced European controller architectures, major robot vendors declined to adopt IRL across their product lines. Proprietary controller languages allowed vendors to tightly integrate their specialized servo algorithms, protect intellectual property, and create customer lock-in. Real vendor-agnostic standardization did not gain traction until the development of open-source middleware like ROS, examined in lesson 2.4.
