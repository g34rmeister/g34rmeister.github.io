2.3 Common Programming Languages

Gerald Lê

01. Why proprietary vendor languages persist

When software engineers first encounter industrial robotics, their immediate question is almost always: why does every robot manufacturer invent its own programming language? In web, cloud, and embedded systems, developers converge around general-purpose languages like Python, C++, Rust, and Java. In the industrial robot sector, however, ABB robots are programmed in RAPID, Universal Robots arms in URScript, KUKA arms in KRL, and FANUC arms in TP (teach pendant) programs or KAREL.[1][2][3][4][5]

Part of the reason is timing. A robot controller is not a desktop computer running ordinary programs whenever it gets around to them. It runs a real-time motion system that must send fresh commands to the arm on a fixed, very short cycle. Universal Robots' e-Series manual, for example, states that the robot must be controlled at 500 Hz, which means the controller has to tell the arm what to do every 0.002 seconds, and that URScript programs are executed in real time in the controller's RuntimeMachine.[2] A vendor language lets the manufacturer run user programs inside that tightly controlled loop.

Vendor languages are also built around the physics of robot arms. Their basic building blocks are not just strings and integers but target positions, tool definitions, speeds, and corner-blending zones: a single RAPID motion instruction names its target, its speed, its zone, and its tool.[6] Graphical tools such as ABB's RobotStudio and UR's PolyScope sit on top of these languages: RobotStudio converts the targets you place in its 3D view into RAPID robtarget data when it synchronizes them to the controller, and PolyScope connects to the UR controller as a client.[7][2] Writing the language directly gives you access to everything the controller offers.

02. ABB RAPID: architecture and routines

RAPID is ABB's high-level robot programming language. It was introduced with ABB's S4 control system in the 1990s, replacing the earlier ARLA language,[8] and it is still the language of ABB's IRC5 controllers, documented in a reference manual of well over a thousand pages.[1] Its code is written in keyword blocks such as PROC ... ENDPROC and IF ... ENDIF, and every data item is declared with a type.[6]

A RAPID program is organized in a clear hierarchy:[7][6]

  • Tasks: A task is a robot program that can run on its own or alongside other programs on the same controller. This lets one task drive the arm while another handles background jobs such as communication.[7]
  • Modules: Within a task, code and data are organized into modules (declared with MODULE ... ENDMODULE). Program modules (.mod files) hold the user's logic and can be loaded and unloaded; system modules (.sys files) hold data and routines that should survive a program change, such as a calibrated tool definition. Only one program module may contain the main procedure.[6][7]
  • Routines: Executable blocks within modules. RAPID recognizes three routine types:[7]
    • Procedures (PROC): A set of instructions that does not return a value (e.g., PROC main() ... ENDPROC).[6]
    • Functions (FUNC): Routines that compute and return a value of a given type, such as a calculated distance.[7]
    • Trap routines (TRAP): Routines triggered by an interrupt. For example, an interrupt tied to a digital input (such as a part-drop sensor) can make the controller run a TRAP routine as soon as the signal changes.[7]

Data is declared as CONST (a constant that cannot change after it is declared), PERS (a persistent value that keeps its last assigned value even when the program is stopped and restarted), or VAR (a variable that is reset if the program pointer is moved back to main).[6]

03. RAPID data types: robtarget, speed, and zones

To control spatial motion, RAPID relies on structured composite data types:[6][9]

  • robtarget: Defines a full spatial destination with four parts, trans, rot, robconf and extax:[6] 
    [[500, 0, 600], [0, 0, 1, 0], [0, -1, 1, 0], [9E9, 9E9, 9E9, 9E9, 9E9, 9E9]]
    The first array is the X, Y, Z position. The second array is the tool orientation written as a four-component quaternion.[9] Quaternions avoid gimbal lock, a problem in which a three-angle (Euler angle) description loses one degree of rotational freedom at certain orientations.[10] The third array holds the axis configuration [cf1, cf4, cf6, cfx]: integers that give the quadrant of the arm's significant axes, so the controller knows which of several possible arm postures to use when more than one can reach the same point.[9][7] The fourth array holds up to six additional (external) axes, such as a linear track or a rotating positioner; unused axes are set to 9E9.[6]
  • speeddata: Specifies the speed with four values, [v_tcp, v_ori, v_leax, v_reax].[9] v_tcp is the speed of the tool center point; the predefined value v1000, for example, means 1000 mm/s, v100 means 100 mm/s, and vmax means the robot's maximum speed.[6] The other three values limit the speed of tool reorientation and of external axes; the reference manual gives their exact definitions.[1]
  • zonedata: Governs corner blending. Its fields are [finep, pzone_tcp, pzone_ori, pzone_eax, zone_ori, zone_leax, zone_reax].[9] If the zone is fine, the robot goes exactly to the programmed position before continuing. With a zone such as z50, the robot is allowed to cut the corner once its path is within 50 mm of the point, so it keeps moving smoothly and saves cycle time.[6]

04. Real-world RAPID program walkthrough

The following RAPID module is this lesson's own pick-and-place example. It uses only instructions and data types documented by ABB: MoveJ, MoveL, Offs, WaitDI, SetDO, WaitTime, Stop, and the robtarget and tooldata types.[6][1] The tooldata value follows ABB's layout: whether the robot holds the tool (robhold), the tool frame (tframe, a position and a quaternion), and the tool load (tload: mass, center of gravity, and inertia values).[9] The signal names (diPartInPosition and so on) are examples that would have to be configured on a real controller. 

MODULE PickAndPlaceModule
    ! Predefined Cartesian targets: position (mm), quaternion, config, external axes
    CONST robtarget pHome := [[600, 0, 750], [0, 0, 1, 0], [0, 0, 0, 0], [9E9, 9E9, 9E9, 9E9, 9E9, 9E9]];
    CONST robtarget pPick := [[450, 200, 120], [0, 0, 1, 0], [0, -1, 1, 0], [9E9, 9E9, 9E9, 9E9, 9E9, 9E9]];
    CONST robtarget pDrop := [[450, -200, 120], [0, 0, 1, 0], [0, 1, -1, 0], [9E9, 9E9, 9E9, 9E9, 9E9, 9E9]];

    ! Tool definition: mass 2.5 kg, TCP offset 150 mm along tool Z-axis
    PERS tooldata tGripper := [TRUE, [[0, 0, 150], [1, 0, 0, 0]], [2.5, [0, 0, 50], [1, 0, 0, 0], 0, 0, 0]];

    PROC main()
        ! Move to safe home position using joint interpolation at 1000 mm/s with 50 mm zone
        MoveJ pHome, v1000, z50, tGripper;

        ! Wait for conveyor part sensor (Digital Input 1) to go HIGH
        WaitDI diPartInPosition, 1;

        ! Approach 100 mm above pick point linearly, then descend
        MoveL Offs(pPick, 0, 0, 100), v500, z10, tGripper;
        MoveL pPick, v100, fine, tGripper;

        ! Actuate pneumatic gripper (Digital Output 1) and confirm grip switch
        SetDO doGripClose, 1;
        WaitTime 0.3;
        IF diGripConfirmed = 0 THEN
            ! If part missing, branch to fault recovery
            SetDO doAlarmLight, 1;
            Stop;
        ENDIF

        ! Retract vertically, transfer across cell, and lower to drop target
        MoveL Offs(pPick, 0, 0, 100), v300, z20, tGripper;
        MoveJ Offs(pDrop, 0, 0, 100), v800, z30, tGripper;
        MoveL pDrop, v100, fine, tGripper;

        ! Release gripper and return to home
        SetDO doGripClose, 0;
        WaitTime 0.2;
        MoveL Offs(pDrop, 0, 0, 100), v300, z10, tGripper;
        MoveJ pHome, v1000, fine, tGripper;
    ENDPROC
ENDMODULE

Lines that start with ! are comments that the controller ignores. Offs(point, x, y, z) returns a copy of a point shifted by the given offsets, which is how the program makes approach points 100 mm above the pick and drop targets. MoveJ moves the arm without forcing a straight-line path, while MoveL moves the tool in a straight line.[6]

05. Universal Robots URScript: syntax and execution

Universal Robots' script language, URScript, looks friendlier than RAPID.[2] Functions are defined with def and closed with end, the lines inside a block must be indented, and variables do not need type declarations: the manual states that a variable's type is deduced from its first assignment. If you know Python, the syntax will feel familiar.

URScript programs are executed in real time by the URControl RuntimeMachine, the low-level controller software that runs on the embedded PC in the control box.[2] On the e-Series, the RuntimeMachine communicates with the robot at 500 Hz, a 2 ms frame.[2] The older CB-series manual gives 125 Hz, a frame of 0.008 seconds.[11]

URScript supports threads. A developer declares a thread with a thread ... end block, starts it with run, and waits for it with join.[2] A thread can, for example, keep watching a sensor input while the main program moves the arm.

06. URScript motion and rotation vectors

In URScript, spatial points are represented by the pose type, written with the prefix p:[2] 

p[x, y, z, rx, ry, rz]

Unlike RAPID, which works in millimeters, URScript uses SI units: positions are in meters, tool speeds in m/s, and blend radii in meters. Orientation is written neither as a quaternion nor as Euler angles, but as an axis-angle rotation vector.[2]

A rotation vector [rx, ry, rz] points along the axis of rotation, and its length is the rotation angle.[12] The angle is therefore \(\theta = \sqrt{rx^2 + ry^2 + rz^2}\), in radians. For example, a 180-degree (\(\pi\) radian) rotation about the Y axis of the base frame is written p[0, 0, 0, 0, 3.14159, 0].

URScript's main motion functions are:[2]

  • movej(q, a=1.4, v=1.05, t=0, r=0): Move to a position, linear in joint space. q is a list of joint angles, or a pose, in which case inverse kinematics is used to find the matching joint positions. a and v are the acceleration and speed of the leading joint (rad/s² and rad/s). Because the joints move together in joint space, the tool tip follows a curved path rather than a straight line.
  • movel(pose, a=1.2, v=0.25, t=0, r=0): Move to a position, linear in tool space: the tool center point travels in a straight line. Here a is in m/s² and v in m/s.
  • movep(pose, a=1.2, v=0.25, r=0): “Move process.” It blends circular and linear moves in tool space and accelerates to, then holds, a constant tool speed v. A steady tool speed is what processes such as dispensing a bead of glue need.
  • movec(pose_via, pose_to, a=1.2, v=0.25, r=0, mode=0): Moves the tool along a circular arc through a via point.

In each case, a non-zero blend radius r lets the robot round off the corner instead of stopping at the point.[2]

07. Real-world URScript program walkthrough

The following script is this lesson's own example. It uses functions listed in the URScript manual (movej, movel, pose_add, get_digital_in, set_digital_out and sleep) to show pose manipulation, digital I/O, timers, and linear tool moves:[2] 

def pick_and_place_demo():
  # Define base positions (x, y, z in meters; rx, ry, rz in radians)
  p_home = p[0.400, 0.000, 0.500, 0.0, 3.14159, 0.0]
  p_pick = p[0.350, 0.250, 0.150, 0.0, 3.14159, 0.0]
  p_drop = p[0.350, -0.250, 0.150, 0.0, 3.14159, 0.0]

  # Move to home position in joint space (a = joint acceleration, v = joint velocity)
  movej(p_home, a=1.4, v=1.05)

  # Check part presence sensor on digital input 0
  if (get_digital_in(0) == True):
    # Approach 8 cm above pick point with 2 cm blend radius (r=0.02)
    p_approach = pose_add(p_pick, p[0, 0, 0.080, 0, 0, 0])
    movel(p_approach, a=0.8, v=0.4, r=0.02)

    # Descend to pick location in a straight line and stop exactly (r=0)
    movel(p_pick, a=0.4, v=0.1, r=0.0)

    # Trigger pneumatic gripper on digital output 0
    set_digital_out(0, True)
    sleep(0.3)

    # Lift vertically to clear fixture
    movel(p_approach, a=0.8, v=0.3, r=0.02)

    # Transfer linearly across cell to drop location
    p_drop_approach = pose_add(p_drop, p[0, 0, 0.080, 0, 0, 0])
    movel(p_drop_approach, a=0.8, v=0.5, r=0.02)
    movel(p_drop, a=0.4, v=0.1, r=0.0)

    # Open gripper and retract
    set_digital_out(0, False)
    sleep(0.2)
    movel(p_drop_approach, a=0.8, v=0.3)
  end

  # Return safely to home
  movej(p_home, a=1.4, v=1.05)
end

08. KUKA Robot Language (KRL)

KUKA Robot Language (KRL) is the language of KUKA's robot controllers. Researchers who studied it describe it as an imperative programming language similar to Pascal, with predefined robot-specific structures such as AXIS and POS.[13]

A distinctive feature of KRL is its two-file program structure: each program is made of two files with the same name.[14][3]

  • Source file (.src): Holds the movement commands and program logic, including the motion types PTP (point-to-point, a joint move in which the tool does not follow a straight line), LIN (linear), and CIRC (circular).[14][3]
  • Data file (.dat): Holds permanent data, such as the stored positions the program moves to.[14] Keeping data apart from logic means a taught point can be changed without editing the motion code.

KRL represents Cartesian targets with structures such as FRAME, POS and E6POS. A FRAME holds a position X, Y, Z and orientation angles A, B, C; POS adds two integers, Status (S) and Turn (T), which store flags that pick out one arm configuration among several; and E6POS adds the external axis values E1 to E6.[14][3] Motions can be blended (KUKA calls this approximate positioning) with parameters such as C_DIS.[13][3]

09. FANUC TP and KAREL

FANUC robots offer two programming languages working at different levels:[5][4]

  • Teach Pendant (TP) programs: The everyday shop-floor language, taught on the teach pendant. Programs use joint and linear motion instructions; speed is given as a percentage of joint speed or as a tool speed in mm/sec; and each move ends with a termination type, either FINE (stop at the point) or CNT with a value from 0 to 100 (blend through it). Number registers (R[x]), labels, IF and JMP statements, digital I/O (DI[x], DO[x]) and position registers (PR[x])—where registers are numbered memory slots used to store global numeric values and position coordinates—provide program control.[5] Two typical motion lines look like this: 
    1: J P[1:Home] 100% FINE
2: L P[2:Pick] 500mm/sec CNT50
  • KAREL: A high-level language whose programs are compiled before being loaded onto the controller (FANUC's WinOLPC tool compiles, debugs, and downloads them).[5] FANUC's KAREL reference manual covers string handling, file input and output, socket messaging over a network, and multi-tasking, and it includes built-in routines for working with TP programs.[4] These features suit KAREL to data handling and communication jobs, while TP programs cover everyday motion sequences.

10. RRL and historical standardization

Unlike URScript and RAPID, RRL is not a language you will find on today’s commercial robots. The only documented robot language by that name is RRL, “an integrated environment of robot programming,” published by Bojan Nemec, Anton Ružić and Vinko Ilc in the journal Informatica in 1992.[15] Nemec has been a researcher at the Jožef Stefan Institute in Ljubljana, Slovenia, since 1983.[16] RRL was an academic research system, not a product sold by a robot manufacturer.

Robotics researchers and standards bodies have also tried to reduce the number of incompatible languages. In 1992, the German standard DIN 66312, Industrial Robot Language (IRL), was published by Beuth Verlag, defining a high-level language for programming industrial robots.[17] European research projects such as the ESPRIT project InterRob later built standardized interfaces around IRL to connect product design, simulation, programming, and robot control.[18]

Even so, the major vendors kept their own languages, as sections 02 to 09 show. One likely reason, and this is this lesson's interpretation rather than a documented vendor policy, is that a proprietary language lets a vendor tie programs closely to its own controller and motion features. Vendor-neutral programming gained much wider traction later through open-source middleware such as ROS, examined in lesson 2.4.

11. Side-by-side technical comparison

The following table summarizes how the four vendor languages compare, using only details documented in this lesson's sources:[6][2][13][14][3][4][5]

Feature ABB RAPID UR URScript KUKA KRL FANUC TP / KAREL
Language Style Keyword blocks, typed declarations (CONST, PERS, VAR) Interpreted in real time, dynamic typing, indented blocks Imperative, similar to Pascal TP: teach pendant instructions; KAREL: compiled high-level language
Position Units Millimeters (speeds in mm/s, zones in mm) Meters (speeds in m/s) X, Y, Z fields of FRAME / POS X, Y, Z of an XYZWPR position; tool speeds in mm/sec
Orientation Quaternion (four values) Rotation vector [rx, ry, rz] (rad) Angles A, B, C Angles W, P, R
Motion Commands MoveJ, MoveL, MoveC movej, movel, movep, movec PTP, LIN, CIRC J (joint), L (linear)
Corner Blending zonedata (e.g. fine, z10, z50) Blend radius r in meters (e.g. r=0.02) Approximate positioning (e.g. C_DIS) FINE, or CNT0 to CNT100
Program Structure Program modules (.mod) and system modules (.sys) Text script of def ... end functions Paired files (.src logic + .dat data) TP programs plus separately compiled KAREL programs
