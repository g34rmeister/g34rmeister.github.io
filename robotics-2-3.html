      2.3 Common Programming Languages

      Gerald Lê
      Chapter 2, lesson 3 of 8 ← Previous: 2.2 Common Programming Environments Next: 2.4 Intro to ROS (Vendor-Agnostic) →
      Start here

      Every major industrial robot brand ships its own programming language tailored to real-time motion loops. This lesson walks side-by-side through real ABB RAPID and Universal Robots URScript programs, then compares them with KUKA KRL and FANUC TP/KAREL. On a first read, focus on how targets, speeds, and blending zones appear directly inside motion instructions.

      • You will learn RAPID structure (modules, PROC/FUNC/TRAP routines, robtarget, speeddata, and zonedata).
      • You will learn URScript syntax, rotation-vector poses, movej/movel/movep commands, and threads.
      • You will learn how vendor languages handle physical I/O and interrupts.

      01. Why every robot brand has its own language

      Imagine programming a factory arm to pick a part off a conveyor and set it on a table. If you already write software, you might expect to use Python or Java for the job. Instead, each major robot brand uses its own language, and knowing why helps you switch between arms on the shop floor.

      In web, cloud, and embedded software, developers share general-purpose languages like Python, C++, Rust, and Java. In industrial robotics, however, each maker ships its own language. ABB arms use RAPID, and Universal Robots (UR) arms use URScript. KUKA arms use KUKA Robot Language (KRL), while FANUC arms use teach pendant (TP) programs or KAREL.[1][2][3][4][5]

      One big reason is timing. A robot controller is not a desktop computer that runs programs whenever it gets around to them. It runs a real-time motion system that sends fresh commands to the arm on a fixed, tiny schedule. For example, Universal Robots’ e-Series manual states that the robot must be controlled at 500 hertz (Hz), or 500 times every second. That means the controller must tell the arm what to do every 0.002 seconds. The manual also states that URScript programs run in real time inside the controller’s RuntimeMachine.[2] A brand’s own language lets user code run right inside that strict loop.

      These languages are also built around the physics of robot arms. Their basic building blocks are not just strings and integers. They center on target positions, tool definitions, speeds, and corner-blending zones. A single RAPID motion command names its target, speed, zone, and tool all at once.[6] Visual tools such as ABB’s RobotStudio and UR’s PolyScope sit on top of these languages. When RobotStudio syncs its three-dimensional (3D) view to the controller, it turns placed targets into RAPID robtarget data.[7] PolyScope connects to the UR controller as a client.[2] Writing the language directly unlocks most of what the controller can do.

      02. How an ABB RAPID program is organized

      Before you command a pick-and-place arm to move, you need a place to store your code and tool settings. A real cell often runs arm motions in the foreground while checking a part sensor or talking to other machines. ABB’s high-level language, RAPID, splits code into tasks, modules, and routines so complex programs stay tidy.

      RAPID uses clear keyword blocks such as PROC ... ENDPROC and IF ... ENDIF. Every data item must be declared with a specific type.[6]

      You organize a RAPID program in a clear hierarchy:[7][6]

      • Tasks: A task is a robot program that runs on its own or alongside other tasks on the same controller. One task can drive the arm while another handles background jobs such as communication.[7]
      • Modules: Inside a task, you group code and data into modules using MODULE ... ENDMODULE. Program modules (.mod files) hold your logic and can be loaded or unloaded. System modules (.sys files) hold data and routines that survive a program change, such as a calibrated tool definition. Only one program module may hold the main procedure.[6][7]
      • Routines: These are the executable blocks inside a module. RAPID has three kinds of routines:[7]
        • Procedures (PROC): A block of instructions that does not return a value, such as PROC main() ... ENDPROC.[6]
        • Functions (FUNC): A routine that computes and returns a typed value, such as a calculated distance.[7]
        • Trap routines (TRAP): A routine triggered by an interrupt when an urgent event happens. For instance, an interrupt tied to a digital input like a part-drop sensor runs a TRAP routine as soon as that signal changes.[7]

      You can also choose how long RAPID remembers each data item. A CONST declaration creates a constant that never changes after you set it. A PERS declaration creates a persistent value that keeps its last value even if you stop and restart the program. A VAR declaration creates a variable that resets whenever the program pointer moves back to main.[6]

      For the curious: RAPID’s controller history and reference manual

      ABB introduced RAPID with its S4 control system in the 1990s, replacing the earlier ARLA language.[8] It remains the language of ABB’s IRC5 controllers and is documented in a reference manual well over a thousand pages long.[1]

      03. RAPID targets, speeds, and corner zones

      Telling a pick-and-place arm to reach a conveyor takes more than an X, Y, Z coordinate. You also have to set which way the gripper tilts, how fast it travels, and whether it stops dead or cuts the corner. RAPID bundles those choices into three built-in data types: robtarget, speeddata, and zonedata.[6][9]

      • robtarget: Stores one full destination in four bracketed parts:[6] 
        [[500, 0, 600], [0, 0, 1, 0], [0, -1, 1, 0], [9E9, 9E9, 9E9, 9E9, 9E9, 9E9]]
        The first array gives the X, Y, and Z position. The second array sets tool orientation as a four-number quaternion.[9] Quaternions avoid gimbal lock, a snag where a three-angle (Euler angle) description loses one direction of rotation at certain poses.[10] The third array stores the axis configuration. Those integers tell the controller which arm posture to pick when more than one posture can reach the same spot.[9][7] The fourth array tracks up to six extra (external) axes, like a linear track or rotating positioner. Any unused external axis is set to 9E9.[6]
      • speeddata: Sets how fast the arm moves. Its main value is v_tcp, the speed of the tool center point (TCP). Predefined names make common speeds easy to read. For example, v1000 means 1000 millimeters per second (mm/s), v100 means 100 mm/s, and vmax means the robot’s top speed.[6]
      • zonedata: Controls corner blending between moves. If you choose fine, the robot moves all the way to the exact point and stops before starting the next move. If you choose a zone such as z50, the arm may round the corner once it comes within 50 millimeters (mm) of the point. Cutting corners keeps the arm moving smoothly and saves cycle time.[6]
      For the curious: exact fields inside robtarget, speeddata, and zonedata

      Inside robtarget, the four fields are named trans, rot, robconf, and extax.[6] The third array holds [cf1, cf4, cf6, cfx], which record the quadrants of the arm’s significant axes.[9][7]

      speeddata holds four numbers: [v_tcp, v_ori, v_leax, v_reax].[9] While v_tcp limits TCP travel speed,[6] the other three values cap tool reorientation speed and external-axis speeds. ABB’s reference manual gives their exact definitions.[1]

      zonedata holds seven fields: [finep, pzone_tcp, pzone_ori, pzone_eax, zone_ori, zone_leax, zone_reax].[9]

      04. Walking through a RAPID pick-and-place program

      Now put those building blocks together in a complete job. The program below waits for a part on a conveyor, picks it up with a gripper, and sets it down on the other side of the cell. Watching how each line uses targets, speeds, zones, and sensor checks makes the syntax much clearer.

      This module is this lesson’s own example. It uses only instructions and data types documented by ABB: MoveJ, MoveL, Offs, WaitDI, SetDO, WaitTime, Stop, robtarget, and tooldata.[6][1] Signal names such as diPartInPosition are examples that you would set up on a real controller. 

      MODULE PickAndPlaceModule
    ! Predefined Cartesian targets: position (mm), quaternion, config, external axes
    CONST robtarget pHome := [[600, 0, 750], [0, 0, 1, 0], [0, 0, 0, 0], [9E9, 9E9, 9E9, 9E9, 9E9, 9E9]];
    CONST robtarget pPick := [[450, 200, 120], [0, 0, 1, 0], [0, -1, 1, 0], [9E9, 9E9, 9E9, 9E9, 9E9, 9E9]];
    CONST robtarget pDrop := [[450, -200, 120], [0, 0, 1, 0], [0, 1, -1, 0], [9E9, 9E9, 9E9, 9E9, 9E9, 9E9]];

    ! Tool definition: mass 2.5 kg, TCP offset 150 mm along tool Z-axis
    PERS tooldata tGripper := [TRUE, [[0, 0, 150], [1, 0, 0, 0]], [2.5, [0, 0, 50], [1, 0, 0, 0], 0, 0, 0]];

    PROC main()
        ! Move to safe home position using joint interpolation at 1000 mm/s with 50 mm zone
        MoveJ pHome, v1000, z50, tGripper;

        ! Wait for conveyor part sensor (Digital Input 1) to go HIGH
        WaitDI diPartInPosition, 1;

        ! Approach 100 mm above pick point linearly, then descend
        MoveL Offs(pPick, 0, 0, 100), v500, z10, tGripper;
        MoveL pPick, v100, fine, tGripper;

        ! Actuate pneumatic gripper (Digital Output 1) and confirm grip switch
        SetDO doGripClose, 1;
        WaitTime 0.3;
        IF diGripConfirmed = 0 THEN
            ! If part missing, branch to fault recovery
            SetDO doAlarmLight, 1;
            Stop;
        ENDIF

        ! Retract vertically, transfer across cell, and lower to drop target
        MoveL Offs(pPick, 0, 0, 100), v300, z20, tGripper;
        MoveJ Offs(pDrop, 0, 0, 100), v800, z30, tGripper;
        MoveL pDrop, v100, fine, tGripper;

        ! Release gripper and return to home
        SetDO doGripClose, 0;
        WaitTime 0.2;
        MoveL Offs(pDrop, 0, 0, 100), v300, z10, tGripper;
        MoveJ pHome, v1000, fine, tGripper;
    ENDPROC
ENDMODULE

      Any line starting with ! is a comment that the controller skips. Notice the helper Offs(point, x, y, z). It returns a shifted copy of a point, which lets the program hover 100 mm above the pick and drop points before dropping straight down.

      The program mixes two motion types to stay both fast and accurate. MoveJ moves the joints freely across open space without forcing a straight path. MoveL guides the tool in a straight line when dipping into a fixture or lifting out of it.[6] Notice that both pPick and pDrop use fine so the arm stops accurately before opening or closing the gripper.

      The motion interpolation simulator needs JavaScript. With it on, you can compare MoveJ joint moves and MoveL linear moves on the two-link arm.

      For the curious: what sits inside tooldata

      The tooldata value follows ABB’s standard layout. It records whether the robot holds the tool (robhold), the tool frame (tframe, a position and a quaternion), and the tool load (tload: mass, center of gravity, and inertia values).[9]

      05. Universal Robots URScript: how it looks and runs

      If RAPID’s keyword blocks look strict, Universal Robots takes a lighter approach with URScript. Its layout looks much closer to Python, so newcomers with general coding experience often find it easier to read. Even so, it runs inside the same kind of fast real-time loop that keeps a robot arm moving safely.

      URScript looks friendlier than RAPID.[2] You start a function with def and close it with end. Lines inside a block must be indented, and variables need no type declarations. The manual states that a variable’s type is deduced from its first assignment. If you know Python, the syntax will feel familiar right away.

      Behind the scenes, the URControl RuntimeMachine runs URScript programs in real time. It is the low-level controller software running on the embedded personal computer (PC) inside the control box.[2] On the e-Series, the RuntimeMachine talks to the robot at 500 Hz, giving a 2 millisecond (ms) frame.[2]

      URScript also supports threads so your program can handle two jobs at once. You declare a thread with a thread ... end block, start it with run, and wait for it with join.[2] For example, a thread can keep watching a sensor input while the main program moves the arm.

      For the curious: older CB-series controller timing

      While the e-Series controller runs at 500 Hz (a 2 ms frame),[2] the older CB-series manual specifies 125 Hz, which is a frame of 0.008 seconds.[11]

      06. How URScript describes poses and moves

      Just like RAPID, URScript needs to know where the gripper goes, which way it points, and how it travels. The main surprise for beginners switching between brands is the units and the math for orientation. URScript measures distances in meters instead of millimeters, and it packs direction and turn angle into one three-number vector.

      In URScript, spatial points use the pose type, written with a p prefix:[2] 

      p[x, y, z, rx, ry, rz]

      Unlike RAPID, URScript uses SI units. Positions are in meters (m), tool speeds are in meters per second (m/s), and blend radii are in meters. Orientation is written neither as a quaternion nor as Euler angles. Instead, it uses an axis-angle rotation vector.[2]

      Think of pointing a pencil along the axis you want to spin around, and making the arrow longer for a bigger turn. A rotation vector [rx, ry, rz] points along the axis of rotation, and its length equals the rotation angle.[12] The angle is therefore \(\theta = \sqrt{rx^2 + ry^2 + rz^2}\) in radians (rad). For example, a 180-degree (\(\pi\) radian) turn around the base frame’s Y axis is written p[0, 0, 0, 0, 3.14159, 0].

      URScript gives you four main motion functions:[2]

      • movej(q, a=1.4, v=1.05, t=0, r=0): Moves to a target in joint space. q can be a list of joint angles, or a pose where inverse kinematics finds the matching joint angles. Here a and v set the acceleration and speed of the leading joint in radians per second squared (rad/s²) and radians per second (rad/s). Because the joints turn together in joint space, the tool tip follows a curved path rather than a straight line.
      • movel(pose, a=1.2, v=0.25, t=0, r=0): Moves the TCP in a straight line in tool space. Here a is in meters per second squared (m/s²) and v is in m/s.
      • movep(pose, a=1.2, v=0.25, r=0): “Move process.” It blends circular and linear moves in tool space while accelerating to, then holding, a steady tool speed v. Processes such as dispensing a bead of glue need that steady speed.
      • movec(pose_via, pose_to, a=1.2, v=0.25, r=0, mode=0): Moves the tool along a circular arc through a via point.

      In every one of these functions, a non-zero blend radius r lets the robot round off the corner instead of stopping at the point.[2]

      07. Walking through a URScript pick-and-place program

      Next, look at the same pick-and-place task written in URScript. Putting this script next to the RAPID program in section 04 makes the brand differences easy to see. Notice how distances shrink from hundreds of millimeters to fractions of a meter, and how indented def ... end blocks replace MODULE and PROC.

      This script is this lesson’s own example. It uses functions listed in the URScript manual: movej, movel, pose_add, get_digital_in, set_digital_out, and sleep. Together, they show pose math, digital input and output (I/O), timers, and straight-line tool moves.[2] 

      def pick_and_place_demo():
  # Define base positions (x, y, z in meters; rx, ry, rz in radians)
  p_home = p[0.400, 0.000, 0.500, 0.0, 3.14159, 0.0]
  p_pick = p[0.350, 0.250, 0.150, 0.0, 3.14159, 0.0]
  p_drop = p[0.350, -0.250, 0.150, 0.0, 3.14159, 0.0]

  # Move to home position in joint space (a = joint acceleration, v = joint velocity)
  movej(p_home, a=1.4, v=1.05)

  # Check part presence sensor on digital input 0
  if (get_digital_in(0) == True):
    # Approach 8 cm above pick point with 2 cm blend radius (r=0.02)
    p_approach = pose_add(p_pick, p[0, 0, 0.080, 0, 0, 0])
    movel(p_approach, a=0.8, v=0.4, r=0.02)

    # Descend to pick location in a straight line and stop exactly (r=0)
    movel(p_pick, a=0.4, v=0.1, r=0.0)

    # Trigger pneumatic gripper on digital output 0
    set_digital_out(0, True)
    sleep(0.3)

    # Lift vertically to clear fixture
    movel(p_approach, a=0.8, v=0.3, r=0.02)

    # Transfer linearly across cell to drop location
    p_drop_approach = pose_add(p_drop, p[0, 0, 0.080, 0, 0, 0])
    movel(p_drop_approach, a=0.8, v=0.5, r=0.02)
    movel(p_drop, a=0.4, v=0.1, r=0.0)

    # Open gripper and retract
    set_digital_out(0, False)
    sleep(0.2)
    movel(p_drop_approach, a=0.8, v=0.3)
  end

  # Return safely to home
  movej(p_home, a=1.4, v=1.05)
end

      Follow the flow from top to bottom. First, movej sends the arm to p_home, and get_digital_in(0) checks whether a part is waiting. Next, pose_add adds 0.080 m, or 8 centimeters (cm), upward so the arm can approach above the part with a 2 cm blend radius (r=0.02).

      Then the arm descends to p_pick and stops cleanly because r=0.0. After set_digital_out(0, True) closes the gripper and sleep(0.3) gives it time to grab, the arm lifts, crosses to p_drop, opens the gripper, and returns home.

      08. How KUKA Robot Language (KRL) splits logic and points

      On a factory floor, a technician often needs to nudge a pick point by a few millimeters without risking changes to the rest of the code. KUKA Robot Language (KRL) makes that safer by splitting every program into two matching files. One file holds the movement steps, and the other file holds the saved positions.

      Researchers who studied KRL describe it as an imperative programming language similar to Pascal, with predefined robot-specific structures such as AXIS and POS.[13]

      Its defining feature is that two-file program structure, which gives both files the same name with different file endings:[14][3]

      • Source file (.src): Holds the movement commands and program logic. Its main motion commands are PTP (point-to-point, a joint move that does not travel in a straight line), LIN (linear), and CIRC (circular).[14][3]
      • Data file (.dat): Holds permanent data, such as the stored positions the robot moves to.[14] Keeping data apart from logic lets you update a taught point without touching the motion code.

      KRL stores Cartesian targets in built-in types such as FRAME, POS, and E6POS. A FRAME holds a 3D position and three orientation angles. POS adds two integers, Status (S) and Turn (T), which act as flags to choose one arm posture when several postures can reach the same point. E6POS adds up to six external axis values.[14][3] To blend smoothly past a corner instead of stopping, KRL uses approximate positioning with parameters such as C_DIS.[13][3]

      For the curious: exact target fields inside FRAME, POS, and E6POS

      Inside FRAME, the position fields are X, Y, Z and the orientation angles are A, B, C. E6POS adds external axis fields named E1 to E6.[14][3]

      09. FANUC’s two languages: Teach Pendant (TP) and KAREL

      Many shop-floor technicians never type lines of code from scratch on a FANUC robot. Instead, they jog the arm with a handheld teach pendant and record each point into a numbered list of steps. When a cell also needs heavy data work or network messaging, engineers pair those simple step lists with a second, compiled language called KAREL.

      FANUC robots offer these two languages at different levels:[5][4]

      • Teach Pendant (TP) programs: This is the everyday shop-floor language taught directly on the pendant. Moves use joint (J) and linear (L) commands. You give speeds as a percentage of joint speed or as a tool speed in mm/sec. Each move ends with a termination type: FINE stops at the point, while CNT with a number from 0 to 100 blends smoothly through it. For program logic and memory, TP gives you number registers (R[x]), position registers (PR[x]), labels, IF and JMP statements, and digital I/O (DI[x], DO[x]). Here, registers are numbered memory slots that hold global numbers and position coordinates.[5] Two typical motion lines look like this: 
        1: J P[1:Home] 100% FINE
2: L P[2:Pick] 500mm/sec CNT50
      • KAREL: This is a high-level language compiled before you load it onto the controller.[5] It handles strings, file input and output, network socket messaging, and multi-tasking, and offers built-in routines for working with TP programs.[4] That makes KAREL ideal for data and network tasks, while TP programs run everyday motion sequences.
      For the curious: how KAREL programs are compiled

      FANUC’s WinOLPC tool compiles, debugs, and downloads KAREL programs to the controller.[5] FANUC’s KAREL reference manual documents string handling, file input and output, socket messaging over a network, multi-tasking, and built-in routines for interacting with TP programs.[4]

      10. Past attempts at one universal robot language

      After seeing four incompatible robot languages, you may wonder why nobody agreed on a single language for all brands. Researchers and standards groups actually tried to build shared robot languages back in the 1990s. Seeing why those efforts stayed separate explains why vendor-neutral tools gained traction later.

      You may occasionally see references to RRL, which sounds like a vendor language alongside URScript and RAPID. In fact, RRL is not a language you will find on today’s commercial robots. It was an academic research system built at a research institute, not a product sold by a robot maker.[15][16]

      Standards bodies also tried to unify robot programming across brands. A German standard created Industrial Robot Language (IRL), a high-level language meant to standardize industrial robot programming.[17] European research projects later built shared interfaces around IRL to link product design, simulation, programming, and robot control.[18]

      Even so, the major vendors kept their own languages, as sections 02 to 09 show. One likely reason (this lesson’s interpretation, not a documented vendor policy) is that a proprietary language lets a vendor tie programs closely to its own controller and motion features. Vendor-neutral programming gained much wider traction later through open-source middleware such as ROS, examined in lesson 2.4.

      For the curious: RRL, DIN 66312 (IRL), and the InterRob project

      The only documented robot language named RRL is “an integrated environment of robot programming,” published by Bojan Nemec, Anton Ružić, and Vinko Ilc in the journal Informatica in 1992.[15] Nemec has been a researcher at the Jožef Stefan Institute in Ljubljana, Slovenia, since 1983.[16]

      In 1992, the German standard DIN 66312, Industrial Robot Language (IRL), was published by Beuth Verlag.[17] European research projects such as the ESPRIT project InterRob later built standardized interfaces around IRL to connect product design, simulation, programming, and robot control.[18]

      11. Side-by-side comparison of all four languages

      Even though ABB, Universal Robots, KUKA, and FANUC look different on your screen, they all solve the same problem. Each one gives you a way to set target positions, orientation, motion paths, and corner blending. Putting all four side by side helps you translate what you know from one brand to another.

      The table below summarizes how the four vendor languages compare, using only details documented in this lesson’s sources:[6][2][13][14][3][4][5]

      Feature ABB RAPID UR URScript KUKA KRL FANUC TP / KAREL
      Language Style Keyword blocks, typed declarations (CONST, PERS, VAR) Interpreted in real time, dynamic typing, indented blocks Imperative, similar to Pascal TP: teach pendant instructions; KAREL: compiled high-level language
      Position Units Millimeters (speeds in mm/s, zones in mm) Meters (speeds in m/s) X, Y, Z fields of FRAME / POS X, Y, Z of an XYZWPR position; tool speeds in mm/sec
      Orientation Quaternion (four values) Rotation vector [rx, ry, rz] (rad) Angles A, B, C Angles W, P, R
      Motion Commands MoveJ, MoveL, MoveC movej, movel, movep, movec PTP, LIN, CIRC J (joint), L (linear)
      Corner Blending zonedata (e.g. fine, z10, z50) Blend radius r in meters (e.g. r=0.02) Approximate positioning (e.g. C_DIS) FINE, or CNT0 to CNT100
      Program Structure Program modules (.mod) and system modules (.sys) Text script of def ... end functions Paired files (.src logic + .dat data) TP programs plus separately compiled KAREL programs
