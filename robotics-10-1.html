10.1 Capstone: Build a Simulated Work Cell

Gerald Lê

01. What you will build and why

In this capstone you build a complete robot work cell in software. A simulated arm picks a part from an infeed position, places it at an outfeed position, uses simulated I/O for its gripper and a part-present sensor, respects a safety configuration you set up yourself, and passes a test sheet modelled on a factory acceptance test (FAT, a formal verification process conducted at the supplier facility to ensure equipment meets contract specifications before delivery). You can use either Universal Robots' URSim or ABB RobotStudio. Both are free to start, and both run the same controller software a real robot runs.

Most of the skills you need were taught earlier in the course; here you combine them and prove that they work. The result is something you can show: a working program, a safety configuration, a test sheet with evidence, and a short report.

The project is organised the way teaching-center guidance recommends for project work. The grading criteria and the rubric are published now, at the start, rather than at the end. The work is split into milestones (a plan, a first working piece, an integrated demo, test evidence and a report), so that problems show up early while there is still time to fix them.[1] The final grade uses a four-level analytic rubric with no neutral middle level, a format documented in an engineering-technology capstone program where each project was rated from “Not Acceptable” to “Exemplary”.[2] The rubric is kept short on purpose: capstone researchers note that rubrics must balance depth against simplicity, and that very detailed rubrics can narrow student creativity.[3] If you work in a team, you also hand in a short contribution statement at each milestone, because milestone evaluations are one documented way to keep each team member accountable to the group.[4][1]

Why a cell and not just a robot? A real cell also has fixtures, sensors, a gripper, guarding and a safety design (see 1.7). Building all of it teaches you to think like an integrator: what must be true before the robot moves, what happens when something fails, and how you prove the cell works.

02. Prerequisites

You should be comfortable with the following lessons before you start. Each one supplies a piece of the cell.

  • 1.7 The Industrial Robot Cell: what a cell contains, PLC-robot handshakes, FAT and SAT, and cycle time. You use this vocabulary in your layout sketch and test sheet.
  • 2.5 End-of-Arm Tooling and I/O: setting payload, and using digital outputs to open and close a gripper and digital inputs to confirm a grip or a part.
  • 2.6 Your First Pick-and-Place: starting URSim or RobotStudio, defining the TCP, teaching targets in a fixture frame, approach offsets and exact stops at the grip.
  • 2.7 Program Structure and Error Handling: splitting a program into routines and recovering from errors such as a missed pick.
  • 5.4 Making a Robot Cell Safe: risk assessment, guards and robot safety functions. You need it to understand what your simulated safety configuration can and cannot prove.

03. Software and equipment (free options first)

You need a computer that can run Docker (for URSim) or Windows (for RobotStudio), a web browser, and a way to take screenshots. No robot hardware is needed. Pick one path and stay on it for the whole project.

Path A: URSim in Docker (free). Universal Robots publishes one Docker image per software generation: universalrobots/ursim_polyscopex for PolyScope X, universalrobots/ursim_e-series for PolyScope 5 and universalrobots/ursim_cb3 for the older CB3 robots.[5] This project assumes the e-Series (PolyScope 5) image, which matches lesson 2.6. You open PolyScope in your browser, so the whole teach pendant runs on your laptop.[6]

Path B: ABB RobotStudio. RobotStudio has a free “Basic functionality mode” that needs no activation but allows only online and basic Virtual Controller features. Without activation, the Premium features run as a trial for up to 30 days and then revert to Basic.[7][8] Those terms come from an older ABB document, so check the current offer. From version 2026.1, RobotStudio uses user-based licensing tied to a Robotics One account (node-locked licenses are the exception), and ABB's comparison lists an “Education” license type alongside Freemium, Trial, Enterprise, Node-Locked and Partner.[9][10] What the Education tier includes was not confirmed, so ask your instructor whether your school has one before you rely on a trial that may expire mid-project.

Whichever path you choose, keep a project folder with three subfolders from day one: plan/ (sketches, I/O list, sequence chart), program/ (exported programs and installation or station files) and evidence/ (screenshots and logs named by test ID). You will hand in that folder at the end.

04. Milestones and what to hand in

The project has five milestones. Each one ends with a small hand-in so that you, and your instructor, can see progress and catch problems early.[1] Suggested timing is for a three to four week project; your instructor may change it.

Milestone Goal Hand in
M0 Plan Decide what the cell does before you touch the simulator. Cell layout sketch, I/O list, sequence chart, draft test list, list of risks to the schedule.
M1 Cell up URSim running in Docker, or a RobotStudio station built; tool and frames set; waypoints taught. Screenshot of the robot at each taught point; saved installation or station file.
M2 Integrated demo Pick-and-place program using simulated gripper outputs and a part-present input. Program file and a short screen recording of three full cycles.
M3 Safety config Add a safety plane and reduced limits (UR) or a stand-in zone (ABB), and show the robot reacts. Screenshots of the safety settings and of the robot stopping or slowing.
M4 Test and report Run a FAT-style test sheet and write up what you learned. Completed test sheet with evidence, two-page report, reflection, project folder.

Team projects add one more item to every hand-in: a contribution statement of a few lines from each member, saying what they did since the last milestone. Individual evidence like this lets an instructor grade the group product and each person's part separately.[1]

05. Build guidance: M0 plan and M1 cell up

M0: plan on paper first. Draw the cell from above: robot base, infeed and outfeed positions, table edge, and where a fence would be in a real cell. Then write an I/O list. A minimal cell has one gripper output, one gripper-closed input (if your simulated gripper offers one) and one part-present input at the infeed. Give each signal a name, a number and a meaning, for example “DO0 gripper close, 1 = closed”. Finally write a sequence chart: a numbered list of steps with the condition that must be true before each step starts. 

Step  Action                          Start condition
 0    Move to Home                    Program started, gripper open
 1    Wait for part                   At Home
 2    Approach above pick             DI part_present = 1
 3    Linear down to pick, exact stop At approach
 4    Close gripper, wait             At pick
 5    Linear up to approach           Grip confirmed (or wait time done)
 6    Move to approach above place    Clear of infeed
 7    Linear down to place, exact stop At place approach
 8    Open gripper, wait              At place
 9    Linear up, return to Home       Gripper open
10    Repeat from step 1

This chart is the core of your program and of your test sheet. Every condition in the right-hand column is something you can test later. Also write a target cycle time, for example in seconds per part, so you have a number to measure against (cycle time is covered in 1.7).

M1 on Path A: start URSim. The basic start command from the Universal Robots Client Library documentation is:[6] 

docker run --rm -it -p 127.0.0.1:5900:5900 -p 127.0.0.1:6080:6080 --name ursim universalrobots/ursim_e-series

PolyScope then runs in your browser at http://127.0.0.1:6080/vnc.html. Keep the 127.0.0.1: bind address in each port option: it keeps the simulator's screen on your own machine. If you leave the bind address out, the simulator is exposed to everyone on your local network.[6]

The --rm option deletes the container when you stop it, so without extra steps your programs disappear. To keep programs and installations between runs, mount a folder on your computer into the container:[6] 

docker run --rm -it -p 127.0.0.1:5900:5900 -p 127.0.0.1:6080:6080 \
  -v ${HOME}/.ursim/programs:/ursim/programs \
  -v ${HOME}/.ursim/urcaps:/urcaps \
  --name ursim universalrobots/ursim_e-series

The second mount is for URCaps, the plug-ins that extend PolyScope. You only need it for the ROS stretch goal below, where the External Control URCap is dropped into that folder.[6] If you already have ROS 2 and the UR driver installed, there is also a helper, ros2 run ur_client_library start_ursim.sh -m <ur_type> -v <version>. It starts URSim on a Docker network at 192.168.56.101 with ports 30001 to 30004 and 29999 published and External Control preinstalled. Without -v it uses the latest PolyScope 5 image, and without -m it uses a UR5e.[5][6]

In PolyScope, power on and release the brakes, set the TCP and payload for your gripper (see 2.5), define a feature frame for the infeed fixture, and teach Home, the pick and place points and their approach points as in 2.6. Save the installation and the program into the mounted folder, then stop and restart the container once to prove they survive.

M1 on Path B: build a RobotStudio station. Create a station with a robot and a virtual controller, add a simple table and two part positions, attach a tool, and create a work object for the infeed fixture. Teach the same targets as in Path A. Save the station and make a backup copy in your program/ folder.

06. Build guidance: M2 integrated pick-and-place

Now turn the sequence chart into a program. Reuse the structure from 2.7: a main routine that loops, a routine for picking, a routine for placing and a routine that returns safely to Home. Keep the motion rules from 2.6: approach and transfer moves may blend, but the robot must make an exact stop wherever the gripper changes state.

The I/O is what makes this a cell rather than a motion demo. Before each pick, the program must wait for the part-present input. At the pick point it sets the gripper output and waits, either for a grip-confirmed input or for a fixed time. At the place point it clears the output and waits again. In the simulator nobody is going to put a real part on the infeed, so you toggle the part-present input yourself from the I/O screen (PolyScope) or the I/O simulator window (RobotStudio). That is also how you will test the cell in M4.

Add at least one error path. For example, if the grip is not confirmed within a time limit, open the gripper, retract to the approach point, and stop with a clear message instead of carrying an empty gripper to the place point. Lesson 2.7 shows the patterns for both RAPID and URScript.

There is one limit of URSim to know about. The UR ROS 2 driver documentation notes that effort control “has no effect in URSim”, so a simulated robot asked to move by effort simply stays still.[5] Keep this project to position-controlled moves; anything that depends on force or effort cannot be tested in URSim and must wait for real hardware.

Run the program slowly first (speed slider or speed override). When three cycles in a row complete without a fault, record them for M2.

07. Build guidance: M3 safety configuration

A safety configuration limits where the robot may go and how fast it may move, independently of the program. Here you set one up and show that the simulated robot reacts. Read the last paragraph of this section first.

Path A: PolyScope safety settings. PolyScope 5 has a dedicated safety menu that covers everything “from creating safety planes to limiting a joint's range of motion”; the current PolyScope 5 release is 5.24.[11] The PolyScope X handbook has matching sections on joint limits, safety planes and tool position restriction,[12] and its joint-limits page covers joint positions and speeds and notes that a wrist clamping-position protection is enabled by default.[13] The PolyScope 5 manuals cover setting a software safety password, the configurable safety functions and the software safety configuration.[14][15] From software 5.17, the System settings screens can be protected by the Admin password, and on new robots they are locked by default.[16] The exact menu steps were not checked for this course, so follow the handbook for your PolyScope version. Your M3 task is:

  • 1. Password: set a safety password and write it in your project notes (it is only a simulator, so this is fine here; never do this for a real robot).
  • 2. One safety plane: add a plane that acts as a virtual wall or table surface, placed so that your normal cycle stays on the allowed side.
  • 3. Reduced limits: lower a joint speed or TCP speed limit and record the values before and after.
  • 4. Show the reaction: jog or program the robot towards the plane and capture what happens: a stop, a switch to reduced mode, or nothing. Record exactly what you saw.

Record what you observe rather than what you expect. Whether URSim's safety menu behaves exactly like a real controller, for example whether a plane violation triggers the same protective stop, was not confirmed by any source used for this course. If the robot does not react the way you expected, that is a valid and interesting result for your report.

Path B: ABB and SafeMove. ABB's safety option is SafeMove, but a participant on ABB's forum replied, while saying he was not sure, that “SafeMove runs on separate hardware which isn't simulated by the virtual controller”.[17] Forum users describe partial workarounds, such as starting the virtual controller separately to reach the Authenticate menu, or forcing safety I/O signals such as AS1 and AS2 (the dual automatic stop safety input channels monitored by ABB safety controllers) on so the robot can run.[17][18] These are community reports, not official procedures. The official reference is ABB's manual “Functional safety and SafeMove for OmniCore” (3HAC066559), which covers the system parameters, safety user grants and how to start Visual SafeMove.[19] For this project, use a programmed stand-in agreed with your instructor, such as a RAPID world zone or software axis limits, and say clearly in your report that it is a stand-in and not a safety function.

Sim settings do not carry over to a real cell. A safety configuration in a simulator is not a validated safety function. Speeds that look slow on screen, distances that look comfortable, and planes that stop a virtual robot say nothing about stopping distances, sensor placement or the performance level a real cell needs. A real cell needs a risk assessment and a validated safety design, as described in 5.4. Treat your M3 work as practice with the tools, not as a design you could install.

08. Testing and verification: M4 FAT-style test sheet

A factory acceptance test is a check, attended by the customer at the supplier before shipment, that confirms the equipment matches the contract specification, operates correctly and has its required safety functions.[20] Industry guidance lists safety items to check such as guarding and pinch points, sharp edges, whether limit switches and E-stops work and are well placed, and the built-in safety components.[21] FAT checklist templates are usually split into a documentation review, pre-test preparation and inspection steps, with items such as testing alarms, interlocks and emergency stops and checking that calibration and material certificates are available.[22]

Your simulated cell cannot have its guarding inspected, but it can be tested the same way. Every row of your test sheet needs an ID, the requirement it checks, the procedure, the expected result, the actual result, pass or fail, and the file name of the evidence (a screenshot or a log). Start from these rows and add your own from the sequence chart:

ID Requirement Procedure (short) Expected result
T01Cycle runs reliablyRun N cycles back to back (agree N with your instructor)All N complete with no fault
T02Cycle timeTime ten cycles, divide by tenAt or below your M0 target
T03No part, no pickStart with part-present = 0Robot waits at Home and does not move to pick
T04Stop halts motionPress E-stop or trigger a protective stop mid-moveMotion halts; state is shown on the pendant
T05Safety planeJog the TCP towards the planeViolation is detected (record what happens)
T06Reduced speedMove in the reduced zone or modeSpeed stays at or below the reduced limit
T07Gripper I/OWatch the I/O screen during one cycleOutput on at pick, off at place, never on during transfer
T08RecoveryStop mid-cycle, reset, restartRobot returns to Home by a safe path before resuming
T09BackupRestore program and installation from your backup in a fresh container or stationCell runs unchanged

Write the expected result before you run each test. When a test fails, do not edit the row: record the failure, fix the cause, and add a dated retest. An honest failure with a documented fix is worth more than a sheet of unbelievable passes.

Keep the limits of simulation in mind when you write up T04 to T06. A cell can pass a demonstration in the shop and still fail on site, because parameters, networks and interfaces differ there; integrators therefore treat the robot, controls, safety functions and plant interfaces as one system with documented acceptance criteria.[23] Your test sheet is a first version of those criteria, not a substitute for a real FAT and site acceptance test.

09. Common problems

  • Programs vanish after restarting URSim: the container was started with --rm and no volume mount. Use the -v options from section 05 and save into /ursim/programs.[6]
  • Robot never leaves Home: the program is waiting for the part-present input. Toggle it on in the I/O screen; if that does not help, check that the program reads the same input number your I/O list names.
  • Gripper closes while the robot is still moving: the grip point is blended. Make it an exact stop (see 2.6).
  • Robot stops for no clear reason after M3: your safety plane or reduced limit also cuts through the normal path. Move the plane or re-teach the path, and record the change.
  • RobotStudio features disappear partway through: the Premium trial has ended and the software reverted to Basic mode.[7] Ask about an Education license early.
  • ABB robot will not run after adding SafeMove: the virtual controller does not simulate SafeMove.[17] Remove it and use the programmed stand-in described in section 07.

10. Grading rubric

The rubric uses four levels with no neutral middle, so a grader has to decide whether each expectation was met.[2] It has only five rows to stay simple enough to use.[3] In team projects, the reflection row and the contribution statements are graded per person; the other rows are graded for the team.[1]

Criterion 1 Not acceptable 2 Developing 3 Proficient 4 Exemplary
Functionality Cycle does not complete. Cycle completes but ignores I/O or fails often. Cycle runs reliably and waits for the part-present input. As 3, plus a working error path and safe recovery to Home.
Test evidence No test sheet. Some tests, missing expected results or evidence. All core rows run with expected result written first and evidence filed. As 3, plus added rows from the sequence chart and documented retests after fixes.
Safety No safety configuration. Configuration set, but not tested. Plane and reduced limit set and tested, with observed behaviour recorded. As 3, plus a clear statement of what the simulation cannot prove for a real cell.
Code and documentation Program missing or unreadable. Program runs but has no structure or I/O list. Routines, named signals, I/O list and sequence chart that match the program. As 3, plus a backup that restores cleanly (T09) and a layout another student could follow.
Reflection Missing. Describes what was done, not what was learned. Explains one failure, how it was diagnosed and what changed. As 3, plus a specific plan for what would change in a real cell.

11. Reflection questions and stretch goals

Reflection works best in two sizes: brief and frequent, and more substantial at key milestones.[1] After M1, M2 and M3, write three or four sentences on what went wrong first and how you found it. At M4, answer these questions in about a page:

  • 1. First failure: What failed first, how did you diagnose it, and how long did it take?
  • 2. Plan versus reality: Which part of your M0 sequence chart changed most, and why?
  • 3. Evidence: Which test result would you trust least if someone else had run it, and how would you make it more convincing?
  • 4. Sim to real: List three things that would have to change before this cell could run with a real robot and real people nearby. Use the ideas in 5.4.
  • 5. Next time: What would you do differently if you started again tomorrow?

Stretch goals. Choose one if you finish early. Each one should add at least one row to your test sheet.

  • PLC handshake: add a “cell ready” output and a “start” input that a PLC would use, and write the handshake into your sequence chart (see 1.7).
  • Second part type: use a second input to choose between two place positions.
  • Cycle time study: change blend radii and approach heights and plot cycle time against the change, keeping exact stops at the grip.
  • Control from ROS 2: start URSim with start_ursim.sh, which preinstalls the External Control URCap, and drive the robot from ROS 2.[5] This leads straight into 10.2.
Try it
  1. Before you start: choose Path A or Path B, start the simulator once, and take a screenshot of the robot at its home position. If you choose RobotStudio, write down which license you are on and when it expires.
  2. Create the project folder with plan/, program/ and evidence/, and save the screenshot into evidence/.
  3. Draft your M0 I/O list (at least a gripper output and a part-present input) and a sequence chart of about ten steps, each with its start condition.
  4. Turn two of your start conditions into test rows with an ID, procedure and expected result. You now have the first lines of your FAT sheet.
