4.8 Moving an Arm with MoveIt 2

Gerald Lê

01. From teach-pendant moves to motion planning

In lesson 2.6 you programmed a pick-and-place by hand: a joint move (MoveJ) to get near the part, then a linear move (MoveL) straight down to it. You chose every waypoint and checked by eye that the arm would not hit anything. That gets hard when the target changes every cycle or the cell is crowded.

MoveIt 2 is the standard ROS 2 framework for this problem. You give it a goal for the arm (a joint configuration, a named pose, or a pose for the tool), and it works out the joint angles, checks the motion against a model of the robot and its surroundings for collisions, produces a timed trajectory, and sends that trajectory to the robot's controllers.[1][2] In this lesson you will see what MoveIt needs to know about a robot and how it plans, then run a Universal Robots UR5e on mock hardware, a software stand-in for the robot, and plan motions in RViz with no robot attached.

The course targets ROS 2 Lyrical Luth, the long-term support release from May 2026, supported until May 2031, with Ubuntu 26.04 "Resolute" as its Tier 1 platform.[3] All three pieces used here are released for Lyrical. The UR driver has its own lyrical branch, released as version 6.2.0.[4][5] The UR robot description is built for Lyrical from its rolling branch (version 4.3.1).[5][6] MoveIt itself is released into Lyrical as version 2.15.2 from its main branch; as of October 2026 there is no separate lyrical branch in the MoveIt repository.[5][7] The MoveIt tutorials site still calls Jazzy "the latest stable version," so its docs lag behind the released code.[8]

02. Describing the arm: URDF and xacro

Before anything can plan for a robot, the software needs a model of it. In ROS that model is the URDF (Unified Robot Description Format), an XML file[9] that describes the robot as a tree of links (rigid bodies) connected by joints.[10] Each joint names a parent link and a child link and gives an <origin xyz rpy> that places the child relative to the parent.[11] This is the base-to-tool chain of frames from lesson 1.6 in machine-readable form.

The joint type says how the child can move. A fixed joint does not move at all. A continuous joint spins to any angle and needs only an <axis>. A revolute joint rotates like a continuous one but has strict limits, and a prismatic joint slides along an axis instead of turning around it.[11] Revolute and prismatic joints must carry a <limit> tag with lower and upper bounds (radians for revolute, meters for prismatic) plus a maximum velocity and effort. The ROS 2 tutorial gives this prismatic example:[11] 

<limit effort="1000.0" lower="0.0" upper="0.548" velocity="0.5"/>

The same tutorial shows how a URDF reaches the screen. A joint state publisher reads the movable joints and their limits and publishes sensor_msgs/msg/JointState messages; robot_state_publisher turns the joint values into the tf2 transform tree; and RViz draws the result.[11]

Writing a full URDF by hand for every robot model would mean a lot of repeated XML. Universal Robots avoids this with xacro, the XML macro language used in ROS. Their documentation explains that all UR models have roughly the same kinematics and differ only in meshes, DH parameters and physical parameters, so "the description uses xacro macros in order to make it reuse as much as possible."[12] The file urdf/ur_macro.xacro is the macro that other projects include, and urdf/ur.urdf.xacro is an example scene with the robot standing alone.[12] Each model is configured by four YAML files in config/urXX/: default_kinematics.yaml (calibration values, which you can replace with values extracted from a real robot so the model matches it exactly at tool0), joint_limits.yaml, physical_parameters.yaml (inertias) and visual_parameters.yaml (meshes).[12]

Inside the macro, the six arm joints are shoulder_pan_joint, shoulder_lift_joint, elbow_joint, wrist_1_joint, wrist_2_joint and wrist_3_joint. The first five are revolute, and the type of wrist_3_joint is set by a parameter. Each joint's <limit> is filled in from the YAML files, and a tf_prefix is added in front of every name.[13] For the UR5e, for example, shoulder_pan_joint may turn from -360° to +360° at up to 180°/s. The file sets has_acceleration_limits: false because, in its own words, "acceleration limits are not publicly available"; the values come from the UR5e user manual.[13] If you only want to look at the model, the description package has a viewer launch file:[6] 

ros2 launch ur_description view_ur.launch.xml ur_type:=ur5e

03. The SRDF: what MoveIt adds on top

The URDF says what the robot is: its geometry, kinematics and hard limits. MoveIt also needs to know how to think about the robot. That information lives in a second file, the SRDF (Semantic Robot Description Format). The header comment in UR's SRDF puts it plainly: "This does not replace URDF, and is not an extension of URDF. This is a format for representing semantic information about the robot structure."[14] An SRDF can define planning groups, named group states, end effectors, a virtual joint that fixes the robot to the world, and pairs of links whose collisions can be ignored.[14]

UR's SRDF defines exactly one planning group, called ur_manipulator, as the chain of links from the base to the tool flange:[14] 

<group name="ur_manipulator">
    <chain base_link="base_link" tip_link="tool0"/>
</group>

It also defines three named poses: home (shoulder_lift at -1.5707 rad, all other joints 0), up (shoulder_lift and wrist_1 both at -1.5707 rad) and test_configuration.[14] Two sections of the file are only comments with no elements in them: the end effector and the virtual joint.[14] There is no end effector because the stock UR description has no gripper. That has a direct consequence for this lesson: the "pick" you plan later is an approach motion of tool0 to a pose above and at a part. Nothing opens or closes.

The last part of the SRDF is a list of 11 <disable_collisions> pairs, each marked with a reason of Adjacent or Never. For example, forearm_link and upper_arm_link are adjacent (they are always touching at the elbow), and tool0 and wrist_1_link can never reach each other.[14] MoveIt stores this in its Allowed Collision Matrix (ACM) and skips those checks. That matters for speed: according to the MoveIt docs, collision checking "often account[s] for close to 90% of the computational expense during motion planning."[15]

MoveIt's central node reads the URDF from the robot_description parameter and the SRDF from robot_description_semantic.[1] The SRDF "is typically created (once) by a user using the MoveIt Setup Assistant," covered in section 09.[1] UR ships one already, in the ur_moveit_config package. Its documentation calls this package an example that contains only the arm. For real work, UR recommends building a description of the robot together with its workcell (table, fixtures, objects) and generating your own scenario_moveit_config from it.[16]

04. ros2_control and mock hardware

MoveIt does not talk to motors. It hands a trajectory to a controller, and in ROS 2 the controllers live in the ros2_control framework. The main component of ros2_control is the controller manager, which "manages lifecycle of controllers, access to the hardware interfaces and offers services to the ROS-world."[17] It connects hardware interfaces (plugins that read and write the joints) to controllers (plugins that turn goals into commands). The hardware plugin is declared in a <ros2_control> tag inside the URDF, with each joint listing its <command_interface> and <state_interface> entries (position, velocity, acceleration).[18]

ros2_control also provides mock components, which the documentation describes as "trivial 'simulations' of the hardware components". They "provide ideal behavior by mirroring commands to their states": if a controller commands a joint to 0.5 rad, the mock reports that the joint is now at 0.5 rad.[18] This lets you test the "piping," "and even integrations with, e.g., MoveIt," without a robot.[18] The mock system plugin is selected with <plugin>mock_components/GenericSystem</plugin>.[18]

The UR driver uses this directly. In its ur.ros2_control.xacro, an xacro:if on the argument use_mock_hardware selects mock_components/GenericSystem, and the matching xacro:unless branch selects the real UR hardware plugin.[19] The argument defaults to false, and the URDF also passes in initial joint positions "for simulations (Mock Hardware, Gazebo, Ignition)."[19] The driver's launch file ur_control.launch.py exposes the same switch, described as "Start robot with mock hardware mirroring command to its states."[20] UR's startup guide adds that it is "Useful for testing launch files, descriptions, etc."[21]

Mock hardware is not a physics simulator. Commands simply become states, so the arm can jump to positions instead of accelerating like a real one. UR's simulation page also lists driver features that do not work on mock hardware: the TCP pose broadcaster, the passthrough trajectory controller, force mode, and GPIO verification (setting an I/O pin reports a failure).[22] That is fine for seeing MoveIt plan and send trajectories; timing, contact and I/O need Gazebo, URSim or a real arm.

Watch out for old tutorials. The argument used to be called use_fake_hardware (with fake_sensor_commands). The UR changelogs record the rename as "Use mock_hardware and mock_sensor_commands instead of fake (#739)."[23] On Lyrical, use use_mock_hardware:=true.

Two controllers matter for MoveIt. The joint_trajectory_controller (JTC) executes "joint-space trajectories on a group of joints," interpolating in time between waypoints that hold positions and optional velocities and accelerations. It accepts goals on the action <controller_name>/follow_joint_trajectory of type control_msgs::action::FollowJointTrajectory.[24] On the UR lyrical branch it is configured as joint_trajectory_controller/JointTrajectoryController over the six UR joints, and it is the driver's default initial_joint_controller.[25][20] The joint_state_broadcaster "reads all state interfaces and reports them on /joint_states." It is not a real controller and takes no commands.[26]

Put together, the data flows in a loop: MoveIt sends a goal to the JTC, the JTC commands the mock hardware, the mock copies commands into states, and the joint_state_broadcaster publishes them on /joint_states for MoveIt and robot_state_publisher. Swapping the mock for a real UR changes only the hardware plugin.

05. Inside move_group

MoveIt's central node is move_group. The documentation describes it as "an integrator: pulling all the individual components together to provide a set of ROS actions and services." You reach it from the RViz Motion Planning plugin or from code.[1] It reads three kinds of configuration: the URDF, the SRDF, and the MoveIt configuration files (joint limits, kinematics, planning and perception) from a *_moveit_config package.[1]

move_group depends on the rest of the ROS graph in a few specific ways:[1]

  • Joint states: it listens on /joint_states and does not start its own joint state publisher.[1]
  • Transforms: it only listens to TF, so a robot_state_publisher must be running.[1]
  • Controllers: "move_group talks to the controllers on the robot using the FollowJointTrajectoryAction interface." It creates only the action client; the robot side (here the JTC) must provide the server.[1]
  • Plugins: capabilities such as kinematics, motion planning, and pick and place are pluginlib plugins configured in YAML, usually generated by the Setup Assistant.[1]

This is why the hands-on uses two terminals. The first starts the robot side (driver, ros2_control, controllers, robot_state_publisher); the second starts move_group and RViz.

06. Planning scene, collisions and kinematics

To avoid collisions, move_group keeps a planning scene: "the representation of the world around the robot and also the state of the robot itself." A Planning Scene Monitor keeps it up to date. move_group's monitor listens on /planning_scene and republishes on monitored_planning_scene, which is what the RViz plugin displays.[27] Objects in the world can come from sensors (point clouds and depth images turned into an Octomap) or be added by the user.[27] From code, the "Planning Around Objects" tutorial adds a collision box through the PlanningSceneInterface with the operation ADD.[28]

Collision checks are done with the FCL library, which handles meshes (.stl, .dae), primitive shapes (box, cylinder, cone, sphere, plane) and Octomaps, with the ACM from the SRDF turning off checks for listed pairs.[15] By default every motion plan request is checked for collisions "(including self-collisions and attached objects)," and a request can add position, orientation, visibility and joint constraints.[2]

The other half of planning is kinematics. Forward kinematics (joint angles to tool pose) and Jacobians are computed by MoveIt's RobotState. Inverse kinematics (tool pose to joint angles, see 1.6) is a plugin, and the default is "the KDL numerical Jacobian-based solver."[15] UR's config uses exactly that for the ur_manipulator group: kdl_kinematics_plugin/KDLKinematicsPlugin with a search resolution of 0.005 and a timeout of 0.005 s.[29] A pose outside the arm's reach simply has no solution, which you will try in RViz.

07. Choosing a planner: OMPL or Pilz

Planners plug into MoveIt through a common interface. The Setup Assistant configures OMPL (the Open Motion Planning Library) as the default, and "other planners that are available by default are the Pilz industrial motion planner and CHOMP." You pick one with the planning_pipeline and planner_id parameters.[2] UR's config package ships settings for all three.[29]

OMPL "primarily implements randomized motion planners" and "has no concept of a robot"; MoveIt supplies the robot model and collision checks.[2] A randomized planner searches for some path that avoids obstacles. It handles clutter well but promises nothing about the shape of the tool path, and two plans to the same goal can differ.

The Pilz industrial motion planner works the way a teach pendant does. It "provides a trajectory generator to plan standard robot motions like point-to-point, linear, and circular," selected with the planner_id "PTP", "LIN" or "CIRC".[30] These map onto the moves you programmed in Chapter 2:

Pilz plannerWhat it doesPendant equivalent
PTP"Fully synchronized point-to-point trajectories with trapezoidal joint velocity profiles." The slowest axis leads and the others are slowed so all finish together. The goal can be in joint or Cartesian space.[30]MoveJ
LIN"A linear Cartesian trajectory between goal and start poses," with a trapezoidal speed profile in Cartesian space.[30]MoveL
CIRCA circular arc in Cartesian space, defined by a center point (always the shorter arc, so no half circle) or an interim point the tool passes through (no full circle).[30]MoveC

Pilz limits come from two places. The joint_limits.yaml in the MoveIt config overrides the URDF limits, and acceleration limits can only be set there. Cartesian limits for LIN and CIRC (max_trans_vel, max_trans_acc, max_trans_dec, max_rot_vel) go in pilz_cartesian_limits.yaml.[30] UR's file sets a maximum translational velocity of 1.0, acceleration of 2.25, deceleration of -5.0 and rotational velocity of 1.57, and its Pilz pipeline uses PTP as the default planner.[29] Pilz can also chain moves into a MotionSequenceRequest with a blend_radius, so the tool rounds a corner instead of stopping, much like a zone or blend on an industrial controller. If any command in a sequence fails to plan, none are executed.[30]

A simple rule for a pick: use OMPL or PTP to get to a safe pose above the part when you care about avoiding obstacles more than the path shape, and use LIN for the short final approach, where the tool must travel straight down. That is the same MoveJ-then-MoveL pattern from 2.6.

08. From path to trajectory to execution

A planner first finds a path, a list of joint configurations. A robot needs a trajectory, which adds timing, velocity and acceleration to every point. MoveIt's output "is a trajectory and not just a path."[2] Planning request adapters do the work around the planner. Before planning, they move a start state that is slightly outside the joint limits back onto the limit (CheckStartStateBounds) and fill in a default 10 m cube as the workspace when the request does not give one (ValidateWorkspaceBounds). They also find a nearby collision-free start state if the given one is in collision (CheckStartStateCollision) and resolve constraint frames (ResolveConstraintFrames). After planning, time parameterization turns the path into a trajectory that respects velocity and acceleration limits.[2] UR's OMPL pipeline uses those four request adapters plus the response adapters AddTimeOptimalParameterization, ValidateSolution and DisplayMotionPath.[29]

Execution is set in moveit_controllers.yaml. UR's file uses moveit_simple_controller_manager/MoveItSimpleControllerManager with one controller, joint_trajectory_controller, reached through the action namespace follow_joint_trajectory with type FollowJointTrajectory over the six joints.[29] It also sets allowed_start_tolerance: 0.01 and turns execution_duration_monitoring off.[29] The UR docs explain that a real UR can run slower than planned because of speed scaling, and that monitoring "will in most cases unnecessarily (and unexpectedly) abort goals."[16] They also make a useful distinction about limits: "the URDF describes the hardware's limits, while the moveit_config provides limits on an application / planning level."[16]

09. The Setup Assistant and the code interfaces

Where do the SRDF and all these YAML files come from for a new robot? The MoveIt Setup Assistant is a graphical wizard that reads a URDF and generates a *_moveit_config package. You start it with ros2 launch moveit_setup_assistant setup_assistant.launch.py.[31] Its panes step through the self-collision matrix, virtual joints, planning groups (with the KDL kinematics plugin), named poses, end effectors (needed to attach objects for pick and place), ros2_control and MoveIt controllers, and launch files, then generate the package.[31] You do not need it for the bare UR, but you would after adding a gripper or table to your workcell description.[16]

Everything you do in RViz can also be done from code. C++ programs use MoveGroupInterface, for example setPoseTarget(target_pose), with PlanningSceneInterface for collision objects.[28] Python programs use MoveItPy. The documented pattern is: create a MoveItPy object, get a planning component for a group, set the start state to the current state, set a goal (a named configuration, a robot state, or a pose for a link), call plan(), and pass the resulting trajectory to execute().[32] Planning parameters can select a pipeline and planner per request, for example planning_pipeline: pilz_industrial_motion_planner with planner_id: "PTP".[32] Adapted to the UR group names, the core looks like this. It is an untested example; running it needs a MoveItPy parameter file and launch file that UR does not ship, so treat it as an extension and test it in simulation first. 

from moveit.planning import MoveItPy

robot = MoveItPy(node_name="moveit_py")
arm = robot.get_planning_component("ur_manipulator")

arm.set_start_state_to_current_state()
arm.set_goal_state(configuration_name="home")   # named pose from the SRDF

plan_result = arm.plan()
if plan_result:
    robot.execute(plan_result.trajectory, controllers=[])

10. Launching a UR5e on mock hardware

The UR README installs the driver with the ur meta-package (its example is sudo apt-get install ros-rolling-ur), which bundles ur_robot_driver, ur_controllers, ur_moveit_config, ur_calibration and ur_dashboard_msgs.[4] The Lyrical release lists the same packages at version 6.2.0, so on Lyrical the package should be ros-lyrical-ur.[5] 

sudo apt update
sudo apt install ros-lyrical-ur

UR documents starting the driver on mock hardware with ur_type, a placeholder robot_ip and use_mock_hardware:=true.[33] The robot_ip argument is required even with mock hardware, because the launch file declares it with no default; any address works.[20] The driver's launch file opens its own RViz by default (launch_rviz is true), so this lesson adds launch_rviz:=false to avoid two RViz windows.[20] MoveIt is then started with ur_moveit.launch.py, which UR documents for "real hardware, URSim or mocked hardware."[16] It waits for the robot description, then starts move_group and RViz.[34] 

# Terminal 1: driver on mock hardware (no robot needed; the IP is a placeholder)
ros2 launch ur_robot_driver ur_control.launch.py ur_type:=ur5e robot_ip:=192.168.56.101 \
  use_mock_hardware:=true launch_rviz:=false

# Terminal 2: MoveIt and RViz with the MotionPlanning plugin
ros2 launch ur_moveit_config ur_moveit.launch.py ur_type:=ur5e launch_rviz:=true

# Optional, in a third terminal: check that the controllers are active
ros2 control list_controllers

These commands were put together from the UR and MoveIt documentation for this lesson and were not run while researching it, so test them on your own Lyrical install before class. Use the same ur_type in both terminals. If MoveIt cannot execute, check the controllers first: ros2 control list_controllers should list joint_trajectory_controller as active, and UR's smoke test ros2 launch ur_robot_driver test_joint_trajectory_controller.launch.py moves the arm without MoveIt. UR warns that "the robot should move (or jump when using emulation)."[33]

In RViz, the Motion Planning panel is the tool UR points to for using MoveIt with its arms.[33] The robot model shows the start state in green and the goal state in orange, and you drag the goal with an interactive marker; if no marker appears, press Interact in the toolbar.[35] Links in collision turn red. With "Use Collision-Aware IK" checked, the IK solver keeps searching for a collision-free solution as you drag.[35] In the Planning tab, Plan computes a trajectory, "Show Trail" draws it, and Execute (or Plan & Execute) sends it to the robot. "Use Cartesian Path" makes the tool move in a straight line. Velocity and acceleration scaling both default to 10% (0.1).[35] The "Trajectory - Trajectory Slider" panel (Panels menu) steps through the waypoints.[35]

Try it
  1. Start the two terminals from section 10 (test the commands on your install first; they were not run for this lesson). In RViz, open the MotionPlanning panel, set the Planning Group to ur_manipulator and the Start State to <current>. Run ros2 control list_controllers and confirm joint_trajectory_controller and joint_state_broadcaster are active.
  2. Pick a "part" location on the floor in front of the robot. Set the Goal State to up, then drag the orange marker to a pre-grasp pose about 10 cm above that spot with the tool pointing down. Press Plan, watch the trail, then Execute. Remember there is no gripper in the stock description: you are moving tool0, not grasping anything.
  3. Return to up, plan the same pre-grasp goal twice more with the default OMPL planner, and compare the trails. Then, if your Planning tab lists the pilz_industrial_motion_planner pipeline, choose it with planner PTP and plan again. Which one behaves like the MoveJ from 2.6?
  4. From the pre-grasp pose, drag the marker straight down 10 cm to the grasp pose. Plan once with Pilz LIN (or OMPL with "Use Cartesian Path" checked) and once with PTP. Use the Trajectory Slider to see which keeps the tool on a straight vertical line. This is your MoveL approach.
  5. Drag the marker far outside the arm's reach and press Plan. Explain what happens using what you learned about numerical IK.
  6. Raise the velocity scaling from 0.1 to 0.5 and execute again. On mock hardware the motion has no physics; write one sentence on what you would need to test next before running this on a real UR5e.
