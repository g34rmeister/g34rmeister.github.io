      4.8 Moving an Arm with MoveIt 2

      Gerald Lê
      Chapter 4, lesson 8 of 10 ← Previous: 4.7 Launch Files and Parameters Next: 4.9 ROS-Industrial and Vendor Drivers →

      01. From teach-pendant moves to motion planning

      Imagine teaching a factory arm to pick up a part. On a quiet bench, you can guide the arm point by point and check by eye that it clears every fixture. Once the part lands in a new spot every cycle, or the cell gets crowded, hand-coding every path breaks down. You need software that finds a safe path on its own.

      In lesson 2.6, you programmed a pick-and-place by hand. You used a joint move (MoveJ) to get near the part, then a linear move (MoveL) straight down to it. You chose every waypoint yourself and checked collisions by eye.

      In Robot Operating System 2 (ROS 2), MoveIt 2 solves that planning problem for you. You give it a goal for the arm, such as joint angles, a saved pose, or a target pose for the tool. MoveIt works out the joint angles to reach that goal. It also checks the path against a 3D model of the robot and its surroundings so nothing collides. Then it builds a timed trajectory and sends it to the robot’s controllers.[1][2]

      In this lesson, you will see what MoveIt needs to know about a robot and how it plans. Then you will run a Universal Robots (UR) UR5e arm on mock hardware, a software stand-in for the robot. You will plan motions in RViz, the 3D visualizer for ROS, with no physical robot attached.

      This course targets ROS 2 Lyrical Luth, the long-term support release from May 2026.[3] All of the UR and MoveIt packages in this lesson are released for Lyrical.

      For the curious: ROS 2 Lyrical Luth support dates, package versions, and branches

      ROS 2 Lyrical Luth is supported until May 2031, with Ubuntu 26.04 “Resolute” as its Tier 1 platform.[3] The UR driver has its own lyrical branch, released as version 6.2.0.[4][5] The UR robot description is built for Lyrical from its rolling branch (version 4.3.1).[5][6]

      MoveIt itself is released into Lyrical as version 2.15.2 from its main branch. As of October 2026, there is no separate lyrical branch in the MoveIt repository.[5][7] The MoveIt tutorials site still calls Jazzy “the latest stable version,” so its docs lag behind the released code.[8]

      02. Building the arm model: URDF and xacro

      Before software can plan a safe move for the UR5e arm, it needs a digital model of the robot. It has to know how long each segment is, where each joint bends, and how far each joint may turn. Without that model, MoveIt could drive the arm into a wall or try to twist a joint past its mechanical stop.

      In ROS, that model lives in a URDF (Unified Robot Description Format) file. It is an Extensible Markup Language (XML) file[9] that describes the robot as a tree of rigid bodies called links connected by joints.[10] Each joint names a parent link and a child link. It also gives an <origin xyz rpy> tag that places and rotates the child relative to the parent.[11] This puts the base-to-tool chain of frames from lesson 1.6 into a file software can read.

      Each joint’s type says how the child link can move:[11]

      • fixed: does not move at all.
      • continuous: spins freely to any angle and needs only an <axis>.
      • revolute: rotates like a continuous joint, but stops at strict angle limits.
      • prismatic: slides along an axis instead of turning around it.

      Revolute and prismatic joints must also carry a <limit> tag. It sets lower and upper bounds (radians for revolute, meters for prismatic), plus a maximum velocity and effort. The ROS 2 tutorial gives this prismatic example:[11] 

      <limit effort="1000.0" lower="0.0" upper="0.548" velocity="0.5"/>

      Three parts work together to turn that URDF into a 3D robot on your screen. First, a joint state publisher reads the movable joints and their limits and publishes sensor_msgs/msg/JointState messages. Next, robot_state_publisher turns those joint values into the tf2 transform tree. Finally, RViz draws the result.[11]

      Writing a full URDF by hand for every robot model would repeat a lot of XML. Universal Robots avoids this with xacro, the XML macro language used in ROS. Their documentation explains that all UR models share roughly the same kinematics, so “the description uses xacro macros in order to make it reuse as much as possible.”[12] Each model swaps in its own YAML (a plain-text settings format) files for dimensions, joint limits, inertias, and 3D meshes.[12]

      Inside the UR macro, the six arm joints are shoulder_pan_joint, shoulder_lift_joint, elbow_joint, wrist_1_joint, wrist_2_joint, and wrist_3_joint. For the UR5e, for example, shoulder_pan_joint can turn from -360° to +360° at up to 180°/s.[13] If you only want to look at the 3D model, the description package includes a viewer launch file:[6] 

      ros2 launch ur_description view_ur.launch.xml ur_type:=ur5e
      For the curious: UR xacro files, YAML calibration files, and joint limit details

      UR models differ only in their meshes, Denavit-Hartenberg (DH) parameters, and physical parameters. The file urdf/ur_macro.xacro is the macro that other projects include, and urdf/ur.urdf.xacro is an example scene with the robot standing alone.[12]

      Each model is configured by four YAML files in config/urXX/: default_kinematics.yaml (calibration values you can replace with values extracted from a real robot so the model matches it exactly at tool0), joint_limits.yaml, physical_parameters.yaml (inertias), and visual_parameters.yaml (meshes).[12]

      In the macro, the first five joints are revolute, and the type of wrist_3_joint is set by a parameter. Each joint’s <limit> is filled in from the YAML files, and a tf_prefix is added in front of every name. For the UR5e, the file sets has_acceleration_limits: false because, in its own words, “acceleration limits are not publicly available.” The values come from the UR5e user manual.[13]

      03. Teaching MoveIt how the arm is grouped: the SRDF

      A URDF tells ROS the shape of each link and how each joint moves, but it does not say which joints work together as an arm. Imagine a robot with an arm, a gripper, and a wheeled base. MoveIt needs to know which chain of joints to plan for, which saved poses are safe, and which neighboring parts always touch so it does not flag them as collisions.

      That extra knowledge lives in a second file called the SRDF (Semantic Robot Description Format). In everyday words, it adds MoveIt rules on top of the physical model without replacing the URDF. The header comment in UR’s SRDF puts it plainly: “This does not replace URDF, and is not an extension of URDF. This is a format for representing semantic information about the robot structure.”[14] An SRDF can define planning groups, named group states, and end effectors. It can also add a virtual joint fixing the robot to the world, plus pairs of links whose collisions can be ignored.[14]

      UR’s SRDF defines one planning group, called ur_manipulator, as the chain of links from the base to the tool flange:[14] 

      <group name="ur_manipulator">
    <chain base_link="base_link" tip_link="tool0"/>
</group>

      It also defines three named poses: home, up, and test_configuration.[14] Because the stock UR description has no gripper, the end-effector section has no elements. That affects the exercise later in this lesson: the “pick” you plan is an approach motion of tool0 to a pose above and at a part. Nothing opens or closes.[14]

      Links that touch at a joint or can never reach each other are listed in the SRDF as disabled collision pairs.[14] MoveIt stores them in its Allowed Collision Matrix (ACM) and skips checking those pairs. That matters for speed, because MoveIt’s docs note that collision checking “often account[s] for close to 90% of the computational expense during motion planning.”[15]

      An SRDF “is typically created (once) by a user using the MoveIt Setup Assistant,” covered in section 09.[1] UR ships one already in the ur_moveit_config package. Its documentation calls this package an example that contains only the arm. For real work, UR recommends describing the robot together with its workcell (table, fixtures, and objects) and generating your own scenario_moveit_config from it.[16]

      For the curious: UR SRDF pose angles, collision-pair reasons, and ROS parameters

      In UR’s SRDF, home sets shoulder_lift to -1.5707 rad and all other joints to 0, while up sets both shoulder_lift and wrist_1 to -1.5707 rad. Both the end-effector and virtual-joint sections contain only comments with no elements.[14]

      The SRDF lists 11 <disable_collisions> pairs, each marked with a reason of Adjacent or Never. For example, forearm_link and upper_arm_link are adjacent (they always touch at the elbow), and tool0 and wrist_1_link can never reach each other.[14]

      MoveIt’s central node reads the URDF from the robot_description parameter and the SRDF from robot_description_semantic.[1]

      04. Testing motions safely with ros2_control and mock hardware

      MoveIt plans where the arm should go, but it never talks to motors directly. Instead, it hands each trajectory to a controller, much like a navigation app hands driving directions to a driver. Before you run code on a real steel arm, you can plug in a software stand-in called mock hardware and test your whole pipeline safely on a laptop.

      In ROS 2, those controllers live in the ros2_control framework. Its main piece is the controller manager. In everyday words, it manages controllers, links them to hardware, and exposes ROS services; the docs say it “manages lifecycle of controllers, access to the hardware interfaces and offers services to the ROS-world.”[17] It connects hardware interfaces (plugins that read and write joints) to controllers (plugins that turn goals into commands).[18]

      Without a physical robot, ros2_control gives you mock components. The documentation calls them “trivial ‘simulations’ of the hardware components” that “provide ideal behavior by mirroring commands to their states.” If a controller commands a joint to 0.5 rad, the mock reports that the joint is now at 0.5 rad. That lets you test the “piping,” “and even integrations with, e.g., MoveIt,” with no robot attached.[18]

      The UR driver uses this through the launch option use_mock_hardware, which defaults to false for a real arm.[19] Setting use_mock_hardware:=true tells ur_control.launch.py to “Start robot with mock hardware mirroring command to its states.”[20] UR’s startup guide notes that it is “Useful for testing launch files, descriptions, etc.”[21]

      Remember that mock hardware is not a physics simulator. Commands simply become states, so the arm can jump to positions instead of accelerating like a real one. Several UR driver features also do not work on mock hardware: the Tool Center Point (TCP) pose broadcaster, the passthrough trajectory controller, force mode, and General-Purpose Input/Output (GPIO) verification (setting an input/output (I/O) pin reports a failure).[22] That is fine for watching MoveIt plan and send paths. However, timing, contact, and I/O still need Gazebo, URSim (Universal Robots’ simulator), or a real arm.

      Watch out for old tutorials. The switch used to be called use_fake_hardware (along with fake_sensor_commands). The UR changelogs record the rename as “Use mock_hardware and mock_sensor_commands instead of fake (#739).”[23] On Lyrical, use use_mock_hardware:=true.

      Two controllers matter for MoveIt. First, the joint_trajectory_controller (JTC) runs “joint-space trajectories on a group of joints,” interpolating in time between waypoints that hold positions and optional velocities and accelerations.[24] On the UR lyrical branch, it controls the six UR joints and acts as the driver’s default initial_joint_controller.[25][20] Second, the joint_state_broadcaster “reads all state interfaces and reports them on /joint_states.” It is not a real controller and takes no commands.[26]

      Put together, the data flows in a loop. MoveIt sends a goal to the JTC, and the JTC commands the mock hardware. Next, the mock copies commands into states. Finally, the joint_state_broadcaster publishes them on /joint_states for MoveIt and robot_state_publisher.

      For the curious: URDF hardware tags, xacro switching, and JTC action details

      In the URDF, the hardware plugin is declared inside a <ros2_control> tag, with each joint listing its <command_interface> and <state_interface> entries (position, velocity, acceleration). The mock system plugin is selected with <plugin>mock_components/GenericSystem</plugin>.[18]

      In UR’s ur.ros2_control.xacro, an xacro:if on use_mock_hardware picks mock_components/GenericSystem, and the matching xacro:unless branch picks the real UR hardware plugin. The URDF also passes initial joint positions “for simulations (Mock Hardware, Gazebo, Ignition).”[19]

      The JTC accepts goals on the action <controller_name>/follow_joint_trajectory of type control_msgs::action::FollowJointTrajectory.[24] On the UR lyrical branch, it is configured as joint_trajectory_controller/JointTrajectoryController.[25]

      05. How move_group connects everything

      You now have an arm model, collision rules, and a joint controller. Something still needs to pull those pieces together so you can drag a goal in RViz and watch the arm move. In MoveIt 2, one central node handles that job.

      That central node is move_group. In everyday words, it acts as the hub that listens to the robot, computes plans, and sends trajectories to the controller. The docs describe it as “an integrator: pulling all the individual components together to provide a set of ROS actions and services.” You reach it from the RViz Motion Planning plugin or from code.[1] It reads three kinds of configuration: the URDF, the SRDF, and the MoveIt files (joint limits, kinematics, planning, and perception) from a *_moveit_config package.[1]

      move_group depends on the rest of the ROS graph in four ways:[1]

      • Joint states: it listens on /joint_states and does not start its own joint state publisher.[1]
      • Transforms: it only listens to TF (the transform tree), so a robot_state_publisher must be running.[1]
      • Controllers: “move_group talks to the controllers on the robot using the FollowJointTrajectoryAction interface.” It creates only the action client, so the robot side (here the JTC) must provide the server.[1]
      • Plugins: capabilities such as kinematics, motion planning, and pick and place are pluginlib plugins configured in YAML, usually generated by the Setup Assistant.[1]

      This is why the hands-on uses two terminals. The first starts the robot side (driver, ros2_control, controllers, and robot_state_publisher). The second starts move_group and RViz.

      06. Avoiding obstacles and solving joint angles

      Planning a move solves two problems at once. First, the arm must not hit a table, a fixture, or itself along the way. Second, you usually specify where the tool should go in 3D space, so MoveIt must find the six joint angles that place it there.

      To avoid collisions, move_group keeps a planning scene. In everyday words, it is a live 3D map of the robot and nearby obstacles; the docs define it as “the representation of the world around the robot and also the state of the robot itself.” A Planning Scene Monitor keeps it current and sends updates to RViz.[27] Objects in the world can come from sensors or be added by the user.[27]

      MoveIt checks collisions using the Flexible Collision Library (FCL). It tests meshes and primitive shapes (box, cylinder, cone, sphere, plane) while skipping pairs listed in the ACM.[15] By default, every motion plan request is checked for collisions “(including self-collisions and attached objects).” A request can also add position, orientation, visibility, and joint constraints.[2]

      The other half of planning is kinematics. Forward kinematics turns joint angles into a tool pose. Inverse kinematics (IK) goes the other way, turning a target tool pose into joint angles (see lesson 1.6). In MoveIt, IK is a plugin. The default is the Kinematics and Dynamics Library (KDL) solver, described in the docs as “the KDL numerical Jacobian-based solver.”[15] A pose outside the arm’s reach has no solution, which you will try in RViz.

      For the curious: scene topics, adding boxes in code, FCL formats, and UR’s KDL settings

      move_group’s Planning Scene Monitor listens on /planning_scene and republishes on monitored_planning_scene, which is what the RViz plugin displays. Sensor inputs such as point clouds and depth images are turned into an Octomap.[27] From code, the “Planning Around Objects” tutorial adds a collision box through the PlanningSceneInterface with the operation ADD.[28]

      FCL handles .stl and .dae meshes as well as primitive shapes and Octomaps.[15] Forward kinematics and Jacobians are computed by MoveIt’s RobotState.[15] UR’s config for the ur_manipulator group uses kdl_kinematics_plugin/KDLKinematicsPlugin with a search resolution of 0.005 and a timeout of 0.005 s.[29]

      07. Choosing how the arm moves: OMPL or Pilz

      Knowing where the arm should end up is not enough. You also choose how it travels there. Sometimes you just want the arm to weave around obstacles any way it can, while other times the tool must move in a straight line onto a part. MoveIt supports both styles through pluggable planners.

      The Setup Assistant sets OMPL (the Open Motion Planning Library) as the default planner. The docs note that “other planners that are available by default are the Pilz industrial motion planner and CHOMP.”[2] Universal Robots ships settings for all three in its config package.[29]

      OMPL “primarily implements randomized motion planners” and “has no concept of a robot”; MoveIt supplies the robot model and collision checks.[2] Because it searches randomly, OMPL handles cluttered spaces well. However, it promises nothing about the shape of the tool path, and two plans to the same goal can differ.

      The Pilz industrial motion planner works the way a teach pendant does. It “provides a trajectory generator to plan standard robot motions like point-to-point, linear, and circular,” selected with planner_id set to "PTP", "LIN", or "CIRC".[30] These map directly onto the moves you programmed in Chapter 2:

      Pilz plannerWhat it doesPendant equivalent
      PTP“Fully synchronized point-to-point trajectories with trapezoidal joint velocity profiles.” The slowest axis leads, and the others slow down so all finish together. The goal can be in joint or Cartesian space.[30]MoveJ
      LIN“A linear Cartesian trajectory between goal and start poses,” with a trapezoidal speed profile in Cartesian space.[30]MoveL
      CIRCA circular arc in Cartesian space, defined by a center point (always the shorter arc, so no half circle) or an interim point the tool passes through (no full circle).[30]MoveC

      Here is a simple rule for a pick. Use OMPL or PTP to get to a safe pose above the part when avoiding obstacles matters more than path shape. Then use LIN for the short final approach, where the tool must travel straight down. That is the same MoveJ-then-MoveL pattern from lesson 2.6.

      For the curious: selecting planners, Pilz speed limits, and blended sequences

      You select a planner in MoveIt using the planning_pipeline and planner_id parameters.[2]

      Pilz limits come from two places. The joint_limits.yaml file in the MoveIt config overrides the URDF limits, and acceleration limits can only be set there. Cartesian limits for LIN and CIRC (max_trans_vel, max_trans_acc, max_trans_dec, max_rot_vel) go in pilz_cartesian_limits.yaml.[30] UR’s file sets a maximum translational velocity of 1.0, acceleration of 2.25, deceleration of -5.0, and rotational velocity of 1.57, and its Pilz pipeline uses PTP as the default planner.[29]

      Pilz can also chain moves into a MotionSequenceRequest with a blend_radius. That lets the tool round a corner instead of stopping, much like a zone or blend on an industrial controller. If any command in a sequence fails to plan, none are executed.[30]

      08. Turning a path into timed robot motion

      A planner gives you a list of joint positions, like pins along a trail. Before motors can follow that trail, the robot also needs timing so it moves smoothly without breaking speed or acceleration limits. MoveIt runs extra helper steps around the planner to turn raw waypoints into a timed trajectory.

      A planner first finds a path, a list of joint configurations. A robot needs a trajectory, which adds timing, velocity, and acceleration to every point. MoveIt’s output “is a trajectory and not just a path.”[2]

      Planning request adapters handle the cleanup before and after planning. Before planning, they nudge a start state that is slightly outside joint limits or touching an obstacle, set a default 10 m cube workspace if none was given, and resolve constraint frames. After planning, time parameterization turns the path into a trajectory that respects velocity and acceleration limits.[2]

      Once timed, the trajectory goes to the joint_trajectory_controller defined in MoveIt’s controller configuration.[29] UR’s documentation also highlights a clear split between hardware and planning limits: “the URDF describes the hardware’s limits, while the moveit_config provides limits on an application / planning level.”[16] That means you can cap planning speeds for a cautious move without changing the robot’s physical URDF.

      The MoveIt 2 pipeline explorer needs JavaScript. With it on, you can inspect each stage from URDF/xacro to hardware, switch between OMPL and Pilz planners, and compare mock hardware with a real arm.

      For the curious: exact planning adapters and UR controller settings

      Before planning, the four planning request adapters are CheckStartStateBounds (moves a start state slightly outside joint limits back onto the limit), ValidateWorkspaceBounds (fills in a default 10 m cube workspace when the request omits one), CheckStartStateCollision (finds a nearby collision-free start state if the given one is in collision), and ResolveConstraintFrames. After planning, UR’s OMPL pipeline runs the response adapters AddTimeOptimalParameterization, ValidateSolution, and DisplayMotionPath.[2][29]

      Execution is configured in moveit_controllers.yaml. UR’s file uses moveit_simple_controller_manager/MoveItSimpleControllerManager with one controller, joint_trajectory_controller, reached through the action namespace follow_joint_trajectory with type FollowJointTrajectory over the six joints.[29]

      It also sets allowed_start_tolerance: 0.01 and turns execution_duration_monitoring off.[29] The UR docs explain that a real UR arm can run slower than planned because of speed scaling, and that monitoring “will in most cases unnecessarily (and unexpectedly) abort goals.”[16]

      09. Setting up a new robot and planning from code

      Dragging markers in RViz works well for testing, and Universal Robots already ships config files for a bare UR5e. Once you bolt a gripper onto the flange, add a table, or want a script to run picks on its own, you need two more tools. One wizard generates config files for your custom cell, and a code interface lets your own programs request plans.

      For a new robot or workcell, the MoveIt Setup Assistant builds the SRDF and YAML files for you. It is a graphical wizard that reads a URDF and generates a *_moveit_config package. You start it with ros2 launch moveit_setup_assistant setup_assistant.launch.py.[31] You do not need it for the bare UR arm, but you will use it after adding a gripper or table to your workcell description.[16]

      Everything you do in RViz can also be done from code. C++ programs use MoveGroupInterface to command the arm and PlanningSceneInterface to add or remove collision objects.[28] Python programs use MoveItPy. You create a MoveItPy object, get the planning component for a group, set the start state to the current state, and set a goal. Then you call plan() and pass the resulting trajectory to execute().[32]

      Adapted to the UR group names, the core Python code looks like this. Treat it as an untested extension and test it in simulation first, because running it needs a MoveItPy parameter file and launch file that UR does not ship. 

      from moveit.planning import MoveItPy

robot = MoveItPy(node_name="moveit_py")
arm = robot.get_planning_component("ur_manipulator")

arm.set_start_state_to_current_state()
arm.set_goal_state(configuration_name="home")   # named pose from the SRDF

plan_result = arm.plan()
if plan_result:
    robot.execute(plan_result.trajectory, controllers=[])
      For the curious: Setup Assistant panes and code-level planner options

      The Setup Assistant’s panes step through the self-collision matrix, virtual joints, and planning groups (with the KDL kinematics plugin). You then configure named poses, end effectors (needed to attach objects for pick and place), ros2_control and MoveIt controllers, and launch files before generating the package.[31]

      In C++, you can set a pose goal with calls like setPoseTarget(target_pose).[28] In MoveItPy, a goal can be a named configuration, a robot state, or a pose for a link. Planning parameters can also pick a pipeline and planner per request, such as planning_pipeline: pilz_industrial_motion_planner with planner_id: "PTP".[32]

      10. Launching a UR5e on mock hardware

      Now you can put every piece together and move a virtual UR5e arm in RViz. With mock hardware turned on, one terminal runs the robot driver and controllers while a second terminal starts MoveIt and the 3D viewer. You get to drag the arm to new goals and test both planners without needing a real robot.

      First, install the UR driver meta-package. The UR README installs the ur meta-package, which bundles five UR packages into one install.[4] The Lyrical release lists those same packages at version 6.2.0, so on Lyrical the package should be ros-lyrical-ur:[5] 

      sudo apt update
sudo apt install ros-lyrical-ur

      UR documents starting the driver on mock hardware with ur_type, a placeholder robot_ip, and use_mock_hardware:=true.[33] Even with mock hardware, you must pass an Internet Protocol (IP) address for robot_ip because the launch file declares it with no default, though any address works.[20] The driver’s launch file opens its own RViz by default (launch_rviz is true), so adding launch_rviz:=false avoids two RViz windows.[20] MoveIt then starts with ur_moveit.launch.py, which UR documents for “real hardware, URSim or mocked hardware.”[16] It waits for the robot description, then starts move_group and RViz:[34] 

      # Terminal 1: driver on mock hardware (no robot needed; the IP is a placeholder)
ros2 launch ur_robot_driver ur_control.launch.py ur_type:=ur5e robot_ip:=192.168.56.101 \
  use_mock_hardware:=true launch_rviz:=false

# Terminal 2: MoveIt and RViz with the MotionPlanning plugin
ros2 launch ur_moveit_config ur_moveit.launch.py ur_type:=ur5e launch_rviz:=true

# Optional, in a third terminal: check that the controllers are active
ros2 control list_controllers

      These commands were put together from the UR and MoveIt documentation for this lesson and were not run while researching it, so test them on your own Lyrical install before class. Use the same ur_type in both terminals. If MoveIt cannot execute, check ros2 control list_controllers to confirm joint_trajectory_controller is active. You can also run UR’s smoke test ros2 launch ur_robot_driver test_joint_trajectory_controller.launch.py to move the arm without MoveIt, though UR warns that “the robot should move (or jump when using emulation).”[33]

      In RViz, UR points you to the Motion Planning panel to drive its arms.[33] The 3D model shows the start state in green and the goal state in orange. Drag the goal with the interactive marker, or click Interact in the toolbar if no marker appears.[35] Colliding links turn red, and checking “Use Collision-Aware IK” tells the IK solver to keep searching for a collision-free pose as you drag.[35]

      In the Planning tab, click Plan to compute a trajectory and “Show Trail” to draw it. Click Execute (or Plan & Execute) to send it to the mock arm. Check “Use Cartesian Path” when you want the tool to move in a straight line. Velocity and acceleration scaling both default to 10% (0.1), and the “Trajectory - Trajectory Slider” panel (under the Panels menu) lets you step through the waypoints.[35]

      For the curious: bundled packages in the UR meta-package

      On ROS 2 Rolling, the UR README installs the meta-package with sudo apt-get install ros-rolling-ur. That meta-package bundles five packages: ur_robot_driver, ur_controllers, ur_moveit_config, ur_calibration, and ur_dashboard_msgs.[4]

      Try it
      1. Start the two terminals from section 10 (test the commands on your install first, because they were not run for this lesson). In RViz, open the MotionPlanning panel, set the Planning Group to ur_manipulator, and set the Start State to <current>. Run ros2 control list_controllers and confirm joint_trajectory_controller and joint_state_broadcaster are active.
      2. Pick a “part” location on the floor in front of the robot. Set the Goal State to up, then drag the orange marker to a pre-grasp pose about 10 cm above that spot with the tool pointing down. Press Plan, watch the trail, then Execute. Remember there is no gripper in the stock description: you are moving tool0, not grasping anything.
      3. Return to up, plan the same pre-grasp goal twice more with the default OMPL planner, and compare the trails. Then, if your Planning tab lists the pilz_industrial_motion_planner pipeline, choose it with planner PTP and plan again. Which one behaves like the MoveJ from lesson 2.6?
      4. From the pre-grasp pose, drag the marker straight down 10 cm to the grasp pose. Plan once with Pilz LIN (or OMPL with “Use Cartesian Path” checked) and once with PTP. Use the Trajectory Slider to see which keeps the tool on a straight vertical line. This is your MoveL approach.
      5. Drag the marker far outside the arm’s reach and press Plan. Explain what happens using what you learned about numerical IK.
      6. Raise the velocity scaling from 0.1 to 0.5 and execute again. Because mock hardware has no physics, write one sentence on what you would need to test next before running this on a real UR5e.
