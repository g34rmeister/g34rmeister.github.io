8.5 From the Plant Floor to IT

Gerald Lê

01. The industrial communication hierarchy: bridging OT and IT

A factory has two kinds of networks. Operational technology (OT) runs the machines: the PLC, robot and I/O networks from 8.1 to 8.4. Information technology (IT) runs the business systems that plan production and store records.

IT systems need data from the machines, such as part counts, alarms and machine health, but they must not disturb the time-critical traffic on the machine networks.

This lesson covers four technologies that sit at different levels: IO-Link at the sensor, OPC UA and MQTT for getting machine data to IT systems, and ROS 2 as a robot software framework that connects to all of them.

02. Device-level intelligence with IO-Link

The sensors in 8.1 send one on/off signal. They cannot report a fault or accept new settings.

IO-Link is the first globally standardized IO technology under IEC 61131-9 for communicating with sensors and actuators.[1] IO-Link is not a fieldbus but an evolutionary development of connection technology for sensors and actuators.[1] IO-Link communication is point-to-point and based on the established 3-wire sensor and actuator connection without additional cable material requirements.[1] IO-Link relies on standards such as M12, M8 or M5 connectors and three-wire cables.[1]

Each device connects to a port on an IO-Link master. IO-Link is fieldbus-independent and can be integrated into all fieldbuses.[1]

IO-Link establishes bidirectional digital communication over the three-wire connection. IO-Link features three communication speeds of 4.8kBaud, 38.4kBaud, and 230.4kBaud.[1] The communication runs in both directions, which allows extended diagnostics of sensors and actuators and fast parameter setting.[1]

To integrate devices into engineering software, manufacturers supply description packages. The IO Device Description is delivered as a compressed ZIP file containing essential data about an IO-Link device.[1] The IODD gives details such as the manufacturer, serial number, article number and operating states.[1]

Safety sensors can use IO-Link too. IO-Link Safety Masters implement communication in higher-level systems such as PROFIsafe, CIPsafety, or FSOE.[1] Those are the safety protocols from 8.4.

03. Structured industrial data: OPC Unified Architecture

Unlike Classic OPC which was based on DCOM and linked to Windows, OPC UA was designed for arbitrary platforms and programming languages.[2]

The OPC UA specifications are publicly accessible and available as the IEC 62541 international standard series.[2]

OPC UA Client-Server communications use an optimized TCP-based binary protocol for data exchange over IANA registered port 4840.[2]

OPC UA organizes data into an object-oriented information model rather than flat numeric registers. All nodes in the OPC UA address space can be reached via the hierarchy and can have references among each other.[2]

Nodes represent objects, variables, and executable methods. References connect nodes into an address space graph. For example, a robot controller's OPC UA server could model an arm as a parent Object node named RobotArm containing child Object nodes for each axis (Joint1 through Joint6), where each joint provides Variable nodes for position and velocity with engineering units, alongside Method nodes to trigger calibration routines.

Security is part of OPC UA itself. The OPC UA SecurityPolicy specifies which encryption algorithms are used; current options include RSA and AES.[2]

Authentication ensures only authorized entities communicate. OPC UA establishes secure connections and bidirectional trust using Public Key Infrastructure with standard X.509v3 certificates.[2]

04. Standardized robot models: VDMA companion specifications

While OPC UA defines how to build information models, it does not specify how particular industrial machines must structure their nodes. Without coordination, two robot makers would organize their address spaces differently. One controller might store joint angles under Axis_1/Pos, while another uses Joint_A/ActualAngle. An integrator connecting both robots to one supervisory system would still need custom software for each manufacturer.

To standardize domain models, industry working groups create companion specifications. The OPC UA Companion Specification for Robotics provides a standardized information model capable of presenting robot-related data in a uniform manner regardless of manufacturer.[3]

Part 1 of the OPC UA Robotics specification permits asset management, condition monitoring, preventive maintenance, and vertical integration independent of robot brand or type.[3]

The OPC UA Robotics companion specification was released as VDMA Specification number 40010 (VDMA 40010).[3]

05. Publish-subscribe telemetry with MQTT

OPC UA's client/server model suits reading structured machine data and calling methods. For sending many small readings from many devices, a publish/subscribe protocol is often used instead.

MQTT is a Client Server publish/subscribe messaging transport protocol designed to be lightweight, open, and easy to implement.[4]

Every MQTT application message has a Topic Name and a Quality of Service.[4] Clients publish messages to the server (often called a broker) under a topic name such as plant/cell_2/robot_1/temperature, and the server forwards them to the clients that subscribed to that topic, so publishers and subscribers never connect to each other directly.

The MQTT protocol requires an underlying transport that provides an ordered, lossless stream of bytes between Client and Server.[4] In practice, MQTT runs over standard TCP/IP.

TCP ports 1883 and 8883 are registered with IANA for non-TLS and TLS MQTT communication respectively.[4]

MQTT defines three qualities of service for message delivery consisting of At most once, At least once, and Exactly once.[4]

  • At most once (QoS 0): Messages transmit once with best-effort delivery and no acknowledgment. Packets can be lost if connections drop. This mode minimizes traffic and fits high-frequency sensor readings.
  • At least once (QoS 1): The recipient acknowledges message delivery. If an acknowledgment fails to return within a set duration, the sender retransmits. Packets arrive reliably, though duplicates can occur.
  • Exactly once (QoS 2): The sender and receiver exchange a four-step handshake to ensure each message arrives without loss or duplication. This level suits high-priority alarms, batch completion flags, and production counts.

For example, an automated guided vehicle (AGV) transporting parts between cells publishes its battery voltage to topic agv_3/battery every ten seconds with QoS 0, while publishing batch completion notices to topic agv_3/completed on port 8883 with QoS 2 to ensure the inventory database records the delivery without duplication.

06. Advanced robotics and IT: ROS 2 and ros2_control

Chapter 4 introduced ROS 2, and 4.6 had you write a ROS 2 package. A common question when connecting plant systems is how ROS 2 interacts with PLCs, fieldbuses, and enterprise networks.

In this course, ROS 2 is treated as robot software that connects to the plant networks, not as a fieldbus or a safety system. Safety signals stay on the safety protocols from 8.4.

To interface ROS 2 motion planning with industrial robot controllers, the robotics community uses the ros2_control framework. In the ros2_control framework, the Controller Manager connects the controllers and hardware-abstraction sides of the framework.[5]

The control loop runs in the Controller Manager's update() method.[5] The Resource Manager stands for the hardware, and its read() and write() methods talk to the hardware components during each loop.[5]

For example, in a vision-guided sorting cell, a ROS 2 computer can plan the arm's motions through ros2_control, while a separate node on the same computer reads part pick counts and publishes those metrics to factory dashboards over MQTT or OPC UA.

Understanding how IO-Link, industrial Ethernet, OPC UA, MQTT, and ROS 2 function together allows integrators to build cohesive automation systems. Deterministic fieldbuses handle motion, IO-Link connects sensors, OPC UA standardizes machine-to-machine modeling, MQTT streams enterprise telemetry, and ROS 2 delivers advanced perception and path planning.
