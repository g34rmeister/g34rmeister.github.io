      10.4 Behavior Trees, Actions and Lifecycle Nodes

      Gerald Lê
      Chapter 10, lesson 4 of 4 ← Previous: 10.3 Planners, Controllers and Recoveries Next: Chapter 11: Capstone Projects →

      01. Actions: asking for a long task

      Driving across a building takes time, so Nav2 is built on ROS 2 actions. Action servers are a common way to control long-running tasks: a client requests a task, the server provides feedback while it runs, and a result comes back at the end.[1] For navigation, the request may be a position. The feedback may be the time spent navigating and the distance to the goal, and the result is a boolean for success.[1]

      A client application reaches Nav2 through a NavigateToPose action, which goes to the BT Navigator. The BT Navigator in turn uses actions to ask the smaller servers for plans, control efforts and recoveries.[1] Each server has its own .action type in nav2_msgs.[1]

      02. Behavior trees decide what happens next

      A behavior tree is a tree structure of tasks to be completed.[2] Nav2’s documentation contrasts it with a finite state machine (6.7 State Machines), which may have dozens of states and hundreds of transitions.[2] With a tree, basic primitives can be created once and reused for many behaviors.[2]

      Nav2 uses BehaviorTree.CPP V4 as its library. Node plugins are assembled into a tree inside the BT Navigator, and the tree itself is read from an XML file.[2] When the tree ticks one of those nodes, the node calls the matching action server from 10.3.[3]

      The library can load subtrees, so the whole Nav2 tree can be used as a single node in a higher-level tree.[2] The documentation also points out that keeping the application logic in the tree, with independent task servers, allows formal analysis.[2]

      03. Lifecycle nodes: starting and stopping in order

      All of Nav2’s servers are lifecycle (managed) nodes: nodes with state machine transitions for bringup and teardown.[1] This helps a ROS system behave deterministically at startup and shutdown.[1]

      • A node starts in the unconfigured state. Only its constructor has run, and that should not set up ROS networking or read parameters.[1]
      • Configuring moves it to inactive. The on_configure() method sets up the parameters and the ROS networking interfaces.[1]
      • Activating, through on_activate(), switches the networking interfaces on, and the node starts processing information.[1]
      • To shut down, the node goes through deactivating, cleaning up and shutting down, and ends in the finalized state.[1]

      The transitions are driven by the launch system or by Nav2’s lifecycle manager.[1] 4.7 Launch Files and Parameters covers launch files.

      05. Check your understanding

      • What three things pass between an action client and an action server during a navigation task?
        Show answer

        A request (for navigation, a position), feedback while the task runs (for navigation, the time spent navigating and the distance to the goal), and a result at the end (for navigation, a boolean for success). (Section 01)

      • Why does Nav2 use a behavior tree in place of one large finite state machine?
        Show answer

        Nav2’s documentation contrasts a behavior tree with a finite state machine, which may have dozens of states and hundreds of transitions. With a tree, basic primitives can be created once and reused for many behaviors. (Section 02)

      • In which lifecycle state is a node right after its constructor runs, and which two transitions bring it to the state where it processes information?
        Show answer

        It is in the unconfigured state. Configuring (which runs on_configure()) moves it to inactive, and activating (through on_activate()) switches the networking interfaces on so the node starts processing information. (Section 03)

      2. Sketch a small behavior tree for “go to the charger” that uses the whole Nav2 tree as one of its nodes. Which feature of the library makes that possible?
