      10.4 Behavior Trees, Actions and Lifecycle Nodes

      Gerald Lê
      Chapter 10, lesson 4 of 5 ← Previous: 10.3 Planners, Controllers and Recoveries Next: 10.5 Lab: Send a Navigation Goal to Nav2 →

      01. Actions: asking for a long task

      Driving an autonomous mobile robot across a warehouse or factory takes time, during which obstacles may move, paths may require replanning, or operators may need to abort the mission.[1] Because synchronous ROS 2 services would block the client thread and cannot report intermediate progress, Nav2 is architected around ROS 2 actions.[1] An action server manages a long-running, asynchronous, and preemptible task: a client dispatches a goal, the server periodically streams feedback during execution, and the server returns a final result status upon completion.[1]

      A client application initiates navigation by calling the NavigateToPose action hosted by Nav2’s BT Navigator server:[1], [2]

      You can dispatch a navigation goal and monitor its streaming feedback directly from the ROS 2 command-line interface:[2] 

      $ ros2 action send_goal /navigate_to_pose nav2_msgs/action/NavigateToPose \
  "{pose: {header: {frame_id: map}, pose: {position: {x: 1.5, y: -0.5}, orientation: {w: 1.0}}}}" \
  --feedback

      The BT Navigator (bt_navigator) acts as the central coordinator. Rather than directly computing trajectories or moving wheel motors, it loads an XML behavior tree and populates the goal pose into a shared blackboard. As the tree ticks, individual behavior tree nodes act as internal action clients that dispatch sub-tasks to the dedicated task servers described in 10.3: /compute_path_to_pose on the planner server, /follow_path on the controller server, and recovery actions like /spin or /backup on the behavior server.[3]

      02. Behavior trees: architecture and node semantics

      Traditional mobile robot control often relied on Finite State Machines (FSMs, 6.7). In an FSM, adding a new recovery action or sensor condition requires adding transitions across dozens of existing states, leading to exponential transition explosion (O(N2) complexity) and brittle spaghetti code.[4]

      Nav2 replaces monolithic state machines with Behavior Trees powered by the BehaviorTree.CPP V4 library.[4] In a behavior tree, control logic is represented as a directed hierarchical tree of reusable nodes. Execution is driven by ticking the root node at a fixed frequency (typically 10–100 Hz). Every node in the tree returns one of three status codes upon each tick:[4], [5]

      • SUCCESS: The node completed its objective successfully.
      • FAILURE: The node encountered an unrecoverable error or its condition was not met.
      • RUNNING: The node is actively executing an asynchronous task across multiple ticks.

      BehaviorTree.CPP defines four fundamental node categories:[5]

      • Action Nodes: Leaf nodes that perform actual work. In Nav2, action nodes typically wrap ROS 2 action or service clients. Examples include ComputePathToPose (queries the planner server), FollowPath (queries the controller server), Spin, Wait, BackUp, and ClearEntireCostmap. They return RUNNING while the server works, and resolve to SUCCESS or FAILURE when the sub-task completes.[5]
      • Condition Nodes: Leaf nodes that inspect system status without executing motor commands or blocking. They evaluate instantaneous state and return SUCCESS or FAILURE immediately; they never return RUNNING. Examples include GoalUpdated (detects if an operator published a new destination), IsGoalNearby (checks Euclidean distance to goal), and WouldAPlannerRecoveryHelp.[5]
      • Control Nodes: Internal branching nodes that have one or more children and define their execution order:[5]
        • Sequence: Ticks children sequentially from left to right. If any child returns FAILURE, the sequence halts and returns FAILURE. It returns SUCCESS only when all children have succeeded.
        • PipelineSequence: A specialized Nav2 control node. Unlike standard Sequence (which only ticks the current running child), PipelineSequence re-ticks preceding running children on every tick. This enables concurrent planning and tracking: the planner continuously updates the path ahead while the controller simultaneously drives the robot.
        • RecoveryNode: Has exactly two children: a primary action and a recovery action. It ticks the first child; if it fails, it ticks the second child. It retries this loop up to number_of_retries before returning FAILURE.
        • RoundRobin: Ticks its children in cyclical order across successive recovery cycles, ensuring alternative recovery behaviors (clearing costmaps, spinning, backing up) are attempted in turn.
        • Fallback (Selector): Ticks children in sequence until one returns SUCCESS. It returns FAILURE only if every child fails.
      • Decorator Nodes: Wrapper nodes that have exactly one child and modify its execution behavior. Examples include RateController (throttles child ticking to a fixed frequency, e.g. hz="1.0" for 1 Hz replanning) and Inverter (inverts SUCCESS to FAILURE and vice versa).[5]

      Nodes exchange data through the Blackboard: a key-value memory space where ports written by one node (e.g. path="{path}" produced by ComputePathToPose) can be read by another (e.g. path="{path}" consumed by FollowPath) without coupling their internal implementations.[5], [6]

      03. Concrete Nav2 Behavior Tree walkthrough

      Nav2 stores behavior trees in XML files parsed at runtime. Here is the canonical default tree, navigate_to_pose_w_replanning_and_recovery.xml, used by the BT Navigator:[6] 

      <root BTCPP_format="4" main_tree_to_execute="NavigateToPoseWReplanningAndRecovery">
  <BehaviorTree ID="NavigateToPoseWReplanningAndRecovery">
    <RecoveryNode number_of_retries="6" name="NavigateRecovery">
      <PipelineSequence name="NavigateWithReplanning">
        <RateController hz="1.0">
          <RecoveryNode number_of_retries="1" name="ComputePathToPose">
            <Fallback name="FallbackComputePathToPose">
              <ReactiveSequence name="CheckIfNewPathNeeded">
                <Inverter>
                  <GlobalUpdatedGoal/>
                </Inverter>
                <IsGoalNearby path="{path}" proximity_threshold="4.0" max_robot_pose_search_dist="1.5"/>
                <TruncatePathLocal input_path="{path}" output_path="{remaining_path}" distance_forward="-1" distance_backward="0.0"/>
                <ValidatePath path="{remaining_path}"/>
              </ReactiveSequence>
              <ComputePathToPose goal="{goal}" path="{path}" planner_id="{selected_planner}" error_code_id="{compute_path_error_code}"/>
            </Fallback>
            <Sequence>
              <WouldAPlannerRecoveryHelp error_code="{compute_path_error_code}"/>
              <ClearEntireCostmap name="ClearGlobalCostmap-Context" service_name="global_costmap/clear_entirely_global_costmap"/>
            </Sequence>
          </RecoveryNode>
        </RateController>
        <RecoveryNode number_of_retries="1" name="FollowPath">
          <FollowPath path="{path}" controller_id="{selected_controller}" error_code_id="{follow_path_error_code}"/>
          <Sequence>
            <WouldAControllerRecoveryHelp error_code="{follow_path_error_code}"/>
            <ClearEntireCostmap name="ClearLocalCostmap-Context" service_name="local_costmap/clear_entirely_local_costmap"/>
          </Sequence>
        </RecoveryNode>
      </PipelineSequence>
      <Sequence>
        <Fallback>
          <WouldAControllerRecoveryHelp error_code="{follow_path_error_code}"/>
          <WouldAPlannerRecoveryHelp error_code="{compute_path_error_code}"/>
        </Fallback>
        <ReactiveFallback name="RecoveryFallback">
          <GoalUpdated/>
          <RoundRobin name="RecoveryActions">
            <Sequence name="ClearingActions">
              <ClearEntireCostmap name="ClearLocalCostmap-Subtree" service_name="local_costmap/clear_entirely_local_costmap"/>
              <ClearEntireCostmap name="ClearGlobalCostmap-Subtree" service_name="global_costmap/clear_entirely_global_costmap"/>
            </Sequence>
            <Spin spin_dist="1.57" error_code_id="{spin_error_code}"/>
            <Wait wait_duration="5.0" error_code_id="{wait_error_code}"/>
            <BackUp backup_dist="0.30" backup_speed="0.15" error_code_id="{backup_error_code}"/>
          </RoundRobin>
        </ReactiveFallback>
      </Sequence>
    </RecoveryNode>
  </BehaviorTree>
</root>

      Let us dissect how this XML tree operates in practice during a real mission:[5], [6]

      1. Top-level Recovery Loop: The root element is a RecoveryNode named NavigateRecovery with number_of_retries="6". Its first child is the entire operational navigation pipeline (NavigateWithReplanning). Its second child is the system recovery subtree executed if the navigation pipeline fails.
      2. Continuous Pipelined Replanning: Inside NavigateWithReplanning, a PipelineSequence controls two concurrent actions. First, RateController hz="1.0" throttles the planner: once every second, it checks if an existing path remains valid, and if not, calls ComputePathToPose to update the {path} on the blackboard. Second, FollowPath runs concurrently, reading {path} and dispatching velocity commands to the base.
      3. Contextual Server Recoveries: If ComputePathToPose or FollowPath fails, their local RecoveryNode intercepts the failure and attempts a quick contextual recovery (e.g. ClearEntireCostmap) before escalating up the tree.
      4. Escalating Recovery Subtree: If contextual fixes fail and NavigateWithReplanning returns FAILURE, the second branch of NavigateRecovery executes. RoundRobin attempts progressively more assertive actions: first clearing both local and global costmaps, then spinning 90 degrees (1.57 rad) to clear sensor blind spots, waiting 5.0 seconds for dynamic obstacles to walk away, and backing up 0.30 meters out of tight corners.

      04. Lifecycle nodes: starting and stopping in order

      In complex distributed robotics stacks, nodes that start processing sensor feeds before parameters load or before coordinate transforms are established cause race conditions and sudden crashes. To achieve deterministic startup and shutdown, all Nav2 servers are implemented as managed lifecycle nodes following ROS 2 lifecycle state machine standards (REP 124).[1]

      A lifecycle node transitions through four primary states:[1]

      • Unconfigured: The node has been instantiated in memory by its C++ constructor. However, the constructor must never read ROS parameters or declare communication interfaces.
      • Inactive: Triggered by the configure transition executing on_configure(). The node declares parameters, allocates internal buffers, subscribes to static maps and sensor topics, and loads plugin algorithms. Crucially, the node is dormant: it does not process callbacks, publish transforms, or output velocity commands.
      • Active: Triggered by the activate transition executing on_activate(). The node activates its lifecycle publishers, enables execution timers, and begins real-time navigation processing.
      • Finalized: Triggered by the shutdown transition. Dynamic resources are freed, threads are terminated, and the node is safely destroyed.

      Instead of relying on random OS thread scheduling, the Nav2 Lifecycle Manager (nav2_lifecycle_manager) coordinates transitions across all servers in strict dependency order: map_server → costmaps → planner_server → controller_server → bt_navigator. Each managed node maintains a bond connection with the lifecycle manager. If any critical server crashes, the bond breaks, triggering the lifecycle manager to gracefully deactivate the entire navigation stack to prevent runaway robots.[1]

      You can inspect and control the lifecycle state of any Nav2 server using the ROS 2 command line:[1] 

      # Query current state of managed nodes
$ ros2 lifecycle get /planner_server
active [3]

$ ros2 lifecycle get /controller_server
active [3]

$ ros2 lifecycle get /bt_navigator
active [3]

# Transition a node into inactive state for maintenance or tuning
$ ros2 lifecycle set /planner_server deactivate
Transitioning successful

      06. Check your understanding

      • Why does Nav2 use ROS 2 Actions instead of ROS 2 Services to handle navigation missions?
        Show answer

        Navigation is a long-running, asynchronous, and preemptible task. Services block the client synchronously and cannot stream intermediate feedback (distance remaining, estimated time, tracking error) or accept goal cancellation requests while in transit. (Section 01)

      • In BehaviorTree.CPP V4, how does a Condition node differ from an Action node?
        Show answer

        An Action node executes work (often calling an action server or service) and can return RUNNING over multiple ticks before completing. A Condition node inspects instantaneous state without blocking or performing work, immediately returning SUCCESS or FAILURE, and never returns RUNNING. (Section 02)

      • What makes PipelineSequence uniquely suited for Nav2 compared to a standard Sequence node?
        Show answer

        A standard Sequence only ticks the current running child. A PipelineSequence re-ticks previous running children on every tick, allowing the global planner to continuously replan the path ahead at a fixed rate while the local controller concurrently executes motion tracking. (Section 02)

      • What sequence of recovery actions does the default Nav2 Behavior Tree execute if continuous replanning fails?
        Show answer

        Through a RoundRobin control node, it executes an escalating series of recovery behaviors: first clearing both local and global costmaps, then spinning in place (1.57 rad), waiting 5.0 seconds for dynamic obstacles to clear, and backing up 0.30 meters. (Section 03)

      • In which lifecycle state does a node configure its parameters and allocate subscriptions, and can it publish velocity commands in that state?
        Show answer

        In the Inactive state (via on_configure()). It cannot publish velocity commands or process active callbacks until it undergoes the activate transition to the Active state. (Section 04)

      1. A custom AMR needs to navigate to a pallet, pause for 10 seconds while an automated conveyor loads a box, and then navigate to a shipping dock. Sketch a BehaviorTree.CPP XML structure combining NavigateToPose, Wait, and Sequence nodes to achieve this workflow.
      2. Open a terminal in a system running Nav2. Use ros2 lifecycle get to inspect the state of /bt_navigator. Then, issue a transition command using ros2 lifecycle set to deactivate and reactivate the node. What happens to the node’s bond connection?
      3. During a navigation run, an obstacle suddenly blocks an aisle and the planner server aborts with an error. Trace the exact sequence of behavior tree node ticks from the failing ComputePathToPose action node up to the RecoveryActions RoundRobin subtree.
