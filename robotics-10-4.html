10.4 Capstone: An Open-Source Cell Monitor

Gerald Lê

01. What you will build and why

The first three capstones each go deep in one area. This one uses a little of everything. You will build a small open-source program that watches a robot cell: it reads the robot's state, the cell's handshake signals and a camera check, writes a maintenance log, and is published so that someone else could use it and contribute to it.

Everything runs on your own computer. The robot and the cell I/O are the stand-in servers from the labs in 8.3 and 9.6, and the camera is the test image publisher from 7.6. On a real cell you would point the same program at the robot's IP address.

It is a monitor, not a controller. It reads and reports, and it never clears a stop on its own: UR's service manual says robot stops must never be acknowledged and reset automatically; resuming must be a deliberate action by a person.[1] Safety functions stay on the safety-rated paths from 5.4 Making a Robot Cell Safe and 8.4 Safety over the Network.

02. Prerequisites

  • 3.2 to 3.4: how open-source contributions and pull requests work.
  • 4.6 Writing Your First ROS 2 Package: a Python ROS 2 package with a node and a topic.
  • 7.6 Lab: A ROS 2 Camera Pipeline: cv_bridge, thresholds and the cam2image test source.
  • 8.3 Lab: Connecting a Robot to a PLC: Modbus registers with pymodbus.
  • 9.2 A Troubleshooting Method and 9.6 Lab: Check a Robot's State from Python: logs, stops and the Dashboard Server.

03. Software (all free)

  • ROS 2 as installed in 4.3, Python 3, and pymodbus==3.16.1.
  • The stand-in servers fake_ur_server.py (8.3) and fake_dashboard_server.py (9.6).
  • The image_tools demo: with burger_mode turned on, cam2image publishes a generated test image instead of a camera feed.[2]
  • A GitHub account.

04. Milestones and what to hand in

  1. M0 Plan and repository: a public repository with a README that says what the monitor does and how to run it, and a LICENSE file. ROS 2's developer guide asks every package to have a LICENSE file, typically Apache 2.0, and a README with a description, usage examples, and build and test instructions.[3] Hand in: the repository link.
  2. M1 Robot state: a ROS 2 node that connects to the Dashboard Server stand-in on port 29999, asks robotmode and safetystatus once a second, and publishes the answers on a topic.[4] Hand in: ros2 topic echo output while you trigger and clear the stand-in's protective stop by hand.
  3. M2 Cell handshake: read and write the handshake signals on the Modbus stand-in. Put up to 16 on/off signals in one general-purpose register (UR's general-purpose registers are 128 to 255).[5] Hand in: a table of which bit means what, and a short run log.
  4. M3 Camera check: subscribe to the cam2image images and publish a simple "part present" flag from a threshold or contour count, as in 7.3 and 7.6. Hand in: the threshold you chose and why.
  5. M4 Maintenance log: write every state change to a log file with a time stamp, and raise a warning, not a reset, when protective stops repeat. Hand in: a log excerpt and the checklist from 9.3 you would follow next.
  6. M5 Open it up: add a CONTRIBUTING file, open one issue that a newcomer could take, and open one real pull request: to your classmates' monitor, to robOSStics, or to a robotics project from Chapter 3. Pull requests do not have to be finished; you can open one early as a draft to get feedback.[6] Hand in: the links.

05. Testing and verification

Write the pass conditions before you test. For example: M1 reports PROTECTIVE_STOP within two seconds of the stand-in entering it; M2 reads back exactly the bits you wrote; M4 never sends unlock protective stop. Run each test, record the result, and keep the record in the repository.

06. Grading rubric

Use the same four-level rubric format as 10.1, with one row per milestone (M0 to M5) and two more rows: "the monitor never resets a stop" (pass/fail) and "someone else could run it from your README".

07. Reflection questions and stretch goals

  • Which signal in your monitor would you trust least on a real cell, and why?
  • What would a maintainer of your repository need to know before accepting a pull request?
  • Stretch: show the robot state and the "part present" flag in RViz2 or a small web page.
  • Stretch: watch your own monitor's Modbus traffic in Wireshark, as in 8.6.
