5.7 State Machines

Gerald Lê

01. Why robots need state machines

A robot rarely does just one thing. It follows a line, then swerves around a box, then hunts for the line again, then stops when someone presses a button. Writing all of that as one long chain of if statements quickly becomes impossible to read or debug. A finite state machine (FSM) organizes the “think” step of sense–think–act into a small number of clearly named behaviors and clear rules for switching between them.

You have already met one: the hospitality robot in 1.5 is described as a state machine with states such as Idle (waiting for a wake word), Listening and Responding, plus a rule that it slows or stops whenever a person comes too close.

02. The parts of a state machine

  • State: what the robot is doing right now, such as FOLLOW_LINE. The robot is in exactly one state at a time.
  • Event: something that happens, usually detected by a sensor or a timer: “obstacle closer than 20 cm,” “line lost,” “5 seconds passed.”
  • Guard: an extra condition that must also be true for a transition to happen, such as “and the path ahead is clear.”
  • Transition: a move from one state to another when its event happens and its guard is true.
  • Action: what the robot does: once on entering a state (entry action, such as starting a timer), or continuously while in it (such as running the line-following controller).

03. Worked example: line follower with obstacle avoidance

Our robot has two floor reflectance sensors, a forward HC-SR04 ultrasonic sensor and a stop button. It has four states:

  • FOLLOW_LINE: steer to keep the line between the two floor sensors.
  • AVOID_OBSTACLE: turn away from something in front.
  • SEARCH: drive in a slow arc looking for the line.
  • STOP: motors off. This is also the safe state.

04. The code: enum, switch and millis()

An enum gives each state a name, and a switch inside loop() runs the current state’s actions and checks its transitions. Timing uses millis() instead of delay(), so loop() never stops: every pass reads the sensors, and the stop button works even halfway through a turn. 

enum State { FOLLOW_LINE, AVOID_OBSTACLE, SEARCH, STOP };
                            State state = FOLLOW_LINE;
                            unsigned long stateStart = 0;      // when we entered the current state
                            unsigned long lastPing = 0;
                            float distanceCm = 999;

                            const int LEFT_PWM = 5, LEFT_DIR = 4, RIGHT_PWM = 6, RIGHT_DIR = 7;
                            const int TRIG = 9, ECHO = 10, STOP_BUTTON = 2;
                            const int LINE_THRESHOLD = 600;    // analogRead value over black tape

                            void setMotor(int pwmPin, int dirPin, int speed) {   // speed -255..255
                              digitalWrite(dirPin, speed >= 0 ? HIGH : LOW);
                              analogWrite(pwmPin, constrain(abs(speed), 0, 255));
                            }
                            void drive(int left, int right) {
                              setMotor(LEFT_PWM, LEFT_DIR, left);
                              setMotor(RIGHT_PWM, RIGHT_DIR, right);
                            }
                            void enterState(State next) {
                              state = next;
                              stateStart = millis();
                            }

                            void setup() {
                              pinMode(LEFT_DIR, OUTPUT);  pinMode(RIGHT_DIR, OUTPUT);
                              pinMode(TRIG, OUTPUT);      pinMode(ECHO, INPUT);
                              pinMode(STOP_BUTTON, INPUT_PULLUP);
                              enterState(FOLLOW_LINE);
                            }

                            void loop() {
                              unsigned long now = millis();

                              // --- sense ---
                              bool leftOnLine  = analogRead(A0) > LINE_THRESHOLD;
                              bool rightOnLine = analogRead(A1) > LINE_THRESHOLD;
                              if (now - lastPing >= 60) {                  // HC-SR04: at least 60 ms apart
                                lastPing = now;
                                digitalWrite(TRIG, HIGH); delayMicroseconds(10); digitalWrite(TRIG, LOW);
                                unsigned long echo = pulseIn(ECHO, HIGH, 12000);   // give up after 12 ms
                                distanceCm = (echo == 0) ? 999 : echo * 0.034 / 2;
                              }
                              if (state != STOP && digitalRead(STOP_BUTTON) == LOW) enterState(STOP);

                              // --- think and act ---
                              switch (state) {
                                case FOLLOW_LINE:
                                  if (distanceCm < 20)               enterState(AVOID_OBSTACLE);
                                  else if (!leftOnLine && !rightOnLine) enterState(SEARCH);
                                  else if (leftOnLine && !rightOnLine) drive(80, 180);   // line is to the left
                                  else if (rightOnLine && !leftOnLine) drive(180, 80);   // line is to the right
                                  else                                 drive(160, 160);
                                  break;
                                case AVOID_OBSTACLE:
                                  drive(150, -150);                                  // spin right
                                  if (now - stateStart >= 600 && distanceCm >= 20) enterState(SEARCH);
                                  break;
                                case SEARCH:
                                  drive(140, 90);                                    // slow arc
                                  if (leftOnLine || rightOnLine)   enterState(FOLLOW_LINE);
                                  else if (now - stateStart > 5000) enterState(STOP);
                                  break;
                                case STOP:
                                  drive(0, 0);                                       // stay here until reset
                                  break;
                              }
                            }

pulseIn() does wait for the echo, but the 12 ms timeout (about 2 m of range) keeps that wait short and bounded. The pins match an Arduino Uno: 5 and 6 are PWM pins, and the motor driver is assumed to take one PWM and one direction input per motor.

05. Common mistakes

  • Using delay(): delay(600) inside AVOID_OBSTACLE would freeze the robot for 600 ms, blind to the stop button and sensors. Compare millis() timestamps instead.
  • Forgetting to reset the timer: always change state through one function like enterState(), so the entry time (and any other entry action) is never skipped.
  • Missing transitions: a state with no way out traps the robot. Check every row of your table, and make sure every state can reach STOP.
  • Chattering: if a reading hovers right at a threshold, the robot can flip between two states on every pass. Use two thresholds (for example, enter AVOID below 20 cm but only leave above 25 cm) or require the condition to hold for a short time.
  • Subtracting time wrongly: write now - stateStart >= 600 with unsigned long values. That form still works when millis() wraps back to zero after about 50 days.

06. The same idea at larger scale

State machines are everywhere in professional robotics. Packaging and other industrial machines commonly follow the PackML state model from ISA-TR88.00.02, with standard states such as Idle, Execute, Held, Stopped and Aborted, so any operator or supervisory system knows what “Held” means on any machine.

In ROS 2, managed (lifecycle) nodes follow a defined state machine with the primary states Unconfigured, Inactive, Active and Finalized, so a launch system can configure and activate a robot’s nodes in a known order. The Nav2 navigation stack uses lifecycle nodes for bringup and organizes its navigation logic as behavior trees, which its documentation presents as a more scalable alternative to a finite state machine with dozens of states and hundreds of transitions. Once your robot’s behavior outgrows a single switch statement, that is the natural next step.

Try it
  1. Add a LOW_BATTERY state to the example. Write its rows in the transition table before you change the code.
  2. Take an old sketch that uses delay() and rewrite one wait using millis(), so the loop keeps reading a button.
