5.7 State Machines

Gerald Lê

01. Why robots require state machines

An autonomous robot rarely performs a single uninterrupted task. A warehouse mobile robot must follow a guide line, navigate around obstacles, search for missing paths, and halt immediately if a safety button is pressed. Novice programmers often attempt to coordinate these behaviors by nesting if and else if conditional statements inside the main control loop.

As robot capabilities grow, this ad hoc approach rapidly degenerates into fragile "spaghetti code." Adding a single new behavior requires modifying multiple nested conditional branches. Hidden side effects emerge, race conditions corrupt motor commands, and predicting robot behavior under unexpected sensor readings becomes mathematically intractable.

To bring formal structure to robot behavior, engineers use a Finite State Machine (FSM).[1] An FSM is a mathematical model of computation consisting of a predetermined set of states, incoming events, and guarded transitions between states. At any given instant, the robot resides in exactly one state. By decoupling what the robot does (the state action) from when it switches behaviors (the state transition), state machines organize the "think" stage of the sense-think-act cycle into modular, verifiable software components.

02. Core components of a state machine

Formally, an extended finite state machine comprises five distinct elements:[1]

  • State: A unique operating mode or behavioral condition in which the robot resides. While in a state, the robot executes specific actions. For example, in FOLLOW_LINE, the robot executes differential motor velocity adjustments based on line reflectance sensors. The system remains in exactly one state at a time.
  • Event: An external or internal stimulus detected by the system. Events originate from hardware sensors (ultrasonic distance drops below 20 cm), timer triggers (elapsed time exceeds 600 ms), or user inputs (digital emergency stop button pressed).
  • Guard: A Boolean conditional expression that must evaluate to true for an event to trigger a transition. For example, the event "turn completed" may be guarded by the condition [path ahead is clear]. If the guard evaluates to false, the transition is inhibited.
  • Transition: The deterministic progression from the current source state to a target destination state, triggered when an event occurs and its associated guard evaluates to true.
  • Action: Executable code invoked by the state machine. In classic automata theory, a Moore machine associates actions strictly with state residency, whereas a Mealy machine associates actions with state transitions. In modern embedded robotics, engineers typically utilize state actions partitioned into entry actions (executed once upon arrival, such as resetting a timer), execution actions (evaluated continuously each control loop), and exit actions (executed once upon departure, such as turning off an indicator LED).

03. Worked example: line follower with obstacle avoidance

To observe an FSM in action, examine a differential-drive robot equipped with two analog floor reflectance sensors (A0 and A1), an HC-SR04 ultrasonic range finder (trigger pin 9, echo pin 10), two DC motors controlled via PWM H-bridge drivers, and a normally high digital emergency stop push-button (pin 2).

The behavioral logic of this robot is partitioned into four distinct states:

  1. FOLLOW_LINE: The robot steers its drive wheels to center a black electrical floor tape between its two reflectance sensors.
  2. AVOID_OBSTACLE: The robot stops forward drive and spins in place to steer clear of an obstacle in its immediate path.
  3. SEARCH: Having lost the line, the robot drives along a wide curved arc seeking to re-acquire the black tape.
  4. STOP: Actuator PWM duty cycles are set to zero. This represents the fail-safe resting state.

Before writing a single line of embedded code, an engineer creates a state transition table. This tabular matrix comprehensively documents all valid state transitions and guards, guaranteeing that no sensor event produces undefined behavior:

Current State Event Trigger [Guard Condition] Target State Actions Performed
FOLLOW_LINE Obstacle detected [distance < 20 cm] AVOID_OBSTACLE Record state entry timestamp; command right spin.
FOLLOW_LINE Line lost [both sensors off tape] SEARCH Record state entry timestamp; command arc sweep.
AVOID_OBSTACLE Turn timer expired [elapsed ≥ 600 ms AND distance ≥ 20 cm] SEARCH Transition to search mode to locate line.
SEARCH Line detected [left OR right sensor on tape] FOLLOW_LINE Resume closed-loop differential line tracking.
SEARCH Search timer expired [elapsed > 5000 ms] STOP Halt all motors; lock system in safe state.
Any State Emergency stop button pressed [pin LOW] STOP Instantly cut PWM to all motors; require manual reset.

04. Non-blocking timing: why delay() is fatal in robotics

In introductory microcontroller tutorials, pauses are commonly implemented using the built-in Arduino delay() function. However, using delay() inside autonomous robot code is catastrophic.

The delay() function is a blocking call: it traps the microcontroller CPU inside an internal busy-wait loop for the requested number of milliseconds. During that period, the CPU cannot execute instructions. If the robot enters AVOID_OBSTACLE and commands a spin using delay(600), the CPU is completely frozen for 600 milliseconds. During this freeze:

  • The robot cannot read its ultrasonic range finder or bumper switches to detect an oncoming wall or sudden drop-off.
  • The emergency stop button is completely ignored, creating a severe physical safety violation.
  • Sensory feedback is severed while the motors continue driving at their previously set speed.

Professional robotic software implements cooperative multitasking using non-blocking timestamps via the millis() timer function.[2] The hardware timer on the microcontroller increments an internal 32-bit counter every millisecond. The millis() function returns this elapsed count as an unsigned long without halting program execution.

To time a 600 ms turning maneuver without blocking, software records the timestamp when the state is entered (stateStart = millis()). On every subsequent pass of the main loop(), the code evaluates elapsed time using unsigned modular subtraction:

\[\text{elapsed} = \text{now} - \text{stateStart}\]

Because loop() completes each cycle in less than a millisecond, the robot evaluates its ultrasonic sensor and emergency stop button hundreds of times per second throughout the turn.

Crucially, embedded software must always write the check as (now - stateStart >= duration) rather than (now >= stateStart + duration). A 32-bit unsigned integer rolls over from 4,294,967,295 back to 0 after approximately 49.71 days of continuous operation. In C and C++, unsigned arithmetic operates modulo \(2^{32}\). When now rolls over, the unsigned subtraction (now - stateStart) correctly computes elapsed duration across the rollover boundary. The addition form fails during rollover, locking the robot into an infinite state freeze.

05. Embedded C++ implementation

In embedded C++, the state machine is implemented cleanly using a scoped enum to name the states, an enterState() helper function to ensure atomic state transitions and timestamp recording, and a switch statement inside loop(): 

enum State { FOLLOW_LINE, AVOID_OBSTACLE, SEARCH, STOP };
State state = FOLLOW_LINE;
unsigned long stateStart = 0;      // Timestamp when entering current state
unsigned long lastPing = 0;        // Ultrasonic sensor rate limiter
float distanceCm = 999.0;

const int LEFT_PWM = 5, LEFT_DIR = 4, RIGHT_PWM = 6, RIGHT_DIR = 7;
const int TRIG = 9, ECHO = 10, STOP_BUTTON = 2;
const int LINE_THRESHOLD = 600;    // analogRead threshold over black tape

void setMotor(int pwmPin, int dirPin, int speed) {   // speed: -255 to 255
  digitalWrite(dirPin, speed >= 0 ? HIGH : LOW);
  analogWrite(pwmPin, constrain(abs(speed), 0, 255));
}

void drive(int left, int right) {
  setMotor(LEFT_PWM, LEFT_DIR, left);
  setMotor(RIGHT_PWM, RIGHT_DIR, right);
}

void enterState(State next) {
  state = next;
  stateStart = millis(); // Atomic entry action: record timestamp
}

void setup() {
  pinMode(LEFT_DIR, OUTPUT);  pinMode(RIGHT_DIR, OUTPUT);
  pinMode(TRIG, OUTPUT);      pinMode(ECHO, INPUT);
  pinMode(STOP_BUTTON, INPUT_PULLUP);
  enterState(FOLLOW_LINE);
}

void loop() {
  unsigned long now = millis();

  // --- 1. SENSE STAGE ---
  bool leftOnLine  = analogRead(A0) > LINE_THRESHOLD;
  bool rightOnLine = analogRead(A1) > LINE_THRESHOLD;

  // HC-SR04 sonar ping: executed at most once every 60 ms to avoid acoustic echoes
  if (now - lastPing >= 60) {
    lastPing = now;
    digitalWrite(TRIG, HIGH);
    delayMicroseconds(10);
    digitalWrite(TRIG, LOW);
    unsigned long echo = pulseIn(ECHO, HIGH, 12000); // 12 ms timeout (~2.0 m max range)
    distanceCm = (echo == 0) ? 999.0 : (echo * 0.0343) / 2.0;
  }

  // Asynchronous Emergency Stop: monitored on every single loop iteration
  if (state != STOP && digitalRead(STOP_BUTTON) == LOW) {
    enterState(STOP);
  }

  // --- 2. THINK & ACT STAGES ---
  switch (state) {
    case FOLLOW_LINE:
      if (distanceCm < 20.0) {
        enterState(AVOID_OBSTACLE);
      } else if (!leftOnLine && !rightOnLine) {
        enterState(SEARCH);
      } else if (leftOnLine && !rightOnLine) {
        drive(80, 180);   // Steer left toward tape
      } else if (rightOnLine && !leftOnLine) {
        drive(180, 80);   // Steer right toward tape
      } else {
        drive(160, 160);  // Both sensors centered on tape
      }
      break;

    case AVOID_OBSTACLE:
      drive(150, -150);   // Spin right in place
      if ((now - stateStart >= 600) && (distanceCm >= 20.0)) {
        enterState(SEARCH);
      }
      break;

    case SEARCH:
      drive(140, 90);     // Trace broad curved arc to re-acquire line
      if (leftOnLine || rightOnLine) {
        enterState(FOLLOW_LINE);
      } else if (now - stateStart > 5000) {
        enterState(STOP); // Line lost timeout: stop robot safely
      }
      break;

    case STOP:
      drive(0, 0);        // De-energize all drive actuators
      break;
  }
}

Notice that pulseIn() incorporates an explicit 12 millisecond timeout. If no echo returns (for example, if ultrasound scatters into an open room), pulseIn() aborts after 12 ms rather than blocking the CPU for its default 1000 ms timeout. This guarantees that loop execution frequency remains above 80 Hz under all acoustic conditions.

06. State machine anti-patterns and pitfalls

When architecting state machines for embedded robots, five widespread software engineering anti-patterns must be avoided:

  • Blocking Delays: Introducing delay() calls inside state branches blinds the robot to sensory events and user e-stops. Every timed behavior must rely on millis() delta comparisons.
  • Neglected Entry Actions: If an engineer changes state = SEARCH; directly in multiple places without updating stateStart, the state timer operates with stale timestamps, causing premature or delayed timeouts. Centralizing transitions inside enterState() guarantees uniform execution.
  • Chattering and State Flapping: If a sensor value hovers directly on a decision boundary (such as distance oscillating between 19.9 cm and 20.1 cm), the FSM can oscillate between FOLLOW_LINE and AVOID_OBSTACLE on successive loop passes. This is resolved by adding hysteresis: trigger obstacle avoidance at 20 cm, but require the path to clear 25 cm before exiting.
  • Terminal Traps: An unhandled exception or missing transition row in the state table can strand a robot in an active state indefinitely. Every state must have at least one valid transition path, and every active state must transition to STOP upon an e-stop event or safety timeout.
  • Duplicate Output Actuation: Writing motor speeds inside scattered conditional checks creates conflicting actuator commands within the same cycle. A well-structured FSM updates actuator outputs only once per pass based on the active state.

07. Industrial automation standards: IEC 61131-3 SFC and PackML

In industrial manufacturing plants, automated guided vehicles (AGVs), robotic workcells, and assembly conveyors rely on standardized state machine architectures to guarantee worker safety and predictable machine sequencing across multi-vendor equipment.

The international standard IEC 61131-3 defines programming languages for industrial Programmable Logic Controllers (PLCs).[3] Among its five standardized languages is Sequential Function Chart (SFC), an engineering formalism derived from Petri nets. SFC models machine operations as a directed graph of:

  • Steps: Discrete operating states that are either active or inactive. An initial step (drawn with double borders) activates automatically upon PLC system boot.
  • Transitions: Boolean condition barriers between steps. When the preceding step is active and its transition condition becomes true, the preceding step deactivates and the succeeding step activates in a single scan cycle.
  • Action Blocks and Qualifiers: SFC decouples actions using standardized qualifiers: N (Non-stored, active while step is active), S (Set/Stored, remains true until explicitly reset), R (Reset), L (Time-limited, deactivates after a set duration), and D (Time-delayed, starts only after a step has been active for a set duration).

For packaging and material-handling robotics, the Organization for Machine Automation and Control (OMAC) standardized PackML under ISA-TR88.00.02.[4] PackML defines 17 standard machine states, including Stopped, Idle, Execute (normal production), Held (temporary pause due to upstream starvation or downstream jam), and Aborted (emergency shutdown).

Because every PackML machine adheres to this shared vocabulary, plant Supervisory Control and Data Acquisition (SCADA) systems can track Overall Equipment Effectiveness (OEE) and enforce interlocks across robots from different vendors.

08. ROS 2 managed nodes: the rclcpp_lifecycle state machine

In ROS 1, node initialization was unmanaged: constructors immediately created publishers, subscribers, and timers upon process launch. If a motor controller node initialized before the laser scanner or safety supervisor was online, the robot could execute open-loop motion without safety watchdogs active.

ROS 2 addresses this with managed (lifecycle) nodes in rclcpp_lifecycle and rclpy.lifecycle.[5] A lifecycle node follows a deterministic state machine with four primary states and six transition states:

Primary State Operational Characteristics Permitted Transitions
Unconfigured Node is instantiated in memory but has not allocated communication buffers or parsed parameters. Transitions to Inactive via configure(), or to Finalized via shutdown().
Inactive Parameters loaded and endpoints bound, but execution is paused: publishers do not transmit and timers are stopped. Transitions to Active via activate(), to Unconfigured via cleanup(), or to Finalized via shutdown().
Active Full operational execution. Timers fire, sensor callbacks execute, and command messages are published. Transitions to Inactive via deactivate(), or to Finalized via shutdown().
Finalized Node has released hardware interfaces, freed memory, and shut down cleanly. Ready for destruction. Terminal state: no further transitions permitted.

The six transition states (Configuring, Activating, Deactivating, CleaningUp, ShuttingDown, ErrorProcessing) run callbacks such as on_configure(). If a sensor fails to respond during configuration, returning failure aborts the activation, allowing the launch coordinator to halt safely.

09. Beyond state machines: Behavior Trees in ROS 2 Nav2

While finite state machines excel at organizing simple behaviors, they face severe structural limitations when scaling to complex autonomous navigation. In a traditional FSM, every state must define transitions to every other possible state. As behaviors \(N\) increase, the transitions grow quadratically:

\[\text{Number of Transitions} \approx \mathcal{O}(N^2)\]

Adding a new behavior requires modifying transitions across multiple existing states, creating tightly coupled code known as the state explosion problem.

To achieve modular autonomy, modern robotics frameworks employ Behavior Trees (BTs).[6] Formalized for robotics by Michele Colledanchise and Petter Ögren, Behavior Trees replace state-to-state transitions with a hierarchical execution tree evaluated via a periodic signal called a Tick. In ROS 2, the Nav2 stack coordinates autonomous navigation with a Behavior Tree engine via the bt_navigator node.[7]

When ticked from its root at a fixed frequency (such as 100 Hz), execution flows downward through four fundamental node types:

  • Control Nodes: Route ticks to children: Sequence, Fallback (Selector), and Parallel.
  • Decorator Nodes: Modify child behavior (such as RateController, RetryUntilSuccessful, or Inverter).
  • Action Nodes: Execute physical tasks (such as ComputePathToPose, FollowPath, Spin, or BackUp).
  • Condition Nodes: Perform non-blocking sensory checks (such as IsBatteryLow, IsPathValid, or TransformAvailable).

Every node in a Behavior Tree returns one of three discrete execution statuses upon being ticked: SUCCESS, FAILURE, or RUNNING.

The two core control nodes govern navigation and error recovery:

  • Sequence Node (→): Ticks children from left to right. If a child returns SUCCESS, it ticks the next child. If a child returns RUNNING, the Sequence returns RUNNING. If any child returns FAILURE, the Sequence immediately halts remaining children and returns FAILURE to its parent.
  • Fallback Node (?): Implements reactive recovery. Ticks children from left to right. If a child returns SUCCESS, the Fallback immediately succeeds. If a child returns FAILURE, the Fallback ticks the next child (the recovery action). It returns FAILURE only if all children fail.

In Nav2, the default navigation tree places a primary navigation Sequence beside a recovery Fallback:

Fallback: NavigateWithRecovery

 └ Sequence: PrimaryNavigate

   └ ⟨Condition: IsPathValid⟩

   └ ⟨Action: FollowPath⟩

 └ Sequence: RecoveryBehaviors

   └ ⟨Action: ClearEntireCostmap⟩

   └ ⟨Action: Spin 1.57 rad⟩

   └ ⟨Action: BackUp 0.20 m⟩

If a human blocks the hallway, FollowPath returns FAILURE. The PrimaryNavigate Sequence halts and returns FAILURE. The parent Fallback catches the failure and immediately ticks RecoveryBehaviors. The robot clears its obstacle costmap, spins in place, and backs away before re-attempting path tracking. Because each behavior is a modular leaf node, new recovery strategies can be inserted without altering existing navigation code.
