5.6 Odometry

Gerald Lê

01. What is odometry?

Odometry is estimating where a robot is by adding up how far its wheels have turned. It is a form of dead reckoning: starting from a known pose, the robot keeps a running total of its small movements, with no outside reference. For a differential-drive robot (two driven wheels on one axle, plus a caster) the inputs are simply the tick counts from the left and right wheel encoders.

The robot’s pose is its position and heading in a fixed world frame (see 1.6 Coordinate Frames): x and y in meters and the heading θ in radians, measured counterclockwise from the x-axis.

02. From ticks to wheel distance

Each update, read how many ticks each encoder counted since the last update and convert them to distance, using the formula from 5.3: 

d_L = (delta_ticks_L / CPR) * (pi * wheel_diameter)
                            d_R = (delta_ticks_R / CPR) * (pi * wheel_diameter)

03. The update equations

With b the wheelbase (the distance between the two wheels’ contact points), the robot’s center moves by the average of the two wheels, and the difference between them turns it: 

d_center = (d_L + d_R) / 2
                            d_theta  = (d_R - d_L) / b

                            x     = x + d_center * cos(theta + d_theta / 2)
                            y     = y + d_center * sin(theta + d_theta / 2)
                            theta = theta + d_theta

If both wheels travel the same distance, d_theta is zero and the robot drives straight. If the right wheel travels farther, d_theta is positive and the robot turns left (counterclockwise).

The d_theta / 2 term uses the heading halfway through the step. That is the form in Siegwart’s textbook, and it is more accurate on curves than the simpler version you will also see, x += d_center * cos(theta), which uses the heading from the start of the step. Both are approximations that work well when the update is frequent and each step is small, so update every 10–20 ms rather than once a second.

04. Odometry in code

This sketch fragment assumes the encoder interrupt routines from 5.3 keep leftTicks and rightTicks up to date. It uses millis() so the update runs on a steady schedule without blocking the rest of the program. 

const float WHEEL_DIAMETER = 0.065;   // meters
                            const float WHEELBASE      = 0.150;   // meters
                            const long  CPR            = 1440;    // counts per wheel revolution
                            const float M_PER_TICK     = PI * WHEEL_DIAMETER / CPR;

                            volatile long leftTicks = 0, rightTicks = 0;  // updated by encoder ISRs
                            long prevLeft = 0, prevRight = 0;
                            float x = 0, y = 0, theta = 0;
                            unsigned long lastUpdate = 0;

                            void updateOdometry() {
                              noInterrupts();                 // copy counts safely
                              long l = leftTicks;
                              long r = rightTicks;
                              interrupts();

                              float dL = (l - prevLeft)  * M_PER_TICK;
                              float dR = (r - prevRight) * M_PER_TICK;
                              prevLeft = l;
                              prevRight = r;

                              float dCenter = (dL + dR) / 2.0;
                              float dTheta  = (dR - dL) / WHEELBASE;

                              x += dCenter * cos(theta + dTheta / 2.0);
                              y += dCenter * sin(theta + dTheta / 2.0);
                              theta += dTheta;
                              theta = atan2(sin(theta), cos(theta));   // keep theta in -pi..pi
                            }

                            void loop() {
                              if (millis() - lastUpdate >= 20) {        // 50 updates per second
                                lastUpdate += 20;
                                updateOdometry();
                              }
                              // ... sensing and motor control continue here ...
                            }

05. Why the error keeps growing

Each update adds a small error, and nothing ever removes it, so odometry error grows without bound the farther the robot drives. Heading errors are the worst: a heading that is off by just one degree pushes the position sideways by almost 2 cm for every meter driven, and that sideways error keeps growing for the rest of the trip.

Borenstein and Feng, who developed the UMBmark test at the University of Michigan, split odometry errors into two kinds:

  • Systematic errors: come from the robot itself and repeat on every run. Examples are unequal wheel diameters, an average wheel diameter that differs from the value in the code, an uncertain effective wheelbase, misaligned wheels, and limited encoder resolution or sampling rate. They found unequal wheel diameters and wheelbase uncertainty to be the two biggest.
  • Non-systematic errors: come from the robot’s interaction with the floor and are unpredictable. Examples are uneven floors, driving over objects, and wheel slip from slippery floors, hard acceleration, fast turns or being pushed.

Systematic errors can be measured and calibrated away. Non-systematic errors cannot; they can only be bounded by checking against other sensors.

06. Calibration tips

  • Wheel diameter: drive straight a measured distance, such as 2 m, and compare it with what odometry reports. Then new_diameter = old_diameter * actual / reported.
  • Wheelbase: spin in place several full turns (more turns makes small errors easier to see) and compare the reported angle with the real one. Then new_b = old_b * reported_angle / actual_angle.
  • UMBmark: Borenstein and Feng’s test drives a 4 m × 4 m square five times clockwise and five times counterclockwise, then compares where odometry thinks the robot ended with where it really ended. Running both directions separates wheel-diameter error from wheelbase error.
  • Drive gently: smooth acceleration and slower turns reduce wheel slip.

07. Correcting odometry with other sensors

Because odometry drifts, robots correct it with sensors that measure the outside world or an absolute reference. A gyroscope in an IMU measures turning directly, so it is not fooled when a wheel slips during a turn, although it drifts slowly itself. Range sensors or a LiDAR can match the robot’s view to walls or a map, and outdoors GPS gives an absolute but noisy position. Combining a smooth, drifting estimate with noisy, drift-free measurements is the job of the Kalman filter, the topic of 5.8.

Try it
  1. By hand, update a pose of (0, 0, 0) with d_L = 0.10 m and d_R = 0.14 m on a 0.20 m wheelbase.
  2. Drive a robot around a 1 m square using odometry only, and measure how far from the start it stops. Repeat in the other direction.
