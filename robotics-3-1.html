3.1 What Open Source Is

Gerald Lê

01. The definition of open source and why licenses matter

In Chapters 1 and 2, we worked with industrial robots and factory controllers. In Lesson 2.4 Intro to ROS (Vendor-Agnostic), we saw how shared communication standards connect robots across different equipment brands. Chapter 4, which comes right after this chapter, focuses on the Robot Operating System (ROS), starting with Lesson 4.1 Definition and Introduction.

Before writing code or running packages, we need to know what open source means and how communities organize their work.

Many programmers assume that any code published publicly on the web is open source. That assumption is incorrect. A software license is a legal document that states what permissions users have to inspect, modify, and share software. Every open source project must have an open source license, and without an open source license a project is not open source.[1]

The license is what gives everyone else permission to use, change and share the code. Without one, you can read the code but you have no permission to reuse it.

02. Public collaboration and career growth

Open-source development takes place in the open. By definition all open source work is public, creating demonstration examples that help contributors grow a reputation and career.[1]

In traditional manufacturing automation, engineers write software inside private company networks or store routines on proprietary robot teach pendants. Potential employers, collaborators, or colleagues cannot see your code or evaluate your problem-solving process.

In open-source software, every step happens in public view. The discussions you start, the defects you report, the pull requests you submit, and the technical explanations you write are visible to anyone worldwide. When you fix a bug in a robot driver or improve an installation manual, that work becomes permanent public evidence of your ability. Other developers can review your commits, observe how you respond to technical feedback, and see how you communicate in a team.

03. Project structure and the LICENSE file

Open-source projects organize their files inside a repository, which is a version-controlled directory that stores code, history, and documentation. The top folder of this repository is called the root directory.

Nearly every open-source project keeps standard files in its root directory so newcomers can find essential information immediately. These files include the license, project overview, contribution guidelines, and community policies.

The core requirement is the license file itself, usually named LICENSE. In robotics, standard frameworks establish clear licensing policies for all components. Every ROS 2 package must have a LICENSE file, typically the Apache 2.0 license unless an existing permissive license is in place.[2]

A permissive software license is a license with minimal restrictions on how others use, modify, and redistribute code. The Apache 2.0 license is permissive and protects both creators and users.

When you contribute to an open-source project, your contributions conform to the repository license. For example, contributions submitted to ros2_control are licensed under the Apache 2 License according to Section 5 of that license.[3] So a project's license covers your changes too, and the project stays under one set of terms.

04. Guiding users: the README file

The document that every user reads first is the README file, typically named README.md. A project README serves as an instruction manual that welcomes community members, explains why the project is useful, and provides getting started instructions.[1]

A project without a clear README leaves newcomers confused. Users cannot tell whether the repository solves their robotics problem, which dependencies they need, or how to install the software.

In ROS 2, package documentation follows a structured pattern. ROS 2 packages should include in their README a description, public API definition, usage examples, build and test instructions, and license statements.[2]

Each of these elements answers a practical question for someone who finds the package:

  • Description and purpose: An explanation of what the package does and what problem it solves, written so someone encountering it for the first time can understand its role.
  • Public API definition: A clear declaration of the public application programming interface (API). The public API consists of the functions, classes, topics, services, or configuration parameters that other packages rely upon. Clearly stating the public API tells developers which interfaces will stay stable across versions.
  • Usage examples: Practical snippets showing how to launch nodes, configure parameters, or call services.
  • Build and test instructions: Step-by-step commands showing how to compile the package from source and run automated test suites.
  • License statements: A statement identifying the license and copyright governing the code.

You will write these exact README sections when you build your own software in Lesson 4.6 Writing Your First ROS 2 Package.

05. Guiding contributors: the CONTRIBUTING guide

While a README helps someone use a project, a contributing guide helps someone change it. A CONTRIBUTING document helps people contribute by explaining what types of contributions are needed and how the project development process works.[1]

Maintainers are the developers responsible for evaluating submissions, answering questions, and deciding which changes merge into a project. When maintainers write a CONTRIBUTING file, they describe their workflow so newcomers do not have to guess.

It usually covers which kinds of help are wanted and how to set up, style and submit a change.

Having a CONTRIBUTING guide lowers the barrier for new developers. Its presence shows that a project welcomes outside collaboration and offers an organized path for first-time contributors.

06. Setting community expectations: CODE_OF_CONDUCT

Technical projects succeed only when their communities remain healthy and collaborative. A CODE_OF_CONDUCT file establishes ground rules for participant behavior to facilitate a friendly, welcoming environment across the project.[1]

It says how people are expected to treat each other, and what is not acceptable.

In the Gazebo simulation project, for example, everyone participating in Gazebo is governed by the Gazebo Code of Conduct, with unacceptable behavior reported through Gazebo support.[4]

Clear behavioral standards ensure that technical discussions remain focused, constructive, and safe for beginners and experienced maintainers alike.

  • What standard sections should a ROS 2 package README include, and why is defining the public API valuable?
