3.1 Definition and Introduction

Gerald Lê

01. Deconstructing the Robot Operating System

The Robot Operating System (ROS) is the most widely adopted open-source software framework in modern robotics.[1] However, its name is a historical misnomer. ROS is not an operating system like Linux, Windows, or macOS. It does not manage low-level computer hardware, manage physical CPU interrupts, control virtual memory paging, or interface directly with hard drives.

Instead, ROS is robot middleware.[1] It runs as a set of user-space processes on top of a standard host operating system (most commonly Ubuntu Linux) to provide five fundamental software capabilities:[2]

  • Plumbing: An asynchronous, anonymous publish-subscribe message-passing architecture that lets distributed software processes talk across CPU cores or across Ethernet networks.
  • Hardware Abstraction: Clean programming interfaces that hide motor buses, serial protocols, and camera registers behind standard data structures.
  • Algorithmic Stacks: Thousands of community-maintained software packages implementing complex mathematics, including path planning, 3D point cloud filtering, visual SLAM, and arm kinematics.
  • Developer Tooling: Diagnostic utilities for 3D simulation (Gazebo), graphical sensor visualization (RViz2), node topology inspection (rqt_graph), and lossless message recording (ros2 bag).
  • Ecosystem and Build Systems: A unified package manager, automated dependency resolution tool (rosdep), and workspace build system (colcon).

02. Historical roots: Stanford and Willow Garage

The conceptual origins of ROS date back to 2007 at the Stanford Artificial Intelligence Laboratory (SAIL).[3] Stanford researchers working under Professor Andrew Ng on the STAIR project (Stanford Artificial Intelligence Robot) developed a message-passing prototype called Switchyard.[3] At the same time, Stanford graduate students Eric Berger and Keenan Wyrobek recognized that robotics research was severely handicapped because every university lab had to build its own software stack from scratch.

In late 2007, private technology incubator Willow Garage, founded in Menlo Park by early Google engineer Scott Hassan, committed significant capital and top-tier software engineers to create an open platform.[4] Willow Garage built the Personal Robot 2 (PR2), an advanced dual-arm mobile manipulation robot that proved the feasibility of a unified robot middleware.[4]

In May 2009, Morgan Quigley, Brian Gerkey, and their team published the seminal paper “ROS: an open-source Robot Operating System” at the IEEE ICRA conference in Kobe, Japan.[3] In 2012, Willow Garage spun off the Open Source Robotics Foundation (OSRF), establishing an independent non-profit foundation to guide the ecosystem.[4]

03. The node-based computational graph

In ROS 2, a robot application is organized as a computational graph.[5] The computational graph is a network of independent peer-to-peer software processes that process and exchange data concurrently.

The fundamental computational building block of this graph is the node.[5] A node is an executable program responsible for a single, well-defined task. For example, in an autonomous mobile delivery robot:

  • One node communicates with the physical lidar hardware over Ethernet, reading raw laser returns and packaging them into messages.
  • A second node reads optical wheel encoders and computes dead-reckoning odometry.
  • A third node takes the lidar scans and odometry to construct a 2D occupancy grid map using Simultaneous Localization and Mapping (SLAM).
  • A fourth node computes an obstacle-free trajectory to a target coordinate.
  • A fifth node translates the trajectory into motor velocity commands sent to the motor controllers.

This modular microservice design offers tremendous resilience. If the camera driver node crashes due to an unexpected USB bus glitch, the motor controller node and safety collision monitor continue running undisturbed. The system can restart the camera driver without rebooting the robot.

04. Topics and the publish-subscribe pattern

The most common way nodes exchange information is through topics.[6] In ROS, what is a topic? A topic is a named, unidirectional communication channel that nodes publish messages to and subscribe to.[5][6]

Topics implement the classic publish-subscribe messaging design pattern.[6] A node that generates data is a publisher; a node that receives data is a subscriber. Publishers and subscribers are completely decoupled in both space and time:

  • Anonymous Communication: A lidar driver node publishes distance scans to the topic /scan. It does not know, nor does it care, which nodes are listening. Three different nodes (a mapping node, a local obstacle detector, and a remote visualization tool on an engineer's laptop) can subscribe to /scan simultaneously.
  • Many-to-Many Decoupling: Multiple publishers can write to a single topic, and multiple subscribers can read from it.
  • Strict Message Typing: Topics are strongly typed. Every topic enforces a specific message interface defined in a .msg specification file. For example, the standard 2D laser scan message sensor_msgs/msg/LaserScan defines arrays of ranges, beam angle increments, and scan timestamps. A node cannot publish a text string onto a topic expecting a LaserScan.

06. Services: request-response transactions

While topics are ideal for continuous data flows, robotics also requires discrete, two-way Remote Procedure Calls (RPC). For example, asking a node to save the current map to disk, querying an onboard battery's health percentage, or commanding a camera to run an autofocus cycle are one-off questions that require an explicit answer.[7]

For these transactions, ROS provides services.[7] A service is a synchronous or asynchronous client-server interaction defined by a .srv file. A service specification consists of two parts separated by three hyphens (---): 

# Example: Trigger.srv
---
bool success
string message

When a client node calls a service, it sends a typed request to the server node and awaits a response. Services guarantee that the caller knows whether the requested action succeeded or failed.

07. Actions: preemptible goals with feedback

What happens when a task takes ten seconds, two minutes, or half an hour to complete, such as commanding a robot arm to pick up a bin or directing an autonomous rover to drive to a waypoint 50 meters down a warehouse corridor?

Using a topic is clumsy because there is no built-in acknowledgment of completion. Using a service is dangerous because the client would block and freeze waiting for the response for minutes, unable to process sensor inputs. Furthermore, a service cannot provide progress feedback, nor can it be easily aborted mid-execution if a human walks in front of the robot.

To solve this, ROS provides actions.[8] An action is a client-server communication pattern designed for long-running, preemptible tasks. Actions are defined by an .action specification consisting of three parts: 

# Example: NavigateToPose.action
geometry_msgs/PoseStamped pose     # 1. Goal: Where to go
---
std_msgs/Empty result               # 2. Result: Final outcome
---
geometry_msgs/PoseStamped current_pose # 3. Feedback: Periodic updates
float32 distance_remaining

An action client submits a Goal to the action server. While the robot navigates, the server continuously publishes Feedback messages (e.g., reporting current distance remaining at 10 Hz). If the operator presses an on-screen cancel button, the client sends a cancel request, and the action server safely decelerates the robot to a stop. Once the destination is reached, the server returns the final Result.[8]

08. Local parameters in ROS 2

In ROS 1, configuration values were stored on a centralized global Parameter Server managed by roscore. If two different packages defined a parameter named update_frequency, they could overwrite each other's settings, leading to hard-to-debug runtime collisions.

In ROS 2, parameters are strictly local to the individual node that owns them.[9] A node declares its parameters on startup, specifying their data types (integer, float, string, boolean, or byte array), default values, and valid numerical ranges. Parameters can be inspected, adjusted on the command line using ros2 param set, or loaded in bulk through YAML configuration files. Furthermore, ROS 2 nodes can register dynamic parameter callbacks, allowing engineers to tune PID controller gains or filter thresholds on a moving robot without restarting the software process.[9]

09. Network isolation: ROS_DOMAIN_ID

Because ROS 2 uses Data Distribution Service (DDS) as its underlying middleware, nodes discover each other automatically by broadcasting UDP multicast discovery packets across the local area network.[10]

This automatic discovery creates a serious hazard in robotics classrooms, university labs, and multi-robot factory environments. If ten students in a laboratory turn on ten separate TurtleBots on the same school Wi-Fi network, every computer discovers every robot. A student attempting to teleoperate their robot on topic /cmd_vel will inadvertently drive every other robot in the room.

To isolate robots on a shared network, ROS 2 provides the ROS_DOMAIN_ID environment variable.[11] An integer between 0 and 101, ROS_DOMAIN_ID instructs the DDS middleware to shift its UDP socket port allocations.[10][11]

Under the OMG Real-Time Publish-Subscribe (RTPS) specification, discovery and user data ports are calculated deterministically from the domain ID:[10]

  • Multicast Discovery Port: \(7400 + (250 \times \text{domain\_id})\)
  • Multicast User Data Port: \(7401 + (250 \times \text{domain\_id})\)
  • Unicast Discovery Port: \(7410 + (250 \times \text{domain\_id}) + (2 \times \text{participant\_id})\)
  • Unicast User Data Port: \(7411 + (250 \times \text{domain\_id}) + (2 \times \text{participant\_id})\)

By default, every node uses domain 0. By assigning each student or robot team a unique integer: 

export ROS_DOMAIN_ID=7

their DDS middleware broadcasts exclusively on port 9150 instead of port 7400. Nodes operating on domain 7 are completely deaf and blind to nodes running on domain 0, 1, or 42, maintaining pristine network isolation.[11]

10. Global adoption and metrics

The growth of the ROS ecosystem over the past fifteen years has transformed robotics from fragmented research silos into a global industrial standard.

According to the annual ROS Metrics Report published by Open Robotics, the community downloads over 60 million pre-compiled Debian binary packages annually from worldwide mirror farms.[12] The metrics show a rapid, decisive transition from legacy ROS 1 to ROS 2: binary downloads of ROS 2 distributions officially surpassed ROS 1 packages in 2023 and now account for over 80% of active package traffic globally.[12]

Today, more than 3,500 open-source packages are officially indexed across the ROS ecosystem, spanning everything from agricultural harvesting rovers and space exploration arms to humanoid walking controllers and surgical assistants.[12]

11. Governance and the Open Source Robotics Alliance

To ensure that ROS remains resilient, neutral, and protected from corporate control, the governance structure of the project underwent a historic evolution. In March 2024, the Open Source Robotics Foundation announced the formation of the Open Source Robotics Alliance (OSRA).[13]

The OSRA operates as a multi-stakeholder consortium bringing together industry leaders (including NVIDIA, Qualcomm, Intrinsic, Bosch, and Siemens) alongside academic institutions and open-source contributors.[13] The Alliance oversees technical project management committees for ROS 2 and Gazebo, ensuring sustainable funding, strict code review standards, and long-term release stability for decades to come.
