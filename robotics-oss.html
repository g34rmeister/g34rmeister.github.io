Chapter 3: How to Contribute to Open Source

Gerald Lê

01. Overview

Modern robotics software relies on open-source code, tools, and shared standards. Contributing to open-source projects helps you build practical experience, publish work that demonstrates your skills, and solve problems you encounter in your own robotics work. Chapter 3 introduces the structure, community norms, and contribution workflows that open-source projects use, with a focus on robotics ecosystems such as ROS 2, MoveIt 2, ros2_control, Gazebo, and Nav2.

The chapter begins with what open source is and how repositories are organized. We examine open-source software licenses, why a project without a license is not open source, and how public contributions create examples that help you build a professional reputation. We tour the core files every project maintains—README, CONTRIBUTING, CODE_OF_CONDUCT, and LICENSE—using ROS 2 packages to show how purpose, public API definitions, usage examples, and licensing are documented.

Next, we explain how to make your first contribution. Contributing to open source does not require writing complex code. Many contributions focus on documentation, issue triage, answering questions, or reviewing pull requests. We show how to find beginner-friendly tasks using issue labels such as first-timers-only, good first issue, and help wanted, and how to use aggregator websites. We then walk through the standard GitHub workflow: forking a repository, cloning locally, connecting the upstream remote, creating feature branches, keeping code in sync to prevent merge conflicts, opening draft pull requests for early feedback, and following public communication norms.

We then explore how robotics open-source projects manage development and quality. Robotics software requires strict stability and testing. We examine ROS 2 development practices, including distribution branches, merging into rolling before backporting to stable releases, prohibiting breaking API changes in released distributions, Developer Certificate of Origin (DCO) commit sign-off, build farm testing at ci.ros2.org, and package quality categories under REP 2004. We compare these practices with MoveIt 2, ros2_control, Gazebo, and Nav2. Finally, in a hands-on lab, you submit your first pull request to the robOSStics repository by fixing a typo or updating a source link directly in your browser or locally.

02. Place in the course

Chapter 3 follows Chapter 2 and connects robot programming with the broader open-source robotics ecosystem. In 2.4 Intro to ROS (Vendor-Agnostic), we introduced ROS as a common, vendor-neutral framework for programming robots. Before developing robot applications, Chapter 3 gives you the tools to explore, navigate, and contribute to open-source repositories.

The ROS chapter (Chapter 4) comes right after this one. Chapter 4 begins with 4.1 Definition and Introduction to explain what ROS is and how nodes communicate, followed by practical development in 4.6 Writing Your First ROS 2 Package and motion planning in 4.8 Moving an Arm with MoveIt 2. The hands-on lab in 3.4 requires only a web browser or a text editor and Git on your computer, with no specialized robotics hardware needed.

03. Articles in this chapter

  1. 3.1 What Open Source Is: What open source is: licenses, public artifacts, core repository files (README, CONTRIBUTING, CODE_OF_CONDUCT, LICENSE), and ROS 2 package examples.
  2. 3.2 Your First Contribution: Finding your first contribution: non-code tasks, beginner labels, the fork and pull request workflow, and public communication norms.
  3. 3.3 How Robotics Projects Work: How robotics projects work: ROS 2 rolling development, backport rules, DCO sign-off, build farm testing, and governance across MoveIt 2, ros2_control, Gazebo, and Nav2.
  4. 3.4 Lab: Your First Pull Request: Lab: making your first pull request to robOSStics by fixing a typo or broken source in the browser or locally with verification checks.
