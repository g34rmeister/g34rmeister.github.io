      4.1 Definition and Introduction

      Gerald Lê
      Chapter 4, lesson 1 of 10 ← Previous: Chapter 4 overview Next: 4.2 ROS 1 vs. ROS 2 →
      Prefer to run something first?

      This lesson and 4.2 explain how ROS 2 works. If concepts stick better once you have seen them run, install ROS 2 in 4.3 and drive the turtle in 4.4 first, then come back here. Lesson 4.4 introduces topics and services as you use them.

      01. What ROS actually is

      Building a robot takes many separate jobs, like reading a camera and spinning motors. You do not have to write all of that software from scratch. The Robot Operating System (ROS) gives you shared building blocks so those parts can talk to each other. Even with “operating system” in its name, ROS is not like Windows or Linux.

      ROS is an open-source ecosystem of frameworks, tools, and libraries for building, running, and maintaining robot applications.[1] In everyday words, it is robot middleware, meaning software that runs on top of a normal host operating system and connects your robot’s programs. The official documentation puts it plainly: ROS is “not an operating system in the traditional sense, but a set of tools and libraries” that help developers build robots on various platforms and in various programming languages.[1]

      ROS does not replace Linux, Windows, or macOS. It does not schedule central processing unit (CPU) time, manage virtual memory, or drive hard disks. Each ROS 2 distribution targets a specific Ubuntu Long Term Support (LTS) release, and Windows and macOS are also possible.[1] The documentation divides the ecosystem into five main areas:[1]

      • Framework (the “plumbing”): Messaging, standard interfaces, and support for several programming languages. For example, a camera can send images to a processing node, or a planner can send commands to a motor controller. Its basic parts are nodes, interfaces (topics, services, and actions), parameters, and client libraries.[1]
      • Tools: Utilities for inspecting what running programs are doing, analyzing data, launching nodes, and debugging. They also help you build code, visualize sensors in three dimensions (3D), and record and play back data.[1]
      • Capabilities: Ready-to-use packages for simulation, motion planning, navigation, manipulation, and perception, so you do not start from scratch.[1] The 2025 ROS Metrics Report counted 34,614 unique ROS packages available through apt.[2]
      • Community and integrations: Contributors, plus related Open Robotics platforms. These include the Gazebo simulator, Open-RMF for coordinating fleets with building systems, and ros-controls for real-time control.[1]
      • Build and dependency tools: The colcon build tool builds whole workspaces of packages.[3] Meanwhile, rosdep installs the system libraries those packages depend on.[4]

      02. How ROS started

      Before ROS existed, robotics teams kept rebuilding the same basic software over and over. Every new robot needed custom code just to pass messages between cameras, planners, and motors. ROS began as a way to stop repeating that work and share code instead. You can skim the names and dates here on a first read.

      The roots of ROS lie at Stanford University. Morgan Quigley worked there as a student on Andrew Ng’s artificial intelligence (AI) project, STAIR (Stanford AI Robot). He built a message-passing system called Switchyard. He describes it as “our first attempt at having the STAIR Project work together.”[5]

      At the same time, Eric Berger and Keenan Wyrobek ran the Personal Robotics Program in Ken Salisbury’s lab at Stanford. They saw that robotics researchers kept rebuilding the same basic software from scratch.[5]

      In 2007, Scott Hassan funded a robotics research lab called Willow Garage, drawing heavily on this Stanford work.[5][6] Willow Garage built the PR2 (Personal Robot 2), a two-armed mobile manipulator. ROS began life as the development environment for that robot.[7]

      In 2009, researchers introduced ROS in a public paper.[8][5] Later, in May 2012, the Open Source Robotics Foundation (OSRF) was created as one of several spin-offs of Willow Garage. Its goal was to continue developing ROS and the Gazebo simulator.[6]

      For the curious: Willow Garage address, exact dates, and the 2009 paper

      Scott Hassan bought a building at 68 Willow Road for Willow Garage.[5][6] The ROS team dates the start of its work to November 2007.[7][5]

      In 2009, Quigley, Gerkey, and colleagues presented the paper “ROS: an open-source Robot Operating System”. They presented it in Kobe, Japan, at a workshop held with the Institute of Electrical and Electronics Engineers (IEEE) International Conference on Robotics and Automation (ICRA), the ICRA Workshop on Open Source Software.[8][5]

      03. Splitting a robot into nodes

      A robot does many things at once, like reading sensors, planning a route, and spinning wheels. Putting all of that code into one giant program makes it hard to test and fix. Instead, ROS 2 splits your robot software into small, single-job programs called nodes. If a camera program crashes, the motor controller can keep running safely.

      In ROS 2, a robot application is organized as a graph of participants that process and exchange data.[9] The basic participant in this graph is the node, a unit of computation that should do one logical thing.[9][10] Nodes can talk to other nodes in the same process, in a different process, or on a different machine.[9]

      As an illustration (our own example), an autonomous delivery robot might be split into five nodes:

      • One node talks to the lidar hardware over Ethernet. It reads raw laser returns and packages them into messages.
      • A second node reads optical wheel encoders and computes dead-reckoning odometry. That means estimating the robot’s change in position by accumulating wheel rotations measured by encoders.
      • A third node uses the lidar scans and odometry to build a two-dimensional (2D) occupancy grid map with Simultaneous Localization and Mapping (SLAM).
      • A fourth node computes an obstacle-free trajectory to a target coordinate.
      • A fifth node turns the trajectory into velocity commands for the motor controllers.

      Splitting a robot into small nodes also helps when things go wrong. Because nodes can run as separate processes,[9] a crash in one node does not have to stop the rest. For example, a Universal Serial Bus (USB) glitch might crash the camera driver. That crash does not have to take down the motor controller or a safety monitor running in other processes. You can restart the driver on its own without rebooting the robot.

      04. Topics: streaming data between nodes

      Once your robot has separate nodes, they need a way to share live updates. Think of a radio station or a live news feed. One node broadcasts sensor readings, and any node that cares can tune in to listen. In ROS 2, those broadcast channels are called topics.

      Topics are the most common way nodes exchange information. The documentation recommends them for continuous data streams such as sensor data and robot state.[11] A topic is a named channel that nodes publish messages to and subscribe to. Any number of other nodes can subscribe to the information a node publishes.[11][12]

      Topics use the publish-subscribe pattern. A node that produces data is a publisher. A node that consumes it is a subscriber.[11]

      In everyday words, nodes do not need to know who they are talking to, and every message has a checked layout. The documentation calls ROS 2 a “strongly-typed, anonymous publish/subscribe system”:[11]

      • Anonymous Communication: A subscriber generally does not know or care which publisher sent a piece of data. You can swap out publishers and subscribers without affecting the rest of the system.[11] For example, a lidar driver can publish scans to /scan. A mapping node, an obstacle detector, and a visualization tool on an engineer’s laptop can all subscribe at once.
      • Many-to-Many Decoupling: A topic can have zero or more publishers and zero or more subscribers. Every subscriber receives the data published by any publisher. Tools such as ros2 bag record work by simply adding another subscriber.[11]
      • Strict Message Typing: Every field in a ROS message has a type that is enforced. Message types are described in .msg files.[11][13] For example, a lidar scan uses the standard sensor_msgs/msg/LaserScan message.
      For the curious: what is inside a LaserScan message

      The standard sensor_msgs/msg/LaserScan message holds a header with a timestamp, the start and end angles of the scan, the angle increment between beams, and arrays of ranges and intensities.[14]

      05. Putting nodes and topics together

      Let us trace how nodes and topics work together on a real job. Imagine an autonomous robot trying to cross a room without hitting anything. One node reads the laser scanner, a second draws the map, and a third plans the route. Each node only connects to the topics it needs.

      The diagram below shows three decoupled nodes guiding an autonomous robot over two named topics. Publishing and subscribing to named topics is the mechanism the ROS documentation describes. The node names here are our own example.[12]

      Here is how data flows through this example pipeline. First, the lidar_driver node publishes sensor_msgs/msg/LaserScan data to /scan (say, at 20 hertz (Hz), or 20 times a second). Next, the slam node subscribes to /scan, estimates the robot’s motion, and publishes updated 2D occupancy grids to the /map topic. Finally, the planner node subscribes to /map, computes an obstacle-free route, and outputs velocity targets. Because topics are anonymous, the driver and the planner never need to know that the other exists.[11]

      06. Services: asking for a quick answer

      Topics fit steady data streams, but robots also need to ask one-off questions and get a reply. For example, you might ask a node to save the current map to disk or report a battery’s health. You do not need a constant broadcast for that. You want a single request followed by a clear answer.

      In ROS 2, those one-off jobs use a remote procedure call. That means one node asks another node to run a calculation and return a result.[15]

      For these transactions, ROS provides services.[15] A service has a server, which does the work, and one or more clients, which send requests. There should only ever be one server per service name.[15] Client libraries let a client wait for the answer synchronously, or keep working and collect it asynchronously.[16]

      You define a service in a .srv file. It has a request part and a response part separated by three hyphens (---).[15][13] For example, the standard std_srvs/srv/Trigger service has an empty request and a response with a success flag and a message:[17] 

      # Example: Trigger.srv
---
bool success
string message

      When a client node calls a service, it sends a typed request to the server node. The server processes the request and returns a typed response, so the caller learns whether the request succeeded.[18][17]

      07. Actions: running long tasks you can cancel

      Some robot tasks take ten seconds, two minutes, or half an hour. For example, a robot arm might pick up a bin, or an autonomous rover might drive to a waypoint 50 meters down a warehouse corridor. For jobs that long, you want progress updates while the robot works. You also need a way to cancel the job if something changes.

      A topic gives no built-in confirmation that the job is done. A service is the wrong tool too. The documentation says services are expected to return quickly because the client is generally waiting. They should never be used for long-running processes that might need to be preempted, for example if a person walks in front of the robot.[15]

      For these tasks, ROS provides actions. An action is a long-running remote procedure call with feedback and the ability to cancel or preempt the goal.[19] You define an action in an .action file with three parts: goal, result, and feedback, separated by ---.[19][13]

      The example below is a simplified version of the NavigateToPose action used by the Nav2 navigation stack. The real definition also includes a behavior tree name, error codes, and more feedback fields.[20] 

      # Simplified from nav2_msgs/action/NavigateToPose.action
geometry_msgs/PoseStamped pose          # 1. Goal: where to go
---
uint16 error_code                       # 2. Result: final outcome
---
geometry_msgs/PoseStamped current_pose  # 3. Feedback: periodic updates
float32 distance_remaining

      Here is how an action runs. First, an action client sends a goal to the action server. While the robot drives, the server sends feedback, such as the distance remaining. If you press a cancel button, the client can cancel the goal, and the server is expected to react to the cancellation. When the task finishes, the server returns the final result.[19][21]

      08. Parameters: settings for each node

      Robots often have settings you want to tune, such as controller gains or speed limits. You should not have to edit code and restart the robot every time you tweak a number. In ROS 2, each node keeps its own live settings called parameters.

      In ROS 1, a program called roscore acted like a global parameter blackboard where every node could get and set parameters.[22] Because that store was shared, one package could change a value another package relied on.

      In ROS 2, parameters belong to the individual node that uses them. Their lifetime is tied to that node.[23][22] You can change parameters on the command line with ros2 param set. You can also save them to or load them from YAML files.[24] Nodes can register callbacks that check or react to parameter changes while running. That lets you tune values such as controller gains without restarting the process.[23]

      For the curious: allowed parameter types and descriptors

      By default, a node must declare every parameter it accepts. Each parameter value has one of a fixed set of types: bool, int64, float64, string, byte[], or arrays of bool, int64, float64, or string. A parameter’s descriptor can also hold a description and a valid value range.[23]

      09. Keeping robots separate on shared Wi-Fi: ROS_DOMAIN_ID

      When you start a ROS 2 robot, its nodes find each other automatically on the network. That saves you from typing addresses by hand. On a shared network, however, automatic search can cause chaos. Picture ten students turning on ten TurtleBots on the same school Wi-Fi. With default settings, your drive commands could move everyone else’s robot too.

      ROS 2’s default middleware is Data Distribution Service (DDS), and nodes find each other through it automatically. A new node advertises itself to other nodes in the same ROS domain, and they reply with information about themselves.[25][26] DDS discovery uses multicast, so the network interface must have multicast enabled.[27]

      That automatic discovery creates a real problem in classrooms, university labs, and multi-robot factories. If ten students run ten TurtleBots on the same Wi-Fi with default settings, every computer can discover every robot. A student teleoperating their robot on /cmd_vel may drive other robots in the room. The ROS documentation warns that running several ROS 2 systems on one network can cause this kind of interference.[27]

      To isolate robots on a shared network, ROS 2 provides the ROS_DOMAIN_ID environment variable. Nodes on the same domain can discover and message each other. Nodes on different domains cannot.[26] Behind the scenes, DDS uses the domain ID to calculate its User Datagram Protocol (UDP) ports.[26] You can test how those ports are calculated in the tool and formulas below.

      The ROS_DOMAIN_ID port calculator needs JavaScript. With it on, you can change domain ID and participant ID to calculate multicast and unicast UDP ports.

      • Multicast Discovery Port: \(7400 + (250 \times \text{domain\_id})\)
      • Multicast User Data Port: \(7401 + (250 \times \text{domain\_id})\)
      • Unicast Discovery Port: \(7410 + (250 \times \text{domain\_id}) + (2 \times \text{participant\_id})\)
      • Unicast User Data Port: \(7411 + (250 \times \text{domain\_id}) + (2 \times \text{participant\_id})\)

      By default, every node uses domain 0.[26] Give each student or robot team its own number: 

      export ROS_DOMAIN_ID=7

      That team’s multicast discovery traffic then moves from port 7400 to port 9150 (7400 + 250 × 7). Nodes on domain 7 cannot discover or exchange messages with nodes on domain 0, 1, or 42.[26]

      For the curious: domain ID limits and the DDS wire protocol

      The ROS documentation recommends choosing a domain ID between 0 and 101 inclusive. The highest ID that can be assigned at all is 232, and IDs above 101 can collide with the Linux ephemeral port range.[26]

      The port formulas follow the port mapping of the DDS wire protocol, Real-Time Publish-Subscribe (RTPS). That protocol uses a port base of 7400, a domain gain of 250, and a participant gain of 2.[26][28]

      10. ROS by the numbers

      When you learn ROS 2, you are learning a tool used across the robotics world, not just in one classroom. Its packages and patterns carry over to many kinds of real hardware. You can skim the exact download numbers on a first read.

      ROS has grown far beyond the single PR2 research robot it was built for. Today it runs on wheeled robots of all sizes, humanoids, industrial arms, self-driving cars, aerial vehicles, and more.[7]

      Open Robotics publishes a periodic ROS Metrics Report.[2] The 2025 report counted 984,135,185 ROS package downloads in 2025, an 85% increase over 2024. It describes its figures as a lower bound because some data was lost.[2] The report also shows the move to ROS 2. In October 2025, ROS 2 packages made up 91.2% of all ROS downloads.[2]

      The same report counted 34,614 unique ROS packages available through apt, which is 9% more than a year earlier. Those packages cover everything from drivers and simulators to complete navigation and manipulation stacks.[2][1]

      11. Who runs the ROS 2 project

      When an open-source tool powers thousands of companies, no single business should control it alone. ROS 2 uses a shared governance model so hardware makers, software teams, and researchers all have a voice. That keeps the project neutral and sustainable over time.

      To keep ROS neutral and sustainable, its governance changed in 2024. The Open Source Robotics Foundation announced the Open Source Robotics Alliance (OSRA), and since 2024 the ROS 2 project has been governed through it.[29][30]

      The OSRA is a membership organization that looks after ROS, Gazebo, Open-RMF, and their supporting infrastructure.[29] A higher committee oversees all OSRA projects, while a ROS Project Management Committee runs the day-to-day work on ROS 2, including reviewing code and making technical decisions.[30]

      For the curious: OSRA founding date, inaugural members, and committees

      The Open Source Robotics Foundation announced the Open Source Robotics Alliance (OSRA) on 18 March 2024. The OSRF Board assigned it ROS, Gazebo, Open-RMF, and their supporting infrastructure.[29]

      Its inaugural members included Intrinsic, NVIDIA, and Qualcomm Technologies (Platinum), Apex.AI and Zettascale (Gold), and Clearpath Robotics, Ekumen, eProsima, and PickNik (Silver).[29]

      A Technical Governance Committee oversees all OSRA projects. The ROS Project Management Committee runs the day-to-day work on ROS 2, including reviewing and merging code and making technical decisions.[30]
