      4.1 Definition and Introduction

      Gerald Lê
      Chapter 4, lesson 1 of 10 ← Previous: Chapter 4 overview Next: 4.2 ROS 1 vs. ROS 2 →
      Prefer to run something first?

      This lesson and 4.2 explain how ROS 2 works. If concepts stick better once you have seen them run, install ROS 2 in 4.3 and drive the turtle in 4.4 first, then come back here. Lesson 4.4 introduces topics and services as you use them.

      01. Deconstructing the Robot Operating System

      The Robot Operating System (ROS) is an open-source ecosystem of frameworks, tools and libraries for building, running and maintaining robot applications.[1] However, its name is a historical misnomer. The official documentation says plainly that ROS is “not an operating system in the traditional sense, but a set of tools and libraries” that help developers build robots on various platforms and in various programming languages.[1] It does not replace Linux, Windows or macOS: it does not schedule CPU time, manage virtual memory or drive hard disks.

      Instead, ROS is best described as robot middleware: software that runs on top of a normal host operating system and connects the parts of a robot program. Each ROS 2 distribution targets a specific Ubuntu LTS release, and Windows and macOS are also possible.[1] The documentation divides the ecosystem into the following areas:[1]

      • Framework (the “plumbing”): Messaging, standard interfaces and support for several programming languages, so that, for example, a camera can send images to a processing node or a planner can send commands to a motor controller. Its basic parts are nodes, interfaces (topics, services and actions), parameters and client libraries.[1]
      • Tools: Utilities for introspection, analysis, launching nodes, debugging, building, visualization (such as showing a robot's sensors in 3D) and recording and playing back data.[1]
      • Capabilities: Ready-to-use packages for simulation, motion planning, navigation, manipulation and perception, so developers do not start from scratch.[1] The 2025 ROS Metrics Report counted 34,614 unique ROS packages available through apt.[2]
      • Community and integrations: Contributors, plus related Open Robotics platforms such as the Gazebo simulator, Open-RMF for coordinating fleets with building systems, and ros-controls for real-time control.[1]
      • Build and dependency tools: The colcon build tool builds whole workspaces of packages,[3] and rosdep installs the system libraries those packages depend on.[4]

      02. Historical roots: Stanford and Willow Garage

      The roots of ROS lie at Stanford University. Morgan Quigley, then a student on Andrew Ng's STAIR (Stanford AI Robot) project, built a message-passing system called Switchyard, which he describes as “our first attempt at having the STAIR Project work together.”[5] At the same time, Eric Berger and Keenan Wyrobek were running the Personal Robotics Program in Ken Salisbury's lab at Stanford, and they saw that robotics researchers kept rebuilding the same basic software from scratch.[5]

      In 2007, Scott Hassan bought a building at 68 Willow Road and funded a robotics research lab there, Willow Garage, which drew heavily on this Stanford work.[5][6] Willow Garage built the PR2 (Personal Robot 2), a two-armed mobile manipulator, and ROS began life as the development environment for it.[7] The ROS team dates the start of its work to November 2007.[7][5]

      In 2009, Quigley, Gerkey and colleagues presented the paper “ROS: an open-source Robot Operating System”. They presented it at the ICRA Workshop on Open Source Software in Kobe, Japan, held with the IEEE International Conference on Robotics and Automation.[8][5] In May 2012 the Open Source Robotics Foundation (OSRF) was created as one of several spin-offs of Willow Garage, to continue developing ROS and the Gazebo simulator.[6]

      03. The node-based computational graph

      In ROS 2, a robot application is organized as a graph of participants that process and exchange data.[9] The basic participant in this graph is the node: a unit of computation that should do one logical thing.[9][10] Nodes can talk to other nodes in the same process, in a different process or on a different machine.[9]

      As an illustration (our own example), an autonomous delivery robot might be split into five nodes:

      • One node talks to the lidar hardware over Ethernet, reads raw laser returns and packages them into messages.
      • A second node reads optical wheel encoders and computes dead-reckoning odometry (estimating the robot’s change in position by accumulating wheel rotations measured by encoders).
      • A third node uses the lidar scans and odometry to build a 2D occupancy grid map with Simultaneous Localization and Mapping (SLAM).
      • A fourth node computes an obstacle-free trajectory to a target coordinate.
      • A fifth node turns the trajectory into velocity commands for the motor controllers.

      Splitting a robot into small nodes also helps when things go wrong. Because nodes can run as separate processes,[9] a crash in the camera driver (for example, after a USB glitch) does not have to take down the motor controller or a safety monitor running in other processes. The driver can be restarted on its own without rebooting the robot.

      04. Topics and the publish-subscribe pattern

      The most common way nodes exchange information is through topics, which the documentation recommends for continuous data streams such as sensor data and robot state.[11] A topic is a named channel that nodes publish messages to and subscribe to; any number of other nodes can subscribe to the information a node publishes.[11][12]

      Topics implement the publish-subscribe pattern. A node that produces data is a publisher, and a node that consumes it is a subscriber.[11] The documentation calls ROS 2 a “strongly-typed, anonymous publish/subscribe system”:[11]

      • Anonymous Communication: A subscriber generally does not know or care which publisher sent a piece of data. Publishers and subscribers can therefore be swapped without affecting the rest of the system.[11] For example, a lidar driver can publish scans to /scan while a mapping node, an obstacle detector and a visualization tool on an engineer's laptop all subscribe at once.
      • Many-to-Many Decoupling: A topic can have zero or more publishers and zero or more subscribers, and every subscriber receives the data published by any publisher. Tools such as ros2 bag record work by simply adding another subscriber.[11]
      • Strict Message Typing: Every field in a ROS message has a type that is enforced, and message types are described in .msg files.[11][13] For example, the standard sensor_msgs/msg/LaserScan message holds a header with a timestamp, the start and end angles of the scan, the angle increment between beams, and arrays of ranges and intensities.[14]

      The diagram below shows three decoupled nodes that guide an autonomous robot by communicating over two named topics. Publishing and subscribing to named topics is the mechanism the ROS documentation describes; the node names are our own example.[12]

      In this example pipeline, the lidar_driver publishes sensor_msgs/msg/LaserScan data to /scan (say, at 20 Hz). The slam node subscribes to /scan, estimates the robot's motion, and publishes updated 2D occupancy grids to the /map topic. The planner node subscribes to /map, computes an obstacle-free route, and outputs velocity targets. Because topics are anonymous, the driver and the planner never need to know that the other exists.[11]

      06. Services: request-response transactions

      Topics suit continuous data flows, but robots also need to ask one-off questions and get an answer. Examples include asking a node to save the current map to disk or to report a battery's health. In ROS 2 these are handled by a remote procedure call, where one node asks another to do a computation and return a result.[15]

      For these transactions, ROS provides services.[15] A service has a server, which does the work, and one or more clients, which send requests; there should only ever be one server per service name.[15] Client libraries let a client wait for the answer synchronously or continue working and collect it asynchronously.[16] A service is defined in a .srv file made of a request part and a response part separated by three hyphens (---).[15][13] The standard std_srvs/srv/Trigger service, for example, has an empty request and a response with a success flag and a message:[17] 

      # Example: Trigger.srv
---
bool success
string message

      When a client node calls a service, it sends a typed request to the server node. The server processes the request and returns a typed response, so the caller learns whether the request succeeded.[18][17]

      07. Actions: preemptible goals with feedback

      Some tasks take ten seconds, two minutes or half an hour. Examples include having a robot arm pick up a bin, or sending an autonomous rover to a waypoint 50 meters down a warehouse corridor.

      A topic gives no built-in acknowledgment that the job is done. A service is the wrong tool too. The documentation says services are expected to return quickly because the client is generally waiting. They should never be used for long-running processes that might need to be preempted, for example if a person walks in front of the robot.[15]

      For these tasks, ROS provides actions: long-running remote procedure calls with feedback and the ability to cancel or preempt the goal.[19] An action is defined in an .action file with three parts, goal, result and feedback, separated by ---.[19][13] The example below is a simplified version of the NavigateToPose action used by the Nav2 navigation stack; the real definition also includes a behavior tree name, error codes and more feedback fields.[20] 

      # Simplified from nav2_msgs/action/NavigateToPose.action
geometry_msgs/PoseStamped pose          # 1. Goal: where to go
---
uint16 error_code                       # 2. Result: final outcome
---
geometry_msgs/PoseStamped current_pose  # 3. Feedback: periodic updates
float32 distance_remaining

      An action client sends a goal to the action server. While the robot drives, the server sends feedback (for example, the distance remaining). If the operator presses a cancel button, the client can cancel the goal, and the server is expected to react to the cancellation. When the task finishes, the server returns the final result.[19][21]

      08. Local parameters in ROS 2

      In ROS 1, roscore acted like a global parameter blackboard where every node could get and set parameters.[22] Because the store was shared, one package could change a value another package relied on.

      In ROS 2, parameters belong to the individual node that uses them, and their lifetime is tied to that node.[23][22] By default a node must declare every parameter it accepts, and each parameter value has one of a fixed set of types: bool, int64, float64, string, byte[], or arrays of bool, int64, float64 or string. A parameter's descriptor can also hold a description and a valid value range.[23] Parameters can be changed on the command line with ros2 param set, and saved to or loaded from YAML files.[24] Nodes can register callbacks that check or react to parameter changes while running, so values such as controller gains can be tuned without restarting the process.[23]

      09. Network isolation: ROS_DOMAIN_ID

      ROS 2's default middleware is DDS, and nodes find each other automatically through that middleware. A new node advertises itself to other nodes in the same ROS domain, and they reply with information about themselves.[25][26] DDS discovery uses multicast, so the network interface must have multicast enabled.[27]

      This automatic discovery creates a real problem in classrooms, university labs and multi-robot factories. Suppose ten students turn on ten TurtleBots on the same school Wi-Fi network with default settings. Every computer can then discover every robot, and a student teleoperating their robot on /cmd_vel may drive other robots in the room. The ROS documentation warns that running several ROS 2 systems on one network can cause this kind of interference.[27]

      To isolate robots on a shared network, ROS 2 provides the ROS_DOMAIN_ID environment variable. Nodes on the same domain can discover and message each other, while nodes on different domains cannot.[26] The documentation recommends choosing a domain ID between 0 and 101 inclusive. The highest ID that can be assigned at all is 232, and IDs above 101 can collide with the Linux ephemeral port range.[26] DDS uses the domain ID to calculate its UDP ports.[26]

      The ports follow the port mapping of the DDS wire protocol (RTPS), with a port base of 7400, a domain gain of 250 and a participant gain of 2:[26][28]

      The ROS_DOMAIN_ID port calculator needs JavaScript. With it on, you can change domain ID and participant ID to calculate multicast and unicast UDP ports.

      • Multicast Discovery Port: \(7400 + (250 \times \text{domain\_id})\)
      • Multicast User Data Port: \(7401 + (250 \times \text{domain\_id})\)
      • Unicast Discovery Port: \(7410 + (250 \times \text{domain\_id}) + (2 \times \text{participant\_id})\)
      • Unicast User Data Port: \(7411 + (250 \times \text{domain\_id}) + (2 \times \text{participant\_id})\)

      By default, every node uses domain 0.[26] Give each student or robot team its own number: 

      export ROS_DOMAIN_ID=7

      That team's multicast discovery traffic then moves from port 7400 to port 9150 (7400 + 250 × 7). Nodes on domain 7 cannot discover or exchange messages with nodes on domain 0, 1 or 42.[26]

      10. Global adoption and metrics

      ROS has grown far beyond the single PR2 research robot it was built for. It is now used on wheeled robots of all sizes, humanoids, industrial arms, self-driving cars, aerial vehicles and more.[7]

      Open Robotics publishes a periodic ROS Metrics Report.[2] The 2025 report counted 984,135,185 ROS package downloads in 2025, an 85% increase over 2024, and describes its figures as a lower bound because some data was lost.[2] The report also shows the move to ROS 2: in October 2025, ROS 2 packages made up 91.2% of all ROS downloads.[2]

      The same report counted 34,614 unique ROS packages available through apt, 9% more than a year earlier, covering everything from drivers and simulators to complete navigation and manipulation stacks.[2][1]

      11. Governance and the Open Source Robotics Alliance

      To keep ROS neutral and sustainable, its governance changed in 2024. On 18 March 2024, the Open Source Robotics Foundation announced the Open Source Robotics Alliance (OSRA), and since 2024 the ROS 2 project has been governed through it.[29][30]

      The OSRA is a membership organization. Its inaugural members included Intrinsic, NVIDIA and Qualcomm Technologies (Platinum), Apex.AI and Zettascale (Gold), and Clearpath Robotics, Ekumen, eProsima and PickNik (Silver). The OSRF Board assigned it ROS, Gazebo, Open-RMF and their supporting infrastructure.[29] A Technical Governance Committee oversees all OSRA projects, and a ROS Project Management Committee runs the day-to-day work on ROS 2, including reviewing and merging code and making technical decisions.[30]
