      10.3 Planners, Controllers and Recoveries

      Gerald Lê
      Chapter 10, lesson 3 of 5 ← Previous: 10.2 Costmaps: How the Robot Sees Its Surroundings Next: 10.4 Behavior Trees, Actions and Lifecycle Nodes →

      01. Task servers and costmap layers

      Planners and controllers are at the heart of a mobile navigation stack.[1] In Nav2, navigation tasks are orchestrated across dedicated action servers: the planner, smoother, route, controller, and behavior servers.[1] Rather than hardcoding navigation logic into a single monolithic loop, each server hosts pluginlib plugins configured dynamically at runtime.[1] For example, a controller plugin might be given the alias FollowPath in ROS 2 parameters, with all its tuning values residing under the FollowPath.<param> namespace.[1]

      Both the global planner and local controller rely on an environmental representation provided by nav2_costmap_2d.[1] A costmap is a regular 2D grid where each cell holds an 8-bit cost value from 0 (free space) to 254 (lethal collision) or 255 (unknown space).[2] To aggregate heterogeneous sensors without conflicting data formats, Nav2 organizes costmaps as a layered stack of plugin plugins:[2], [3]

      • StaticLayer (nav2_costmap_2d::StaticLayer): Subscribes to the /map topic published by a SLAM node or map_server. It populates the baseline grid with permanent architectural features (walls, columns, safety barriers) and resizes the master costmap to match the building geometry.[3]
      • ObstacleLayer (nav2_costmap_2d::ObstacleLayer): Subscribes directly to live sensor feeds such as 2D LiDAR sensor_msgs/msg/LaserScan or 3D sensor_msgs/msg/PointCloud2. Using 2D Bresenham raycasting, it clears free space along beam rays up to raytrace_max_range (typically 3.0 m) and marks lethal obstacles up to obstacle_max_range (typically 2.5 m) within the designated height window [min_obstacle_height, max_obstacle_height]. For 3D volumetric clearance, Nav2 provides VoxelLayer and SpatioTemporalVoxelLayer.[3]
      • InflationLayer (nav2_costmap_2d::InflationLayer): Operates as the final step across all obstacle layers. It does not mark new sensor obstacles; instead, it propagates an exponential cost decay field outward from every lethal cell to ensure the robot maintains safe clearance.[2]

      The cell cost computed by the InflationLayer follows a strict mathematical piecewise formulation based on distance d from the nearest lethal obstacle:[2]

      Nav2 Inflation Cost Formula

      When d = 0, the cell is an obstacle: cost = 254 (LETHAL_OBSTACLE).
      When d ≤ rinscribed, the robot is in guaranteed collision regardless of orientation: cost = 253 (INSCRIBED_INFLATED_OBSTACLE).
      When rinscribed < d ≤ rinflation, costs decay exponentially: 

      cost = (INSCRIBED_INFLATED_OBSTACLE - 1) * exp(-cost_scaling_factor * (d - r_inscribed))

      When d > rinflation, the cell is completely clear: cost = 0 (FREE_SPACE).

      Here rinscribed is the radius of the largest circle fitting entirely inside the robot’s footprint (configured as robot_radius or derived from polygon vertices).[2] The parameter cost_scaling_factor (typically 3.0 in local costmaps, 10.0 default) controls the steepness of the penalty gradient: a large scaling factor produces a sharp cliff that drops to zero quickly, allowing the robot to pass through narrow corridors, while a smaller scaling factor creates a wide repulsive potential that pulls paths toward the open centerline of aisles.[2], [3]

      In production systems, Nav2 instantiates two distinct costmaps configured via YAML parameters:[3] 

      # Excerpt from nav2_params.yaml
global_costmap:
  global_costmap:
    ros__parameters:
      update_frequency: 1.0
      publish_frequency: 1.0
      global_frame: map
      robot_base_frame: base_link
      robot_radius: 0.22
      resolution: 0.05
      track_unknown_space: true
      plugins: ["static_layer", "obstacle_layer", "inflation_layer"]
      static_layer:
        plugin: "nav2_costmap_2d::StaticLayer"
        map_subscribe_transient_local: true
      obstacle_layer:
        plugin: "nav2_costmap_2d::ObstacleLayer"
        enabled: true
        observation_sources: scan
        scan:
          topic: scan
          max_obstacle_height: 2.0
          clearing: true
          marking: true
          data_type: "LaserScan"
          raytrace_max_range: 3.0
          obstacle_max_range: 2.5
      inflation_layer:
        plugin: "nav2_costmap_2d::InflationLayer"
        cost_scaling_factor: 3.0
        inflation_radius: 0.70

local_costmap:
  local_costmap:
    ros__parameters:
      update_frequency: 5.0
      publish_frequency: 2.0
      global_frame: odom
      robot_base_frame: base_link
      rolling_window: true
      width: 3
      height: 3
      resolution: 0.05
      robot_radius: 0.22
      plugins: ["voxel_layer", "inflation_layer"]
      inflation_layer:
        plugin: "nav2_costmap_2d::InflationLayer"
        cost_scaling_factor: 3.0
        inflation_radius: 0.70

      Notice the design contrast: the global_costmap uses the fixed map frame, includes the static_layer, and updates at 1 Hz to cover the entire building for long-range planning. The local_costmap operates in the continuous odom frame, enables rolling_window: true (a 3×3 m sliding grid centered on the robot base), updates at 5 Hz directly from sensor voxels, and discards stale static information for reactive obstacle avoidance.[3]

      02. Global path planners

      The planner server computes an obstacle-free, kinematically valid path from the robot’s current pose to a target goal pose using the global costmap.[1] Nav2 supports multiple swappable planner plugins:[4]

      • NavFn Planner (nav2_navfn_planner::NavfnPlanner): The legacy ROS navigation mainstay. It computes a global navigation function using Dijkstra’s wave-front propagation or 2D A* over the grid. It assumes the robot is a holonomic point mass. While computationally fast (~100–150 ms on large maps), it produces paths with angular discontinuities and tends to cut corners closely around obstacles, requiring aggressive downstream path smoothing.[1], [4]
      • Smac Planner 2D (nav2_smac_planner::SmacPlanner2D): A modern, cost-aware 2D A* implementation on 4- or 8-connected grid graphs. Unlike naive search, it includes a cost_travel_multiplier parameter (default 2.0) that penalizes traveling through inflated costmap cells, naturally guiding the robot down corridor centerlines. It features built-in multi-resolution costmap downsampling (e.g. searching a 5 cm grid at 10 cm via downsampling_factor: 2) and an integrated conjugate gradient smoother. Ideal for circular differential-drive and omnidirectional robots.[4]
      • Smac Planner Hybrid-A* (nav2_smac_planner::SmacPlannerHybrid): A kinematically feasible SE(2) path planner for non-holonomic, car-like (Ackermann) and industrial mobile robots constrained by a physical minimum_turning_radius (e.g., 0.4 m). It discretizes headings into angular quantization bins (typically 72 bins, yielding 5° resolution). It generates curvature-continuous trajectories using Dubins or Reeds-Shepp motion models, supports bidirectional search with a configurable reverse_penalty, and executes frequent analytic expansions to snap directly to the target pose once within heuristic distance.[4]
      Planner Plugin State Space Kinematic Feasibility Reversing Support Key Tuning Parameters Typical Drivetrain
      NavFn 2D Grid (x, y) No (point mass) No tolerance, use_astar Differential, Omnidirectional
      Smac 2D 2D Grid (x, y) No (cost-aware grid) No cost_travel_multiplier, downsampling_factor Differential, Omnidirectional
      Smac Hybrid-A* SE(2) (x, y, θ) Yes (curvature bounded) Yes (Reeds-Shepp) minimum_turning_radius, reverse_penalty, angle_quantization_bins Ackermann, Car-like, Industrial AMRs

      To configure a planner in nav2_params.yaml:[3], [4] 

      planner_server:
  ros__parameters:
    expected_planner_frequency: 20.0
    planner_plugins: ["GridBased"]
    GridBased:
      plugin: "nav2_smac_planner::SmacPlanner2D"
      tolerance: 0.125
      downsample_costmap: false
      allow_unknown: true
      max_iterations: 1000000
      max_planning_time: 2.0
      cost_travel_multiplier: 2.0
      smoother:
        max_iterations: 1000
        w_smooth: 0.3
        w_data: 0.2
        tolerance: 1.0e-10

      03. Smoothers and the route server

      A smoother receives a planned path and returns an improved version. Smoothers typically reduce path raggedness, smooth abrupt rotations, and increase distance from high-cost obstacles using gradient-based optimization algorithms like SimpleSmoother or SavitzkyGolaySmoother.[1] When paired with non-holonomic planners such as Hybrid-A*, smoothers respect cusp points where the robot shifts between forward and reverse gears via enforce_path_inversion: true.[3]

      The route server is a specialized planner. It computes a route through a predefined navigation graph, not through the free-space costmap.[1] The graph can represent designated warehouse aisles, virtual highway lanes, or teach-and-repeat paths, scored by plugins like DistanceScorer and CostmapScorer.[1], [3]

      04. Local trajectory controllers

      While global planners operate periodically at 1–2 Hz over whole maps, controllers (historically termed “local planners” in ROS 1) execute in a tight real-time control loop at 20–50 Hz.[1] A controller evaluates the local costmap, inspects current robot odometry, and outputs feasible velocity commands (geometry_msgs/msg/Twist on cmd_vel) to track the path while dodging dynamic obstacles.[1] Nav2 features three premier controller architectures:[5], [6], [7]

      • DWB Controller (dwb_core::DWBLocalPlanner): An extensible, modular reimplementation of the Dynamic Window Approach (DWA). At each tick, it discretely samples reachable velocity pairs (vx, vy, ω) within the robot’s acceleration limits (acc_lim_x, acc_lim_theta) and forward-simulates short trajectory arcs over sim_time (typically 1.7 s). Each trajectory is scored against a customizable array of critic plugins:[5]
        • ObstacleFootprintCritic / BaseObstacleCritic: Discards or heavily penalizes rollouts colliding with obstacles or entering inflated cost zones.
        • PathAlignCritic and PathDistCritic: Scores alignment with the path heading and minimizes lateral offset from the planned path.
        • GoalAlignCritic and GoalDistCritic: Pulls the robot directly toward the final goal pose when within sight.
        • RotateToGoalCritic: Guides in-place rotation to match the target orientation once within spatial tolerance.
        • OscillationCritic: Penalizes rapid directional flipping that causes robots to jitter in tight doorways.
      • Regulated Pure Pursuit (nav2_regulated_pure_pursuit_controller::RegulatedPurePursuitController): A geometric tracking algorithm designed specifically for industrial service robots and AMRs. Rather than brute-force velocity sampling, it computes the exact circular arc required to steer the robot toward a lookahead point (“carrot”) placed on the path at distance L = clamp(v · tlookahead, Lmin, Lmax).[6] Crucially, it introduces three adaptive regulation mechanisms:[6]
        • Curvature Regulation: Automatically decelerates the linear velocity around sharp curves (when path turning radius drops below regulated_linear_scaling_min_radius), preventing high-speed centrifugal skidding.
        • Cost Proximity Regulation: Scales linear speed down as the robot approaches high-cost obstacles within cost_scaling_dist, granting sensors more integration time in tight corridors.
        • Approach Velocity Scaling: Linearly ramps speed down to min_approach_linear_velocity over approach_velocity_scaling_dist to achieve clean, overshoot-free stops.
        It verifies safety by projecting the robot footprint forward along the lookahead arc up to max_allowed_time_to_collision_up_to_carrot, halting immediately if a collision is imminent.[6]
      • MPPI Controller (nav2_mppi_controller::MPPIController): Model Predictive Path Integral controller, an advanced stochastic Model Predictive Control (MPC) algorithm. Unlike traditional gradient-based MPC, MPPI does not require objective functions to be convex or mathematically differentiable.[7] At each control cycle, it applies Gaussian perturbations to the previous optimal control sequence to generate a large batch (e.g. 1000–2000) of candidate rollouts across a prediction horizon (time_steps: 56 with model_dt: 0.05 yielding 2.8 seconds). These rollouts are forward-simulated through kinematically verified motion models (DiffDrive, Omni, Ackermann) and scored by critic plugins. The optimal control is computed as a softmax-weighted sum across the batch, running effortlessly at 30–100+ Hz on modern multi-core CPUs.[7]

      DWB Discrete velocity space grid sampling (DWA) Short arc (1.5–2.0 s) Critic scoring (rejects colliding velocity pairs) Low–Moderate sim_time, vx_samples, critics.*.scale
      Regulated Pure Pursuit (RPP) Geometric carrot pursuit with adaptive velocity scaling Lookahead distance (0.3–1.0 m) Forward collision checks along lookahead arc Minimal (lightweight) lookahead_time, cost_scaling_dist, regulated_linear_scaling_min_radius
      MPPI Stochastic sampling and softmax path-integral optimization Multi-step trajectory (2.0–4.0 s, 56 steps) Trajectory scoring across batch (1000+ rollouts) High (multi-threaded SIMD) batch_size, time_steps, model_dt, temperature

      05. Behaviors and recovery

      Recovery behaviors deal with unknown or failure conditions and handle them autonomously.[1] In Nav2, the behavior_server hosts modular behavior plugins that share costmaps and TF buffers without duplicating expensive memory instances:[1], [3]

      • ClearCostmap: Flushes accumulated sensor artifacts or ghost obstacles from costmaps when dynamic obstructions have moved or perception filters misbehaved.[1]
      • Spin: Rotates the robot in place (e.g. 1.57 or 3.14 rad) to clear sensor blind spots and recalculate valid free-space paths.[1], [3]
      • BackUp: Reverses a designated distance (e.g. 0.30 m) at low speed to extract the robot from tight cul-de-sacs or doorway bottlenecks.[1], [3]
      • Wait: Pauses execution for a configurable duration (e.g. 5.0 s) to allow transient obstacles, such as pedestrians or forklifts, to clear the aisle.[1], [3]

      If autonomous recovery routines fail, a final recovery handler can trigger remote operator alerts via SMS, Slack, or factory SCADA systems.[1]

      06. Waypoints and fleets

      The nav2_waypoint_follower sends the robot to several destinations and has a plugin interface for a task at each one, such as taking a picture, picking up a box or waiting for user input.[1] Nav2 describes two schools of thought for fleets: a dumb robot with a smart centralized dispatcher, or a smart robot with a dumb one.[1] In the first, a request to the waypoint follower is one unit of work, such as one pick in a warehouse, after which the robot returns to the dispatcher for its next task.[1] In the second, the robot runs its own high-level mission behavior tree, managing battery levels, docking, and multi-step tasks locally.[1]

      07. Check your understanding

      • What is the role of each layer in Nav2’s standard costmap stack (StaticLayer, ObstacleLayer, InflationLayer), and what cost is assigned to cells within the inscribed radius?
        Show answer

        StaticLayer loads permanent architectural geometry from /map; ObstacleLayer processes live 2D/3D sensor feeds using raycasting to clear free space and mark occupied obstacles; InflationLayer propagates an exponential cost decay field outward from obstacles. Any cell within the robot’s inscribed radius receives a cost of 253 (INSCRIBED_INFLATED_OBSTACLE), signifying that any robot rotation at that cell is a guaranteed collision. (Section 01)

      • How does the cost_scaling_factor parameter affect path planning around obstacles?
        Show answer

        It controls the exponential decay rate. A larger scaling factor causes cost to drop steeply with distance, allowing the planner to route closer to obstacles and through narrower doorways; a smaller scaling factor creates a gradual cost slope across the inflation radius, strongly repelling paths toward the centerline of corridors. (Section 01)

      • How do NavFn, Smac 2D, and Smac Hybrid-A* differ in kinematic feasibility and robot compatibility?
        Show answer

        NavFn plans via 2D Dijkstra/A* assuming a circular point mass (fast but cuts corners and lacks kinematic feasibility); Smac 2D is a cost-aware 2D A* planner that uses a cost travel multiplier to stay centered in aisles for differential/omnidirectional bases; Smac Hybrid-A* plans in SE(2) space (x, y, θ) with minimum turning radius and Reeds-Shepp reversing constraints, ensuring kinematically feasible trajectories for car-like (Ackermann) and non-holonomic vehicles. (Section 02)

      • What are the primary operational differences between DWB, Regulated Pure Pursuit, and MPPI controllers?
        Show answer

        DWB discretely samples achievable velocity pairs and scores short forward arcs using weighted critic plugins; Regulated Pure Pursuit geometrically pursues a carrot on the path while adaptively regulating linear speed for curvature, obstacle proximity, and goal approach; MPPI stochastically samples large batches (1000+ rollouts) across a multi-second prediction horizon and optimizes control via softmax weighting, excelling at high speeds and complex vehicle kinematics. (Section 04)

      • How does the route server differ from a standard costmap planner?
        Show answer

        The route server computes a route through a predefined topological navigation graph (such as designated warehouse aisles, AGV guide paths, or virtual road networks) rather than searching through the unconstrained free-space costmap grid. (Section 03)

      Try it
      1. You are commissioning an Ackermann-steered autonomous industrial tugger with a 1.2 m minimum turning radius in a manufacturing plant. Which global planner and which local controller should you select, and which specific kinematic parameters must you configure?
      2. A differential-drive AMR struggles to navigate through a narrow 1.0 m doorway between warehouse aisles because the global planner treats the passage as impassable. The robot’s inscribed radius is 0.3 m. Which costmap parameter should you tune in nav2_params.yaml, and should you increase or decrease it?
      3. A mobile delivery robot in a hospital corridor must navigate smoothly around oncoming medical carts without jerky, abrupt stops. Contrast how Regulated Pure Pursuit’s cost proximity regulation and MPPI’s stochastic batch rollouts handle this dynamic obstacle encounter.
