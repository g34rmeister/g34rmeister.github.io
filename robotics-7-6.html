      7.6 Lab: A ROS 2 Camera Pipeline

      Gerald Lê
      Chapter 7, lesson 6 of 6 ← Previous: 7.5 Inspection and Measurement Next: Chapter 8: Industrial Networks →

      01. Cameras in the ROS 2 architecture

      In a robot cell, the camera is often the robot's main way of seeing what has changed. In earlier chapters, we examined how ROS 2 nodes communicate over topics to coordinate robot trajectories and handle sensor streams. In Lesson 4.6 Writing Your First ROS 2 Package, you wrote a Python node with the rclpy client library, built it with colcon and ran it. In Lesson 2.8 Vision-Guided Picking, you explored how physical cameras are mounted in eye-in-hand or eye-to-hand configurations and calibrated relative to robot work coordinates.

      A ROS 2 vision architecture keeps hardware device drivers separate from high-level computer vision processing. At the hardware boundary, a dedicated camera driver node talks directly to the camera sensor over an industrial bus. Industrial machine vision cameras follow standard device architectures so that the same software works across hardware vendors. The GenICam standard provides a generic programming interface for all camera types regardless of interface hardware.[1]

      For example, a ROS 2 driver node can interact with camera features such as exposure time and gain through standardized interfaces without custom code for every vendor. The driver node converts incoming hardware image frames into standard ROS 2 messages and publishes them across the middleware graph. Downstream perception nodes subscribe to these published topics, execute image filtering or geometric feature extraction, and send target grasp poses or quality inspection flags to robot motion controllers.

      To understand the modular structure of this pipeline, here is how the work is split across separate ROS 2 nodes:

      • Camera driver node: Interfaces directly with the camera hardware or simulator. It queries raw pixel buffers from the sensor, attaches precise timestamp and optical coordinate frame metadata, and publishes synchronized message streams.
      • Image processing node: Subscribes to the raw image topic, converts serialized message buffers into multidimensional arrays, applies OpenCV filtering algorithms, and publishes annotated diagnostic images.
      • Perception and motion control nodes: Take in extracted workpiece bounding boxes, part centroid coordinates, or edge contours to calculate robot grasping trajectories or trigger sorting mechanisms.

      02. Image data representation: sensor_msgs/Image

      So that nodes written in Python, C++ or Rust can exchange images, ROS 2 standardizes the representation of digital raster frames. The sensor_msgs/Image message defines uncompressed raster image data using height, width, and encoding fields.[2]

      Every image message begins with a standard ROS header structure containing timing and coordinate frame metadata. In sensor_msgs/Image the header timestamp represents image acquisition time and frame_id specifies the optical frame of the camera.[2] A driver should stamp each image with the time it was captured. That timestamp is needed to match vision data with joint encoder states when a robot arm moves while its eye-in-hand camera takes images, or when tracking moving conveyor belts.

      The frame_id field ties the camera data to the robot kinematic coordinate tree maintained by the TF2 transform library. In the ROS optical camera coordinate frame, +x points right, +y points down, and +z points into the image plane.[2] This optical convention places the coordinate origin directly at the camera's optical center. This differs from standard robot body coordinate frames (where +x points forward, +y points left, and +z points upward), which is why transform trees are needed when mapping 2D pixel coordinates into 3D robot grasping poses.

      The remaining fields describe how the pixel data is laid out in memory. The height field specifies the number of image rows, while width specifies the number of image columns. The encoding string defines channel organization and color bit depth, such as "bgr8", "rgb8", or "mono8". In sensor_msgs/Image the step field indicates full row length in bytes, making total matrix data size equal to step times rows.[2]

      For example, consider an uncompressed color camera streaming at a resolution of 1,920 columns by 1,080 rows with an encoding of “bgr8”. Each color pixel requires 3 bytes (one byte each for blue, green, and red), yielding a full row step of 1,920 × 3 = 5,760 bytes. The complete image data payload in the data byte array evaluates to 5,760 × 1,080 = 6,220,800 bytes per frame. Suppose the camera instead streams a single-channel 8-bit monochrome stream (“mono8”) at a resolution of 640 columns by 480 rows. Here each row requires exactly 640 bytes, producing a message data array of 640 × 480 = 307,200 bytes.

      Understanding the distinction between width × bytes_per_pixel and the step field matters when rows are padded. In some hardware drivers and image processing pipelines, memory buffers are padded to 32-byte or 64-byte boundaries to improve memory alignment on host processors. For example, imagine a monochrome image with a width of 642 pixels. A hardware driver might pad each row to 672 bytes to satisfy memory alignment requirements. In that scenario, reading only width bytes per row would cause subsequent scanlines to drift diagonally across the raster buffer. Relying on the step field guarantees that subscriber nodes calculate row offsets accurately regardless of internal memory padding.

      03. Calibration metadata: sensor_msgs/CameraInfo

      Raw pixel buffers alone are not enough for robotic manipulation. To determine where an imaged object is located in three-dimensional physical space, downstream nodes require precise optical and geometric calibration parameters. A camera driver node therefore publishes a synchronized companion sensor_msgs/msg/CameraInfo message alongside every sensor_msgs/msg/Image message.

      The CameraInfo message specifies mathematical models of lens distortion and projective geometry. The plumb_bob distortion model in sensor_msgs/CameraInfo represents standard radial and tangential lens distortion.[3] The distortion parameters array D for the plumb_bob model consists of five coefficients: k1, k2, t1, t2, and k3.[3] Coefficients k1, k2, k3 model radial lens distortion (such as barrel or pincushion distortion), while coefficients t1, t2 model tangential distortion caused by slight physical misalignments between optical glass elements and the sensor plane.

      The geometric mapping between 3D camera coordinates and 2D pixel coordinates is parameterized by three distinct matrix structures:

      • Intrinsic camera matrix K: The 3x3 intrinsic camera matrix K projects 3D camera frame coordinates to 2D pixel coordinates using focal lengths and principal point offsets.[3] It is stored as a 9-element row-major array [fx, 0, cx, 0, fy, cy, 0, 0, 1]. It defines horizontal and vertical focal lengths fx, fy in pixel units, along with optical principal point coordinates cx, cy.
      • Rectification matrix R: The sensor_msgs/CameraInfo rectification matrix R is a 3x3 row-major rotation matrix that aligns coordinates to the rectified camera frame.[3] In monocular setups, R is typically an identity matrix, whereas in stereo vision systems, R aligns left and right optical sensors into a shared parallel image plane.
      • Projection matrix P: The projection matrix P in sensor_msgs/CameraInfo is a 3x4 row-major matrix specifying the intrinsic matrix of the rectified image.[3] It projects 3D points directly into rectified 2D pixel coordinates, so downstream algorithms do not have to repeat the non-linear undistortion step.

      For example, imagine a calibrated monocular camera whose intrinsic matrix K has focal lengths fx = 800.0, fy = 800.0 pixels and principal point offsets cx = 320.0, cy = 240.0 pixels. Suppose a workpiece corner is located at physical 3D camera coordinates [X, Y, Z] = [0.10 m, 0.05 m, 1.00 m]. Under ideal pinhole projection, the normalized coordinates evaluate to x' = X / Z = 0.10 and y' = Y / Z = 0.05. Multiplying by the focal lengths and adding the principal point offsets gives the pixel coordinates. The horizontal pixel coordinate is u = 800.0 × 0.10 + 320.0 = 400.0 pixels. The vertical pixel coordinate is v = 800.0 × 0.05 + 240.0 = 280.0 pixels. When lens distortion is present, downstream rectification nodes use the coefficients in D alongside matrix K. They remap raw distorted pixels into ideal rectilinear coordinates described by matrix P.

      The pinhole camera projection calculator needs JavaScript. With it on, you can adjust 3D coordinates and focal length to project physical points to 2D pixel coordinates.

      04. Streaming transport and message synchronization

      A single 1080p uncompressed color stream at 30 frames per second generates over 180 megabytes per second of raw data. Multiple perception nodes might subscribe to an uncompressed camera topic across an industrial Ethernet switch or wireless network. In that case, the physical bus can become saturated, resulting in dropped packets and processing jitter.

      To manage network load, ROS 2 provides the image_transport package. The image_transport tutorials demonstrate how to publish and subscribe to camera streams across discoverable transport plugins.[4] Instead of building compression into the driver, image_transport allows an application to publish a single base topic (such as /camera/image_raw). image_transport finds the transport plugins installed on the system at runtime, and each one advertises an extra topic derived from the base topic. For example, with the compressed plugin installed (the compressed_image_transport package), a JPEG- or PNG-compressed copy appears on /camera/image_raw/compressed.[4] Downstream subscriber nodes can select their preferred transport plugin at runtime depending on available network bandwidth and CPU resources.

      When an algorithm needs both an image and its matching calibration, subscribing to the two topics independently can cause race conditions. The message_filters TimeSynchronizer synchronizes incoming message streams based on matching timestamps in their message headers.[5] When incoming messages arrive on /camera/image_raw and /camera/camera_info, TimeSynchronizer pairs messages that carry identical header timestamps before invoking the user callback. This synchronization guarantees that image frames are never processed with stale or misaligned calibration metadata.

      For example, suppose a vision node requires synchronized access to both image data and calibration parameters. In Python, the node constructs two message_filters.Subscriber objects, passing the node, the message type and the topic name. It then creates a TimeSynchronizer filter that takes both filter sources and a queue size (such as 10 frames). The node registers a dual-argument callback sync_callback(image_msg, info_msg) using registerCallback. Whenever an image message and a calibration message share identical header timestamps, the synchronizer invokes the callback with both messages matched together. If one message arrives late, the synchronizer holds the other in its queue until the match arrives or the queue overflows, so the callback never sees an image paired with the wrong calibration.

      05. Bridging ROS 2 and OpenCV with cv_bridge

      ROS 2 sends images as serialized byte buffers inside standard messages, but practical computer vision code in Python and C++ relies on optimized libraries such as OpenCV. In Python, OpenCV represents images as multidimensional NumPy arrays (numpy.ndarray). The cv_bridge library converts between ROS 2 message buffers and OpenCV image matrices.

      The cv_bridge package converts in both directions, handling memory buffers, channel order, and color conversion. In cv_bridge, imgmsg_to_cv2 converts a ROS Image message into an OpenCV NumPy image with an optional desired_encoding format.[6] You can specify the desired_encoding parameter (such as "bgr8" or "mono8"). The camera hardware might transmit data in RGB, BGR, or Bayer formats. Regardless of the input format, this ensures the output NumPy array is converted into the exact memory layout expected by your OpenCV algorithms.

      An OpenCV pipeline analyzes or annotates an image matrix. The resulting NumPy array often needs to be re-published onto the ROS 2 network for visualization in RViz2 or logging with ros2 bag. In cv_bridge, cv2_to_imgmsg converts an OpenCV image array into a ROS Image message with a specified pixel encoding string.[6] This function formats the NumPy array into a compliant sensor_msgs/msg/Image message. It includes calculated row step bytes and matching encoding metadata, ready for immediate publication.

      For example, imagine a driver publishes a raw monochrome image formatted with "mono8" encoding. If downstream algorithms expect color representation, calling bridge.imgmsg_to_cv2(msg, desired_encoding='bgr8') converts the single-channel buffer into a three-channel BGR NumPy array where blue, green, and red channels replicate the grayscale intensity. Conversely, passing desired_encoding='passthrough' keeps the source encoding without converting the pixel channels. Industrial nodes also wrap conversion calls inside try...except CvBridgeError blocks. If a driver sends an encoding cv_bridge cannot convert, the node logs the error and skips that frame instead of crashing the robot control process.

      06. Lab: Implementing an OpenCV vision node

      In this hands-on lab exercise, you will implement an end-to-end Python ROS 2 node. It subscribes to an incoming camera stream and converts image messages with cv_bridge. It then applies OpenCV color conversion, binary thresholding, and Canny edge detection, and publishes the processed results.

      Computer vision pipelines routinely convert multi-channel color images into single-channel representations to reduce computation. The cv.cvtColor function converts an image from one color space to another using conversion codes such as cv.COLOR_BGR2GRAY.[7] For example, converting a 3-channel BGR image into a 1-channel grayscale image reduces array memory volume by two-thirds, so later spatial filters run faster.

      Once an image is converted to single-channel intensity, binarization isolates candidate foreground workpieces from the background fixture or conveyor. Simple binary thresholding with cv.threshold assigns pixels above a threshold value to maxval and all other pixels to zero.[8] For example, consider setting a threshold parameter of 128 with a maximum value of 255. All bright workpiece pixels exceeding 128 are assigned to 255 (pure white), while darker background pixels are assigned to 0 (pure black).

      Edge detection finds part boundaries and contours for robot inspection by locating sharp changes in intensity. The Canny edge detector uses hysteresis thresholding with minVal and maxVal to distinguish true edges from noise.[9] For example, gradient values exceeding maxVal are immediately classified as confirmed edges, while gradients falling below minVal are discarded. Pixels with gradient values between minVal and maxVal are retained only if they connect directly to confirmed edge pixels, preserving continuous object boundaries while eliminating spurious noise.

      The complete Python node implementation is structured into six logical steps:

      1. Parameter declaration: In the node constructor, declare ROS 2 parameters for binary_threshold, canny_min_val, and canny_max_val so that threshold parameters can be changed at runtime without recompiling code.
      2. Subscription and publishers: Subscribe to the raw camera stream on topic /camera/image_raw, and create two image publishers on /vision/thresh_image and /vision/edge_image.
      3. Image conversion: In the subscription callback, invoke bridge.imgmsg_to_cv2(msg, desired_encoding='bgr8') to extract an OpenCV-compatible BGR NumPy array.
      4. Image filtering: Convert the BGR array to grayscale using cv.cvtColor(cv_bgr, cv.COLOR_BGR2GRAY), apply binary thresholding using cv.threshold, and execute Canny edge detection using cv.Canny.
      5. Header preservation and message conversion: Convert the resulting binary and edge NumPy arrays back into ROS 2 image messages using bridge.cv2_to_imgmsg(..., encoding='mono8'). Copy the original incoming message header (msg.header) to both output messages so that downstream nodes retain image acquisition timestamps and camera frame_id metadata.
      6. Publication: Publish both processed image messages onto their respective ROS 2 topics.

      The following Python script implements this complete vision processing pipeline inside an rclpy Node class: 

      import rclpy
from rclpy.node import Node
from sensor_msgs.msg import Image
from cv_bridge import CvBridge, CvBridgeError
import cv2 as cv

class VisionPipelineNode(Node):
    def __init__(self):
        super().__init__('vision_pipeline_node')
        
        # Initialize cv_bridge instance
        self.bridge = CvBridge()
        
        # Declare configurable threshold parameters
        self.declare_parameter('binary_threshold', 128.0)
        self.declare_parameter('canny_min_val', 50.0)
        self.declare_parameter('canny_max_val', 150.0)
        
        # Subscribe to camera image stream
        self.sub_image = self.create_subscription(
            Image,
            '/camera/image_raw',
            self.image_callback,
            10
        )
        
        # Publish processed edge and threshold images
        self.pub_edges = self.create_publisher(Image, '/vision/edge_image', 10)
        self.pub_thresh = self.create_publisher(Image, '/vision/thresh_image', 10)
        
        self.get_logger().info('Vision pipeline node initialized and waiting for camera images.')

    def image_callback(self, msg: Image):
        try:
            # Convert ROS Image message to OpenCV BGR array
            cv_bgr = self.bridge.imgmsg_to_cv2(msg, desired_encoding='bgr8')
        except CvBridgeError as err:
            self.get_logger().error(f'Failed to convert ROS image: {err}')
            return

        # 1. Convert BGR color image to single-channel grayscale
        cv_gray = cv.cvtColor(cv_bgr, cv.COLOR_BGR2GRAY)
        
        # 2. Apply simple binary thresholding
        thresh_val = self.get_parameter('binary_threshold').value
        _, cv_thresh = cv.threshold(cv_gray, thresh_val, 255, cv.THRESH_BINARY)
        
        # 3. Apply Canny edge detection with hysteresis thresholding
        canny_min = self.get_parameter('canny_min_val').value
        canny_max = self.get_parameter('canny_max_val').value
        cv_edges = cv.Canny(cv_gray, canny_min, canny_max, apertureSize=3)
        
        try:
            # Convert OpenCV arrays back to ROS Image messages
            msg_thresh = self.bridge.cv2_to_imgmsg(cv_thresh, encoding='mono8')
            msg_thresh.header = msg.header  # Preserve timestamp and optical frame_id
            
            msg_edges = self.bridge.cv2_to_imgmsg(cv_edges, encoding='mono8')
            msg_edges.header = msg.header   # Preserve timestamp and optical frame_id
            
            # Publish processed streams
            self.pub_thresh.publish(msg_thresh)
            self.pub_edges.publish(msg_edges)
        except CvBridgeError as err:
            self.get_logger().error(f'Failed to publish processed image: {err}')

def main(args=None):
    rclpy.init(args=args)
    node = VisionPipelineNode()
    try:
        rclpy.spin(node)
    except KeyboardInterrupt:
        node.get_logger().info('Shutting down vision pipeline node.')
    finally:
        node.destroy_node()
        rclpy.shutdown()

if __name__ == '__main__':
    main()

      07. Running and testing the node

      Put the script in an ament_python package the same way as in 4.6. Add rclpy, sensor_msgs and cv_bridge as dependencies in package.xml. Next, register the script as an entry point, then build with colcon and source the workspace. If cv_bridge is missing, install ros-lyrical-cv-bridge.

      You do not need a camera to test the node. The image_tools demo package has a cam2image executable that publishes images from the computer's default camera on the /image topic. With burger_mode turned on, it publishes a generated test image instead.[10] Remap its topic to the one your node subscribes to: 

      # Terminal 1: test images, no camera needed
ros2 run image_tools cam2image --ros-args -p burger_mode:=true -r image:=/camera/image_raw

# Terminal 2: your node (use your package and entry point names)
ros2 run vision_lab vision_pipeline

# Terminal 3: change a threshold while the node runs
ros2 param set /vision_pipeline_node binary_threshold 100.0

      Then check the pipeline with the ROS 2 command-line tools:

      1. Inspect active topics: Verify that the camera driver and vision node are actively publishing by running ros2 topic list in a terminal. You should see /camera/image_raw, /vision/thresh_image and /vision/edge_image, plus /camera/camera_info when a real camera driver is running.
      2. Inspect topic metadata: Run ros2 topic info /camera/image_raw to verify that the message type is sensor_msgs/msg/Image and to confirm publisher and subscriber counts.
      3. Verify calibration metadata (real camera driver only; cam2image does not publish it): Execute ros2 topic echo /camera/camera_info --once to confirm that the camera driver publishes valid calibration parameters. Check that the distortion model specifies plumb_bob, and that the distortion parameters array d contains the five coefficients [k1, k2, t1, t2, k3]. Also check that intrinsic matrix k and projection matrix p contain non-zero focal lengths and principal point values.
      4. Measure streaming frequency: Check that edge processing meets real-time cycle deadlines by executing ros2 topic hz /vision/edge_image. The rate should match the camera's frame rate; if it is lower, the node is dropping frames because processing takes too long.
      5. Examine available transport plugins: Execute ros2 run image_transport list_transports to list discoverable transport plugins available on your system, such as raw and, if installed, compressed.
      6. Visualize streams in RViz2: Open the visualizer with rviz2, add an Image display plugin, and configure the topic to /vision/edge_image. Verify that thin, continuous part contours appear clearly and that the optical frame_id aligns with the robot TF coordinate tree.

      08. Check your understanding

      • In the standard ROS optical camera coordinate frame convention, what directions do the +x, +y, and +z axes point?
        Show answer

        In the ROS optical camera coordinate frame, +x points right, +y points down, and +z points into the image plane. (Section 02)

      • What functions in cv_bridge perform bidirectional data conversion between ROS 2 Image messages and OpenCV NumPy arrays?
        Show answer

        imgmsg_to_cv2 converts a ROS Image message into an OpenCV NumPy image, and cv2_to_imgmsg converts an OpenCV image array into a ROS Image message. (Section 05)

      • Which distortion model in sensor_msgs/CameraInfo represents radial and tangential distortion, and what five coefficients are contained in its distortion parameters array D?
        Show answer

        The plumb_bob distortion model represents standard radial and tangential lens distortion. Its distortion parameters array D has five coefficients: k1, k2, t1, t2 and k3. (Section 03)

      • How does the message_filters TimeSynchronizer prevent race conditions when pairing image frames with camera calibration metadata?
        Show answer

        It synchronizes incoming message streams based on matching timestamps in their message headers. It pairs the messages on /camera/image_raw and /camera/camera_info that carry identical header timestamps before invoking the callback, so image frames are never processed with stale or misaligned calibration metadata. (Section 04)
