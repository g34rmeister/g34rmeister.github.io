      10.5 Lab: Send a Navigation Goal to Nav2

      Gerald Lê
      Chapter 10, lesson 5 of 5 ← Previous: 10.4 Behavior Trees, Actions and Lifecycle Nodes Next: Chapter 11: Capstone Projects →

      01. Why this lab

      In lesson 10.1 we studied the coordinate frames and odometry transforms that locate a mobile robot. In lesson 10.2 we examined how Nav2 represents obstacles with static costmap layers and costmap filters. In lesson 10.3 we looked at the dedicated task servers for global planning, local path following, trajectory smoothing, and recovery behaviors. In lesson 10.4 we followed how behavior trees orchestrate those servers and how lifecycle nodes manage their startup order.

      Throughout those four lessons, the concepts remained theoretical. In this lesson you run those components for the first time. Readers who completed the hands-on exercises in lesson 4.3 and lesson 4.4 already know how to start ROS 2 nodes, list topics, and inspect communication flows.

      Many people learn robotics on a laptop, with no robot. Nav2 has a simulator for exactly that case: its loopback simulator lets you test navigation without starting a compute-heavy process such as Gazebo or Isaac Sim.[1] In this lab you start Nav2 with that simulator, look at the servers it runs, and send the simulated robot a goal, first from the terminal and then from a short Python program.

      02. What you need and how to install it

      To complete this lab you need a computer running Linux on the x86-64 architecture, several gigabytes of free disk space, and standard user permissions. You do not need root access or sudo privileges. The practice transcript in this lesson was recorded on an Ubuntu 26.04.1 LTS system running micromamba 2.10.0 and Python 3.14.10.

      This lab installs ROS 2 and Nav2 from RoboStack, a project that packages ROS for the conda family of package managers. RoboStack packages can be installed with Pixi, Micromamba or conda.[2] RoboStack recommends Pixi for new installations.[2] This lab uses micromamba because that is what was tested. A channel is an online location that a package manager downloads packages from. The commands below use two channels: conda-forge for general software and robostack-lyrical for ROS 2 Lyrical.[3]

      Micromamba is a fully statically linked, self-contained executable.[4] In other words, it is a single program file that needs nothing else installed. It keeps its environments under a folder named by the MAMBA_ROOT_PREFIX variable.[4] An environment is a folder that holds its own set of packages, separate from the rest of the system. Installing in user space means installing only inside your own home folder, with no administrator rights. The commands below put micromamba and the environment in one folder, ~/robosstics-lab, and deleting that folder removes them again.

      RoboStack’s micromamba page gives two cautions.[3] Do not install ROS packages in the base environment. And do not source a system ROS install (for example one from /opt/ros) in the same terminal, because the paths it sets conflict with the environment.[3] Use a separate, named environment, as the commands below do.

      This lab was not tested with the apt install from lesson 4.3. The same ros2 commands should work there once the Nav2 packages are installed, but that route was not run. If you already have ROS 2 from 4.3, keep it out of the terminals you use for this lab, as the caution above says.

      To install micromamba and create the Nav2 environment, open a terminal and execute the following commands. On a fresh computer, downloading the packages requires several gigabytes of network transfer: 

      $ mkdir -p ~/robosstics-lab
$ cd ~/robosstics-lab
$ curl -Ls https://micro.mamba.pm/api/micromamba/linux-64/latest | tar -xvj bin/micromamba
$ export MAMBA_ROOT_PREFIX=~/robosstics-lab/root
$ eval "$(~/robosstics-lab/bin/micromamba shell hook -s bash)"
$ micromamba create -y -n nav2 -c conda-forge -c robostack-lyrical ros-lyrical-ros-base ros-lyrical-nav2-bringup ros-lyrical-nav2-loopback-sim ros-lyrical-nav2-simple-commander ros-lyrical-nav2-minimal-tb3-sim
$ micromamba activate nav2
$ echo $ROS_DISTRO
lyrical
$ ros2 pkg list | grep -c nav2
36

      The first two commands make a folder for the lab and move into it. The export line tells micromamba where to keep its environments, and the eval line makes the micromamba command available in this terminal. micromamba activate nav2 then switches the terminal to the new environment. echo $ROS_DISTRO prints lyrical, and the last command counts the installed packages whose names contain “nav2”. It printed 36. In the recorded run the create command took 11 seconds, because the packages were already in micromamba’s download cache from an earlier install. A first install downloads several gigabytes. In the recorded runs the real folder was ~/.local/share/robosstics-lab, shown here as ~/robosstics-lab, and two extra variables were set, ROS_DOMAIN_ID=77 and ROS_LOCALHOST_ONLY=1. 4.1 explains what a domain ID is.

      A new terminal does not know about micromamba yet. A plain micromamba activate nav2 there fails with “command not found”. In every new terminal, run these three lines first: 

      $ export MAMBA_ROOT_PREFIX=~/robosstics-lab/root
$ eval "$(~/robosstics-lab/bin/micromamba shell hook -s bash)"
$ micromamba activate nav2

      The lesson calls this “activating the environment” from here on.

      03. What the loopback simulator is

      The loopback simulator replaces both robot hardware and physics simulators such as Gazebo, Bullet or Isaac Sim.[1] It works out the robot’s odometry from the velocity that Nav2 commands, which makes it a perfect “frictionless plane” simulation.[1] The robot moves exactly as commanded, with no wheel slip and no motor dynamics.

      Its README lists what it is good for: testing behaviors and higher-level systems without worrying about localization accuracy or system dynamics, and running on a computer that could not run a heavy simulator.[1] That is a good fit for a first run, where the goal is to see Nav2’s parts work together, not to tune a real robot.

      Specifically, the loopback simulator provides three core capabilities:

      • The map to odom transform. It stands in for global localization (10.1), so no AMCL is needed.[1]
      • The odom to base_link transform and odometry. It publishes odometry on the odom topic and both transforms on tf.[1]
      • The initial pose. It listens on the standard /initialpose topic, so you can place the robot anywhere on the map.[1]

      It does not simulate real sensors. It can publish a laser scan computed from the static map, to keep the collision monitor fed.[1] The launch log of this lab shows that scan being switched on (“Laser scan will be populated using map data”). The README still says the global (and probably the local) costmap must include the static layer from 10.2 so that the robot avoids obstacles.[1]

      These are the frames from 10.1. The map frame is fixed to the world, odom moves smoothly with the robot, and base_link is the robot itself. On a real robot, the map to odom link comes from localization and the odom to base_link link from odometry. Here the loopback simulator publishes both.[1]

      04. Start Nav2

      Running this lab requires two separate terminal windows. Terminal 1 runs the navigation bringup launch file and displays system logging output. Terminal 2 is your command console where you inspect node lifecycles, query coordinate frames, and dispatch navigation requests.

      In Terminal 1, activate the environment with the three lines from Section 02, then launch Nav2 with the loopback simulator: 

      $ ros2 launch nav2_bringup tb3_loopback_simulation_launch.py use_rviz:=False

      The launch file has a use_rviz argument, “Whether to start RVIZ”, and its default is True.[5] Setting use_rviz:=False tells the launch script not to start the RViz graphical visualizer. This option is helpful when working over SSH or in an environment without a display monitor. On a desktop with a screen you can leave use_rviz:=False out to watch the robot in RViz. The recorded runs had no display, so that part was not tested here.

      05. Tell Nav2 where the robot is

      An initial pose is the starting position and orientation that defines where a robot is located on a navigation map. In this lab the loopback simulator needs one before it can tell the rest of Nav2 where the robot is.

      The loopback simulator takes the starting pose from the /initialpose topic.[1] Until a pose arrives, Terminal 1 repeats a message from the global costmap: “Timed out waiting for transform from base_link to map”. The planner server cannot finish activating without that transform, so bringup waits.

      Do not wait too long. In one exploratory run the pose was published too late. Bringup gave up 60.5 seconds after “Activating planner_server”, with these lines: 

      [component_container-3] [ERROR] [1794446258.436573106] [global_costmap.global_costmap]: Failed to activate global_costmap because transform from base_link to map did not become available before timeout
[component_container-3] [ERROR] [1794446258.437254582] [lifecycle_manager_nav2]: Failed to change state for node: planner_server
[component_container-3] [ERROR] [1794446258.437270740] [lifecycle_manager_nav2]: Failed to bring up all requested nodes. Aborting bringup.

      Following this timeout, the nodes remained in the inactive state and the entire stack had to be stopped and restarted.

      Where you put the robot matters. In an exploratory run the robot was placed at x = 0, y = 0, and that did not work: one goal was reported as succeeded although the robot had not moved, and another failed with planner error code 208 (“Failed to create plan”). A start at x = −2.0 m, y = −0.5 m worked in every run, so the lab uses it.

      07. Send a goal from the command line

      A feedback message is a periodic status update published by an action server while executing a long-running request. Goal tolerance is the allowable spatial and angular margin of error within which a robot is considered to have arrived at its destination.

      Send a navigation goal requesting the robot to travel to x = 1.5 meters and y = -0.5 meters on the map. The --feedback flag tells the CLI tool to print feedback messages as they arrive from the BT Navigator: 

      $ ros2 action send_goal /navigate_to_pose nav2_msgs/action/NavigateToPose "{pose: {header: {frame_id: map}, pose: {position: {x: 1.5, y: -0.5}, orientation: {w: 1.0}}}}" --feedback

      $ ros2 run tf2_ros tf2_echo map base_link
At time 31.77976
- Translation: [1.292, -0.591, 0.010]
- Rotation: in Quaternion (xyzw) [0.000, 0.000, 0.018, 1.000]
- Rotation: in RPY (radian) [0.000, -0.000, 0.036]

      The target coordinates were (1.5, -0.5). The robot came to a stop at (1.292, -0.591). Calculating the Euclidean distance between the requested goal and the stopped position yields:

      $$\sqrt{(1.5 - 1.292)^2 + (-0.5 - (-0.591))^2} = \sqrt{0.208^2 + 0.091^2} = 0.227\text{ m}$$

      Why did the action declare success when the robot stopped 0.23 meters short of the destination coordinate? The default Nav2 parameters define a general_goal_checker within the controller server that configures an xy_goal_tolerance of 0.25 meters and a yaw_goal_tolerance of 0.25 radians.[7] Because the final distance of 0.227 meters is within the configured 0.25-meter tolerance threshold, the controller goal checker marks the task complete. In the other recorded run, the move completed after 900 feedback messages with an end translation of (1.293, -0.591), which similarly falls within the tolerance boundary.

      08. The same task from Python

      The nav2_simple_commander package gives Python users “navigation as a library”.[9] Its API handles the ROS 2 and action server details for you, so you can focus on your application.[9] You create a BasicNavigator and call its methods instead of writing an action client yourself.

      Create a script named go_to_goal.py with the following content: 

      """Send one navigation goal to Nav2 and print its progress.

Start Nav2 first (see the lesson). This script sends the robot back to
where it started, at x = -2.0, y = -0.5 on the tb3_sandbox map.
"""
from geometry_msgs.msg import PoseStamped
from nav2_simple_commander.robot_navigator import BasicNavigator, TaskResult
import rclpy


def main():
    rclpy.init()
    navigator = BasicNavigator()

    # The loopback simulator has no AMCL. This value of localizer makes
    # waitUntilNav2Active() skip the localizer check and wait only for
    # bt_navigator.
    navigator.waitUntilNav2Active(localizer='robot_localization')

    goal = PoseStamped()
    goal.header.frame_id = 'map'
    goal.header.stamp = navigator.get_clock().now().to_msg()
    goal.pose.position.x = -2.0
    goal.pose.position.y = -0.5
    goal.pose.orientation.w = 1.0

    task = navigator.goToPose(goal)
    last_second = -1
    while not navigator.isTaskComplete(task=task):
        feedback = navigator.getFeedback(task=task)
        # Print once per second of navigation time, not on every loop.
        if feedback and feedback.navigation_time.sec != last_second:
            last_second = feedback.navigation_time.sec
            print('{:2d} s: {:.2f} m to go'.format(
                last_second, feedback.distance_remaining))

    result = navigator.getResult()
    if result == TaskResult.SUCCEEDED:
        print('Goal succeeded!')
    elif result == TaskResult.CANCELED:
        print('Goal was canceled!')
    elif result == TaskResult.FAILED:
        print('Goal failed!')

    navigator.destroy_node()
    rclpy.shutdown()


if __name__ == '__main__':
    main()

      Let us walk through the script step by step:

      • Start: rclpy.init() starts the ROS 2 client library, and BasicNavigator() creates the navigator node. The first output line, bt_navigator/get_state service not available, waiting..., is normal while the script connects.
      • Wait for Nav2: waitUntilNav2Active() waits until Nav2 is ready. By default it expects AMCL as the localizer: it waits for the AMCL node, then keeps setting the initial pose until AMCL reports a pose.[10] This lab runs no AMCL node, because the loopback simulator replaces it, so the script does not use the default. With localizer='robot_localization', the method skips both localizer checks and waits only for bt_navigator.[10] The name is misleading here: nothing in this lab uses the robot_localization package. It is simply the value that turns those checks off.
      • The goal: A PoseStamped message holds the goal: back to (−2.0, −0.5) in the map frame. goToPose(goal) sends it to the BT Navigator and returns a task that the loop below checks.
      • Progress: The loop runs until isTaskComplete(task=task) is true. getFeedback() returns the latest feedback message. The loop runs many times per second, so the script prints only when the whole number of seconds in navigation_time changes.
      • Completion and cleanup: Once the task finishes, navigator.getResult() evaluates the final outcome against the TaskResult enumeration. Finally, navigator.destroy_node() and rclpy.shutdown() terminate the ROS client cleanly.

      The final tf2_echo reading puts the robot at (−1.961, −0.517), about 0.04 m from the goal.

      In Nav2's example navigation script, the demo sets an initial pose explicitly and includes timeout logic to illustrate task cancellation as well as destination updates to illustrate task preemption.[11] Our practice script leaves out cancellation thresholds and in-flight preemption to provide the most direct possible demonstration of sending a goal and monitoring its completion.

      09. Stop Nav2

      When you finish your navigation experiments, shut down the running processes cleanly.

      In Terminal 1, press Ctrl+C. Nav2 and the loopback simulator shut down.

      The ros2 command-line tools start a background process, the ROS 2 daemon, the first time you use them. In the recorded runs it kept running after Nav2 had stopped. To stop it too, run this in Terminal 2: 

      $ ros2 daemon stop
The daemon has been stopped

      Nothing from the lab is running now.

      10. From here to a contribution

      Every step in this lab used standard Nav2 packages and official documentation. As you progress in robotics, you will frequently install community packages, run developer launch files, and test example scripts. Open-source documentation is written and updated by community contributors, and discrepancies occasionally emerge between project guides and released code.

      Consider the launch command in the loopback simulator README. The package README instructs users to run ros2 launch nav2_bringup tb3_loopback_simulation.launch.py. However, when inspecting the installed package files in the current release, the launch script is named tb3_loopback_simulation_launch.py with an underscore instead of a period before launch. The command from the README cannot find that file. Listing the package’s launch folder shows the real name: ls $(ros2 pkg prefix nav2_bringup)/share/nav2_bringup/launch.

      A mismatch like this one, between a project’s documentation and what it installs, is the kind of small, checkable problem that makes a good first contribution. 3.5 shows how the Nav2 project takes contributions, and 4.10 shows how to write a bug report a maintainer can act on: what you ran, what you expected, what you saw, and your versions. Before you report anything, search the project’s issues, because someone may already have reported it. The Nav2 entry on the Open-Source Map links the repository and its issue tracker.

      Try it
      1. Send a navigation goal from the command line to x = 0.0 m, y = −0.5 m. That spot lies between the start and the goal of Section 07, on ground the robot has already driven over. After the action reports success, execute ros2 run tf2_ros tf2_echo map base_link, calculate the Euclidean distance between your goal coordinates and the reported translation, and verify that the distance falls within the 0.25-meter goal tolerance.
      2. In a fresh terminal session, launch the loopback simulation without publishing to /initialpose. Observe how Terminal 1 halts at "Activating planner_server" and records an error from global_costmap approximately 60 seconds later. Run ros2 lifecycle get /planner_server to confirm that the planner remains inactive.
      3. Modify go_to_goal.py so that the feedback loop prints feedback.estimated_time_remaining.sec along with distance remaining. Run the script and watch how the estimate changes as the robot moves.
      4. Run ros2 action list in Terminal 2 and pick an action other than /navigate_to_pose, such as /spin or /backup. Consult lesson 10.3 to identify which navigation server hosts that action and what task it performs during robot operation.

      11. Check your understanding

      • Why does the loopback simulation pause at “Activating planner_server” until an initial pose is published on /initialpose?
        Show answer

        The global costmap inside the planner server requires an active coordinate transform from base_link to map before it can activate. Until an initial pose is published, the loopback simulator does not publish the map to odom transform, causing costmap activation to wait. (Section 05)

      • Why did the command-line goal report success even though the robot stopped 0.23 meters away from the exact target coordinate?
        Show answer

        In nav2_params.yaml, the controller server’s general_goal_checker specifies an xy_goal_tolerance of 0.25 meters. Because the final distance of 0.227 meters is within this 0.25-meter threshold, the goal checker declares that the destination has been reached. (Section 07)

      • Why does go_to_goal.py pass localizer='robot_localization' to navigator.waitUntilNav2Active()?
        Show answer

        By default, waitUntilNav2Active() expects AMCL as the localizer and waits for an amcl_pose message. Because the loopback simulator replaces AMCL and provides the map to odom transform directly, setting localizer='robot_localization' tells the navigator to bypass AMCL checks and wait only for the bt_navigator node. (Section 08)

      • What happens if an initial pose is not published within approximately 60 seconds of starting Nav2?
        Show answer

        The global costmap times out while waiting for the transform from base_link to map. The lifecycle manager logs an error and aborts bringup, leaving the navigation servers in an inactive state until Nav2 is restarted. (Section 05)
