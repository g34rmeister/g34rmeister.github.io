2.7 Program Structure and Error Handling

Gerald Lê

01. From one cycle to a program that keeps running

In 2.6 you wrote one pick-and-place cycle as a straight list of moves. A production program has to repeat the cycle, put each part in a different place, survive a restart halfway through, and react sensibly when something goes wrong, such as a gripper closing on nothing. This lesson covers how robot programs are organized (modules, routines, data and loops) and how they recover from errors. The main examples are ABB RAPID and Universal Robots (UR) URScript and PolyScope, with a short look at the FANUC teach-pendant language.

The short code excerpts in this lesson are copied from three open-source programs that run on real controllers: the ROS-Industrial driver for ABB robots,[1] the motion-program executor maintained by Rensselaer Polytechnic Institute (RPI),[2] and the External Control script in UR's own client library.[3] The longer examples are this course's own, built from the same syntax: test them in RobotStudio or URSim (see 2.6) before using them on a real robot.

One idea runs through the lesson. At every point where something can fail, a good program has the same three answers: retry automatically a limited number of times, then tell the operator what is wrong, then stop in a safe, known state.

02. How a RAPID program is organized

A RAPID program is a set of modules. Each module starts with MODULE and a name and ends with ENDMODULE. Inside, data declarations come first, at the top, and routines follow. RAPID has three kinds of routine:[1]

  • PROC (procedure): does work, such as moving the robot or setting outputs, and returns nothing. It ends with ENDPROC.
  • FUNC (function): computes and returns a value of a stated type, for example FUNC bool for a yes/no answer. It ends with ENDFUNC.
  • TRAP (interrupt routine): runs when an interrupt it is connected to fires, for example when a signal or variable changes. It ends with ENDTRAP.

Execution starts at PROC main. The ROS-Industrial driver module shows the whole layout. The listing below is abridged; ... marks lines left out:[1] 

MODULE ROS_motion
    LOCAL CONST zonedata DEFAULT_CORNER_DIST := z10;
    LOCAL VAR num trajectory_size := 0;
    LOCAL VAR intnum intr_new_trajectory;

    PROC main()
        ...
    ENDPROC

    LOCAL PROC init_trajectory()
        ...
    ENDPROC

    LOCAL FUNC bool is_near(jointtarget target, num deg_tol, num mm_tol)
        ...
    ENDFUNC

    LOCAL PROC abort_trajectory()
        ...
    ENDPROC

    LOCAL TRAP new_trajectory_handler
        ...
    ENDTRAP
ENDMODULE

The keyword LOCAL limits a name to its own module.[1] Inside main, the driver first declares its routine-local data (VAR num current_index; VAR speeddata move_speed := v10; and so on). It then wires the interrupt to its TRAP with IDelete intr_new_trajectory;, CONNECT intr_new_trajectory WITH new_trajectory_handler; and IPers ROS_new_trajectory, intr_new_trajectory;, so a change in the persistent variable ROS_new_trajectory runs the TRAP. Finally it enters an endless loop, WHILE true DO ... WaitTime 0.05; ENDWHILE.[1]

The IDelete line deserves attention. Its comment in the source reads "clear interrupt handler, in case restarted with ExitCycle".[1] Because main can be entered again while the old interrupt still exists, the start-up code removes it before connecting a new one. Start-up code that also works the second time it runs is a habit worth copying.

03. Three kinds of RAPID data: CONST, VAR and PERS

Every RAPID data declaration starts with a storage type. RobotStudio's programming interface lists the storage types as CONST, PERS, TASK PERS and VAR.[4] They behave differently when the program is stopped and restarted:[5]

  • CONST: cannot change after it is declared. RPI's module uses constants as named command codes, for example CONST num MOTION_PROGRAM_CMD_MOVEL:=3;.[2]
  • VAR: keeps its value when the program is stopped and started again, but it is reset when the program pointer is moved back to main.[5]
  • PERS (persistent): "remembers the last value it was assigned, even if the program is stopped and started from the beginning again." A PERS declaration must have an initial value.[5] RPI's module keeps the tool, the work object and the payload as persistent data, for example TASK PERS tooldata motion_program_tool:=[TRUE,[[0,0,0],[1,0,0,0]],[0.001,[0,0,0.001],[1,0,0,0],0,0,0]];.[2]

When a module is loaded as shared, its data is available to all tasks on the controller.[6] One more rule affects programs that build targets on the fly: a data item can be modified only if it is declared PERS or VAR, not CONST. A program that writes into the fields of a robtarget therefore cannot use a CONST point.[7]

A practical rule: CONST for numbers that never change, such as pallet spacing; PERS for taught points, tool data and anything that must survive a restart, such as a cycle counter; VAR for scratch values inside one routine.

04. How a URScript and PolyScope program is organized

URScript is flatter than RAPID. There are no modules or routine types, only functions written with def. A function looks like def terminateProgram(): ... end, and every indented block is closed with end.[3] URScript has no separate keyword for a function that returns a value; a def simply uses return. Variables shared across the program are declared with global, for example global control_mode = MODE_UNINITIALIZED and global trajectory_points_left = 0.[3] Poses are written as p[x, y, z, rx, ry, rz], in meters and radians, as in 2.3.[3]

URScript can run several things at once with threads. A thread is declared like a function, as in thread servoThread(): ... end. UR's script starts one with thread_clear = run clearTrajectoryPointsThread(), waits for it to finish with join thread_clear, and stops another early with kill thread_move. Data that two threads both touch is protected between enter_critical and exit_critical, and sync() hands control back to the scheduler so other threads can run.[3]

Most UR programs are built on the pendant as a program tree in PolyScope rather than typed as script. The PolyScope 5 handbook lists program nodes such as SubProgram, Thread and Palletizing.[8] A UR Academy page describes a Before Start sequence, a set of commands placed ahead of the main program and used, for example, to avoid collisions or bumps when a program starts again after the previous run has ended.[9] In the newer PolyScope X, Thread, Call and Function are program nodes,[10] and the release notes for version 10.8 say a Function can now be converted into a Thread in the user interface.[11]

If you already know RAPID, a rough mapping helps. It is an analogy, not an exact match:

  • MODULE: roughly the UR program file (.urp) or script file.
  • PROC and FUNC: a def function in script, or a SubProgram in the tree.
  • TRAP: loosely, a thread that watches a signal and reacts to it.
  • CONST, PERS and VAR: loosely, installation variables, global variables and local variables. PERS versus installation variables is the weakest part of the analogy: how variables persist was not checked for PolyScope 5 or X, so test what survives a restart on your version.
  • Start-up code in main: the Before Start sequence.

05. Loops and conditionals in both languages

Both languages have a counted loop, a conditional loop and an IF. These lines are taken from the ROS-Industrial driver:[1] 

FOR current_index FROM 1 TO trajectory_size DO
    ...
ENDFOR

IF (current_index = trajectory_size) stop_mode := fine;    ! one-line IF

IF (trajectory_size > 0) THEN                               ! block IF
    ...
ENDIF

skip_move := (current_index = 1) AND is_near(target, 0.1, 0.1);

WHILE true DO
    ...
ENDWHILE

The one-line IF has no THEN and runs one instruction. The skip_move line stores a condition in a bool and calls the FUNC is_near inside it.[1] RPI's module adds a loop driven by a flag: WHILE keepgoing DO motion_program_do_preempt; keepgoing:=try_motion_program_run_next_cmd(cmd_num,cmd_op); ENDWHILE, followed by WaitRob\ZeroSpeed; to wait until the robot has actually stopped.[2]

In URScript the official script uses while and if, each with a colon after the condition and an end to close the block, for example while control_mode == MODE_SERVOJ: ... end.[3]

Both languages have further forms, such as a multi-way branch in RAPID and a counted loop in URScript. This lesson sticks to the forms above, which appear in production code, and builds URScript counted loops from while and a counter. Check your manual before using the others.

06. One taught point, nine pallet slots

Suppose a pallet holds nine parts in a 3 by 3 grid. Teaching nine place points means nine chances to make a mistake and nine points to re-teach if the pallet moves. A better program teaches one corner slot, measures the spacing (the pitch) between slots, and computes the rest.

RAPID's Offs(robtarget, XOffset, YOffset, ZOffset) returns a copy of a target moved by the given distances in millimeters. For example, MoveL Offs(p2,0,0,10), ... moves to a point 10 mm above p2. The offset is applied in the coordinate system of the work object.[12] URScript's math functions include pose_add(p_1, p_2) and pose_trans(p_from, p_from_to), which combine two poses.[13][14]

The trick that keeps the program short is to number the slots 0 to 8 and compute the row and column from the number with integer division and remainder: 

row = i DIV 3      (whole-number division: 0,0,0, 1,1,1, 2,2,2)
col = i MOD 3      (remainder:             0,1,2, 0,1,2, 0,1,2)
slot = corner moved by (col * PITCH_X, row * PITCH_Y, 0)

One loop from 0 to 8 visits all nine slots, row by row. Here is the RAPID routine that places a part in one slot. It is this course's own example; test it in RobotStudio first, and check in the RAPID manual for your RobotWare version that DIV and MOD behave as described: 

PROC PlaceAt(num row, num col)
    VAR robtarget pSlot;
    pSlot := Offs(pPalletCorner, col * PITCH_X, row * PITCH_Y, 0);
    MoveJ Offs(pSlot, 0, 0, APPROACH_Z), v500, z10, tGripper;   ! above the slot
    MoveL pSlot, v100, fine, tGripper;                            ! exact stop
    SetDO doGripClose, 0;                                         ! release (see 2.5)
    WaitTime 0.3;
    MoveL Offs(pSlot, 0, 0, APPROACH_Z), v500, z10, tGripper;   ! retract
ENDPROC

It is called as PlaceAt i DIV 3, i MOD 3;. In RAPID a procedure call lists its arguments after the name, separated by commas, without parentheses. The URScript version below writes the same loop with while. Instead of a DIV operator it uses floor(i / 3) for the row, and it gets the column as what is left over, i - row*3. It is an example to test in URSim first: 

def pallet3x3():
  corner = p[0.40, -0.10, 0.05, 0, 3.1416, 0]   # taught slot (row 0, col 0); replace with your own
  pitch = 0.06                                   # meters between slots
  i = 0
  while i < 9:
    row = floor(i / 3)
    col = i - row*3
    slot = pose_trans(corner, p[col*pitch, row*pitch, 0, 0, 0, 0])   # offset in the corner's frame
    above = pose_trans(slot, p[0, 0, -0.08, 0, 0, 0])               # tool Z points down, so -Z is up
    # pick a part here (section 09)
    movej(above)
    movel(slot)
    set_standard_digital_out(0, False)          # release (see 2.5)
    sleep(0.3)
    movel(above)
    i = i + 1
  end
end

The choice of function matters. As a general explanation, pose_trans(corner, offset) applies the offset along the corner pose's own axes, while pose_add applies it along the robot base axes. If the corner was taught square to a tilted pallet, pose_trans makes the grid follow the pallet; but for a tool pointing down those axes may not match the base axes, so watch which way the first row grows in the simulator, and confirm both functions in the URScript manual. In RAPID the same benefit comes from teaching pPalletCorner in a work object on the pallet, as in 2.6: re-teach that one frame and the whole grid moves with it.

For production palletizing, vendors sell or bundle tools that generate this kind of code. PolyScope has a Palletizing program node.[8] One user on PolyScope 5.12 reported on UR's forum that the node ran only the first item until an outer loop was added.[15] ABB merged its PickMaster 5 palletizing software into RobotStudio as the Palletizing PowerPac, and its newer Palletizing Template is a free RobotStudio add-in that ABB describes as a starting point rather than a turnkey product.[16][17] FANUC's PalletTool lets operators create and compare pallet patterns from the product dimensions, with the space efficiency of each,[18] and FANUC's PalletPRO is offline simulation software for palletizing applications.[19] Write the loop by hand first, so you can tell whether a wizard did what you meant.

07. Error handling in RAPID: ERROR, ERRNO and four ways out

RAPID has structured error recovery. When an instruction in a routine fails, execution jumps to that routine's ERROR section, and the predefined variable ERRNO holds the number of the error. The handler then chooses one of four ways out:[12]

  • RETRY: run the instruction that caused the error again.
  • TRYNEXT: skip that instruction and continue with the next one.
  • RETURN: end the routine and go back to the caller.
  • RAISE: pass the error on. Used inside a handler, it continues in the error handler of the calling routine.[12][20][21]

You can also define your own errors. RPI's module declares an error number at module level and books it with the controller in its start-up routine:[2] 

VAR errnum ERR_INVALID_MP_FILE:=-1;
...
BookErrNo ERR_INVALID_MP_VERSION;
BookErrNo ERR_INVALID_MP_FILE;

After booking, the program can raise the error like a system error, usually after writing a message to the event log: ErrWrite "Invalid Motion Program","Invalid motion program file version"; RAISE ERR_INVALID_MP_VERSION;. System errors are raised the same way, as in RAISE ERR_FILESIZE;.[2] ABB's reference manual includes an example of this kind, in which a custom error booked with BookErrNo is raised and then caught in an ERROR handler.[12]

Real handlers in the same code show the common patterns. A handler that checks which error occurred and skips the failing instruction only for that error:[2] 

ERROR
    IF ERRNO=ERR_RANYBIN_EOF THEN
        SkipWarn;
        TRYNEXT;
    ENDIF
ENDFUNC

End of file is expected here, so SkipWarn keeps it out of the event log and TRYNEXT carries on.[2] A different handler cleans up and then passes the error on: ERROR motion_program_state{task_ind}.running:=FALSE; RAISE ; ENDPROC. A bare RAISE with no error name re-raises the same error to the caller.[2] The ROS-Industrial driver's main logs a warning and runs a recovery routine instead: ERROR ErrWrite \W, "Motion Error", "Error executing motion. Aborting trajectory."; abort_trajectory; ENDPROC. The \W switch writes the message as a warning, and RPI's code uses ErrWrite\I for an information message.[1][2]

08. The RETRY trap, and how to avoid it

Now take a missed pick: the gripper closes, but the part-present input stays low. A first attempt usually puts the check and the handler in the routine that does the pick: 

PROC PickPart()                      ! looks right, but does not re-grip
    VAR num nTries := 0;
    MoveJ Offs(pPick,0,0,APPROACH_Z), v500, z10, tGripper;
    MoveL pPick, v100, fine, tGripper;
    SetDO doGripClose, 1;
    WaitTime 0.3;
    IF DInput(diPartPresent) = 0 RAISE ERR_MISSED_PICK;
    MoveL Offs(pPick,0,0,APPROACH_Z), v500, z10, tGripper;
ERROR
    IF ERRNO = ERR_MISSED_PICK THEN
        nTries := nTries + 1;
        SetDO doGripClose, 0;
        IF nTries < 3 RETRY;
    ENDIF
    RAISE;
ENDPROC

The trap is in what RETRY repeats. It re-executes only the instruction that raised the error, not the whole routine.[12] Here that instruction is the IF line. So after a miss, the handler opens the gripper and RETRY just reads the sensor again, with the gripper open and the robot still at the pick point. The robot never re-grips; the check fails three times in a fraction of a second and the program stops.

The fix is to raise the error from a small routine that does the whole pick, and to put the RETRY in the caller. When the caller's handler retries, the instruction that failed is the call itself, so the whole pick runs again. This course's version, to be tested in RobotStudio first: 

PROC PickPart()
    VAR num nTries := 0;
    TryPick;                                 ! RETRY re-runs this whole call
ERROR
    IF ERRNO = ERR_MISSED_PICK THEN
        nTries := nTries + 1;
        IF nTries < 3 THEN
            ErrWrite \W, "Missed pick", "Retrying, attempt " + NumToStr(nTries, 0);
            RETRY;
        ENDIF
        ErrWrite "Missed pick", "3 failed attempts. Check the feeder.";
    ENDIF
    RAISE;                                   ! give up: pass the error on
ENDPROC

PROC TryPick()
    MoveJ Offs(pPick, 0, 0, APPROACH_Z), v500, z10, tGripper;
    MoveL pPick, v100, fine, tGripper;
    SetDO doGripClose, 1;
    WaitTime 0.3;
    IF DInput(diPartPresent) = 0 RAISE ERR_MISSED_PICK;
    MoveL Offs(pPick, 0, 0, APPROACH_Z), v500, z10, tGripper;
ERROR
    SetDO doGripClose, 0;                    ! clean up: open the gripper
    MoveL Offs(pPick, 0, 0, APPROACH_Z), v100, fine, tGripper;   ! back off
    RAISE;                                   ! let the caller decide
ENDPROC

TryPick cleans up after its own failure (gripper open, robot above the part) and passes the error up, just as RPI's handler clears its running flag before RAISE.[2] PickPart decides: retry the whole pick up to three times, then log an error and pass it on. If no routine above it handles the error, the program stops. The counter nTries keeps its value between retries because PickPart is not called again, and it starts from 0 the next time PickPart is called. Another fix is a WHILE loop with a counter instead of RETRY, as in the URScript version in section 09.

There is also a limit outside your code. On ABB's IRC5 controller, reaching the maximum number of retries in a handler stops the system, and the instruction ResetRetryCount resets that count.[22] Your own counter stays below that limit and gives the operator a clear message.

09. Without exceptions: URScript and FANUC TP

URScript has no exception mechanism like RAPID's ERROR handler, and no try/catch. A third-party article states that an unhandled runtime error stops the whole program, whichever thread raised it; that source is of low quality and no official UR statement was found, so treat it as a reasonable working assumption rather than a documented rule.[23] Either way, in URScript you check for failure yourself with an if and branch.

UR's External Control script works this way. When a target breaks a limit, it shows a non-blocking operator message, popup(str, title="External Control speed limit", blocking=False, warning=True), writes to the log with textmsg(...), and uses a counter, violation_popup_counter, so the popup does not repeat endlessly. When it has to give up, it calls a short routine that slows the robot down before ending the program:[3] 

def terminateProgram():
  textmsg("Terminating robot program due to targets sent to the robot is violating robot constraints.")
  stopj(STOPJ_ACCELERATION)
  halt
end

Decelerate first with stopj, then end with halt.[3] The URScript manual lists popup(s, title, warning, error, blocking) among its functions.[13][14]

For a missed pick, the check should be a branch at the moment the grip is confirmed, using a part-present input or the gripper's own grip-detected status (for a Robotiq gripper, rq_is_object_detected(), as in 2.5), not a fixed delay.[24] Robotiq's example re-attempts the grasp until the object is detected and then prompts the operator.[25] The retry with a counter, written as a loop, looks like this. It is this course's example, to be tested in URSim; the input and output numbers depend on your gripper, and Robotiq and OnRobot URCaps supply their own functions or nodes: 

def pick_with_retry(pick_pose, pick_above):
  tries = 0
  while True:
    movel(pick_above)
    movel(pick_pose)
    set_standard_digital_out(0, True)    # close gripper (see 2.5)
    sleep(0.3)
    if get_standard_digital_in(0):       # part-present / grip-detected input
      movel(pick_above)
      return True
    end
    set_standard_digital_out(0, False)   # missed: open and back off
    movel(pick_above)
    tries = tries + 1
    textmsg("Missed pick, attempt ", tries)
    if tries >= 3:
      popup("3 missed picks - refill feeder and restart", title="Missed pick", error=True, blocking=True)
      halt
    end
  end
end

Because the loop body contains the approach, grip and check, every retry really re-grips. Place the function inside pallet3x3 and call it at the comment in section 06.

A popup is not a safety function. Users on UR's forum point out that a popup followed by halt cannot be resumed, and a popup without halt does not stop the program at all; for real safety behavior they are directed to the configured safety functions, such as a protective stop, rather than script messages.[26] UR does document a protective_stop() script function, and UR's error code C209 reads "A protective stop was triggered (for test purposes only)".[27][28] Error handling keeps production running and tells people what went wrong; it does not protect people. Guarding, safety-rated stops and safety I/O do that, as covered in 5.4 Making a Robot Cell Safe.

FANUC's teach-pendant (TP) language is also built from explicit checks, not exceptions. A wait can name a jump label for the timeout case, as in WAIT DI[n]=ON TIMEOUT,LBL[x]; the time limit is set separately. In the timeout branch, a user alarm UALM[n] shows a message that the programmer defined, and if the operator resumes the program, execution continues at the next line.[29][30] Sources disagree about exactly when a user alarm pauses the program, so check the FANUC manual for your controller before relying on that behavior. These FANUC details come from secondary sources.

10. Putting it together: a structure that survives restarts

Here is the top of the RAPID module that joins sections 06 and 08. It is this course's example, to be tested in RobotStudio; targets, tool and signal names are placeholders, and confirm in the manual that a FOR loop may start from a PERS variable: 

MODULE Pallet3x3
    CONST num PITCH_X := 60;          ! mm between columns (measure your parts)
    CONST num PITCH_Y := 60;          ! mm between rows
    CONST num APPROACH_Z := 80;       ! mm approach height
    CONST jointtarget jHome := [[0,0,0,0,30,0],[9E9,9E9,9E9,9E9,9E9,9E9]];
    PERS tooldata tGripper := [TRUE,[[0,0,150],[1,0,0,0]],[1,[0,0,50],[1,0,0,0],0,0,0]];
    PERS robtarget pPick := [[450,200,120],[0,0,1,0],[0,0,0,0],[9E9,9E9,9E9,9E9,9E9,9E9]];
    PERS robtarget pPalletCorner := [[450,-200,50],[0,0,1,0],[0,0,0,0],[9E9,9E9,9E9,9E9,9E9,9E9]];
    PERS num nPlaced := 0;            ! slots already filled; survives a restart
    VAR errnum ERR_MISSED_PICK := -1;

    PROC main()
        BookErrNo ERR_MISSED_PICK;
        SetDO doGripClose, 0;                   ! known state: gripper open
        MoveAbsJ jHome, v200, fine, tGripper;   ! start from home, slowly
        FOR i FROM nPlaced TO 8 DO              ! resume where we stopped
            PickPart;
            PlaceAt i DIV 3, i MOD 3;
            nPlaced := i + 1;                   ! count only after a good place
        ENDFOR
        nPlaced := 0;                           ! pallet full: ready for the next
        MoveAbsJ jHome, v500, fine, tGripper;
    ENDPROC

    ! PickPart, TryPick (section 08) and PlaceAt (section 06) go here
ENDMODULE

The counter is the part that makes restarts work. Because nPlaced is PERS, it keeps its value even if the program is stopped and started from the beginning,[5] so after a stop at slot 5 the loop resumes at slot 5 instead of stacking a part on slot 0. It is written only after a successful place. The FOR loop's counter i is declared by the FOR statement itself and needs no declaration.

The patterns add up to a checklist of recommended practice, drawn from the production code above rather than vendor rules:

  1. Separate start-up from the cycle. RPI's module keeps motion_program_init(), which books the error numbers, apart from motion_program_run(), and a separate motion_program_fini() logs completion with ErrWrite\I.[2] On a UR, put start-up steps in the Before Start sequence.[9] Reset outputs there, and make it safe to run twice.[1]
  2. Check where the robot is before it moves. The ROS-Industrial driver skips its first move when the robot is already there, using a FUNC is_near that compares the current and target joint positions within tolerances.[1] The same idea gives a home check: if not near home, show a message and move home slowly, or refuse to start.
  3. Keep data at the top, not inside move lines. Pitches and heights as CONST; taught frames, tool, payload and counters as PERS, the way RPI keeps its tool, work object and load.[2]
  4. One loop, small routines. Small routines keep each error handler close to its failure. Count progress only after success.
  5. Never wait forever. Every wait on a sensor has a time limit and a defined outcome: retry a few times, then tell the operator, then stop.
  6. Keep flags honest. Clear state flags in the error handler as well as on a normal exit.[2]
  7. Teach one frame on the pallet. Re-teaching one work object then moves the whole grid.
Try it
  1. In RobotStudio, build the Pallet3x3 module from sections 06, 08 and 10. Run it and check that the robot visits all nine slots in order, with row = i DIV 3 and col = i MOD 3. Then stop it after the fourth part, move the program pointer to main, start again, and confirm that it resumes at slot 4 because nPlaced is PERS.
  2. In URSim, run pallet3x3 from section 06 with pose_trans. Rotate the corner pose a few degrees about Z and watch the grid follow it. Then change the slot line to use pose_add and describe what changes.
  3. Simulate a missed pick by keeping the part-present input low (set it by hand in the simulator's I/O window). Confirm that each of the three attempts re-approaches and re-grips, then the program shows its message and stops. Then try the "looks right" PickPart from section 08 and watch RETRY re-read the sensor without re-gripping.
  4. Explain in two sentences why popup plus halt is not a safety stop, and what in the cell provides safety (see 5.4).
