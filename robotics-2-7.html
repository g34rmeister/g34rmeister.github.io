      2.7 Program Structure and Error Handling

      Gerald Lê
      Chapter 2, lesson 7 of 8 ← Previous: 2.6 Your First Pick-and-Place Next: 2.8 Vision-Guided Picking →
      Start here

      Production programs repeat hundreds of cycles, fill multi-slot pallets, survive mid-job restarts, and recover cleanly when a pick fails. This lesson moves beyond one-off scripts to show how RAPID and URScript organize loops, persistent counters, and bounded error recovery.

      • You will learn how to structure RAPID modules and URScript functions/threads.
      • You will learn when to use CONST, VAR, and PERS data so pallet counters survive restarts.
      • You will learn how to index a 3×3 pallet from one corner and recover safely from missed picks.

      01. From one cycle to a program that keeps running

      A real factory robot rarely picks up just one part and stops. It might fill a nine-slot pallet, pause when a feeder runs empty, or restart halfway through a shift. If your program is just one flat list of moves, a small hiccup forces you to start over from scratch.

      In lesson 2.6, you wrote one pick-and-place cycle as a straight list of moves. A production program repeats that cycle and places each part in a new spot. It also remembers where it stopped if someone restarts it. And when something goes wrong, such as a gripper closing on nothing, it recovers cleanly.

      One idea runs through this lesson. At every point where a task can fail, a good program follows three steps. First, retry a limited number of times. Second, tell the operator what went wrong. Third, stop in a safe, known state.

      The main examples use ABB RAPID and Universal Robots (UR) URScript and PolyScope. You will also see a short look at the FANUC teach-pendant language. Short code excerpts come from three open-source programs that run on real controllers. Those are the ROS-Industrial driver for ABB robots,[1] the motion-program executor maintained by Rensselaer Polytechnic Institute (RPI),[2] and the External Control script in UR's own client library.[3] The longer examples are this course's own, built from the same syntax. Test them in RobotStudio or URSim (see lesson 2.6) before using them on a real robot.

      02. How a RAPID program is organized

      Before you write a loop or handle an error, you need a clean way to organize your code. Putting a whole factory job into one long block makes it hard to read and hard to fix. Instead, you split the job into named pieces that each do one job. One piece picks a part, another places it on a pallet, and another reacts when a signal changes.

      In ABB's RAPID language, a program is a set of modules. Each module starts with MODULE and a name, and ends with ENDMODULE. Inside a module, data declarations come first at the top, and routines follow below them. RAPID has three kinds of routine:[1]

      • PROC (procedure): does work, such as moving the robot or setting outputs, and returns nothing. It ends with ENDPROC.
      • FUNC (function): computes and returns a value of a stated type, such as FUNC bool for a yes-or-no answer. It ends with ENDFUNC.
      • TRAP (interrupt routine): runs when an interrupt it is connected to fires, such as when a signal or variable changes. It ends with ENDTRAP.

      Execution starts at PROC main. The ROS-Industrial driver module shows the whole layout below. This listing is shortened, and ... marks lines left out:[1] 

      MODULE ROS_motion
    LOCAL CONST zonedata DEFAULT_CORNER_DIST := z10;
    LOCAL VAR num trajectory_size := 0;
    LOCAL VAR intnum intr_new_trajectory;

    PROC main()
        ...
    ENDPROC

    LOCAL PROC init_trajectory()
        ...
    ENDPROC

    LOCAL FUNC bool is_near(jointtarget target, num deg_tol, num mm_tol)
        ...
    ENDFUNC

    LOCAL PROC abort_trajectory()
        ...
    ENDPROC

    LOCAL TRAP new_trajectory_handler
        ...
    ENDTRAP
ENDMODULE

      The keyword LOCAL limits a name to its own module.[1] Inside main, the driver declares its routine-local data, connects the interrupt to its TRAP, and enters an endless loop that waits for new work.[1]

      Look closely at how it handles restarts. Before connecting the interrupt, it runs IDelete to clear any leftover interrupt from an earlier run. Because main can start again while an old interrupt still exists, the start-up code removes the old one first. Writing start-up code that works cleanly the second time it runs is a habit worth copying.

      For the curious: exact start-up lines in the ROS-Industrial driver

      Inside main, the driver first declares routine-local data such as VAR num current_index; and VAR speeddata move_speed := v10;. It then wires the interrupt to its TRAP with IDelete intr_new_trajectory;, CONNECT intr_new_trajectory WITH new_trajectory_handler;, and IPers ROS_new_trajectory, intr_new_trajectory;. A change in the persistent variable ROS_new_trajectory then runs the TRAP. Next to IDelete, the source comment reads “clear interrupt handler, in case restarted with ExitCycle”. Finally, it enters an endless loop: WHILE true DO ... WaitTime 0.05; ENDWHILE.[1]

      03. How RAPID data survives a restart: CONST, VAR, and PERS

      Suppose a robot has already placed four parts on a nine-slot pallet when someone stops the job. When you start the program again from the top, should it remember that four parts are placed, or reset to zero? What about the spacing between pallet slots, which should never change by accident? RAPID lets you pick how data behaves on a restart by choosing its storage type.

      Every RAPID data declaration starts with a storage type. RobotStudio's programming interface lists the storage types as CONST, PERS, TASK PERS, and VAR.[4] They behave differently when the program is stopped and restarted:[5]

      • CONST (constant): cannot change after it is declared. RPI's module uses constants as named command codes, for example CONST num MOTION_PROGRAM_CMD_MOVEL:=3;.[2]
      • VAR (variable): keeps its value when the program is stopped and started again. However, it resets when the program pointer moves back to main.[5]
      • PERS (persistent): remembers its value even across a full restart. In the manual's words, it “remembers the last value it was assigned, even if the program is stopped and started from the beginning again.” A PERS declaration must have an initial value.[5] RPI's module keeps the tool, the work object, and the payload as persistent data.[2]

      When a module is loaded as shared, its data is available to all tasks on the controller.[6] One more rule affects programs that build targets on the fly. You can modify a data item only if it is declared PERS or VAR, not CONST. A program that writes into the fields of a robtarget therefore cannot use a CONST point.[7]

      Here is a practical rule. Use CONST for numbers that never change, such as pallet spacing. Use PERS for taught points, tool data, and anything that must survive a restart, such as a cycle counter. Use VAR for scratch values inside one routine.

      For the curious: an example TASK PERS declaration from RPI's module

      RPI's motion-program executor stores its tool, work object, and payload using TASK PERS, for example TASK PERS tooldata motion_program_tool:=[TRUE,[[0,0,0],[1,0,0,0]],[0.001,[0,0,0.001],[1,0,0,0],0,0,0]];.[2]

      04. How a URScript and PolyScope program is organized

      Universal Robots controllers organize code in a flatter way than ABB RAPID. Instead of sorting routines into modules and special types, URScript uses plain functions. It also lets you run tasks side by side with threads, such as moving the arm while watching a signal. Most shop-floor programmers build this structure visually on the teach pendant rather than typing script.

      URScript has no modules or separate routine types, only functions written with def. A function looks like def terminateProgram(): ... end, and every indented block closes with end.[3] You do not need a separate keyword for a function that returns a value. A def function simply uses return. Variables shared across the program are declared with global, for example global control_mode = MODE_UNINITIALIZED and global trajectory_points_left = 0.[3] Poses are written as p[x, y, z, rx, ry, rz], in meters and radians, as in lesson 2.3.[3]

      URScript can run several tasks at once using threads. You declare a thread like a function, as in thread servoThread(): ... end. UR's script starts a thread with thread_clear = run clearTrajectoryPointsThread(). It waits for a thread to finish with join thread_clear, and stops another early with kill thread_move. Data that two threads both touch is protected between enter_critical and exit_critical. Calling sync() hands control back to the scheduler so other threads can run.[3]

      Most UR programs are built on the pendant as a program tree in PolyScope rather than typed as script. PolyScope includes building blocks such as SubProgram, Thread, and Palletizing nodes.[8] A UR Academy page also describes a Before Start sequence, a set of commands placed ahead of the main program. For example, it helps avoid collisions or bumps when a program starts again after the previous run has ended.[9]

      If you already know RAPID, a rough mapping helps. Keep in mind that it is an analogy, not an exact match:

      • MODULE: roughly the UR program file (.urp) or script file.
      • PROC and FUNC: a def function in script, or a SubProgram in the program tree.
      • TRAP: loosely, a thread that watches a signal and reacts to it.
      • CONST, PERS and VAR: loosely, installation variables, global variables, and local variables. Comparing PERS with installation variables is the weakest part of the analogy. Variable persistence was not checked for PolyScope 5 or X, so test what survives a restart on your version.
      • Start-up code in main: the Before Start sequence.
      For the curious: PolyScope 5 vs. PolyScope X node names

      The PolyScope 5 handbook lists program nodes including SubProgram, Thread, and Palletizing.[8] In the newer PolyScope X, Thread, Call, and Function are program nodes.[10] The release notes for version 10.8 state that a Function can now be converted into a Thread in the user interface.[11]

      05. How to write loops and checks in both languages

      To fill a tray of parts or retry a missed pick, your program needs two basic tools. It needs loops to repeat moves, and checks (if statements) to decide what to do next. Even though RAPID and URScript look different on the screen, both give you the same building blocks.

      Both languages have a counted loop, a conditional loop, and an IF. These lines are taken from the ROS-Industrial driver:[1] 

      FOR current_index FROM 1 TO trajectory_size DO
    ...
ENDFOR

IF (current_index = trajectory_size) stop_mode := fine;    ! one-line IF

IF (trajectory_size > 0) THEN                               ! block IF
    ...
ENDIF

skip_move := (current_index = 1) AND is_near(target, 0.1, 0.1);

WHILE true DO
    ...
ENDWHILE

      The one-line IF has no THEN and runs one instruction. The skip_move line stores a true-or-false condition in a bool (boolean) and calls the function is_near inside it.[1] RPI's module adds a loop driven by a flag: WHILE keepgoing DO motion_program_do_preempt; keepgoing:=try_motion_program_run_next_cmd(cmd_num,cmd_op); ENDWHILE. Right after that loop, it calls WaitRob\ZeroSpeed; to wait until the robot has actually stopped.[2]

      In URScript, the official script uses while and if, each with a colon after the condition and an end to close the block. An example is while control_mode == MODE_SERVOJ: ... end.[3]

      Both languages have further forms, such as a multi-way branch in RAPID and a counted loop in URScript. This lesson sticks to the forms above, which appear in production code. For URScript counted loops, we build them from while and a counter. Check your manual before using the other forms.

      06. One taught point, nine pallet slots

      Suppose a pallet holds nine parts in a 3-by-3 grid. Teaching nine separate place points takes time and gives you nine chances to make a mistake. If the pallet shifts slightly, you also have to re-teach all nine points. A better program teaches one corner slot, measures the spacing (the pitch) between slots, and calculates the other eight.

      RAPID handles this with Offs(robtarget, XOffset, YOffset, ZOffset). It returns a copy of a target moved by the given distances in millimeters. For example, MoveL Offs(p2,0,0,10), ... moves to a point 10 mm above p2. The offset is applied in the coordinate system of the work object.[12] In URScript, built-in math functions include pose_add(p_1, p_2) and pose_trans(p_from, p_from_to), which combine two poses.[13][14]

      The trick that keeps the program short is to number the slots 0 to 8. You then compute each slot's row and column using whole-number division and its remainder: 

      row = i DIV 3      (whole-number division: 0,0,0, 1,1,1, 2,2,2)
col = i MOD 3      (remainder:             0,1,2, 0,1,2, 0,1,2)
slot = corner moved by (col * PITCH_X, row * PITCH_Y, 0)

      The pallet indexing simulator needs JavaScript. With it on, you can select slot index i from 0 to 8 to see integer division and remainder calculations on a 3x3 grid.

      One loop from 0 to 8 visits all nine slots, row by row. Below is the RAPID routine that places a part in one slot. It is this course's own example, so test it in RobotStudio first. Also check the RAPID manual for your RobotWare version to confirm that DIV and MOD behave as described: 

      PROC PlaceAt(num row, num col)
    VAR robtarget pSlot;
    pSlot := Offs(pPalletCorner, col * PITCH_X, row * PITCH_Y, 0);
    MoveJ Offs(pSlot, 0, 0, APPROACH_Z), v500, z10, tGripper;   ! above the slot
    MoveL pSlot, v100, fine, tGripper;                            ! exact stop
    SetDO doGripClose, 0;                                         ! release (see 2.5)
    WaitTime 0.3;
    MoveL Offs(pSlot, 0, 0, APPROACH_Z), v500, z10, tGripper;   ! retract
ENDPROC

      You call this routine as PlaceAt i DIV 3, i MOD 3;. In RAPID, a procedure call lists its arguments after the name without parentheses, separated by commas. The URScript version below writes the same loop with while. Instead of a DIV operator, it uses floor(i / 3) for the row. It gets the column as what is left over, i - row*3. Test this example in URSim first: 

      def pallet3x3():
  corner = p[0.40, -0.10, 0.05, 0, 3.1416, 0]   # taught slot (row 0, col 0); replace with your own
  pitch = 0.06                                   # meters between slots
  i = 0
  while i < 9:
    row = floor(i / 3)
    col = i - row*3
    slot = pose_trans(corner, p[col*pitch, row*pitch, 0, 0, 0, 0])   # offset in the corner's frame
    above = pose_trans(slot, p[0, 0, -0.08, 0, 0, 0])               # tool Z points down, so -Z is up
    # pick a part here (section 09)
    movej(above)
    movel(slot)
    set_standard_digital_out(0, False)          # release (see 2.5)
    sleep(0.3)
    movel(above)
    i = i + 1
  end
end

      The choice of function matters. In general terms, pose_trans(corner, offset) applies the offset along the corner pose's own axes. By contrast, pose_add applies it along the robot base axes. If you taught the corner square to a tilted pallet, pose_trans makes the grid follow the pallet. For a tool pointing down, those axes may not match the base axes. Watch which way the first row grows in the simulator, and confirm both functions in the URScript manual. In RAPID, you get the same benefit by teaching pPalletCorner in a work object on the pallet, as in lesson 2.6. Re-teach that one frame and the whole grid moves with it.

      For production palletizing, robot makers sell or bundle wizards that generate this kind of code. Even so, write the loop by hand first. Once you understand the math, you can tell whether a wizard did what you meant.

      For the curious: built-in palletizing tools from UR, ABB, and FANUC

      PolyScope has a Palletizing program node.[8] One user on PolyScope 5.12 reported on UR's forum that the node ran only the first item until an outer loop was added.[15] ABB merged its PickMaster 5 palletizing software into RobotStudio as the Palletizing PowerPac. Its newer Palletizing Template is a free RobotStudio add-in that ABB describes as a starting point rather than a turnkey product.[16][17] FANUC's PalletTool lets operators create and compare pallet patterns from the product dimensions, with the space efficiency of each.[18] FANUC's PalletPRO is offline simulation software for palletizing applications.[19]

      07. How RAPID handles errors: ERROR, ERRNO, and four ways out

      Things go wrong on a factory floor. A feeder runs out of parts, a file is missing, or a sensor fails to trigger. Without error handling, any failure stops the whole cell until someone resets it. RAPID gives every routine a built-in safety net so your program can catch a problem and decide what to do next.

      When an instruction in a routine fails, execution jumps to that routine's ERROR section. The predefined variable ERRNO (error number) holds the number of the error. Your handler then chooses one of four ways out:[12]

      • RETRY: run the instruction that caused the error again.
      • TRYNEXT: skip that instruction and continue with the next one.
      • RETURN: end the routine and go back to the caller.
      • RAISE: pass the error on. Used inside a handler, it continues in the error handler of the calling routine.[12][20][21]

      You can also define your own errors. RPI's module declares an error number at module level and books it with the controller in its start-up routine:[2] 

      VAR errnum ERR_INVALID_MP_FILE:=-1;
...
BookErrNo ERR_INVALID_MP_VERSION;
BookErrNo ERR_INVALID_MP_FILE;

      After booking, the program can raise that error like a system error. It usually writes a message to the event log first, such as ErrWrite "Invalid Motion Program","Invalid motion program file version"; RAISE ERR_INVALID_MP_VERSION;. System errors are raised the same way, as in RAISE ERR_FILESIZE;.[2] ABB's reference manual includes an example of this kind, where a custom error booked with BookErrNo is raised and caught in an ERROR handler.[12]

      A handler can also check which error happened and skip the failing line only for that error:[2] 

      ERROR
    IF ERRNO=ERR_RANYBIN_EOF THEN
        SkipWarn;
        TRYNEXT;
    ENDIF
ENDFUNC

      End of file (EOF) is expected here. So SkipWarn keeps it out of the event log, and TRYNEXT carries on.[2]

      Other handlers clean up first and then pass the error up. Writing a bare RAISE with no error name sends the same error up to the calling routine.[2] A top-level routine like main can also log a message and call a recovery routine instead. You can mark a log entry as a warning with \W or as an information message with \I.[1][2]

      For the curious: cleanup and logging lines in RPI and ROS-Industrial code

      RPI's handler clears its running flag and then re-raises: ERROR motion_program_state{task_ind}.running:=FALSE; RAISE ; ENDPROC.[2] The ROS-Industrial driver's main logs a warning and runs a recovery routine instead: ERROR ErrWrite \W, "Motion Error", "Error executing motion. Aborting trajectory."; abort_trajectory; ENDPROC. The \W switch writes the message as a warning, and RPI's code uses ErrWrite\I for an information message.[1][2]

      08. The RETRY trap, and how to avoid it

      Suppose the gripper closes, and the part-present sensor stays low. Your first thought might be to put a RETRY command right inside the pick routine. That leads to a common trap. Instead of moving back to grab a part, the robot stands still and checks the empty sensor three times.

      Look at this first attempt. It puts both the check and the ERROR handler inside the routine that does the pick: 

      PROC PickPart()                      ! looks right, but does not re-grip
    VAR num nTries := 0;
    MoveJ Offs(pPick,0,0,APPROACH_Z), v500, z10, tGripper;
    MoveL pPick, v100, fine, tGripper;
    SetDO doGripClose, 1;
    WaitTime 0.3;
    IF DInput(diPartPresent) = 0 RAISE ERR_MISSED_PICK;
    MoveL Offs(pPick,0,0,APPROACH_Z), v500, z10, tGripper;
ERROR
    IF ERRNO = ERR_MISSED_PICK THEN
        nTries := nTries + 1;
        SetDO doGripClose, 0;
        IF nTries < 3 RETRY;
    ENDIF
    RAISE;
ENDPROC

      The trap is in what RETRY repeats. It re-runs only the single instruction that raised the error, not the whole routine.[12] Here, that instruction is the IF line. So after a miss, the handler opens the gripper and RETRY just reads the sensor again. With the gripper open and the robot still at the pick point, the robot never re-grips. The check fails three times in a fraction of a second, and the program stops.

      The fix is to raise the error from a small routine that does the whole pick, and put RETRY in the caller. When the caller's handler retries, the instruction that failed is the call itself. That makes the whole pick run again. Test this course version in RobotStudio first: 

      PROC PickPart()
    VAR num nTries := 0;
    TryPick;                                 ! RETRY re-runs this whole call
ERROR
    IF ERRNO = ERR_MISSED_PICK THEN
        nTries := nTries + 1;
        IF nTries < 3 THEN
            ErrWrite \W, "Missed pick", "Retrying, attempt " + NumToStr(nTries, 0);
            RETRY;
        ENDIF
        ErrWrite "Missed pick", "3 failed attempts. Check the feeder.";
    ENDIF
    RAISE;                                   ! give up: pass the error on
ENDPROC

PROC TryPick()
    MoveJ Offs(pPick, 0, 0, APPROACH_Z), v500, z10, tGripper;
    MoveL pPick, v100, fine, tGripper;
    SetDO doGripClose, 1;
    WaitTime 0.3;
    IF DInput(diPartPresent) = 0 RAISE ERR_MISSED_PICK;
    MoveL Offs(pPick, 0, 0, APPROACH_Z), v500, z10, tGripper;
ERROR
    SetDO doGripClose, 0;                    ! clean up: open the gripper
    MoveL Offs(pPick, 0, 0, APPROACH_Z), v100, fine, tGripper;   ! back off
    RAISE;                                   ! let the caller decide
ENDPROC

      TryPick cleans up after its own failure (gripper open, robot above the part) and passes the error up. That works just like RPI's handler clearing its running flag before RAISE.[2] Then PickPart decides what to do. It retries the whole pick up to three times, logs an error, and passes it on. If no routine above it handles the error, the program stops.

      Notice how nTries keeps its count across retries. Because PickPart is not called again during a retry, nTries keeps its value, and starts at 0 the next time PickPart is called. Another fix is to use a WHILE loop with a counter instead of RETRY, like the URScript version in section 09.

      For the curious: ABB IRC5 retry limits and ResetRetryCount

      There is also a limit outside your code. On ABB's IRC5 controller, reaching the maximum number of retries in a handler stops the system, and the instruction ResetRetryCount resets that count.[22] Your own counter stays below that limit and gives the operator a clear message.

      09. Handling errors without exceptions: URScript and FANUC

      Not every robot language has an ERROR block like RAPID. In URScript and FANUC's teach-pendant (TP) language, you cannot jump to a separate handler at the bottom of a routine. Instead, you check sensors and limits right where a problem can happen, using if checks and loops. When retries run out, you warn the operator and stop the arm safely.

      URScript has no exception mechanism like RAPID's ERROR handler, and no try/catch. A third-party article states that an unhandled runtime error stops the whole program, whichever thread raised it.[23] That source is of low quality and no official UR statement was found, so treat this as a working assumption, not a documented rule. Either way, in URScript you check for failure yourself with an if and branch.

      UR's External Control script works this way. When a target breaks a limit, it shows a non-blocking operator message: popup(str, title="External Control speed limit", blocking=False, warning=True). It also writes to the log with textmsg(...) and uses a counter, violation_popup_counter, so the popup does not repeat endlessly. When it has to give up, it calls a short routine that slows the robot down before ending the program:[3] 

      def terminateProgram():
  textmsg("Terminating robot program due to targets sent to the robot is violating robot constraints.")
  stopj(STOPJ_ACCELERATION)
  halt
end

      Decelerate first with stopj, then end with halt.[3] The URScript manual lists popup(s, title, warning, error, blocking) among its functions.[13][14]

      For a missed pick, check the sensor at the moment the grip is confirmed, not after a fixed delay alone. Use a part-present input or the gripper's own grip-detected status, such as rq_is_object_detected() for a Robotiq gripper (see lesson 2.5).[24] Robotiq's example re-attempts the grasp until the object is detected and then prompts the operator.[25] Here is the retry with a counter, written as a loop. It is this course's example, to be tested in URSim. Your input and output numbers depend on your gripper, and Robotiq and OnRobot URCaps supply their own functions or nodes: 

      def pick_with_retry(pick_pose, pick_above):
  tries = 0
  while True:
    movel(pick_above)
    movel(pick_pose)
    set_standard_digital_out(0, True)    # close gripper (see 2.5)
    sleep(0.3)
    if get_standard_digital_in(0):       # part-present / grip-detected input
      movel(pick_above)
      return True
    end
    set_standard_digital_out(0, False)   # missed: open and back off
    movel(pick_above)
    tries = tries + 1
    textmsg("Missed pick, attempt ", tries)
    if tries >= 3:
      popup("3 missed picks - refill feeder and restart", title="Missed pick", error=True, blocking=True)
      halt
    end
  end
end

      Because the loop body contains the approach, grip, and check, every retry really re-grips. Place the function inside pallet3x3 and call it at the comment in section 06.

      Do not confuse an error message on the pendant with safety input/output (I/O) or a real safety stop.

      A popup is not a safety function. Users on UR's forum point out that a popup followed by halt cannot be resumed, and a popup without halt does not stop the program at all. For real safety behavior they are directed to the configured safety functions, such as a protective stop, rather than script messages.[26] UR does document a protective_stop() script function, and UR's error code C209 reads "A protective stop was triggered (for test purposes only)".[27][28] Error handling keeps production running and tells people what went wrong; it does not protect people. Guarding, safety-rated stops and safety I/O do that, as covered in 5.4 Making a Robot Cell Safe.

      FANUC's teach-pendant (TP) language is also built from explicit checks, not exceptions. A wait can name a jump label for the timeout case, as in WAIT DI[n]=ON TIMEOUT,LBL[x]. You set the time limit separately. In the timeout branch, a user alarm UALM[n] shows a message that the programmer defined. If the operator resumes the program, execution continues at the next line.[29][30] Sources disagree about exactly when a user alarm pauses the program, so check the FANUC manual for your controller before relying on that behavior. These FANUC details come from secondary sources.

      10. Putting it together: a structure that survives restarts

      Now let us combine the 3-by-3 pallet loop from section 06 with the retry logic from section 08. Imagine your robot has filled five slots on a pallet when someone stops the job. When you start the program again, you do not want it to smash a part onto slot 0. By keeping the slot count in persistent memory and counting only after a good place, the program picks up where it stopped.

      Here is the top of the RAPID module that joins sections 06 and 08. It is this course's example, so test it in RobotStudio first. Targets, tool, and signal names are placeholders. Confirm in the manual that a FOR loop may start from a PERS variable: 

      MODULE Pallet3x3
    CONST num PITCH_X := 60;          ! mm between columns (measure your parts)
    CONST num PITCH_Y := 60;          ! mm between rows
    CONST num APPROACH_Z := 80;       ! mm approach height
    CONST jointtarget jHome := [[0,0,0,0,30,0],[9E9,9E9,9E9,9E9,9E9,9E9]];
    PERS tooldata tGripper := [TRUE,[[0,0,150],[1,0,0,0]],[1,[0,0,50],[1,0,0,0],0,0,0]];
    PERS robtarget pPick := [[450,200,120],[0,0,1,0],[0,0,0,0],[9E9,9E9,9E9,9E9,9E9,9E9]];
    PERS robtarget pPalletCorner := [[450,-200,50],[0,0,1,0],[0,0,0,0],[9E9,9E9,9E9,9E9,9E9,9E9]];
    PERS num nPlaced := 0;            ! slots already filled; survives a restart
    VAR errnum ERR_MISSED_PICK := -1;

    PROC main()
        BookErrNo ERR_MISSED_PICK;
        SetDO doGripClose, 0;                   ! known state: gripper open
        MoveAbsJ jHome, v200, fine, tGripper;   ! start from home, slowly
        FOR i FROM nPlaced TO 8 DO              ! resume where we stopped
            PickPart;
            PlaceAt i DIV 3, i MOD 3;
            nPlaced := i + 1;                   ! count only after a good place
        ENDFOR
        nPlaced := 0;                           ! pallet full: ready for the next
        MoveAbsJ jHome, v500, fine, tGripper;
    ENDPROC

    ! PickPart, TryPick (section 08) and PlaceAt (section 06) go here
ENDMODULE

      The counter is what makes restarts work. Because nPlaced is PERS, it keeps its value even if the program is stopped and started from the beginning.[5] After a stop at slot 5, the loop resumes at slot 5 instead of stacking a part on slot 0. Notice that nPlaced is written only after a successful place. The FOR loop's counter i is declared by the FOR statement itself and needs no separate declaration.

      These patterns add up to a practical checklist, drawn from the production code above rather than vendor rules:

      1. Separate start-up from the cycle. RPI's module keeps motion_program_init() (which books error numbers) apart from motion_program_run(). A separate motion_program_fini() logs completion with ErrWrite\I.[2] On a UR, put start-up steps in the Before Start sequence.[9] Reset outputs there, and make start-up safe to run twice.[1]
      2. Check where the robot is before it moves. The ROS-Industrial driver skips its first move when the robot is already there. It uses a FUNC called is_near that compares current and target joint positions within tolerances.[1] The same idea gives a home check: if not near home, show a message and move home slowly, or refuse to start.
      3. Keep data at the top, not inside move lines. Keep pitches and heights as CONST. Keep taught frames, tool, payload, and counters as PERS, just as RPI keeps its tool, work object, and load.[2]
      4. One loop, small routines. Small routines keep each error handler close to its failure. Count progress only after success.
      5. Never wait forever. Every wait on a sensor has a time limit and a clear outcome: retry a few times, then tell the operator, then stop.
      6. Keep flags honest. Clear state flags in the error handler as well as on a normal exit.[2]
      7. Teach one frame on the pallet. Re-teaching that one work object then moves the whole grid.
      Try it
      1. In RobotStudio, build the Pallet3x3 module from sections 06, 08 and 10. Run it and check that the robot visits all nine slots in order, with row = i DIV 3 and col = i MOD 3. Then stop it after the fourth part, move the program pointer to main, start again, and confirm that it resumes at slot 4 because nPlaced is PERS.
      2. In URSim, run pallet3x3 from section 06 with pose_trans. Rotate the corner pose a few degrees about Z and watch the grid follow it. Then change the slot line to use pose_add and describe what changes.
      3. Simulate a missed pick by keeping the part-present input low (set it by hand in the simulator's I/O window). Confirm that each of the three attempts re-approaches and re-grips, then the program shows its message and stops. Then try the "looks right" PickPart from section 08 and watch RETRY re-read the sensor without re-gripping.
      4. Explain in two sentences why popup plus halt is not a safety stop, and what in the cell provides safety (see 5.4).
