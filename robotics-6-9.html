6.9 Motion Profiles and Interpolation

Gerald Lê

01. From "go there" to a plan in time

In lessons 1.6 and 2.3 you wrote motion commands such as MoveJ, MoveL and MoveC and chose a speed and a zone for each one. In this chapter you met the hardware underneath: PWM drives the motor, the encoder measures the shaft, and a PID loop pushes the measured position toward a setpoint. This lesson connects the two. Between "move to this target at 250 mm/s" and the PID loop sits a motion profile generator, which turns one target into a smooth stream of setpoints, a new one every control cycle.

The WPILib robot library describes its trapezoidal profile in exactly these terms: it generates "a sequence of setpoints that smoothly interpolate" between the current state and the goal state, while respecting a maximum velocity and a maximum acceleration.[1] Sent the final target in one step, the PID error would jump to its largest value at once. A profile asks for the motion a little at a time, so the controller only corrects small errors.

It helps to split every move into two separate questions:

  • The path (interpolation): Which points in space does the robot pass through? A joint move, a straight line and a circular arc are three different paths.
  • The time scaling (profile): How fast does the robot move along that path at each instant? A trapezoid, an S-curve, a cubic and a quintic are four different time scalings.

The Modern Robotics code library is built this way. Its trajectory functions take a time-scaling method (cubic or quintic) as one argument and compute the path separately, either in joint space or in Cartesian space.[2] Any profile can drive any path. Sections 02 to 05 cover profiles; sections 06 and 07 cover paths and corners.

02. The trapezoidal velocity profile

The most widely taught profile is the trapezoidal velocity profile. Picture a rest-to-rest move of distance D. The axis accelerates at a constant rate amax until it reaches the speed limit vmax, cruises at vmax, and then decelerates at amax until it stops exactly at the target. Plotted against time, the velocity rises in a straight ramp, stays flat, and falls in a straight ramp: a trapezoid. One survey describes this profile, with its constant-acceleration, constant-velocity and constant-deceleration phases, as the most common one for industrial robot trajectory planning.[3]

Production code uses the same three phases. WPILib's TrapezoidProfile class works out the acceleration time as maxVelocity / maxAcceleration and then computes how much distance is left for the cruise phase.[4] Peter Corke's Robotics Toolbox for Python describes its trapezoidal() function as "a linear motion segment with parabolic blends": in the position plot, a parabola, a straight line, then a parabola.[5]

The equations below follow from constant-acceleration kinematics (s = ½at2, v = at). They are written for a rest-to-rest move with D > 0. This lesson's own Python check (section 03) confirms that they land exactly on D. 

Accel time and distance:  t_a = v_max / a_max         d_a = v_max^2 / (2 a_max)
Trapezoid exists if:      D >= v_max^2 / a_max        (that is, 2 d_a <= D)
Cruise time:              t_c = (D - v_max^2 / a_max) / v_max
Total time:               T   = 2 t_a + t_c  =  D / v_max + v_max / a_max

Phase 1  (0 <= t < t_a):          a = +a_max   v = a_max t         s = 0.5 a_max t^2
Phase 2  (t_a <= t < t_a + t_c):  a = 0        v = v_max           s = d_a + v_max (t - t_a)
Phase 3  (t_a + t_c <= t <= T):   a = -a_max   v = a_max (T - t)   s = D - 0.5 a_max (T - t)^2

A useful self-check is the area under the velocity curve. Distance is the integral of velocity, so the area of the trapezoid must equal D. The area is vmax × (ta + tc): the two triangular ramps together make one rectangle of width ta.

Worked example. Take D = 0.5 m, vmax = 0.25 m/s and amax = 0.5 m/s².

  • Check the case: vmax² / amax = 0.0625 / 0.5 = 0.125 m. Since 0.5 m ≥ 0.125 m, the axis does reach full speed.
  • Accelerate: ta = 0.25 / 0.5 = 0.5 s, covering da = 0.0625 m.
  • Cruise: tc = (0.5 − 0.125) / 0.25 = 1.5 s, covering 0.375 m.
  • Total: T = 2(0.5) + 1.5 = 2.5 s. The shortcut D/vmax + vmax/amax = 2 + 0.5 = 2.5 s agrees.
  • Area check: 0.25 × (0.5 + 1.5) = 0.5 m = D.

In the total-time formula, D/vmax is the time at full speed the whole way, and vmax/amax is the extra time spent on the ramps.

03. When the move is too short: the triangular profile

The trapezoid needs room to speed up and slow down. Accelerating to vmax takes da and braking takes another da, so the move must be at least 2da = vmax²/amax long. For a shorter move the axis must start braking before it reaches vmax. The cruise phase disappears and the velocity plot becomes a triangular profile. Setting tc = 0 and requiring the two ramps to cover D gives: 

Triangular case (D < v_max^2 / a_max):
  t_a    = sqrt(D / a_max)
  v_peak = a_max t_a = sqrt(D a_max)     (always less than v_max)
  t_c    = 0
  T      = 2 sqrt(D / a_max)

WPILib handles this case explicitly. After computing the cruise distance, the code checks whether it is negative, with the comment "Handle the case where the profile never reaches full speed". If it is, the code sets the acceleration time to sqrt(dist / maxAcceleration) and the cruise distance to zero, which is the triangle above.[4] Corke's toolbox approaches the same limit from a different direction. Its trapezoidal() function takes the move duration as given and checks the requested speed V: it raises "V too small" if the speed could not cover the distance in time, and "V too big" if V is more than twice the average speed, which is the point where the trapezoid has collapsed into a triangle.[5]

Worked example. Keep vmax = 0.25 m/s and amax = 0.5 m/s² but shorten the move to D = 0.05 m. Since 0.05 m < 0.125 m, the profile is triangular: ta = √(0.05 / 0.5) = √0.1 = 0.316 s, vpeak = 0.5 × 0.316 = 0.158 m/s and T = 0.632 s. The area check is ½ × 0.632 × 0.158 = 0.05 m. For short moves, cycle time is set by acceleration, not by the programmed speed.

The trapezoidal velocity profile explorer needs JavaScript. With it on, you can adjust distance, maximum velocity and acceleration to inspect trapezoidal and triangular profiles and the area under the curve.

The short script below is the lesson's own example. It implements both branches and checks the area under v(t). It was run with Python 3 and prints the output shown after it. 

import math

def trapezoid(D, v_max, a_max):
    """Rest-to-rest trapezoidal (or triangular) profile timing."""
    if D >= v_max**2 / a_max:          # full trapezoid: v_max is reached
        t_a = v_max / a_max
        v_peak = v_max
        t_c = (D - v_max**2 / a_max) / v_max
    else:                              # triangle: v_max is never reached
        t_a = math.sqrt(D / a_max)
        v_peak = a_max * t_a
        t_c = 0.0
    T = 2 * t_a + t_c
    return t_a, t_c, T, v_peak

for D in (0.5, 0.05):
    t_a, t_c, T, v_peak = trapezoid(D, v_max=0.25, a_max=0.5)
    area = v_peak * (t_a + t_c)        # area under v(t) must equal D
    print(f"D={D} m: t_a={t_a:.3f} s, t_c={t_c:.3f} s, "
          f"T={T:.3f} s, v_peak={v_peak:.3f} m/s, area={area:.3f} m")
D=0.5 m: t_a=0.500 s, t_c=1.500 s, T=2.500 s, v_peak=0.250 m/s, area=0.500 m
D=0.05 m: t_a=0.316 s, t_c=0.000 s, T=0.632 s, v_peak=0.158 m/s, area=0.050 m

04. Jerk and the S-curve profile

Look at the acceleration plot of a trapezoidal profile. It is a set of rectangles: +amax, then 0, then −amax. At each corner the acceleration changes instantly. Jerk is the rate of change of acceleration, so at those corners the jerk is, in theory, infinite. Engineering sources describe trapezoidal profiles as having effectively infinite jerk at the corners, and give this as the reason S-curve profiles are used.[6]

There is a physical reason to care, and it ties back to this chapter. Motor torque is roughly proportional to motor current, and the acceleration demand sets the torque. A step in acceleration is therefore a step in the torque the drive is asked for, and so a sudden change in current and PWM duty. Real arms and gearboxes are slightly flexible, so a torque step makes them ring. Motion-control references note that higher jerk produces more unwanted vibration energy.[7][8]

An S-curve profile adds a jerk limit to the trapezoid. Instead of jumping to amax, the acceleration ramps up at a constant jerk, holds, and ramps down again. The full move then has seven segments: jerk up, constant acceleration, jerk down, cruise, and the mirror image of the first three for braking.[7][8] The velocity plot gets rounded "S"-shaped shoulders, which gives the profile its name. The same idea moves one derivative higher: the trapezoid's acceleration plot is made of rectangles, while the S-curve's acceleration plot is made of trapezoids. A study of third-order (jerk-limited) trajectories reports that this 7-segment profile produces less vibration than a trapezoidal profile.[9]

The price is more algebra: the seven segment durations depend on whether the move is long enough to reach amax and vmax, so there are several cases. In practice, engineers use a library. Ruckig is an open-source example: it generates trajectories "limited by velocity, acceleration, and jerk constraints" and its README says it "guarantees a time-optimal solution" for moves from one state to another.[10] The README also points out a subtle feasibility rule. If an axis is already near its velocity limit, any remaining positive acceleration will carry it past the limit, because the jerk limit means acceleration cannot drop to zero instantly. Ruckig's check is |a| ≤ √(2 · jmax · (vmax − |v|)).[10]

05. Polynomial time scaling: cubic and quintic

Another way to time a move is to choose a smooth function s(t) that rises from 0 at the start to 1 at the end, then place the robot at the fraction s of the way along its path. This function is called a time scaling. The Modern Robotics library offers two polynomial time scalings, where T is the move duration:[2] 

CubicTimeScaling(T, t)   = 3 (t/T)^2 - 2 (t/T)^3
QuinticTimeScaling(T, t) = 10 (t/T)^3 - 15 (t/T)^4 + 6 (t/T)^5

The library's documentation says the cubic is "for a third-order polynomial motion that begins and ends at zero velocity", and the quintic "begins and ends at zero velocity and zero acceleration". Its worked examples use T = 2 s and t = 0.6 s, which give 0.216 (cubic) and 0.16308 (quintic).[2] You can check both by hand: t/T = 0.3, so the cubic gives 3(0.09) − 2(0.027) = 0.216.

Where do the coefficients come from? A cubic q(t) = a0 + a1t + a2t² + a3t³ has four unknown coefficients, and a rest-to-rest move gives four conditions: start position, end position, zero start velocity and zero end velocity. Solving them gives a0 = q0, a1 = 0, a2 = 3(qf − q0)/T² and a3 = −2(qf − q0)/T³, which is the normalized cubic above. A quintic has six coefficients, so it can also meet zero start and end acceleration. Those six conditions lead to the 10, −15, 6 form. Differentiating gives these peak values for a move of distance D in time T (this lesson's own calculation, checked numerically):

Time scaling Peak velocity Peak acceleration Acceleration at start and end
Cubic 1.5 D/T 6 D/T² Jumps from 0 to its peak at t = 0 (and back at t = T)
Quintic 1.875 D/T about 5.77 D/T² Starts and ends at 0, so no jump

The cubic shares the trapezoid's weakness: its acceleration jumps at the ends, so jerk is infinite there. The quintic pays with a higher peak velocity but starts and stops gently. Corke's toolbox provides both kinds of tool: quintic and jtraj for joint-space polynomial trajectories, alongside trapezoidal.[5]

06. Interpolation: joint, linear and circular paths

Now for the path. In joint interpolation (MoveJ) each joint moves along a straight line in joint space, from its start angle to its end angle. The Modern Robotics function JointTrajectory(thetastart, thetaend, Tf, N, method) "computes a straight-line trajectory in joint space" and applies one time scaling (method 3 for cubic, 5 for quintic) to every joint.[2] Because all joints share the same s(t), they start together, reach the halfway point together, and finish together. The tool, however, traces a curve in space, because the forward kinematics that map joint angles to tool position are not linear.

Universal Robots' parameter units show the same idea. For moveJ, velocity is the "Joint speed of leading axis [rad/s]" and acceleration is in rad/s².[11] The leading axis is the joint with the largest move. It sets the duration, and the other joints are slowed so that everyone arrives at once.

In linear interpolation (MoveL) the tool center point (TCP) follows a straight line in Cartesian space. The Modern Robotics CartesianTrajectory function makes "the origin of the end-effector frame follow a straight line, decoupled from the rotational motion". It interpolates position as s·pend + (1 − s)·pstart, and orientation as a rotation about one fixed axis from the start orientation to the end orientation.[2] Corke's ctraj does the same job with a trapezoidal velocity profile along the path, and its documentation says "orientation interpolation is performed using unit-quaternion interpolation" (using unit quaternions, four-component mathematical representations of three-dimensional rotation that avoid gimbal lock).[5] This quaternion method is often called SLERP (spherical linear interpolation). For UR's moveL, moveP and moveC, the units change to "Tool speed [m/s]" and "Tool acceleration [m/s²]", because these moves are planned in Cartesian space. The client library's default values are a = 1.4 and v = 1.04.[11]

Circular interpolation (MoveC) sends the TCP along an arc. UR's moveC(via, target, ...) moves "in a circular motion going through via", where the circle is defined by the current pose, the via point and the target.[11] ABB's RAPID has the same three-point idea in MoveC circPoint, toPoint, speed, zone, tool, which appears in the open_abb RAPID server.[12]

07. Corners: zones, blend radius and parabolic blends

If every move in a chain used a full rest-to-rest profile, the robot would stop at every point. That is right where the gripper must open, and wasteful everywhere else. Lesson 2.3 introduced the fix: blending (zones).

In ABB RAPID, a stop point is set with fine, and a fly-by point is set with zone data. The open_abb RAPID server shows the fields of zonedata: finep (TRUE means a stop point), pzone_tcp (the TCP zone), pzone_ori (the zone for orientation) and further zone sizes. The same program defines z0 as [FALSE, 0.3, 0.3, 0.3, 0.03, 0.3, 0.03] and builds "fine" by setting finep to TRUE with all zone sizes at 0.[12] ABB's RAPID reference manual lists the fly-by zone z0 as 0.3 mm, which matches those values.[13] Sources disagree on whether the zone number gives a radius or a diameter: an ABB API page calls pzone_tcp the radius of the TCP zone in mm, while a university course page calls it a diameter.[14][15] Check your controller's own manual before relying on the exact size. Position and orientation have separate zone parameters, so their blends can start and end independently.[16]

Once the TCP enters the zone around a fly-by point, the controller starts on the next segment. The braking ramp of one move overlaps the speeding-up ramp of the next, so the TCP keeps moving and rounds the corner instead of passing through the programmed point. A bigger zone is faster and smoother but stays farther from the point; forum users give the same advice to robots that hesitate at fine points.[17] A corner path failure occurs when the program does not supply the next move instruction in time, so the controller turns the fly-by point into a stop point.[13] Users of ABB's community forum report it as event 50024, often caused by a wait right after a zone point.[18]

Universal Robots uses a blend radius. In the UR client library every move type (moveJ, moveL, moveP, moveC) takes a blend_radius parameter, and its default of 0 means no blending.[11] URScript sources describe the radius r, in meters, as what prevents a stop at the waypoint. They add that if a move's blend region overlaps the previous or next one, the move is skipped with an "Overlapping Blends" warning.[19] For processes such as extrusion or dispensing, users recommend movep, which keeps the tool speed constant instead of ramping it up and down.[20]

The textbook version of a blended corner is the LSPB (linear segments with parabolic blends) trajectory. Corke's trapezoidal() function is literally "a linear motion segment with parabolic blends", and the toolbox keeps the old name lspb() as an alias.[5] A parabolic blend in position is a ramp in velocity, so a trapezoid and an LSPB are two views of one motion. MoveIt applies the same idea to whole paths: its time-optimal planner states that "the intermediate waypoints of the input path need to be blended so that the entire path is differentiable", and its default path tolerance of 0.1 (rad or m) sets how far the blended path may stray from a waypoint.[21] That tolerance plays the same role as a zone size.

08. Time parameterization in ROS and MoveIt

In ROS 2 these steps are visible. The MoveIt tutorial states: "MoveIt is currently primarily a kinematic motion planning framework – it plans for joint or end effector positions but not velocity or acceleration."[22] A planner first returns a geometric path, a list of joint positions with no timing. A post-processing step called time parameterization then adds a timestamp, velocity and acceleration to every waypoint.[22]

The limits come from the robot's URDF or a joint_limits.yaml file (max_velocity, max_acceleration, max_jerk). Users can also slow a motion with velocity and acceleration scaling factors between 0 and 1.[22] The default algorithm is Time-Optimal Trajectory Generation (TOTG), written by Tobias Kunz at Georgia Tech. Its computeTimeStamps function takes the trajectory and the two scaling factors, and it resamples the result every 0.1 s by default.[21] The tutorial says TOTG "produces trajectories with very smooth and continuous velocity profiles" and that "it is the default everywhere in MoveIt 2". It also warns that resampled waypoints "may divert from the original trajectory within a certain tolerance", so extra collision checks may be needed.[22]

TOTG limits velocity and acceleration but not jerk. The tutorial is direct about the risk: "None of the time parameterization algorithms support jerk limits", and "large jerks along a trajectory can cause jerky motion or damage hardware". Its remedy is to add a Ruckig smoothing step (AddRuckigTrajectorySmoothing) after AddTimeOptimalParameterization.[22] If limits are missing from the robot description, MoveIt's Ruckig smoother falls back to defaults of 5 rad/s, 10 rad/s² and 1000 rad/s³.[23] Do not rely on those numbers for a real arm. Set the limits yourself.

One way to remember the pair, in rough terms: TOTG finds the fastest trapezoid-like timing along the whole path, and Ruckig rounds off the acceleration corners into an S-curve. That is the same trapezoid versus S-curve contrast as in section 04. Ruckig itself is described as "Instantaneous Motion Generation for Robots and Machines". It works from any initial state (position, velocity and acceleration) to a target state, runs inside a real-time control loop, is used by MoveIt 2 and CoppeliaSim, and installs with pip install ruckig.[10]

09. Why MoveL can fail where MoveJ succeeds

The choice of path has a practical side effect that every robot programmer meets. A joint move commands joint angles directly, so the motion is always well defined. A linear move commands TCP poses. The Modern Robotics CartesianTrajectory function returns only a list of poses, and turning each pose into joint angles requires inverse kinematics at every step. JointTrajectory needs none.[2]

Near a kinematic singularity—a configuration where joint axes align and eliminate one or more degrees of freedom—that step becomes a problem. A classic case on a six-axis arm is the wrist singularity, where joint 5 is close to zero and two wrist axes line up. Holding a constant TCP speed through that region can demand very large joint speeds, so the controller slows, stops or reports an error. ABB's RAPID manual offers SingArea \Wrist, which lets the tool orientation differ somewhat so a linear move can pass the wrist singularity, where axes 4 and 6 are parallel (axis 5 at 0 degrees); the setting applies until the next SingArea instruction, and SingArea \Off is the default.[13][24] Users on ABB's forum add a second way through: replace the move with a MoveJ.[25] One forum thread reports that ABB support confirmed MoveL errors cannot be caught with an error handler, and suggests checking the path first with non-motion execution, which runs the program without moving the robot.[26]

The practical rule: use MoveJ for large repositioning moves in the air, and save MoveL for the approach, the process and the retreat. If a linear move fails near "axis 5 = 0", tilt the wrist in the taught target or switch to a joint move.

10. Choosing a profile in practice

The table brings the profiles together. "Continuous" means the quantity has no jumps from start to finish of a rest-to-rest move.

Profile Limits it respects Continuous up to Typical use
Trapezoid / triangle vmax, amax Velocity (acceleration jumps) Simple axes, WPILib mechanisms, LSPB corners
S-curve (7 segments) vmax, amax, jmax Acceleration (jerk is limited) Arms and machines where vibration matters; Ruckig
Cubic Duration T Velocity (acceleration jumps at the ends) Simple point-to-point joint moves
Quintic Duration T Acceleration (starts and ends at 0) Smooth joint moves, such as jtraj or QuinticTimeScaling

Note the difference in the "Limits" column. The trapezoid and the S-curve start from the limits and compute the shortest time that respects them. The polynomials start from a chosen duration T. For a quintic you must then check 1.875 D/T ≤ vmax and about 5.77 D/T² ≤ amax, so T must be large enough to satisfy both.

Whichever profile you use, it feeds the loop from this chapter: the profile produces the setpoint, the encoder reports the position, and PID corrects the small difference.

Try it
  1. By hand, plan a move with D = 0.5 m, vmax = 0.25 m/s and amax = 0.5 m/s². First check that D ≥ vmax²/amax, then compute ta, tc and T (you should get 0.5 s, 1.5 s and 2.5 s). Sketch v(t) on graph paper and confirm that the area under it is 0.5 m.
  2. Repeat for the short move D = 0.05 m with the same limits. Explain why the profile becomes a triangle, and compute T (0.632 s) and the peak speed (0.158 m/s).
  3. Run the Python script from section 03 and check that it prints your hand results. Then try D = 0.125 m, exactly on the boundary between the two cases, and explain what happens to tc.
  4. Double amax to 1.0 m/s² and rerun both moves. Which move gets faster by a larger fraction, and why does the total-time formula predict this?
  5. For D = 0.5 m and a quintic time scaling, find the smallest T that keeps the peak velocity under 0.25 m/s and the peak acceleration under 0.5 m/s². Compare it with the trapezoid's 2.5 s.
