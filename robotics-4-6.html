      4.6 Writing Your First ROS 2 Package

      Gerald Lê
      Chapter 4, lesson 6 of 10 ← Previous: 4.5 ROS Tools Next: 4.7 Launch Files and Parameters →

      01. From running examples to building your own package

      In earlier lessons, you ran robots that someone else built. When you write your own robot program, Robot Operating System 2 (ROS 2) expects it to live inside a package. A package is a folder with a standard layout so ROS 2 can find, build, and share your code. In this lesson, you will build a package called turtle_square that drives the Turtlesim turtle around a square.

      In lesson 4.4, you drove Turtlesim from the keyboard and wrote two small nodes. In lesson 4.5, you met the tools used to inspect a running system. Here you will slow down and set up a workspace on purpose instead of copying commands blindly. You will learn what each file created by ros2 pkg create does, list the packages your code depends on so others can build it, and run your own node.

      Everything in this lesson targets ROS 2 Lyrical Luth, the twelfth release of ROS 2. It is a long-term support (LTS) release that came out in May 2026 and is supported until May 2031.[1] A few details of package building changed in the last two releases. Many online tutorials target older releases, so this lesson points out where Lyrical differs.

      For the curious: supported platforms, Python versions, and moved tutorials

      Lyrical’s Tier 1 platforms are Ubuntu 26.04 (Resolute) on amd64 and arm64, and Windows 11 with Visual Studio 2022 on amd64. It supports Python 3.12 to 3.14, and Ubuntu 26.04 ships Python 3.14.3.[2]

      The official tutorials also moved on Lyrical. They now live in a “Working with Client Libraries” section under ROS-Framework/client-libraries/ instead of the old Tutorials/Beginner-Client-Libraries/ path. The pages carry redirects from the old addresses, so if a bookmark from an older course stops working, look in the new section.[3]

      02. How workspaces layer your code on ROS 2

      Before you create a package like turtle_square, you need a home folder for your own code. That home folder is called a workspace, and it lets you add new packages without touching your main ROS 2 install. Think of it like laying a clear plastic sheet over a printed map: you can draw your own routes on top without ruining the map underneath.

      In everyday words, a workspace is simply a folder that holds your ROS 2 packages. The official documentation puts it this way: “A workspace is a directory containing ROS 2 packages.”[3]

      Workspaces are built in layers. Your main ROS 2 installation in /opt/ros/lyrical is the bottom layer, called the underlay. Your own workspace, such as ~/ros2_ws, sits on top as an overlay. In everyday words, an overlay lets you add or change packages safely without breaking your base ROS 2 setup. The documentation defines it as “a secondary workspace where you can add new packages without interfering with the existing ROS 2 workspace that you're extending.” The underlay must already hold the dependencies of every package in your overlay. If a package in your overlay shares the same name as one in the underlay, your overlay version wins.[3]

      On Ubuntu, first install the build tools with sudo apt update && sudo apt install ros-dev-tools.[4] Then create your workspace. The documented best practice is a new directory for every workspace, with all packages placed inside its src folder:[3] 

      source /opt/ros/lyrical/setup.bash
mkdir -p ~/ros2_ws/src
cd ~/ros2_ws/src

      When you later run colcon build from ~/ros2_ws, the colcon build tool creates three folders next to src. The build folder holds intermediate files, with one subfolder per package. The install folder holds each installed package, by default in its own subfolder. The log folder “contains various logging information about each colcon invocation.”[5]

      To use your overlay, you have to source it so your terminal knows where to find your packages. Always open a brand-new terminal for this, never the same one where you ran the build. The tutorial is firm about this rule: “it is very important that you open a new terminal, separate from the one where you built the workspace. Sourcing an overlay in the same terminal where you built, or likewise building where an overlay is sourced, may create complex issues.”[3] In the new terminal, source the underlay first and then the overlay: 

      source /opt/ros/lyrical/setup.bash
cd ~/ros2_ws
source install/local_setup.bash

      Your install folder includes two setup scripts. Sourcing local_setup “will only add the packages available in the overlay to your environment,” while setup loads the overlay along with the underlay it was built against.[3] That means sourcing underlay setup and then overlay local_setup gives the same result as sourcing overlay setup on its own.

      The workspace tutorial proves how this layering works with a small experiment. If you clone Turtlesim into your overlay and change its window title in turtle_frame.cpp from "TurtleSim" to "MyTurtleSim", rebuilding lets your copy replace the system one. A terminal with the overlay sourced shows the new title, while a terminal with only the underlay sourced still shows the original. That shows “the overlay takes precedence over the underlay.”[3] A good mental model is a stack: whatever you source last sits on top.

      Windows 11 note

      The Lyrical Windows install uses pixi and conda-forge. In every Command Prompt you run pixi shell and then call C:\dev\lyrical\local_setup.bat. C++ builds need Visual Studio Build Tools 2022, run from the “x64 Native Tools Command Prompt for VS 2022”.[6] On Windows you build with colcon build --merge-install and source with call install\setup.bat (or install\setup.ps1 in PowerShell).[3][5] The Lyrical workspace and colcon tutorials still mention the VS 2019 prompt and C:\dev\ros2, so follow the install page where they disagree.[3][6]

      For the curious: stacking more layers, older catkin workspaces, and other shells

      Workspace layers can be stacked more than two deep.[3]

      Unlike the older catkin tool from ROS 1, colcon creates no devel folder and builds out of the source tree.[5]

      Underlay scripts come as setup.bash, setup.sh, or setup.zsh,[4] and Lyrical adds a setup.fish script for fish shell users.[1]

      03. Creating a Python package

      Now that your workspace is ready, you need to create a package folder inside src. You could create each configuration file by hand, but it is easy to miss a required setting. Instead, ROS 2 provides the ros2 pkg create command to generate a working Python package for you in seconds. You will use it now to create turtle_square.

      Always create packages from inside your src directory. Here is the documented Python form of ros2 pkg create:[7] 

      cd ~/ros2_ws/src
ros2 pkg create --build-type ament_python --license Apache-2.0 --node-name my_node my_package

      Each flag sets up part of your new package. Passing --node-name “creates a simple Hello World type executable,” and --license records the package’s license.[7] The one flag you must never forget is --build-type. In Lyrical, the default build type is still ament_cmake, so leaving --build-type out gives you a C++ package with a CMakeLists.txt instead of a Python one.[8]

      For this lesson’s project, create a package called turtle_square with one node called square_driver. Your node will import rclpy and geometry_msgs, and the stretch version in section 10 also imports turtlesim_msgs. You can list all three dependencies at creation time: 

      ros2 pkg create --build-type ament_python --license Apache-2.0 \
    --node-name square_driver turtle_square \
    --dependencies rclpy geometry_msgs turtlesim_msgs

      A workspace can hold packages of different build types side by side. However, you cannot nest one package inside another package’s folder.[7]

      For the curious: all build types, extra flags, and package.xml formats

      In the Lyrical source code of ros2 pkg create, the choices for --build-type are cmake, ament_cmake, ament_cargo (used for compiling packages written in Rust), and ament_python, with ament_cmake as the default.[8] The two recommended build types are ament_cmake and ament_python.[5]

      Other useful options include --dependencies (one or more packages to depend on), --description, --maintainer-name, and --maintainer-email (filled in from your git config when available). You can also pass --package-format (2 or 3, default 3), --destination-directory, and --library-name. Passing --license ? lists the licenses that also produce a LICENSE file.[8]

      colcon reads package.xml files in format 3, defined by ROS Enhancement Proposal (REP) 149, with format 2 also supported.[5]

      04. Inside the generated package files

      When ros2 pkg create finishes, it writes several files and folders inside turtle_square. Seeing a handful of extra files for one short Python script can look overwhelming at first. Each file has one specific job, such as listing dependencies or telling ROS 2 how to run square_driver. Knowing what each piece does makes it much easier to fix missing-file errors later.

      Five parts are required for a Python (ament_python) package to build and run cleanly:[7]

      • package.xml: The manifest. It records the name, version, description, maintainer, license, dependencies, and build type.[7]
      • resource/<package_name>: An empty marker file installed into the ament resource index so ROS tools can find the package.[7][9]
      • setup.cfg: Tells ROS where executables live. It is “Required when a package has executables, so ros2 run can find them.”[7]
      • setup.py: Tells Python’s setuptools how to install the package.[7]
      • <package_name>/: A Python module folder with the same name as the package, containing __init__.py. Your node files go here.[7]

      Here is the shape of the setup.py that the Lyrical template generates for turtle_square, with the maintainer fields shortened:[9] 

      from setuptools import find_packages, setup

package_name = 'turtle_square'

setup(
    name=package_name,
    version='0.0.0',
    packages=find_packages(exclude=['test']),
    data_files=[
        ('share/ament_index/resource_index/packages',
            ['resource/' + package_name]),
        ('share/' + package_name, ['package.xml']),
    ],
    package_data={'': ['py.typed']},
    install_requires=['setuptools'],
    zip_safe=True,
    maintainer='...',
    maintainer_email='...',
    description='TODO: Package description',
    license='Apache-2.0',
    extras_require={'test': ['pytest']},
    entry_points={
        'console_scripts': [
            'square_driver = turtle_square.square_driver:main',
        ],
    },
)

      Two sections in setup.py do most of the ROS wiring. First, data_files copies your resource marker and package.xml to the folders where ROS expects them. Second, entry_points maps command names to Python functions. Each entry in console_scripts reads <executable name> = <python package>.<module>:<function>, as in the tutorial’s 'talker = py_pubsub.publisher_member_function:main'.[10] The name on the left is what you type after ros2 run turtle_square.

      Meanwhile, the generated setup.cfg holds two short sections: [develop] script_dir=$base/lib/turtle_square and [install] install_scripts=$base/lib/turtle_square. They place your executables inside lib “because ros2 run will look for them there.”[9][10] Also make sure the name, version, description, maintainer, and license match between package.xml and setup.py, so edit both files when you replace the TODO placeholders.[7]

      Watch out: a typo in the official page

      The setup.py listing in the Lyrical “Creating a package” tutorial uses package_name = 'my_py_pkg' and the entry point 'my_node = my_py_pkg.my_node:main', while the rest of that page uses my_package.[7] If you copy it word for word, the names will not match your package. Always check that the names in setup.py match your folder names.

      For the curious: every generated file and Lyrical template differences

      The documented output for an ament_python package includes the root configuration files package.xml, setup.py, setup.cfg, and resource/my_package. It also creates the module folder with my_package/__init__.py and the node file my_package/my_node.py, plus three tests: test/test_copyright.py, test/test_flake8.py, and test/test_pep257.py.[7]

      The Lyrical template also writes a py.typed marker file and two extra tests, test/test_mypy.py and test/test_xmllint.py, which the documentation’s sample output does not show.[8][9] The package_data line for py.typed appears in the Kilted and Lyrical templates, but not in Humble or Jazzy, so older projects may lack it.[9]

      05. Listing the packages your code needs

      Your square_driver script will import code from other ROS 2 packages such as rclpy and geometry_msgs. Python imports let the code run on your machine, but they do not tell another computer what packages to install before building yours. Listing those dependencies in package.xml lets ROS 2 install everything your package needs before a build starts.

      Every package your code imports should be declared inside package.xml. Different tags tell ROS 2 when each dependency is needed:[11]

      • <depend>: Needed at both build time and run time.[11]
      • <build_depend> and <build_export_depend>: Needed only for building, or for headers exported to packages that build against yours.[11]
      • <exec_depend>: “Shared libraries, executables, Python modules, launch scripts and other files required when running.”[11]
      • <test_depend>: Needed only to run tests.[11]

      Because turtle_square is a pure Python package, its imports are only needed when running. Following the rosdep guide, declare them as <exec_depend> lines in package.xml:[11] 

      <exec_depend>rclpy</exec_depend>
<exec_depend>geometry_msgs</exec_depend>
<exec_depend>turtlesim_msgs</exec_depend>

      Why bother writing these lines if Python already imports the modules? Because rosdep reads them. In plain words, rosdep checks your package.xml files and installs missing system packages for you. The documentation calls it “a meta-package manager”. It looks up each key from package.xml in the rosdistro index and installs the matching system package through apt or dnf. Released ROS packages use their package name as the key.[11]

      Initialize rosdep once per machine, then run it from your workspace root before every build of new code:[11][3] 

      sudo rosdep init
rosdep update

cd ~/ros2_ws
rosdep install -i --from-path src --rosdistro lyrical -y

      On success, it prints #All required rosdeps installed successfully. Checking dependencies first saves you wasted time. As the workspace tutorial explains, “You wouldn't want a build to fail after a long wait only to realize that you have missing dependencies.”[3] Note that “rosdep only works on Linux and macOS; Windows is not supported.”[11]

      For the curious: test dependencies and <exec_depend> vs <depend> in the docs

      The generated Python package.xml uses format 3, includes TODO placeholders for the description and license, and ends with <export><build_type>ament_python</build_type></export>. It lists ament_copyright, ament_flake8, ament_pep257, and python3-pytest as test dependencies.[7] The Lyrical template also adds ament_mypy and ament_xmllint to those test dependencies.[8]

      The official docs are not fully consistent on runtime tags. The publisher tutorial adds <exec_depend>rclpy</exec_depend> and <exec_depend>std_msgs</exec_depend> by hand, one per import.[10] Passing --dependencies at creation time “will automatically add the necessary dependency lines” for you, yet the template writes them as <depend> tags.[12][9] Meanwhile, the rosdep page says pure Python packages “should never use” <depend> and should use <exec_depend>, while the parameters tutorial shows <depend>rclpy</depend>.[11][13] Both forms build.

      06. How a Python node starts and shuts down

      Before writing square_driver, look at the standard skeleton every ROS 2 Python node shares. Whether a node drives a turtle, reads a camera, or logs sensor readings, it starts ROS 2, loops while waiting for events, and cleans up when you quit. On ROS 2 Lyrical, a single Python with block handles both startup and cleanup for you.

      The Lyrical publisher tutorial gives the pattern every Python node in this course follows. Its main function looks like this:[10] 

      import rclpy
from rclpy.executors import ExternalShutdownException
from rclpy.node import Node

from std_msgs.msg import String

# ... class MinimalPublisher(Node) defined here ...

def main(args=None):
    try:
        with rclpy.init(args=args):
            minimal_publisher = MinimalPublisher()
            rclpy.spin(minimal_publisher)
    except (KeyboardInterrupt, ExternalShutdownException):
        pass


if __name__ == '__main__':
    main()

      Read this code as a lifecycle. First, rclpy.init starts the ROS client library. Because it sits inside a with block, ROS shuts down automatically when the block ends. As a result, the Lyrical tutorial leaves out explicit destroy_node() and rclpy.shutdown() calls that you still see in code written for older distributions.[10]

      Inside the block, you create your node. Its __init__ method calls super().__init__('minimal_publisher') to name the node and creates its publishers, subscriptions, and timers. Next, rclpy.spin() “spins” the node “so its callbacks are called.” Pressing Ctrl+C raises KeyboardInterrupt, which the except block catches so the program exits quietly.[10]

      Three node methods do most of the everyday work:[10]

      • self.create_publisher(String, 'topic', 10): Sets the message type, the topic name, and a queue size of 10. In plain words, queue size sets how many messages wait in line if a receiver falls behind. The tutorial calls it “a required Quality of Service (QoS) setting that limits the amount of queued messages if a subscriber is not receiving them fast enough.”
      • self.create_timer(0.5, self.timer_callback): Runs a callback function every 0.5 seconds.
      • self.create_subscription(String, 'topic', self.listener_callback, 10): Registers a callback that runs “as soon as it receives a message”, so a subscriber needs no timer. The topic name and type must match on both sides.

      Nodes can also provide services and hold parameters. Lesson 4.7 covers parameters in depth, so for now square_driver uses topics only.

      For the curious: services and parameters inside a node

      A service server is created with create_service(Type, 'name', callback), where the callback fills in and returns a response. A client uses create_client, wait_for_service, and call_async, and the docs warn: “Do not use rclpy.spin_until_future_complete in a ROS 2 callback.”[12]

      A node can also declare a parameter with self.declare_parameter('my_parameter', 'world'), where the type comes from the default value. You read it with self.get_parameter('my_parameter').get_parameter_value().string_value, and you can change it at run time with ros2 param set.[13]

      07. How to talk to Turtlesim

      Before writing a controller, check what messages Turtlesim listens to and sends back. Just like checking a motor’s datasheet before wiring it up, reading the simulator’s topic names keeps you from guessing. Turtlesim reads speed commands on one topic and broadcasts the turtle’s position and heading on another.

      The Lyrical Turtlesim source shows that each turtle subscribes to <name>/cmd_vel using geometry_msgs/msg/Twist. It publishes <name>/pose using turtlesim_msgs/msg/Pose, as well as <name>/color_sensor.[14] For the first turtle, those topic names become /turtle1/cmd_vel and /turtle1/pose.

      Three details from Turtlesim’s source code shape how you design square_driver:[14]

      • Only two velocity fields are used: Turtlesim reads linear.x and angular.z from the Twist message. It uses linear.y only if its holonomic parameter is true.[14]
      • A one-second command timeout: If more than 1.0 s passes since the last cmd_vel message, Turtlesim sets all velocities to zero. A node that publishes once and stops will make the turtle move briefly and halt.[14]
      • Walls are hard limits: Positions are clamped to the canvas. When the turtle reaches the edge, Turtlesim logs “Oh no! I hit the wall!”[14]

      When you add feedback later, your node will read the Pose message. It has five float32 fields: x, y, theta, linear_velocity, and angular_velocity.[15] In this pose, y points up the screen and theta is the heading in radians.[14] The first turtle spawns at x=5.544445, y=5.544445, theta=0.0, near the center and facing to the right.[16]

      Old tutorials will break: turtlesim_msgs

      Starting with Kilted, Turtlesim’s message and service definitions moved out of the turtlesim package into a new turtlesim_msgs package. On the Kilted and Lyrical branches, turtlesim_msgs/msg/Pose.msg exists and turtlesim/msg/Pose.msg does not. On Humble and Jazzy, it is the other way round.[15][14] Many tutorials online still write from turtlesim.msg import Pose and <depend>turtlesim</depend>. On Lyrical, use from turtlesim_msgs.msg import Pose, from turtlesim_msgs.srv import TeleportAbsolute, and depend on turtlesim_msgs. You can confirm with ros2 interface show turtlesim_msgs/msg/Pose.

      For the curious: Turtlesim services, actions, and QoS profile

      Each turtle also offers the services set_pen, teleport_relative, and teleport_absolute, along with the action rotate_absolute. The Turtlesim node itself provides the services clear, reset, spawn, and kill.[14]

      Turtlesim’s topics use a reliable QoS profile that keeps the last 7 messages.[14]

      08. Driving the turtle in a square

      Now you are ready to write square_driver. The simplest way to draw a square is to drive forward for a set time, turn for a set time, and repeat four times. Engineers call this open-loop control because the node never checks where the turtle actually is while moving. Instead, it trusts a timer and simple speed-times-time math.

      The one-second timeout from section 07 decides the node’s structure. You cannot send one “go forward” message and sleep, because the turtle would stop after 1.0 s. Instead, the node uses a timer that fires 10 times a second (every 0.1 s, well under the 1.0 s timeout). On each tick, it updates a small state machine with three states: FORWARD, TURN, and DONE.[14][10]

      The timing is simple motion math. At 1.0 m/s, a 2.0 m side takes 2.0 s. At 1.0 rad/s, a 90° turn (π/2 rad) takes about 1.57 s. Starting near (5.54, 5.54), a 2 m square stays well clear of the walls. Replace the generated ~/ros2_ws/src/turtle_square/turtle_square/square_driver.py with the code below. Because it is an example written for this lesson, test it on your own Lyrical install before relying on it. 

      import math

import rclpy
from rclpy.executors import ExternalShutdownException
from rclpy.node import Node

from geometry_msgs.msg import Twist


class SquareDriver(Node):

    def __init__(self):
        super().__init__('square_driver')
        self.publisher_ = self.create_publisher(Twist, '/turtle1/cmd_vel', 10)
        self.dt = 0.1             # timer period in seconds (10 Hz)
        self.side_length = 2.0    # metres
        self.speed = 1.0          # forward speed, m/s
        self.turn_speed = 1.0     # turning rate, rad/s
        self.state = 'FORWARD'
        self.elapsed = 0.0        # time spent in the current state
        self.sides_done = 0
        self.timer = self.create_timer(self.dt, self.timer_callback)

    def timer_callback(self):
        # 1. Decide whether it is time to change state.
        if self.state == 'FORWARD' and self.elapsed >= self.side_length / self.speed:
            self.state, self.elapsed = 'TURN', 0.0
        elif self.state == 'TURN' and self.elapsed >= (math.pi / 2) / self.turn_speed:
            self.sides_done += 1
            self.get_logger().info(f'Finished side {self.sides_done}')
            self.state, self.elapsed = 'FORWARD', 0.0
            if self.sides_done == 4:
                self.state = 'DONE'

        # 2. Build the command for the current state.
        msg = Twist()             # every field starts at 0.0
        if self.state == 'FORWARD':
            msg.linear.x = self.speed
        elif self.state == 'TURN':
            msg.angular.z = self.turn_speed
        # In DONE we keep publishing zeros, so the turtle stays stopped.

        self.publisher_.publish(msg)
        self.elapsed += self.dt


def main(args=None):
    try:
        with rclpy.init(args=args):
            node = SquareDriver()
            rclpy.spin(node)
    except (KeyboardInterrupt, ExternalShutdownException):
        pass


if __name__ == '__main__':
    main()

      Each piece follows the tutorial pattern from section 06. The publisher and timer are created in __init__, all the behavior lives in the timer callback, and main uses the with rclpy.init(...) block.[10] The callback checks for a state change before building the message, so the command sent on each tick always matches the current state.

      Do not expect a perfect square. The timer only checks the clock every 0.1 s, so a turn that should last 1.57 s actually lasts until the next tick after that. Turtlesim also integrates the motion in its own small time steps.[14] These small errors add up from corner to corner, so the last side will not land back on the exact start point. That drift shows the limit of open-loop control, and it is why section 10 adds feedback.

      The square driver state machine needs JavaScript. With it on, you can step through timer ticks or run the trajectory to observe state transitions and open-loop drift.

      09. Building, running, and fixing common errors

      With square_driver.py saved, you are ready to build your package and drive the turtle. Building installs your Python code and entry point into your workspace’s install folder so ros2 run can find it. You will check dependencies with rosdep, build turtle_square with colcon, and run it alongside Turtlesim in separate terminals.

      Because you used --node-name square_driver earlier, the entry point 'square_driver = turtle_square.square_driver:main' is already in setup.py.[7][9] From your workspace root, check dependencies and build just this package:[7][3] 

      cd ~/ros2_ws
rosdep install -i --from-path src --rosdistro lyrical -y
colcon build --packages-select turtle_square

      If you plan to tweak your Python code often, add --symlink-install to the build command. It “saves you from having to rebuild every time you tweak python scripts” (on Windows it needs administrator rights or Developer Mode).[3][5] Even with a symlink install, rebuild after you change setup.py, setup.cfg, or package.xml, because those files control what gets installed.

      Now open a new terminal for each program, and source your overlay in each terminal that runs your package:[3][10] 

      # Terminal 1
source /opt/ros/lyrical/setup.bash
ros2 run turtlesim turtlesim_node

# Terminal 2
source /opt/ros/lyrical/setup.bash
cd ~/ros2_ws
source install/setup.bash
ros2 run turtle_square square_driver

      The turtle should trace four sides and stop. Terminal 2 should log “Finished side 1” through “Finished side 4”. In a third terminal, you can watch it move with ros2 topic echo /turtle1/pose, check connections with ros2 topic info /turtle1/cmd_vel, or open rqt_graph from lesson 4.5. To clear the drawing and put the turtle back in the center, call ros2 service call /reset std_srvs/srv/Empty. If that type is rejected, check it with ros2 service type /reset.[14]

      When something goes wrong, the error message usually points to one of five common causes:

      • Package 'turtle_square' not found: This terminal has not sourced install/setup.bash, or the build failed. Source the overlay in a fresh terminal and check the build output.[3]
      • No executable found: ros2 run looks for the program under lib/<package>. Check that setup.cfg exists, that the console_scripts entry is spelled right, and that you rebuilt after editing setup.py. A community report traces this error to a missing setup.cfg, which installed the program in bin instead of lib/<package>.[10][17]
      • ModuleNotFoundError for turtlesim.msg: The code was written for Jazzy or earlier. Import from turtlesim_msgs.msg instead.[15]
      • The node runs but the turtle does not move: Check the topic name with ros2 topic info /turtle1/cmd_vel. Make sure you publish repeatedly from a timer, not once, because of the one-second timeout.[14]
      • Strange build problems after sourcing: You built in a terminal where the overlay was already sourced. Open a new terminal, source only the underlay, and build again.[3]
      For the curious: more colcon build options

      Three extra colcon flags help as your workspaces grow. --packages-up-to builds a package plus everything it depends on. --event-handlers console_direct+ shows build output live instead of writing it only to log/. Finally, --executor sequential builds one package at a time on low-resource machines such as a Raspberry Pi.[3][5]

      10. Stretch: steering with live pose feedback

      Your open-loop square in section 08 drifted because it only counted seconds. A smarter approach is to watch where the turtle actually is and adjust your commands as it moves. Engineers call this closed-loop control because sensor feedback closes the loop between your commands and the robot’s motion. In this stretch step, you subscribe to /turtle1/pose so the turtle drives the true distance and turns to the true angle.

      Here is how the feedback loop works. Subscribe to /turtle1/pose and store the latest message. In FORWARD, save the start point at the beginning of each side and drive until the straight-line distance from it reaches the side length. In TURN, aim for a target heading 90° past the previous one and turn at a speed proportional to the remaining heading error. All of these fields come straight from the Pose message.[15][10] Like the main example, treat the fragment below as a starting point to test, not finished code. 

      from turtlesim_msgs.msg import Pose   # Lyrical: turtlesim_msgs, not turtlesim

# in __init__:
        self.pose = None
        self.pose_sub = self.create_subscription(
            Pose, '/turtle1/pose', self.pose_callback, 10)

    def pose_callback(self, msg):
        self.pose = msg

# in timer_callback (skip the tick while self.pose is None):
        # FORWARD: distance from the corner where this side started
        dist = math.hypot(self.pose.x - self.start_x, self.pose.y - self.start_y)

        # TURN: heading error wrapped to the range -pi..pi
        error = math.atan2(math.sin(self.target_theta - self.pose.theta),
                           math.cos(self.target_theta - self.pose.theta))
        msg.angular.z = max(-1.0, min(1.0, 2.0 * error))   # proportional, clamped
        # switch back to FORWARD when abs(error) < 0.01

      The atan2(sin, cos) formula keeps the heading error between −π and π, so the turtle always turns the short way even when the target wraps past π. The proportional term slows the turn down as the error shrinks, which is the same idea you will meet again in the control chapter. Remember to add turtlesim_msgs to package.xml (we already did) and rebuild.

      Try it
      1. Create the turtle_square package with ros2 pkg create as in Section 03. Open setup.py and package.xml, and find the entry point, the py.typed line and the dependency tags you asked for.
      2. Add the timer-based square_driver node from Section 08, build with colcon build --packages-select turtle_square, and run it against turtlesim_node in a fresh, sourced terminal. The code is an example to test on your install, so watch the log and the drawing carefully.
      3. Change the timer period from 0.1 to 1.5 seconds and run it again. Explain what you see using Turtlesim's one-second command timeout.
      4. Measure the drift: run ros2 topic echo /turtle1/pose and compare the final x, y and theta with the start pose.
      5. Stretch goal: build the pose-feedback version from Section 10 and compare how closely its square closes with the open-loop version.
