3.4 Lab: Your First Pull Request

Gerald Lê

01. Choosing a first contribution to robOSStics

You now know what open source is and how contributions work (3.2). In this lab you make one, to this site.

Before building standalone packages, this lab guides you through opening your first pull request. robOSStics is an open-source learning platform for robotics newcomers hosted at github.com/g34rmeister/g34rmeister.github.io.[1] It is organized to provide a friendly, safe place to make your first pull request, where every improvement helps whether you fix a single typo or suggest a new lesson.

You do not need to be an expert in robotics to contribute.[1] The project highlights three easy ways to make a first contribution:

  • Fix a typo: If you spot a spelling mistake, grammatical error, or confusing sentence, you can submit an edit. Clear wording helps every learner.
  • Suggest or fix a source: Every factual claim on this site must trace back to a verified source. If you see a missing citation, an outdated link, or a better manual, you can suggest it.
  • Report a broken link: Documentation links move or disappear over time. If a reference link leads to a 404 error, reporting it helps keep lessons working.

If you want to take on a larger contribution, such as proposing a lesson idea for a robotics topic or hands-on lab, open an issue first.[1] Maintainers discuss the outline, scope, and sources together with you before you write code or text.

02. Lab Path A: Editing directly in your browser

You do not need to install Git or Python to fix typos or wording.[1] You can complete the entire edit directly in your web browser.

To submit an edit using your browser, follow the seven steps documented in the repository contributing guide:[1]

  1. Step 1: Visit https://github.com/g34rmeister/g34rmeister.github.io.
  2. Step 2: Find the file you want to edit. Lesson pages are in the root directory and look like robotics-1-1.html.
  3. Step 3: Click the pencil icon near the top right of the file preview to open the editor.
  4. Step 4: Edit the text in your browser.
  5. Step 5: Scroll down to the Propose changes section at the bottom of the page.
  6. Step 6: Write a short title and a one-sentence summary explaining what you changed.
  7. Step 7: Click Propose changes, then click Create pull request.

Maintainers will review your pull request, answer questions, and help you merge it.[1]

This browser-based flow allows anyone encountering a typo or broken URL while reading a lesson to submit a fix immediately without configuring local development tools.

03. Lab Path B: Working locally with Git and running checks

If you want to make larger changes or test files on your machine, you can work locally.[1] This workflow gives you access to the project scripts and verification checks before you submit your pull request.

To work locally, follow these steps:

  1. Step 1: Clone the repository. Download a local copy of the repository and switch into its directory: 
    git clone https://github.com/g34rmeister/g34rmeister.github.io.git
cd g34rmeister.github.io
  2. Step 2: Open and inspect your changes. Open the project in your text editor. Because this is a static site with no build step, you can open any HTML file directly in your web browser to see your changes.
  3. Step 3: Renumber references. If you add or edit citations in a lesson file, renumber the references in order of appearance: 
    python3 scripts/renumber_refs.py robotics-X-Y.html
  4. Step 4: Regenerate synced files. If you change a lesson or update sources, regenerate synced files: 
    python3 scripts/sources.py sync && python3 scripts/build_index.py && python3 scripts/site_sync.py
  5. Step 5: Run the four checks. Run the four checks from CLAUDE.md to ensure everything passes: 
    python3 scripts/site_sync.py --check && python3 scripts/check_site.py && python3 scripts/sources.py check && python3 scripts/build_index.py --check

04. The source rule and repository constraints

Accuracy is central to this project.[1] Every factual claim must trace to a checked source.

The repository uses two files to manage citation verification:[1]

  • docs/sources.json: Stores every cited source along with its verification status and per-lesson claim checks.
  • scripts/sources.py: Inspects and updates citation records.

When pull requests run, python3 scripts/sources.py check ensures that no cited reference is unverified.[1] If you add a new citation or claim, it must be recorded in docs/sources.json.

If you are new to the source checking script, do not worry.[1] You can open an issue or pull request with your suggested source URL. Maintainers will check the claims, run the script, and update docs/sources.json for you.

To keep the site reliable for readers and search engines, contributors must avoid two actions:[1]

  • Do not renumber lessons: URLs must stay stable so existing links do not break. Append new lessons to the end of a chapter instead.
  • Do not hand-edit generated regions: Several files and page sections are built automatically by python3 scripts/site_sync.py. Never edit these parts by hand: sitemap.xml, lesson rows on the course hub (robotics.html), the chapter list, previous and next lesson navigation links, navigation bars, the page set in site-hygiene.yml, and the source-check line in each lesson. Instead, update the underlying data or templates and run python3 scripts/site_sync.py to regenerate them.

05. Opening the pull request with the repository template

A pull request is a request to merge changes from your edit branch into the repository.

You do not need to wait until your work is complete before asking for feedback. Pull requests do not have to represent finished work and can be opened early as a draft or marked WIP to get early feedback from reviewers.[2]

When opening a pull request, robOSStics supplies a standard pull request template. Using the template ensures that you provide the necessary context for maintainers. The template consists of two parts:

  • Summary: A concise statement detailing what changed and why, alongside a list of which lesson or page files were touched.
  • Checklist: A list of confirmation items verifying that:
    • Every factual claim traces to a source in docs/sources.json (or none was added).
    • If citations were edited, references were renumbered with python3 scripts/renumber_refs.py <file>.
    • If lesson or source data changed, sync scripts were run (python3 scripts/sources.py sync && python3 scripts/build_index.py && python3 scripts/site_sync.py).
    • The four checks from CLAUDE.md were run and passed.
    • For larger changes, an entry was appended to CHANGELOG.agents.md.

Completing the template enables reviewers to understand your intentions quickly and inspect test results before approving the change.

06. Responding to review and getting help

Once your pull request is open, communication takes place on GitHub. Keep the conversation in the pull request, in public, as 3.2 explained.

If you get stuck, run into an error, or want feedback before starting, please open an issue: https://github.com/g34rmeister/g34rmeister.github.io/issues.[1] You do not need to select issue labels. Maintainers will label it, answer questions, and help you with your contribution.

When a reviewer asks a question or suggests a wording change, reply directly in the pull request discussion thread. If edits are requested, update your branch. Once discussions conclude and automated checks succeed, a maintainer merges your contribution into the repository.
