3.4 Running Your First Example (Turtlesim)

Gerald Lê

01. Hands-on robotics with Turtlesim

Having configured our ROS 2 installation in lesson 3.3, it is time to transition from theory to practice. In robotics education, jumping straight into physical multi-thousand-dollar hardware carries risks: improper motor commands can tip over rovers or strip gearbox teeth.

To give developers a lightweight, safe sandbox, the ROS core distribution includes Turtlesim.[1] Turtlesim is a 2D animated simulation package originally inspired by Seymour Papert's educational Logo turtle graphics. Behind its colorful, friendly appearance lies a fully functional ROS 2 computational graph.

Turtlesim instantiates nodes, publishes telemetry topics, listens to Cartesian velocity commands, advertises service servers, and executes long-running actions. Every command-line tool, message format, and Python script you master in Turtlesim transfers directly to multi-ton factory arms and industrial mobile robots.

02. Launching and teleoperating your first robot

Turtlesim is included in the ros-lyrical-desktop package. If you installed a base headless image, install it manually: 

sudo apt install -y ros-lyrical-turtlesim

Open a fresh terminal (with your ROS 2 environment sourced) and launch the simulator executable using the ros2 run command:[1] 

ros2 run turtlesim turtlesim_node

A graphical window appears displaying a blue ocean background and an animated turtle centered at Cartesian coordinates (x = 5.54, y = 5.54) within an 11.08 by 11.08 meter square arena.

Now, open a second terminal to start the keyboard teleoperation node:[1] 

ros2 run turtlesim turtle_teleop_key

With the teleop terminal active, press the keyboard arrow keys. The Up and Down arrows command forward and reverse linear velocity; the Left and Right arrows command counterclockwise and clockwise angular rotation. As the turtle moves across the screen, it lowers an electronic pen, drawing colored lines along its trajectory.

03. Topic introspection and the Twist message

What is happening behind the graphical window? Open a third terminal to introspect the active ROS computational graph using command-line diagnostic tools.[1][2]

First, query the active nodes: 

ros2 node list

The terminal reports two running nodes: /turtlesim (the simulator) and /teleop_turtle (the keyboard controller). Next, list all active communication topics: 

ros2 topic list

You will see topics such as /turtle1/cmd_vel, /turtle1/color_sensor, and /turtle1/pose. In Turtlesim, which topic carries the velocity commands from the teleop node? The answer is /turtle1/cmd_vel.[1] The teleop node publishes on /turtle1/cmd_vel, and the simulator subscribes to it to move the simulated turtle.

To inspect the data streaming across that topic in real time, run:[2] 

ros2 topic echo /turtle1/cmd_vel

When you press the Up arrow in the teleop terminal, the echo window prints: 

linear:
  x: 2.0
  y: 0.0
  z: 0.0
angular:
  x: 0.0
  y: 0.0
  z: 0.0
---

To find out what message type this topic carries, query its interface:[2] 

ros2 topic type /turtle1/cmd_vel

The output is geometry_msgs/msg/Twist.[3] A Twist is a fundamental geometric primitive in robotics: it expresses spatial velocity decomposed into three linear coordinates (x, y, z in meters per second) and three rotational coordinates (x, y, z in radians per second). Because Turtlesim is a planar differential-drive robot, it only responds to linear velocity along the forward X axis (linear.x) and angular yaw velocity around the vertical Z axis (angular.z).

You can even command the robot directly from the command line without using the teleop node at all: 

ros2 topic pub --once /turtle1/cmd_vel geometry_msgs/msg/Twist "{linear: {x: 2.0, y: 0.0, z: 0.0}, angular: {x: 0.0, y: 0.0, z: 1.8}}"

The turtle immediately traces a smooth circle across the arena.

04. Calling services from the CLI: spawning robots

While topics stream continuous velocity and pose data, discrete commands are managed via services.[4] Query Turtlesim's active services: 

ros2 service list

You will see services including /clear, /reset, /spawn, /kill, and /turtle1/set_pen. Let us call the /spawn service to introduce a second robot into our simulation arena:[4] 

ros2 service call /spawn turtlesim/srv/Spawn "{x: 2.0, y: 2.0, theta: 0.0, name: 'turtle2'}"

The service client sends the request, the simulator instantiates a second turtle at coordinates (2, 2), and the terminal outputs: 

response:
  name: "turtle2"

If you list topics again with ros2 topic list, you will see an entirely new set of isolated channels: /turtle2/cmd_vel and /turtle2/pose.

05. Dynamic remapping on the command line

If you return to your teleop terminal and press arrow keys, only turtle1 moves. The compiled binary of turtle_teleop_key has the topic string /turtle1/cmd_vel hardcoded into its source code. How can we drive our new turtle2 without modifying or recompiling the software?

In ROS 2, any topic, service, or node name can be redirected at process startup using remapping arguments (--ros-args --remap).[5] Open a fourth terminal and launch a second teleoperation node remapped to turtle2:[5] 

ros2 run turtlesim turtle_teleop_key --ros-args --remap turtle1/cmd_vel:=turtle2/cmd_vel

Now you have two independent teleop terminals: one driving turtle1 and the other driving turtle2. Dynamic remapping is the primary mechanism industrial engineers use to reuse standard sensor drivers and navigation stacks across multi-robot factory fleets.

06. ROS 2 workspace architecture

Driving demo nodes from the terminal is educational, but true robotics engineering requires writing custom software. In ROS 2, software is organized inside a workspace.[6]

A ROS 2 workspace is a directory following a strict four-folder structure:[6]

  • src/ (Source Directory): The only directory where human developers write code. Every custom package, node script, and Git repository is placed inside src/.
  • build/ (Intermediate Artifacts): Created automatically by the build tool. Stores intermediate object files, compiler caches, and CMake build logs.
  • install/ (Deployment Target): Created automatically by the build tool. Stores final compiled binaries, Python modules, and the critical local environment script install/setup.bash.
  • log/ (Diagnostic Records): Created automatically by the build tool. Stores detailed compiler output and error traces.

Create your first workspace in your home directory: 

mkdir -p ~/ros2_ws/src
cd ~/ros2_ws/src

07. Python package layout: package.xml and setup.py

Rather than creating loose scripts, ROS code must be encapsulated inside a formal package.[6] Use the ros2 pkg create command to generate a new Python package named my_robot_controller:[6] 

ros2 pkg create --build-type ament_python my_robot_controller --dependencies rclpy geometry_msgs turtlesim

This command creates a standardized folder hierarchy inside ~/ros2_ws/src/my_robot_controller/:

  • package.xml: The package manifest file. It records the package name, software license, maintainer email, and declares build and runtime dependencies (rclpy, geometry_msgs, turtlesim).
  • setup.py: The Python setuptools deployment configuration. It defines where libraries are installed and contains the entry_points dictionary that binds terminal commands to Python functions.
  • setup.cfg: Tells setuptools to install executable scripts into the package lib directory.
  • my_robot_controller/: The Python module directory containing an empty __init__.py. This is where your custom Python node scripts reside.

08. Writing a custom rclpy velocity publisher

Let us write a Python node that autonomously commands the turtle to drive in a continuous circle by publishing velocity commands at 2 Hz.[7]

Create a new file named ~/ros2_ws/src/my_robot_controller/my_robot_controller/draw_circle.py:[7] 

#!/usr/bin/env python3
import rclpy
from rclpy.node import Node
from geometry_msgs.msg import Twist

class DrawCircleNode(Node):
    def __init__(self):
        # 1. Initialize the parent Node class with the node name
        super().__init__('draw_circle_node')

        # 2. Create a publisher on topic /turtle1/cmd_vel with queue depth 10
        self.cmd_vel_pub_ = self.create_publisher(Twist, '/turtle1/cmd_vel', 10)

        # 3. Create a timer callback running at 2 Hz (every 0.5 seconds)
        self.timer_ = self.create_timer(0.5, self.send_velocity_command)
        self.get_logger().info('Draw Circle Node has started successfully!')

    def send_velocity_command(self):
        msg = Twist()
        msg.linear.x = 2.0   # Forward speed: 2.0 meters per second
        msg.angular.z = 1.0  # Yaw rate: 1.0 radian per second
        self.cmd_vel_pub_.publish(msg)

def main(args=None):
    rclpy.init(args=args)            # Initialize the ROS 2 communications context
    node = DrawCircleNode()          # Instantiate our custom node class
    rclpy.spin(node)                 # Block thread and process incoming callbacks
    node.destroy_node()              # Clean up node memory
    rclpy.shutdown()                 # Shut down ROS 2 context

if __name__ == '__main__':
    main()

Notice the object-oriented structure: our class inherits from rclpy.node.Node. Inside the constructor, create_publisher instantiates a publisher for Twist messages. create_timer(0.5, callback) triggers our motion function every 500 milliseconds. Finally, rclpy.spin(node) blocks the main thread, entering an event loop that services timers and messages until the process is terminated with Ctrl+C.[7]

09. Writing a custom rclpy pose subscriber

Next, let us write a subscriber node that listens to the turtle's real-time position updates and logs them to the console.[7]

Create a new file named ~/ros2_ws/src/my_robot_controller/my_robot_controller/pose_subscriber.py: 

#!/usr/bin/env python3
import rclpy
from rclpy.node import Node
from turtlesim.msg import Pose

class PoseSubscriberNode(Node):
    def __init__(self):
        super().__init__('pose_subscriber_node')

        # Create a subscription to /turtle1/pose
        self.pose_sub_ = self.create_subscription(
            Pose,
            '/turtle1/pose',
            self.pose_callback,
            10
        )
        self.get_logger().info('Pose Subscriber Node has started!')

    def pose_callback(self, msg: Pose):
        self.get_logger().info(
            f'Coordinates: x={msg.x:.2f}, y={msg.y:.2f}, heading={msg.theta:.2f} rad'
        )

def main(args=None):
    rclpy.init(args=args)
    node = PoseSubscriberNode()
    rclpy.spin(node)
    node.destroy_node()
    rclpy.shutdown()

if __name__ == '__main__':
    main()

In this subscriber node, create_subscription takes four arguments: the message type (Pose), the topic name (/turtle1/pose), the callback function (self.pose_callback), and the QoS history depth (10). Whenever Turtlesim publishes a new pose sample, the middleware automatically invokes pose_callback, passing the populated msg object.

10. Compiling with colcon and running custom nodes

Before our Python scripts can be executed using ros2 run, they must be registered in setup.py.[6] Open ~/ros2_ws/src/my_robot_controller/setup.py in a text editor and locate the entry_points dictionary: 

entry_points={
    'console_scripts': [
        'draw_circle = my_robot_controller.draw_circle:main',
        'pose_subscriber = my_robot_controller.pose_subscriber:main',
    ],
},

Now, return to the root of your workspace and compile with colcon:[8] 

cd ~/ros2_ws
colcon build --symlink-install
Developer Tip: Symlink Install

The --symlink-install flag creates symbolic links to your Python source scripts instead of copying them into the install/ folder. This allows you to edit your Python node code and test changes immediately without having to run colcon build every time.[8]

Finally, source your newly created workspace underlay: 

source install/setup.bash

With Turtlesim running in another window, launch your custom nodes: 

# Terminal 1: Run your autonomous circle driver
ros2 run my_robot_controller draw_circle

# Terminal 2: Run your real-time pose logger
ros2 run my_robot_controller pose_subscriber

The turtle immediately begins drawing perfect circles on screen, while your subscriber node streams real-time Cartesian coordinates to the console.

11. Transferring skills to physical robots

While steering a cartoon turtle across a screen is a classic beginner exercise, every software technique you practiced here is identical to real-world industrial robotics:

  • A physical Clearpath Husky mobile robot uses the exact same geometry_msgs/msg/Twist on topic /cmd_vel to drive its high-torque electric wheels through outdoor terrain.
  • An industrial AMR in an automotive warehouse publishes its wheel-encoder dead reckoning on a pose topic structured identically to Turtlesim's pose feed.
  • The rclpy.node.Node object-oriented architecture, timer callbacks, and publisher/subscriber methods are the universal syntax of modern robotics.

In lesson 3.5, we examine the advanced developer tools of the ROS ecosystem: visualizing sensor transforms in RViz2, diagnosing node communication topologies with rqt_graph, and recording real-time mission telemetry with ros2 bag.
