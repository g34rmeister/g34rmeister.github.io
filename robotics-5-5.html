5.5 AI in Robotics: Uses and Limits

Gerald Lê

01. Why this lesson exists

Artificial intelligence (AI) now appears in robot cameras, maintenance dashboards and programming tools, and in research models that try to control a robot directly from images and words. The marketing around these products often blurs one important line: helping people build and run a robot cell is different from deciding, in real time, whether the robot is safe to move. This lesson draws that line clearly.

A useful picture to keep in mind is that, in industry today, AI mostly sits around the robot. It helps the robot see parts, helps engineers predict when a gearbox will fail, and helps programmers write code faster. The safety-rated controller and its safety configuration (the speed limits, safety planes, stop functions and safeguard inputs you met in 5.4) stay conventional and deterministic. They do the same thing every time for the same input, and they have been validated against a standard.

Product claims change quickly in this field, so every product statement below carries a date. The figures quoted for commercial products are what the vendors say; the research for this lesson found no independent benchmarks for them.

02. Learned vision: bin picking, pose estimation and inspection

The most mature use of AI in industrial robotics is perception: using models trained on data to find parts and judge their position and quality.

On 21 October 2024, Universal Robots (UR) launched the AI Accelerator, a hardware and software kit for its PolyScope X software. It is built on NVIDIA Isaac libraries running on an NVIDIA Jetson AGX Orin computer, paired with an Orbbec Gemini 335Lg 3D camera. UR listed its functions as pose estimation, tracking, object detection, path planning, image classification, quality inspection and state detection.[1]

At NVIDIA's GTC conference in March 2025, UR's parent company Teradyne and its partners showed version 1.1 of the AI Accelerator, which integrates NVIDIA Isaac Manipulator components. In one partner demo (from Groundlight), the system "trains a model to detect a workpiece and generate a robot program for picking."[2] At GTC Paris in June 2025, a UR15 arm running PolyScope X picked objects whose positions it was not given in advance, to show how applications built with the AI Accelerator cope with variation; UR reportedly named machine tending and bin picking as target uses.[3]

Notice what the AI does in these systems. It answers the question "where is the part, and is it a good part?" and hands the answer to the robot program as a target pose. The robot still moves under its normal controller, with its normal safety limits. If the vision model makes a mistake, the result is a missed pick or a wrong target. That is why the target poses a vision system produces still need sensible limits in the program, a topic you will meet again in the checklist.

03. Predictive maintenance

The second established use is predictive maintenance: watching data from the robot, such as motor currents and error logs, to spot wear before it causes a breakdown.

FANUC's Zero Down Time (ZDT) service "continuously monitors robot condition and performance data to identify potential issues before they impact production," according to FANUC America's product page (launch date not found for this lesson).[4] In March 2025, Siemens extended its Industrial Copilot to maintenance through Senseye Predictive Maintenance, and claimed that pilot users saved "on average 25% reactive maintenance time."[5] That 25% figure is a vendor claim, not an independent study.

Predictive maintenance has a low safety risk compared with the other uses in this lesson, because it advises people rather than moving the robot. Either way, a technician still follows lockout/tagout (5.4) before working on the arm.

04. LLM programming assistants ("copilots")

A large language model (LLM) is a model trained on very large amounts of text that predicts likely next words, which lets it answer questions and write code. Since 2025, several automation vendors have built LLM assistants into their programming tools. It is worth being precise about what each one does, because "AI writes your robot program" and "AI suggests the next line" are very different promises.

  • ABB RobotStudio (September 2025): ABB added a generative-AI assistant to RobotStudio, its offline programming and simulation software. It is LLM-based, draws on ABB's manuals and documentation, gives real-time coding suggestions and syntax help, and is aimed at less experienced users.[6][7] Coverage describes it as a guidance and suggestion assistant; none of the sources consulted for this lesson say that it writes whole programs on its own.[7]
  • Siemens Industrial Copilot (March 2025 coverage): Generates PLC code in SCL (Structured Control Language) from natural-language requests. Siemens claims it speeds up SCL code generation by "an estimated 60%."[5] This is code for a programmable logic controller, not robot motion code.
  • Rockwell FactoryTalk Design Studio Copilot (date not captured): Also generates PLC code from natural language, according to an industry overview by A3, the US automation trade association.[8]

As of October 2026, the research for this lesson did not find a Universal Robots or FANUC LLM assistant specifically for writing robot programs, and KUKA and Yaskawa announcements were not searched. The examples in this lesson's exercise therefore use a general-purpose chatbot as the "AI author," not a vendor product.

05. Foundation models that output robot actions

A foundation model is a large model trained on broad data that can be adapted to many tasks. In robotics, the most discussed kind is the vision-language-action (VLA) model: it takes camera images and a written instruction ("put the red block in the bowl") and outputs robot actions directly. These models are exciting, but they were all released between 2023 and 2026 as research or early-access platforms, not as certified industrial controllers.

The developers of these models are open about their limits, and those limits matter for a factory. OpenVLA's documentation says that "out-of-the-box, it only works well on domains from the training dataset," that adapting it to a new setup typically needs fine-tuning on about 100 demonstrations, and that it "struggles with high-frequency data."[12] NVIDIA warns that GR00T users "may observe 5-6% variance between runs" because of random data augmentation during training.[13] In other words, two training runs on the same data can give noticeably different robots. That is the opposite of the repeatable, validated behaviour a safety function needs.

Even the most advanced of these systems does not use the learned model as its safety layer. Google DeepMind describes Gemini Robotics 1.5 as "thinking about safety before acting," but also triggering "low-level safety sub-systems (e.g. for collision avoidance) on-board the robot," and it built a benchmark called ASIMOV to test semantic safety (whether the model understands that an action is unsafe).[16] The learned model reasons about the task; separate conventional systems keep the robot from hitting things.

06. What the evidence says about AI-written code

How often is AI-written code wrong in ways you will not notice? The best peer-reviewed evidence comes from general software, not robotics, but it is clear.

At USENIX Security 2025, Spracklen and colleagues tested 16 code-writing LLMs on 576,000 generated code samples in Python and JavaScript. The models regularly told programmers to install software packages that do not exist. The average rate of these hallucinated packages was at least 5.2% for commercial models and 21.7% for open-source models, and the study found 205,474 unique invented package names.[17][18] The authors also reported that mitigation techniques reduced the rate, but did not remove it.[17] A 2026 replication on newer models, not yet peer reviewed, reported rates between 4.62% and 6.10%; treat it as provisional.[19] A hallucination, in this sense, is output that looks confident and plausible but is not grounded in fact.

Robotics research shows similar failure types:

  • ChatGPT for Robotics (Microsoft, February 2023): Vemprala, Bonatti, Bucker and Kapoor explored prompting ChatGPT to control robots, including a drone in the AirSim simulator. Their public repository of prompts notes that submitted examples are "not necessarily 'correct' or 'optimal'."[20]
  • Code as Policies (Google Research): LLMs turned spoken-style commands into robot policy code that calls perception functions and sets parameters for control primitives, demonstrated on several real robots.[21] The code only worked because it called a hand-written library of perception and control functions that the researchers provided. The LLM was composing trusted building blocks, not inventing motion control.
  • RoboEval / CodeBotler (2023): A benchmark for LLM-written service-robot programs. Its failure categories include ordinary Python errors, attempts to execute infeasible robot actions, and programs that run but do not complete the task.[22]
  • "Forgetful" LLMs (2023): A study of ChatGPT, Bard and LLaMA-2 for robot programming found execution errors caused by the models "forgetting" key information given in the prompt.[23]
  • RoboRepair (2024): Its authors summarise the problem directly: "LLM-generated programs may be faulty, either due to ambiguity in instructions, misinterpretation of the desired task, or missing information about the world state."[24]

One gap is important to state honestly. As of October 2026, the research for this lesson found no published study of LLM error rates for industrial robot languages such as URScript, RAPID, KRL or KAREL. Until such a study exists, the safe assumption is that any AI-written robot code is a draft.

07. How AI mistakes look in robot code

In ordinary software, an invented package usually causes a crash or an install error, which at least tells you something is wrong. Robot code is more dangerous, because many mistakes are perfectly valid syntax. The program runs, and the arm goes somewhere you did not intend. Three kinds of error deserve special attention.

Units. URScript uses SI units. The script manual's entry for movel(pose, a=1.2, v=0.25, t=0, r=0) gives acceleration in m/s², speed in m/s, time in seconds and blend radius in metres. Its example pose p[0.2,0.3,0.5,0,0,3.14] means 200, 300 and 500 mm with a 180° rotation, and "v = 0.25 -> velocity of 250 mm/s."[25] UR's support articles say the same thing plainly: X, Y and Z values are in metres, and Rx, Ry and Rz values are in radians.[26] Joint positions passed to movej are also in radians, which is why URScript provides d2r() to convert degrees. Confusion here is real, not hypothetical: one thread on the UR forum points out that the manual's description of the pose type does not state units clearly, and that a third-party wrapper (RoboDK) assumed millimetres.[27] An LLM trained on RAPID examples (which use millimetres, as you saw in 2.3) can easily carry that habit into URScript.

Invented functions. The robotics version of a hallucinated package is a function that sounds right but does not exist, such as set_gripper() or move_linear(). In URScript, a gripper is normally driven through digital outputs or through a function added by the gripper maker's URCap, so the correct call depends on your hardware. The only reliable check is the official script manual for your exact software version.

Frames. A pose only means something relative to a frame: the robot base, the tool, or a feature frame on the fixture. URScript's pose_add adds an offset in the base frame, while pose_trans applies an offset expressed in the frame of the first pose, so pose_trans(pick, p[0, 0, -0.05, 0, 0, 0]) means "50 mm back along the tool's own Z axis." Mixing them up is a classic error. When the tool points straight down, its Z axis points the opposite way to the base's Z axis, so an offset meant to back the tool away from a part can instead drive it 50 mm into the part. A wrong tool center point (TCP) setting causes the same kind of silent offset.

The exact function signatures in this lesson (movej, pose_trans, pose_add, d2r, set_standard_digital_out) should be checked against the script manual for the PolyScope version you use. The code examples are illustrations to test in URSim first, not programs to run on a real arm.

08. The safety layer stays deterministic

Robot safety standards were tightened just as AI tools spread. ISO 10218-1:2025 and ISO 10218-2:2025 are the first major revision of the industrial robot safety standard since 2011, and they replace the 2011 editions. The revision makes functional-safety requirements "more explicit rather than implied," introduces Class I and Class II robots with different functional-safety requirements, moves away from a blanket Performance Level d requirement towards levels chosen by risk assessment, and adds cybersecurity requirements and collaborative-application content that used to sit in ISO/TS 15066.[28][29][30] None of the sources consulted for this lesson says that ISO 10218:2025 addresses machine-learning components specifically.

In practice, the robot controller enforces protections that no external program can wish away. UR's ROS 2 driver documentation, for example, lists support for "pause at emergency stop, safeguard stop, automatic speed scaling" and manual speed scaling from the teach pendant.[31] When a safeguard stop happens, the controller stops the arm whatever the program wanted.

This gives a simple rule for the classroom and the workplace. An LLM can help write the application program. It must never write, alter or bypass the safety configuration: the safety planes, speed and force limits, emergency stop and safeguard I/O settings. Those settings are password protected on the teach pendant for a reason, and changing them means the cell's risk assessment has to be revisited. If an AI tool suggests muting a safeguard or disabling a protective stop "to avoid interruptions," the correct response is to refuse and to treat everything else it wrote with extra suspicion.

09. Regulation (as of October 2026)

The legal picture in the European Union is still settling, so read this section as a snapshot as of October 2026, based on law-firm and expert summaries rather than on the legal texts themselves. Check the Official Journal and EUR-Lex before relying on any detail.

The Machinery Regulation (EU) 2023/1230 (introduced in 5.1) lists, in its Annex I Part A, the products that need mandatory third-party conformity assessment—the formal verification process proving that a product complies with statutory safety requirements. That list includes "safety components with fully or partially self-evolving behaviour using machine learning approaches ensuring safety functions," and machinery that embeds such systems.[32][33] Most of the regulation applies from January 2027; most summaries give 20 January 2027, while one secondary source gives 14 January 2027, so confirm the date on EUR-Lex.[32][33] "Self-evolving behaviour" has no formal definition. The Danish Technological Institute works with a practical one: machine-learning software that operates on generalisations it learned from data, during training and during operation.[34] In short, if a learned model performs a safety function, an independent body has to examine it.

The EU AI Act treats an AI system as high-risk when it is a safety component of a product (or is itself a product) covered by EU product legislation that requires third-party conformity assessment.[35] In 2026 the EU changed how that applies to machinery. According to law-firm summaries, a provisional agreement on the "Digital Omnibus on AI" was reached on 7 May 2026 and voted by the European Parliament on 16 June 2026.[36] It was published in the Official Journal on 24 July 2026 as Regulation (EU) 2026/1744 (firms write the number in different forms, so check the Official Journal)[37] and entered into force on 27 July 2026.[38] It moves the Machinery Regulation from Section A to Section B of the AI Act's Annex I, so AI-enabled machinery is regulated through the Machinery Regulation, whose essential requirements the Commission is to amend by delegated acts. The high-risk obligations for products in Annex I are delayed to 2 August 2028, and those for Annex III uses to 2 December 2027.[38][37]

The direction is clear even if the details are still moving. Regulators expect learned components that perform safety functions to be independently assessed, and they keep that responsibility with the people who build and integrate the machine.

10. Accountability, and this course

No source found for this lesson makes an AI vendor responsible for a user's robot program. The structure of conformity assessment points the other way: the manufacturer and the integrator who signs the risk assessment answer for the cell, and the programmer who deploys code answers for that code. This is a reading of how the system is set up, not a legal ruling, but it is the safe way to work. It also connects to the "moral crumple zone" from 5.3: if AI writes the code and a human only presses Play, the human can end up absorbing the blame for a system they did not really control. The cure is genuine review, not a rubber stamp.

The same rule applies to what you are reading. This course was itself drafted with AI help: lessons, including this one, were researched and drafted with an AI assistant, then checked against their sources by a person. The page How this course was made explains which tools were used and how references were verified. You should read these lessons the way you will read AI-written robot code: follow the citations, notice where a source is marked as unverified, and check anything that would matter if it were wrong. If this course later offers an AI tutor, check its answers in the same way.

A practical habit follows from this: record provenance. In a comment or a change log, note which parts of a program were AI-written, which prompt or tool produced them, and who reviewed and tested them.

Try it

A chatbot was asked to "write a URScript program that picks a part and lifts it." Below is its answer, with errors seeded on purpose. Do not run it. Find every problem by reading, write down the fix, and only then test your corrected version in URSim. 

def pick_part():
  # AI draft: pick a part from the fixture and lift it
  home = [0, -90, 90, -90, -90, 0]          # joint angles
  pick = p[200, 300, 150, 0, 3.14, 0]       # pick pose
  movej(home, a=1.4, v=1.05)

  # approach 50 mm above the part, along the tool axis
  approach = pose_add(pick, p[0, 0, -0.05, 0, 0, 0])
  movel(approach, a=1.2, v=2.0)
  move_linear(pick, speed=0.1)
  set_gripper(1)
  movel(approach, a=1.2, v=0.25)
  # disable protective stop here to avoid interruptions
end

Then review your corrected program against this nine-point checklist:

  1. Simulate first. Run it in URSim or an offline tool before the real arm.
  2. Check every function name against the official script manual for your software version.
  3. Units: poses in metres and radians, speed in m/s, acceleration in m/s², and d2r() around any degree values.
  4. Frames: base, tool or feature frame? Is pose_trans used where the offset is along the tool, and is the TCP set correctly?
  5. First real run at reduced speed (speed slider low), hand on the emergency stop, cell clear of people.
  6. Never touch the safety configuration: no code that changes safety limits, mutes safeguard inputs or disables protective stops.
  7. Reachability and singularities: every target is inside the workspace, and approach and retreat poses exist.
  8. I/O: the correct outputs, in the correct order (for example, the gripper closes and confirms before the lift).
  9. Record provenance: note which parts were AI-written and who reviewed them.

Answer key (read after you try): (1) home is in degrees, so the controller would read -90 as -90 radians (more than 14 full turns); use d2r() on each value, for example d2r(-90). (2) pick is in millimetres; p[0.200, 0.300, 0.150, 0, 3.14, 0] is the intended pose, while the draft asks for a point 200 m away. (3) The offset should follow the tool, so use pose_trans(pick, p[0, 0, -0.05, 0, 0, 0]), not pose_add. With the tool pointing down, the draft's base-frame offset puts the “approach” 50 mm below the pick pose, inside the part. (4) v=2.0 is 2 m/s, far too fast for an approach; use a low speed such as 0.25 m/s or less. (5) move_linear and set_gripper do not exist; use movel(pick, a=1.2, v=0.1) and the digital output or URCap function your gripper actually uses, such as set_standard_digital_out(0, True), then wait for the grip before lifting. (6) The last comment proposes a safety bypass. Delete it, and never try to do this from a program.
