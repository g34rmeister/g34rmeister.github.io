      4.10 Lab: From a Failing Test to a Bug Report

      Gerald Lê
      Chapter 4, lesson 10 of 10 ← Previous: 4.9 ROS-Industrial and Vendor Drivers Next: Chapter 5: Ethics →

      01. Why this lab

      In lesson 3.4 you made your first pull request to fix a documentation typo. In lesson 4.6 you created a ROS 2 package from scratch, declared dependencies, and ran a node. This lab bridges the gap between those two milestones. In open-source robotics projects, you often download another developer's package and run automated checks. What should you do when a test fails?

      A newcomer might decide that the code is broken beyond repair, or give up. Experienced contributors do something else: they run the checks, read what the checks report, fix the mistake and share what they found. In this lab you run the tests of a small robot arm package, read a test failure, trace it to a wrong trigonometric formula, confirm a one-line fix, and write a bug report that a maintainer can act on.

      02. What you need

      To run this lab you need Python 3, a virtual environment, and colcon installed with pip. A virtual environment is a folder that keeps one project’s Python packages separate from the rest of the system. The colcon documentation gives the pip command used below and says it assumes a virtual environment with Python 3.5 or higher.[1]

      This lab requires no ROS 2 installation on your computer. The package is written in standard Python, and colcon is a general build tool that builds and tests pure Python packages without any robotics libraries present. If you later work on a computer with a full ROS 2 installation, as introduced in lesson 4.3, the exact same colcon workflow and commands apply. The lab transcript below was produced on an Ubuntu 26.04 machine running Python 3.14 with colcon-core 0.21.3 installed from pip.

      Set up the environment and an empty workspace with these commands. They are the ones used to produce the transcript in this lesson: 

      $ python3 -m venv venv
$ . venv/bin/activate
$ pip install -U colcon-common-extensions pytest
$ mkdir -p ws/src

      After you have created the package files from Section 03, change into ws and run every colcon command from there.

      03. The package

      The practice package for this lab is called two_link. It computes the forward kinematics of the planar two-link arm from lesson 1.4: given the two link lengths and the two joint angles, it returns where the tip of the arm is. Create these four files inside ws/src/two_link. The file two_link/__init__.py is empty. It only tells Python that the folder is a package. 

      ws/src/two_link/
├── setup.py
├── tests/
│   └── test_kinematics.py
└── two_link/
    ├── __init__.py
    └── kinematics.py

      The ROS 2 testing tutorial says that test code goes in a folder named tests in the root of the package.[2] Any file with tests that should run must be named test_FOO.py, where FOO can be anything.[2] The file setup.py must also declare a test dependency on pytest inside extras_require.[2]

      Here is the complete content of setup.py. It configures package metadata and specifies that pytest is required to run tests: 

      from setuptools import find_packages, setup

setup(
    name='two_link',
    version='0.0.1',
    packages=find_packages(exclude=['tests']),
    install_requires=['setuptools'],
    extras_require={
        'test': ['pytest'],
    },
)

      Here is two_link/kinematics.py. It defines the forward() function, which takes link lengths and joint angles in degrees, converts the angles to radians, and computes the coordinates of the tool tip: 

      import math


def forward(l1, l2, theta1_deg, theta2_deg):
    """Return (x, y) of the tip of a planar two-link arm. Angles in degrees."""
    t1 = math.radians(theta1_deg)
    t2 = math.radians(theta2_deg)
    x = l1 * math.cos(t1) + l2 * math.cos(t1 + t2)
    y = l1 * math.sin(t1) + l2 * math.sin(t2)
    return x, y

      Here is tests/test_kinematics.py. It defines two tests that check the output of forward() against expected coordinates. A test is an automated check that runs a function with specific inputs and checks whether the result matches expectations. An assertion is a statement in a test that checks if a condition is true, raising an error if the condition is false: 

      import pytest

from two_link.kinematics import forward


def test_straight_arm():
    x, y = forward(0.5, 0.3, 0, 0)
    assert x == pytest.approx(0.8)
    assert y == pytest.approx(0.0)


def test_elbow_bent():
    x, y = forward(0.5, 0.3, 90, -90)
    assert x == pytest.approx(0.3)
    assert y == pytest.approx(0.5)

      04. Build and run the tests

      You run colcon from the root of the workspace, which here is the ws folder. The ROS 2 documentation says that sourcing the workspace before testing should not be necessary, because colcon test makes sure the tests run with the right environment and can reach their dependencies.[3]

      First, build the package with colcon build, then run the test suite with colcon test: 

      $ colcon build
Starting >>> two_link
Finished <<< two_link [0.36s]

Summary: 1 package finished [0.50s]
$ colcon test
Finished <<< two_link [0.26s]	[ with test failures ]

Summary: 1 package finished [0.42s]
  1 package had test failures: two_link

      The build succeeded, but colcon test reported that two_link had test failures. Notice that colcon test does not print the failure details. The command line testing guide explains that to see the exact test cases which fail, you use the verbose flag.[3] Run colcon test-result --all --verbose to see the full failure report: 

      $ colcon test-result --all --verbose
build/two_link/pytest.xml: 2 tests, 0 errors, 1 failure, 0 skipped
- two_link.tests.test_kinematics test_elbow_bent
  <<< failure message
    assert 0.2 == 0.5 ± 5.0e-07
      
      comparison failed
      Obtained: 0.2
      Expected: 0.5 ± 5.0e-07
  >>>

Summary: 2 tests, 0 errors, 1 failure, 0 skipped

      05. Read the failure

      Let us walk through the failure output line by line. The first line indicates that colcon parsed build/two_link/pytest.xml, recording two tests, zero unhandled execution errors, one failure, and zero skipped tests. The next line names the exact failing test function: test_elbow_bent in the two_link.tests.test_kinematics module.

      Inside the failure block, pytest shows the failed assertion: assert 0.2 == 0.5 ± 5.0e-07. The comparison failed because the function returned an obtained value of 0.2, whereas the expected value was 0.5 within a tolerance of 5.0e-07. A stack trace is a diagnostic report showing the sequence of function calls that ran up to the moment of a failure. Here, the failure points directly to the assertion on the y-coordinate inside test_elbow_bent.

      Now let us calculate the correct kinematics by hand. In test_elbow_bent, the arm parameters are length L1 = 0.5, length L2 = 0.3, shoulder angle θ1 = 90 degrees, and elbow angle θ2 = -90 degrees.

      Link 1 starts at the base origin (0, 0) and points straight up along the positive y-axis at 90 degrees. The elbow position is x1 = 0.5 · cos(90°) = 0.0, and y1 = 0.5 · sin(90°) = 0.5.

      Link 2 is attached to the elbow. Its orientation relative to the global world frame is the sum of both joint angles: θ1 + θ2 = 90° + (-90°) = 0°. Because this total angle is 0 degrees, link 2 points horizontally to the right, parallel to the positive x-axis. The tip coordinates are:

      • Correct x: 0.5 · cos(90°) + 0.3 · cos(90° - 90°) = 0.0 + 0.3 · cos(0°) = 0.3.
      • Correct y: 0.5 · sin(90°) + 0.3 · sin(90° - 90°) = 0.5 · 1.0 + 0.3 · sin(0°) = 0.5 + 0.0 = 0.5.

      Now look at line 9 of two_link/kinematics.py: 

      y = l1 * math.sin(t1) + l2 * math.sin(t2)

      The buggy line computes 0.5 · sin(90°) + 0.3 · sin(-90°) = 0.5 · 1.0 + 0.3 · (-1.0) = 0.5 - 0.3 = 0.2. It took the sine of t2 alone instead of the sine of t1 + t2.

      Why did the first test, test_straight_arm, pass? In that test, θ1 = 0 degrees and θ2 = 0 degrees. When θ1 is 0, the sum t1 + t2 equals 0 + t2 = t2. Therefore, whenever θ1 is 0, the buggy formula produces the exact same numerical result as the correct formula. The bug was completely hidden when testing only a fully extended horizontal arm.

      06. Fix it and test again

      To fix the bug, edit line 9 of two_link/kinematics.py so that it adds the two angles together, matching the x-coordinate line above it: 

      y = l1 * math.sin(t1) + l2 * math.sin(t1 + t2)

      Save the file, then rebuild and test the package again: 

      $ colcon build
Finished <<< two_link [0.37s]

Summary: 1 package finished [0.50s]
$ colcon test
Finished <<< two_link [0.25s]

Summary: 1 package finished [0.41s]
$ colcon test-result --all --verbose
build/two_link/pytest.xml: 2 tests, 0 errors, 0 failures, 0 skipped

Summary: 2 tests, 0 errors, 0 failures, 0 skipped

      Both tests pass with zero failures. A regression is an unintended software bug introduced into code that previously worked correctly. Re-running the test suite ensures that fixing the bent-arm calculation did not break the straight-arm case.

      When developing in large repositories, you often want to run a single test rather than the entire test suite. The Python testing tutorial explains that you can specify arguments to the pytest framework from the command line with the --pytest-args flag.[2] The transcript demonstrates filtering for a specific test function by name with the -k option: 

      $ colcon test --packages-select two_link --pytest-args -k test_straight_arm
Finished <<< two_link [0.25s]

Summary: 1 package finished [0.42s]
$ colcon test-result --all
build/two_link/pytest.xml: 1 test, 0 errors, 0 failures, 0 skipped

Summary: 1 test, 0 errors, 0 failures, 0 skipped

      To see the pytest output while the tests run, the tutorial gives one more flag: colcon test --event-handlers console_cohesion+.[2] With the bug still in place, this run printed pytest’s own summary with one failed and one passed test. It is not shown in the transcript above.

      07. In a real ROS 2 package

      In a real ROS 2 package, tests are not the only automated check. A linter is a tool that reads source code without running it and reports style errors, formatting problems and likely bugs. ROS 2 has a family of them called ament_lint. All ament_lint tools accept files or directories, analyze them, and generate reports.[4] The documentation lists ament_copyright to check or add copyright and license notices, ament_flake8 for Python linting, ament_cppcheck for C++ static analysis, ament_cpplint for C++ style checks, and ament_uncrustify to check and reformat C++ code with --reformat.[4] It names ament_pep257 among other useful tools.[4]

      The same page says these command-line programs help people write code that meets the ROS 2 coding standards, and it recommends that ROS developers get to know the tools and use them before submitting pull requests.[4] For a contributor this means one more step before a pull request: run the linters the project uses, and fix what they report.

      08. Write the bug report

      The official issue reporting guide explains that you can report code issues in the ROS repository for the package where the error occurred.[5] This is generally the last file listed in the stack trace. Core ROS 2 packages live in repositories under the ros2 organization on GitHub, while binary packages listed on the ROS Index link to their corresponding source repositories. Documentation issues belong in the ros2_documentation tracker, and issues with an unclear destination can be opened in the top-level ros2/ros2 repository.

      Before opening an issue, the guide asks you to check whether someone has already reported it: search across the ros2 and ament GitHub organizations, and check the Robotics Stack Exchange.[5] If nothing matches, open a new issue and give it a descriptive title.[5] A title such as “kinematics broken” does not help. Say what fails and under what condition.

      Then fill in the fields of the issue template. The guide asks for your environment, the steps and commands that lead to the problem, the exact output, and any troubleshooting you have already tried.[5] A maintainer who can repeat your steps and see the same failure can start on a fix at once.

      Below is an example bug report for the bug fixed in this lab. This report is an educational example about our practice package, not an issue for any real upstream project:

      Example bug report (practice package)

      Title: two_link: forward kinematics y-coordinate uses theta2 instead of theta1 + theta2

      Description:

      In two_link/kinematics.py, the forward() function calculates the y-coordinate of the arm tip using math.sin(t2) instead of math.sin(t1 + t2). This causes incorrect tip coordinates whenever θ1 is non-zero.

      Steps to reproduce:

      1. Clone the two_link package into a colcon workspace.
      2. Run colcon test --packages-select two_link.
      3. Run colcon test-result --all --verbose.

      Expected behavior:

      For L1 = 0.5, L2 = 0.3, θ1 = 90°, and θ2 = -90°, the arm tip should be at x = 0.3 and y = 0.5. The test test_elbow_bent should pass.

      Actual behavior:

      The test fails with the following assertion failure: 

      build/two_link/pytest.xml: 2 tests, 0 errors, 1 failure, 0 skipped
- two_link.tests.test_kinematics test_elbow_bent
  <<< failure message
    assert 0.2 == 0.5 ± 5.0e-07
      
      comparison failed
      Obtained: 0.2
      Expected: 0.5 ± 5.0e-07
  >>>

      Environment:

      OS: Ubuntu 26.04 LTS, Python: 3.14, colcon-core: 0.21.3, pytest: 9.2.0.

      Proposed fix:

      Change line 9 of two_link/kinematics.py from y = l1 * math.sin(t1) + l2 * math.sin(t2) to y = l1 * math.sin(t1) + l2 * math.sin(t1 + t2).

      09. From report to pull request

      Once you have identified a bug and confirmed a working fix with tests, you can propose the fix to the project. The contribution guidelines in ROS projects recommend several practices for newcomers making their first code pull request:

      • Scope and focus: The pull request guidelines advise contributors to limit each pull request to a single, well-defined change.[6] Keep your patch small and avoid incidental changes like reformatting unrelated lines.
      • Fork and branch: Make your changes on a development branch taken from the rolling branch, in your fork of the target repository.[6]
      • Keep generated files out: ROS 2 workspaces generate build artifacts that should generally not be committed to source control.[7] That covers the build/, install/ and log/ folders that colcon created in this lab, and Python’s temporary files such as __pycache__/ and *.pyc.[7] A .gitignore file in the repository tells git to leave them out.[7]
      • Link the issue: In the pull request description, include the ID of the issue your change fixes, in the format Fixes #(issue).[6]
      • Say what you are doing: Comment on the issue to let others know that you are working on it.[8] When you create the pull request, select the “Allow edits by maintainers” checkbox, which helps maintainers make small changes directly when needed.[6]
      • Responding to review: Reviewers comment on the pull request on GitHub. Answer in the same thread and add commits to your branch for the changes they ask for. The guide says to aim to reply to review comments within one week, so that you and the reviewers do not lose the context of the change.[6]

      To review the open-source etiquette covered earlier in the course, revisit lesson 3.2 on how community collaboration works and lesson 3.5 on contributing to Nav2. To explore active robotics projects and their issue trackers, visit the Robotics Open-Source Map.

      Try it
      1. Add a third test function called test_straight_up() to tests/test_kinematics.py for θ1 = 0 degrees and θ2 = 90 degrees with link lengths 0.5 and 0.3. Calculate the expected x and y tip coordinates by hand first, write the assertions with pytest.approx, and run colcon test to verify your calculation.
      2. In two_link/kinematics.py, break the x-coordinate formula on purpose by changing math.cos(t1 + t2) to math.cos(t2). Predict which of your three tests will pass and which will fail before running the test command, then verify your prediction using colcon test-result --all --verbose.
      3. Draft a complete bug report for that second bug using the bug report format from Section 08. Include clear steps to reproduce, the failing pytest assertion, and the proposed code change.
      4. Open the Robotics Open-Source Map, select one project (such as ROS 2 or Nav2), and navigate to its GitHub repository. Locate the issues tab, search for the good first issue label, and inspect how community members report bugs and claim tasks.

      10. Check your understanding

      • Why can colcon build and test the two_link package without a ROS 2 installation on your computer?
        Show answer

        The two_link package is a pure Python package using standard setuptools and pytest. Colcon is a general build tool that builds and tests standard Python packages without requiring ROS 2 client libraries or middleware. (Section 02)

      • What folder name and file naming pattern does colcon require for pytest test discovery in an ament_python package?
        Show answer

        Test files must be placed in a directory named tests at the package root, and test files must match the pattern test_FOO.py where FOO can be any name. (Section 03)

      • Why did the original bug in kinematics.py fail to trigger in test_straight_arm?
        Show answer

        In test_straight_arm, θ1 is 0 degrees. When θ1 is 0, the sum t1 + t2 equals t2, so math.sin(t2) produces the exact same numerical result as math.sin(t1 + t2). The bug only produces an error when θ1 is non-zero. (Section 05)

      • Which generated files and folders should generally not be committed to a git repository?
        Show answer

        Workspace build artifacts including the build/, install/, and log/ directories, as well as Python bytecode files such as __pycache__/ and *.pyc files, should generally not be committed to source control. (Section 09)
