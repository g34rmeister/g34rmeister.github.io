8.6 Network Design, Security and Diagnostics

Gerald Lê

01. Industrial network security and ISA/IEC 62443

In Lesson 1.7 The Industrial Robot Cell, we introduced the cell PLC and emphasized keeping safety signals separate from regular control wiring. In Lesson 5.4 Making a Robot Cell Safe, we explored interlocks and emergency stop buttons. Once the robot, PLC and other devices share a network, that network also has to be protected against attacks.

The ISA/IEC 62443 series of standards defines requirements and processes for implementing and maintaining electronically secure industrial automation and control systems.[1]

A founding principle of ISA/IEC 62443 is shared responsibility among stakeholder groups including asset owners, product suppliers, integrators, and service suppliers.[1] In a robot cell, the robot maker is a product supplier, the company that builds the cell is the integrator, and the plant that runs it is the asset owner.

In the ISA/IEC 62443 series, Part 3-2 specifies security risk assessment for system design while Part 3-3 specifies system security requirements and security levels.[1]

The IEC recognized the ISA/IEC 62443 series as a horizontal standard in 2021 that applies to a broad range of different industries.[1]

02. Network segmentation: zones, conduits, and the DMZ

If every computer and controller in a plant sits on one flat network, an attacker who gets into one office PC can reach every machine. Defense in depth means using several layers of protection instead of relying on one.

Industrial defense-in-depth strategies implement zones and conduits to secure communication pathways between trusted environments.[2] In simple terms, a zone is a group of devices with the same security needs, and a conduit is the controlled path that connects two zones.

Plant layouts group devices into hierarchical tiers based on their function. The Cell Security Zone contains Level 2 area control, Level 1 controller LANs, and Level 0 field basic input/output devices such as sensors and actuators.[2] A robot cell, with its PLC, robot controller and I/O, is one such zone.

A demilitarized zone is a physical and logical subnet that acts as an intermediary so connected devices avoid direct exposure to untrusted networks.[2] Often abbreviated as DMZ, this buffer subnet sits between the industrial control network and the enterprise corporate network.

Placing corporate-accessible components in a DMZ ensures that no direct communication paths are required from the corporate network to the control network.[2] If an enterprise accounting application requires production data, it connects only to a database or reporting server located inside the DMZ. The corporate application never touches a robot controller or safety PLC directly.

Secure DMZ communication models require control zones to push data to the DMZ and enterprise users to pull data from DMZ application servers.[2] For example, the cell sends its production records to a server in the DMZ, and an office application reads them from that server, so nothing in the office ever connects to the robot.

Remote access into industrial control systems should be routed through hardened intermediary authentication jump boxes in the DMZ using multifactor authentication.[2] A jump box is a computer in the DMZ that a remote user must log in to before reaching the cell.

The network segmentation diagram needs JavaScript. With it on, you can select zones, conduits and devices to inspect defense-in-depth communication pathways.

03. Managed switches and VLAN configuration

A managed switch can be configured, for example to split one physical network into several logical ones. An unmanaged switch cannot.

A virtual LAN divides physical networks into smaller logical broadcast domains that isolate traffic from other VLANs.[2] For example, assigning robot motion traffic to VLAN 20 and human-machine interface (HMI) traffic to VLAN 30 keeps high-volume display graphics from interfering with motion control packets on the same physical switch hardware.

Managed switches in industrial networks should disable Dynamic Trunking Protocol and configure switch ports as static access ports to prevent switch spoofing.[2] A trunk port carries several VLANs; if a device can talk a port into becoming a trunk, it can reach VLANs it should not see.

Network administrators should prune VLAN 1 from trunks and use a dedicated VLAN to keep management traffic separate from user data and protocol traffic.[2]

04. Deterministic communication and Time-Sensitive Networking

8.2 showed how PROFINET IRT and EtherCAT get precise timing with their own mechanisms. Time-Sensitive Networking aims to give standard Ethernet that kind of timing. Variation in delay is called jitter.

Time-Sensitive Networking is an IEEE 802 standards family designed to provide deterministic connectivity with bounded latency, low packet delay variation, and low packet loss.[3]

IEEE Std 802.1AS (IEEE 802.1AS) provides Layer 2 timing and synchronization for time-sensitive applications as a profile of IEEE 1588.[3] It gives the devices on the network a shared sense of time.

TSN includes IEEE 802.1Qbv for enhancements for scheduled traffic and IEEE 802.1Qbu for frame preemption in bridged networks.[3] Scheduled traffic means time-critical frames get reserved slots; frame preemption means an urgent frame can interrupt a long, less urgent one.

IEEE Std 802.1CB specifies frame replication and elimination for reliability across bridged networks.[3] Frames are sent over two paths and the duplicate is removed, so losing one path does not lose the frame.

IEC/IEEE 60802 defines a joint international Time-Sensitive Networking profile specifically for industrial automation.[3] A profile picks which of the TSN options a device must support, so equipment from different makers works together.

05. Network diagnostics and Wireshark packet analysis

When an industrial network experiences communication failures, dropped packets, or unexpected register values, technicians need diagnostic tools to inspect traffic directly on the wire. Wireshark is a packet analyzer: it records network traffic and decodes each protocol layer.

Loopback traffic can be captured on Linux and macOS, but on Windows only with Npcap, which adds an adapter for loopback traffic capture.[4] The 8.3 lab sends its traffic to 127.0.0.1, the computer itself, so it never reaches a real network card and must be captured on the loopback interface.

Wireshark picks a decoder (a dissector) mostly from the port number. Modbus TCP normally uses port 502, but the 8.3 lab server uses port 5020, so Wireshark shows its packets as plain TCP. Wireshark's Decode As, opened from the Analyze menu, overrides Wireshark's choice of dissector, for example for traffic on a non-standard port.[5] This feature lets the user instruct Wireshark to interpret raw TCP data on port 5020 as Modbus TCP frames.

Capturing traffic on an active network can produce thousands of packets in a few seconds. To locate specific transactions, technicians apply display filters in Wireshark. Wireshark display filters check for protocol presence or field values and can be combined with logical operators into complex expressions.[6]

In Wireshark, the Modbus/TCP display filter protocol name is mbtcp, which defines fields including Transaction Identifier, Protocol Identifier, and Length.[7] Typing mbtcp into the filter bar restricts the packet list to Modbus TCP frames. Technicians can also filter by header values, such as matching a specific transaction identifier.

In Wireshark, the Modbus dissector uses the protocol field name modbus, providing fields such as Function Code, Exception Code, and response time.[8] These protocol fields allow targeted troubleshooting. For example, entering modbus.func_code == 16 filters for write-multiple-registers requests and responses, while modbus.exception_code isolates error responses returned by a controller.

06. Lab: Watching Modbus traffic on the wire

In Lesson 8.3 Lab: Connecting a Robot to a PLC, you wrote and read registers on a stand-in Modbus server with pymodbus. In this hands-on lab, you will run the stand-in robot server and client scripts while capturing the interaction in Wireshark to inspect the underlying protocol frames.

Modbus TCP messages include a 7-byte MBAP header and transmit over TCP on registered port 502.[9] The MBAP header contains four fields: the Transaction Identifier (2 bytes), the Protocol Identifier (2 bytes, set to 0 for Modbus), the Length field (2 bytes indicating remaining bytes), and the Unit Identifier (1 byte). Because our developmental test server runs on port 5020 rather than the registered port 502, you will configure Wireshark to decode the custom port.

Follow these six steps to capture and analyze the transaction:

  1. Launch Wireshark and choose the capture interface: Open Wireshark. On Linux or macOS systems, double-click the loopback interface (such as lo or lo0). On Windows systems, select the “Adapter for loopback traffic capture” provided by Npcap. Click the blue shark fin icon in the upper left toolbar to start capturing packets.
  2. Start the stand-in Modbus server: Open a terminal window, navigate to your lab directory, and launch the stand-in server from Lesson 8.3: 
    python fake_ur_server.py
    The server starts listening on local address 127.0.0.1 at port 5020.
  3. Execute the Python client script: In a second terminal window, run the client script: 
    python client.py
    The script connects to 127.0.0.1:5020, writes register 128, writes registers 129 and 130, reads back registers 128 through 130, and prints Registers 128-130: [1, 250, 7] before closing the socket.
  4. Stop capture and configure protocol decoding: In Wireshark, click the red square icon on the toolbar to stop capturing packets. Locate a packet sent to or from port 5020. Because port 5020 is not the registered Modbus port, Wireshark initially displays these frames as generic TCP packets. Select a packet on port 5020, click the Analyze menu at the top of the window, and choose Decode As.... In the dialog that appears, click the + button to add a rule, ensure the field is set to TCP port with value 5020, change the current protocol column to Modbus/TCP, and click OK. Wireshark immediately re-dissects all packets on port 5020 as Modbus frames.
  5. Filter for write-multiple transactions: The Modbus server responds to function code 0x06 to write a single register and 0x10 to write multiple registers.[10] Function code 0x10 in hexadecimal equals 16 in decimal. In the Wireshark display filter bar, enter the filter expression: 
    mbtcp && modbus.func_code == 16
    Press Enter to apply the filter. The packet list now isolates the write-multiple request sent by the client and the acknowledgment response returned by the server.
  6. Inspect the MBAP header and Modbus payload: Select the write-multiple request packet in the top pane, then inspect the lower details panes:
    • In the Modbus/TCP protocol layer, examine the 7-byte MBAP header. Note the value of the Transaction Identifier field.
    • Select the matching response packet immediately following the request. Observe that its Transaction Identifier matches the request's identifier exactly. The client uses this matching identifier to pair asynchronous responses with pending requests over the single TCP socket.
    • In the Modbus application layer, verify that the Function Code displays 16 (Write Multiple Registers). In the request packet details, note the starting address (129), the register count (2), and the register values written (250 and 7).
