2.1 Types of Programming

Gerald Lê

01. The spectrum of programming methods

An industrial robot is a reprogrammable, multipurpose manipulator, but writing instructions for a six-axis arm is fundamentally different from writing software for a desktop computer.[1] A conventional software bug might throw an uncaught exception or display an error dialog. A bug in a robot program can crash a multi-ton mechanical arm into steel tooling at three meters per second, shattering end-effectors, ruining expensive fixtures, and creating severe hazards for workers nearby.

For this reason, robot programming methods have evolved along distinct engineering paths to balance safety, execution speed, setup time, and geometric precision. ISO 8373:2021 categorizes robot programming broadly by how instructions are introduced to the control system: through direct interaction with the manipulator (online programming), or through external computer models and code generation (offline programming).[1] A third paradigm, block-based visual programming, has also emerged to allow line technicians and shop-floor operators without computer science degrees to deploy collaborative and light industrial robots quickly.[2]

Understanding which programming method to select depends on production volume, path complexity, safety envelope restrictions, and the financial cost of stopping the factory floor.

02. Online programming: teach pendants in practice

Online programming means taking the robot out of automatic production, switching the controller into manual teach mode, and authoring the motion program directly on the physical machine.[3] The primary tool for this workflow is the teach pendant, a ruggedized, handheld industrial computer tethered to the robot controller by an emergency-stop-rated cable.[4]

In a standard teach pendant workflow, the technician enters the safety cell, drives each axis of the robot to a desired destination, and records the spatial coordinates into the program as a target point. Industry estimates, such as those published by automation analyst Jonathan Wilkins, suggest that teach pendants have historically accounted for over 90% of all programming performed on installed industrial robots worldwide.[5]

Major robot manufacturers have developed proprietary teach pendant hardware tailored to their controller software architectures:

  • ABB FlexPendant: Used with ABB IRC5 and OmniCore controllers, the FlexPendant features a color touchscreen, customizable physical hotkeys, and an integrated three-axis joystick.[4] Programmers use the joystick to jog multiple joints simultaneously or drive the tool in straight lines along Cartesian vectors.
  • FANUC iPendant: The iPendant (standard on R-30iB and R-30iB Plus controllers) provides a dual-screen display, dedicated axis direction keys (+X, -X, +Y, -Y), and real-time 3D graphic rendering (4D graphics) that visualizes the robot model, user frames, and motion envelopes directly on the handheld screen.[6]
  • KUKA smartPAD: Engineered for KUKA KR C4 and KR C5 controllers, the smartPAD combines an industrial touchscreen with an ergonomic 6D mouse (a multidirectional space mouse) that allows operators to translate and rotate the robot tool center point intuitively in six degrees of freedom.[7]
  • Universal Robots Teach Pendant: Paired with UR cobot controllers running PolyScope, this lightweight pendant emphasizes a touch-first graphical interface without physical joysticks, relying on on-screen jog buttons or direct hand guiding.[8]

03. Pendant safety interlocks and reduced speed

Because online programming places a human inside the mechanical reach of an industrial manipulator, international safety standards enforce strict hardware and software interlocks. ISO 10218-1:2025 (and its predecessor ISO 10218-1:2011) mandates specific protective mechanisms whenever a robot is operated in manual mode.[9]

First, the teach pendant must be equipped with a three-position enabling device (often called a deadman switch).[9] This switch is mounted on the rear or side grip of the pendant. To enable servo drive power and allow motion, the operator must squeeze the switch into its center position (position 2). If the operator panics and releases the switch (position 1), or suffers a muscle spasm and squeezes the switch tightly (position 3), the safety circuit opens immediately, removing power or activating a category 0 or category 1 safe stop.[9]

Second, ISO 10218-1 requires that manual jogging operate under reduced teach speed (T1 mode), restricting the tool center point (TCP) to a maximum speed of 250 mm/s.[9] This speed ceiling ensures that an operator in close proximity has sufficient reaction time to release the enabling device or hit the pendant emergency stop button before a collision occurs.

04. Coordinate frames for manual jogging

When driving an industrial arm with a teach pendant, the operator must select a coordinate system. Choosing the correct frame determines how the manipulator moves when a joystick or directional button is engaged:[4][6]

  • Joint Jogging: Moves one individual motor axis at a time (axes 1 through 6). Joint jogging is mathematically the simplest mode because it requires no inverse kinematics calculations. It is used to uncoil axes from joint limits or move the arm away from mechanical singularities.
  • World / Base Coordinates: The controller calculates coordinated multi-joint motions so the tool center point moves linearly along the fixed Cartesian X, Y, and Z axes of the robot base or the manufacturing shop floor. Moving along +Z lifts the tool straight up toward the ceiling regardless of current joint angles.
  • Tool Coordinates (TCP Frame): Motion is defined relative to the tool mounted on the robot wrist. Pushing +Z moves the tool outward along its working vector (such as advancing a drill bit into a pilot hole or extending a dispensing nozzle into a cavity).
  • User / Work Object Coordinates: Motion is aligned with a tilted fixture, an inclined conveyor, or a rotary pallet. If a metal bracket sits tilted at 30 degrees, defining a user frame along the bracket surface lets the technician jog parallel to the workpiece with single-axis inputs.[4]

05. Lead-through programming and collaborative robots

While traditional industrial arms require jogging through pendant buttons or joysticks, collaborative robots (cobots) introduced lead-through programming (also termed direct teaching or hand guiding).[3] In this method, the programmer grasps the robot arm or an auxiliary handle and physically guides the mechanism through space to demonstrate the desired trajectory.[8]

Lead-through is the primary online programming method for collaborative robots.[3][8] Universal Robots models, such as the UR5e or UR10e, feature a dedicated "Freedrive" button on the rear of the teach pendant or near the tool flange.[8] When pressed, the controller enters gravity compensation mode. The controller calculates the exact gravitational torques acting on each link using joint position measurements and an internal rigid-body dynamics model. The motors generate just enough counter-torque to float the arm weightlessly in space, allowing the human operator to maneuver the arm effortlessly with fingertips.[8]

Industrial cobots implement hand guiding through two distinct sensing methods:

  • Joint Torque Sensors: Cobots like the KUKA LBR iiwa or ABB GoFa incorporate sensitive torque sensors at each individual joint. The controller reads external forces applied by human hands and servos each motor to minimize resistive torque in the direction of human motion.[10]
  • Wrist Force/Torque Sensors: Robots like the Universal Robots e-Series embed a 6-axis force/torque sensor directly between the tool flange and the end-effector.[8] When guiding from the tool, the sensor measures three orthogonal forces (Fx, Fy, Fz) and three orthogonal torques (Mx, My, Mz) to guide coordinated arm motion.

Lead-through programming dramatically lowers setup time for simple pick-and-place, machine tending, and palletizing. However, teaching complex curved paths purely by hand is prone to human inconsistency. A human cannot hand-guide an arm along a mathematically perfect line or hold a constant speed of 12.5 mm/s for precision sealing. For high-precision continuous contours, engineers rely on offline tools.

06. Offline programming (OLP) principles and architecture

Offline programming (OLP) is the process of generating robot motion programs entirely within an external computer environment without using or stopping the physical robot.[3] The programmer works inside a 3D digital simulation containing exact computer-aided design (CAD) models of the robot manipulator, end-effector tooling, parts, fixtures, and safety fences.[11]

The software architecture of an offline programming system consists of four primary functional engines:[3][12]

  • CAD Feature Extraction: The software extracts geometric curves, surfaces, and vertex normals directly from part CAD models. For an arc welding seam, the programmer clicks the boundary line of two plates, and the software automatically computes thousands of trajectory points maintaining the specified torch angle and travel distance.[11]
  • Kinematic and Dynamic Solver: The solver checks that every Cartesian waypoint falls within the robot's physical reach envelope, verifies joint travel limits, computes inverse kinematics solutions, and detects kinematic singularities (such as wrist alignment or shoulder boundary singularities).[12]
  • Collision Detection Engine: The simulation calculates bounding volume hierarchies (such as oriented bounding boxes) for the moving robot links and static cell fixtures. It flags any mechanical collision or near-miss clearance violation before code ever touches hardware.[11]
  • Post-Processor: The post-processor is a compiler module that translates the universal 3D trajectory data into vendor-specific robot syntax.[12] The same simulated path can be post-processed into RAPID code for ABB controllers, KRL code for KUKA controllers, Karel or TP for FANUC, or URScript for Universal Robots.[12]

07. The simulation-to-reality gap and cell calibration

The primary technical barrier in offline programming is the simulation-to-reality gap.[12] In a 3D CAD environment, parts are mathematically perfect, link lengths have zero tolerance variation, and fixtures sit precisely at their nominal Cartesian coordinates. In the physical factory, however, sheet metal parts warp, weld fixtures are bolted down several millimeters away from their CAD coordinates, and robot gearboxes flex under heavy payload inertia.[12][13]

While modern industrial robots have outstanding pose repeatability (often +/- 0.02 mm under ISO 9283), their uncalibrated pose accuracy is often much worse, ranging between 1 mm and 5 mm.[13] If an uncalibrated OLP program is downloaded directly to a real arm, a weld gun programmed to follow a seam may miss the joint entirely or gouge into the metal.

Bridging this gap requires rigorous calibration before running production:[12][13]

  • Tool Center Point (TCP) Calibration: The real physical tool is calibrated using a four-point or six-point touch-up method against a sharp reference spike, determining the exact position and orientation offsets from the robot's mounting flange.
  • Work Object / User Frame Calibration: Three reference points on the physical fixture (an origin, a point on the X axis, and a point on the XY plane) are touched with the calibrated TCP. The controller calculates the exact coordinate transformation between the CAD world and the physical cell floor.
  • Kinematic Calibration: For aerospace drilling or precision laser cutting, external laser trackers, optical cameras, or ballbar instruments measure the robot across hundreds of poses. Mathematical optimization algorithms identify exact kinematic parameters (link lengths, zero offsets, joint compliance, and gear ratios) to update the robot controller's internal kinematic model, reducing absolute positioning error to under 0.2 mm.[12][13]

08. Block-based visual programming

While heavy industrial manufacturing relies on teach pendants and offline simulation suites, collaborative applications increasingly use block-based programming.[2] Inspired by visual educational tools like Google Blockly and MIT Scratch, block-based robot programming represents commands, logic branches, and I/O signals as interlocking visual jigsaw blocks.[14]

In 2020, ABB launched Wizard Easy Programming for its YuMi single- and dual-arm collaborative robots, subsequently expanding it across its entire OmniCore-controlled industrial robot portfolio.[2][15] Operators construct programs by dragging visual blocks (such as "MoveJ", "WaitDI", or "SetDO") into a sequence on the FlexPendant. Behind the user interface, the Wizard engine compiles the graphical arrangement into clean, syntax-verified ABB RAPID code in real time.[2] If an engineer needs advanced functionality, such as error recovery traps or complex matrix math, they can open the generated RAPID file in a text editor and add native code directly.[2]

Universal Robots implements a similar visual paradigm within PolyScope. A program is displayed as an indented hierarchical tree of motion commands and logic statements. Line technicians can adjust waypoint positions by hand-guiding the robot, selecting the node in the tree, and tapping "Set Waypoint."[8]

09. Economic and operational trade-offs

Selecting a robot programming methodology requires balancing capital software expense against operational downtime costs.[3]

Criteria Teach Pendant Jogging Cobot Lead-Through Offline Programming (OLP)
Robot Downtime High; production must cease completely during teaching. Medium; teaching is fast, but cell is unavailable while running. Near Zero; 95% of programming happens while robot runs production.
Software License Cost Zero extra cost; pendant is bundled with the controller. Zero extra cost; integrated directly into cobot firmware. High ($5,000 to $30,000+ per workstation seat).
Geometric Precision Subject to human eyesight and jog alignment errors. Low on continuous paths; human hand tremors transfer to points. Extremely high; points derived directly from exact CAD models.
Operator Skill Required Medium; requires knowledge of robot frames and manual modes. Low; intuitive physical guidance with minimal training. High; requires CAD/CAM expertise, simulation skills, and post-processors.
Ideal Application Simple pick-and-place, small batch adjustments, machine tending. Palletizing, light assembly, packaging, benchtop cobots. Automotive spot welding, multi-axis laser cutting, complex deburring.

In automotive assembly plants, line downtime costs can exceed $20,000 to $50,000 per hour.[16] Stopping a framing line to program hundreds of weld spots by hand pendant would cost millions of dollars in lost throughput. In that environment, offline programming software pays for itself on its first deployment. Conversely, for a small machine shop running five CNC mills with a single cobot tending parts, the capital investment of an OLP license cannot be justified, making lead-through programming the most economical choice.

10. Case study: spot welding vs. custom deburring

Consider an automotive spot-welding cell containing two six-axis articulated arms. A new car chassis requires 450 spot welds across stamped steel body panels. If programmed online using a teach pendant, jogging to 450 distinct points, verifying gun closure clearances, and programming approach vectors would take two technicians approximately 40 to 60 hours inside the physical cell. During that week, no cars could be manufactured on that line.

Using an offline programming suite like ABB RobotStudio or FANUC ROBOGUIDE, manufacturing engineers import the car body CAD data, auto-generate weld locations along structural flanges, simulate dual-robot coordination to eliminate inter-arm collisions, and calculate cycle time down to tenths of a second.[4][6] When the line shuts down for model changeover over the weekend, the program is downloaded to the controller. The technician spends only four hours touching up cell calibration frames, after which production launches immediately.

In contrast, consider an aerospace deburring task where an operator deburrs cast aluminum housings of varying shapes in small batches of twenty units. Setting up an offline CAD cell for every minor part variation would take longer than the manufacturing run itself. Here, an operator can use collaborative lead-through or block-based routines to teach the contour in three minutes, making online programming far superior.

11. Comparing online and offline workflows

Try it
  1. Imagine an industrial cell where an ABB arm palletizes boxes coming off a conveyor. Would you program this task using joint coordinates, base Cartesian coordinates, or work object coordinates? Justify your decision.
  2. An offline simulation predicts a total cycle time of 14.2 seconds, but the real robot completes the cycle in 16.1 seconds. Identify two physical factors that could account for this discrepancy.
  3. Explore the free Google Blockly visual environment at developers.google.com/blockly and construct a loop with an if/else conditional branch. Inspect how visual blocks translate into text-based code.
