4.4 Running Your First Example (Turtlesim)

Gerald Lê

01. Hands-on robotics with Turtlesim

Having configured our ROS 2 installation in lesson 4.3, it is time to move from theory to practice. Jumping straight onto real hardware is risky for a beginner: a wrong motor command can tip over a rover or damage a gearbox, so it pays to practise somewhere harmless first.

The official ROS 2 documentation uses Turtlesim for exactly this purpose: it is a lightweight simulator that demonstrates core ROS concepts without any hardware, representing the robot as a turtle you can drive around a 2D window.[1] Behind its friendly appearance it is a real ROS 2 program.

The Turtlesim node creates topics (velocity commands in, pose and colour readings out), offers services (such as spawning, clearing and teleporting turtles) and serves an action that rotates the turtle to an absolute heading.[1][2] The command-line tools, message types and Python patterns you practise here are the same ones you will use with real robots later in the course.

02. Launching and teleoperating your first robot

REP 2001, which defines the ROS 2 install variants, lists turtlesim in the desktop variant (both the Jazzy and Rolling lists include it), so a ros-lyrical-desktop install normally has it already.[3] If you installed the smaller ros-base variant, install it with apt:[1] 

sudo apt update
sudo apt install ros-lyrical-turtlesim

Open a fresh terminal (with your ROS 2 environment sourced) and start the simulator with the ros2 run command:[1] 

ros2 run turtlesim turtlesim_node

A window opens with a turtle in the middle of a blue background, and the terminal logs where the default turtle was spawned:[1] 

[INFO] [turtlesim]: Starting turtlesim with node name /turtlesim
[INFO] [turtlesim]: Spawning turtle [turtle1] at x=[5.544445], y=[5.544445], theta=[0.000000]

Now open a second terminal, source ROS 2 again, and start the keyboard teleoperation node:[1] 

ros2 run turtlesim turtle_teleop_key

Keep the teleop terminal active and press the arrow keys. Up and Down drive the turtle forward and backward; Left and Right turn it. The turtle draws its path with an attached "pen". Each key press moves it only a short distance before it stops, because a robot should not keep carrying out an old command if, for example, the operator loses the connection.[1] In the Turtlesim source code, the turtle stops if no new velocity command has arrived for one second.[2]

03. Topic introspection and the Twist message

What is happening behind the window? Open a third terminal and inspect the running ROS graph with the command-line tools.[1][4]

First, list the running nodes: 

ros2 node list

The terminal reports two nodes: /turtlesim (the simulator) and /teleop_turtle (the keyboard controller).[4] Next, list the topics, adding -t to show each topic's message type: 

ros2 topic list -t

The documented output is:[4] 

/parameter_events [rcl_interfaces/msg/ParameterEvent]
/rosout [rcl_interfaces/msg/Log]
/turtle1/cmd_vel [geometry_msgs/msg/Twist]
/turtle1/color_sensor [turtlesim_msgs/msg/Color]
/turtle1/pose [turtlesim_msgs/msg/Pose]

In Turtlesim, which topic carries the velocity commands from the teleop node? The answer is /turtle1/cmd_vel. The /teleop_turtle node publishes your keystrokes as velocity commands on /turtle1/cmd_vel, and the /turtlesim node subscribes to it to move the simulated turtle.[4] (On Lyrical, Turtlesim's own message types live in the turtlesim_msgs package; on Jazzy they are still in turtlesim, so you will see turtlesim/msg/Pose there.[2][5])

To watch the data on that topic in real time, run:[4] 

ros2 topic echo /turtle1/cmd_vel

Nothing appears until you press a key. When you press the Up arrow in the teleop terminal, the echo window prints:[4] 

linear:
  x: 2.0
  y: 0.0
  z: 0.0
angular:
  x: 0.0
  y: 0.0
  z: 0.0
---

The value 2.0 comes from the teleop node's default scale_linear parameter; turning uses a default scale_angular of 2.0 as well.[2] To see how many nodes publish and subscribe to the topic, and its type, query it with info:[4] 

ros2 topic info /turtle1/cmd_vel

The first line of the output is Type: geometry_msgs/msg/Twist.[4] You can print the structure of that type with ros2 interface show geometry_msgs/msg/Twist: a Twist "expresses velocity in free space broken into its linear and angular parts", each part a three-element vector (x, y, z).[4][6] By ROS convention, distances are in meters, angles in radians and time in seconds, and a robot's body frame has x pointing forward and z pointing up.[7] Turtlesim only reads linear.x (forward speed) and angular.z (turning rate about the vertical axis), plus linear.y if its optional holonomic parameter (allowing the robot to translate in any direction immediately without first rotating its chassis) is turned on.[2]

You can also command the turtle directly from the command line, without the teleop node:[4] 

ros2 topic pub /turtle1/cmd_vel geometry_msgs/msg/Twist "{linear: {x: 2.0, y: 0.0, z: 0.0}, angular: {x: 0.0, y: 0.0, z: 1.8}}"

This publishes the same command repeatedly (once per second by default), so the turtle keeps driving in a circle until you press Ctrl+C. Adding --once publishes a single message and exits, so the turtle traces only a short arc and stops.[4]

04. Calling services from the CLI: spawning robots

Topics suit continuous streams such as velocity and pose. For one-off requests, ROS uses services, a call-and-response model in which a client sends a request and a server returns a response.[5] List Turtlesim's services: 

ros2 service list

Besides the parameter services that almost every node has, you will see the Turtlesim services /clear, /kill, /reset, /spawn, /turtle1/set_pen, /turtle1/teleport_absolute and /turtle1/teleport_relative.[5] Let us call /spawn to add a second turtle to the arena:[5] 

ros2 service call /spawn turtlesim_msgs/srv/Spawn "{x: 2.0, y: 2.0, theta: 0.0, name: 'turtle2'}"

On Jazzy (or any distribution older than Kilted), use the type turtlesim/srv/Spawn instead.[5] The simulator creates a second turtle at (2, 2), and the terminal prints the request and the response, which contains the new turtle's name:[5] 

requester: making request: turtlesim_msgs.srv.Spawn_Request(x=2.0, y=2.0, theta=0.0, name='turtle2')

response:
turtlesim_msgs.srv.Spawn_Response(name='turtle2')

Each turtle needs a unique name; if you leave name empty, Turtlesim picks one for you.[1][2] If you run ros2 topic list again, you will see a new set of topics for the new turtle, including /turtle2/cmd_vel, /turtle2/pose and /turtle2/color_sensor.[2]

05. Remapping names on the command line

If you go back to your teleop terminal and press the arrow keys, only turtle1 moves, because turtle_teleop_key sends its commands to topics and actions under the turtle1 namespace.[1] How can we drive turtle2 without changing or recompiling any code?

In ROS 2, topic and service names inside a node can be redirected when the node starts by passing remapping arguments after the --ros-args flag, using the syntax --remap old_name:=new_name (or the short form -r).[8] Open a fourth terminal and start a second teleop node pointed at turtle2:[1] 

ros2 run turtlesim turtle_teleop_key --ros-args --remap turtle1/cmd_vel:=turtle2/cmd_vel --remap turtle1/rotate_absolute:=turtle2/rotate_absolute

The second remap redirects the rotation action as well, so the teleop node's absolute-rotation keys also control turtle2. Now you have two teleop terminals: one drives turtle1 and the other drives turtle2.[1] These remappings are "static": they apply for the whole lifetime of the node, and changing names after a node has started is not supported.[8] Remapping is what lets you reuse the same executable for a different robot or topic name without changing its code.[1]

06. ROS 2 workspace architecture

Driving demo nodes from the terminal is a good start, but real robotics work means writing your own nodes. In ROS 2 you develop them in a workspace: a directory that you build as an "overlay" on top of your main ROS 2 installation (the "underlay"), so new packages can be added without disturbing the installation you are extending.[9]

After a build, a typical workspace contains four directories side by side:[9][10]

  • src/ (source): Where you put your packages. Keeping packages in src is the documented best practice, and it is the only folder you edit by hand.[9]
  • build/ (intermediate files): Created by colcon. It holds intermediate build files, with one subfolder per package (for example, where CMake is run).[10]
  • install/ (installed packages): Created by colcon. Each package is installed here, along with the setup scripts (such as install/setup.bash) that you source to use the workspace.[9][10]
  • log/ (logs): Created by colcon. It holds logging information about each colcon run, including build output.[10]

Create your first workspace in your home directory:[9] 

mkdir -p ~/ros2_ws/src
cd ~/ros2_ws/src

07. Python package layout: package.xml and setup.py

ROS code is organised into packages, which you create from the workspace's src directory with ros2 pkg create, choosing either the ament_cmake or ament_python build type.[11] Create a Python package named my_robot_controller: 

ros2 pkg create --build-type ament_python --license Apache-2.0 my_robot_controller --dependencies rclpy geometry_msgs turtlesim_msgs

The --dependencies option adds the listed packages to package.xml for you, so you do not have to type them in by hand.[12] (On Jazzy, depend on turtlesim instead of turtlesim_msgs.[5]) The command creates the following inside ~/ros2_ws/src/my_robot_controller/:[11]

  • package.xml: The package manifest, with meta information such as the package name, description, maintainer and license, and its dependencies (here rclpy, geometry_msgs and turtlesim_msgs).[11][12]
  • setup.py: Instructions for how to install the package. Its entry_points field is where you register the commands that ros2 run can start.[11][13]
  • setup.cfg: Required when a package has executables, so ros2 run can find them; it tells setuptools to put the executables in the package's lib folder.[11][13]
  • resource/my_robot_controller: A marker file for the package.[11]
  • my_robot_controller/: A Python module directory with the same name as the package, containing __init__.py. Your node scripts go here.[11]
  • test/: A folder for the package's tests.[11]

08. Writing a custom rclpy velocity publisher

Let us write a Python node that drives the turtle in a continuous circle by publishing velocity commands twice a second (2 Hz). It follows the structure of the official "simple publisher" tutorial, which uses a timer that fires every 0.5 seconds.[13]

Create a new file named ~/ros2_ws/src/my_robot_controller/my_robot_controller/draw_circle.py: 

#!/usr/bin/env python3
import rclpy
from rclpy.executors import ExternalShutdownException
from rclpy.node import Node
from geometry_msgs.msg import Twist


class DrawCircleNode(Node):
    def __init__(self):
        # 1. Initialize the parent Node class with the node name
        super().__init__('draw_circle_node')

        # 2. Create a publisher on topic /turtle1/cmd_vel with queue size 10
        self.cmd_vel_pub_ = self.create_publisher(Twist, '/turtle1/cmd_vel', 10)

        # 3. Create a timer that calls send_velocity_command every 0.5 s (2 Hz)
        self.timer_ = self.create_timer(0.5, self.send_velocity_command)
        self.get_logger().info('Draw Circle Node has started.')

    def send_velocity_command(self):
        msg = Twist()
        msg.linear.x = 2.0   # forward speed
        msg.angular.z = 1.0  # turning rate (rad/s)
        self.cmd_vel_pub_.publish(msg)


def main(args=None):
    try:
        with rclpy.init(args=args):      # initialize ROS 2, shut down on exit
            node = DrawCircleNode()      # create our node
            rclpy.spin(node)             # process timer callbacks until stopped
    except (KeyboardInterrupt, ExternalShutdownException):
        pass


if __name__ == '__main__':
    main()

Our class inherits from rclpy.node.Node, and super().__init__ gives the node its name. create_publisher declares that the node publishes Twist messages on a topic with a "queue size" of 10, a Quality of Service setting that limits how many messages are queued if a subscriber cannot keep up. create_timer makes a callback run every 0.5 seconds. In main, the ROS client library is initialised, the node is created, and rclpy.spin(node) keeps the node running so its callbacks are called, until you stop it with Ctrl+C.[13] The Jazzy version of the tutorial writes main in an older style (rclpy.init(), rclpy.spin(), then destroy_node() and rclpy.shutdown()), which you will also see in many existing projects.[14] Because the 0.5 s timer is shorter than Turtlesim's one-second command timeout, the turtle never stops between messages.[2]

09. Writing a custom rclpy pose subscriber

Next, let us write a subscriber node that listens to the turtle's pose and logs it to the console, following the official "simple subscriber" tutorial.[13] The turtlesim_msgs/msg/Pose message holds x, y, theta, linear_velocity and angular_velocity.[2]

Create a new file named ~/ros2_ws/src/my_robot_controller/my_robot_controller/pose_subscriber.py: 

#!/usr/bin/env python3
import rclpy
from rclpy.executors import ExternalShutdownException
from rclpy.node import Node
from turtlesim_msgs.msg import Pose   # On Jazzy: from turtlesim.msg import Pose


class PoseSubscriberNode(Node):
    def __init__(self):
        super().__init__('pose_subscriber_node')

        # Create a subscription to /turtle1/pose
        self.pose_sub_ = self.create_subscription(
            Pose,
            '/turtle1/pose',
            self.pose_callback,
            10)
        self.get_logger().info('Pose Subscriber Node has started.')

    def pose_callback(self, msg: Pose):
        self.get_logger().info(
            f'Coordinates: x={msg.x:.2f}, y={msg.y:.2f}, heading={msg.theta:.2f} rad')


def main(args=None):
    try:
        with rclpy.init(args=args):
            node = PoseSubscriberNode()
            rclpy.spin(node)
    except (KeyboardInterrupt, ExternalShutdownException):
        pass


if __name__ == '__main__':
    main()

Here create_subscription takes the message type (Pose), the topic name (/turtle1/pose), the callback function (self.pose_callback) and the queue size (10). The topic name and message type must match the publisher's for the two to communicate. The subscriber needs no timer: its callback is called as soon as a message arrives.[13]

10. Compiling with colcon and running custom nodes

Before ros2 run can start our scripts, they must be registered as entry points in setup.py.[13] Open ~/ros2_ws/src/my_robot_controller/setup.py and add these lines inside the console_scripts brackets of entry_points: 

entry_points={
    'console_scripts': [
        'draw_circle = my_robot_controller.draw_circle:main',
        'pose_subscriber = my_robot_controller.pose_subscriber:main',
    ],
},

Now return to the root of your workspace and build with colcon:[10] 

cd ~/ros2_ws
colcon build --symlink-install
Developer Tip: Symlink Install

With --symlink-install, the installed files are linked to the files in your source space, so changes to Python scripts take effect without rebuilding every time.[9][10]

Next, open a new terminal (the documentation warns against sourcing an overlay in the same terminal where you built it), source your main ROS 2 installation, and then source your workspace as an overlay:[9] 

source /opt/ros/lyrical/setup.bash
cd ~/ros2_ws
source install/setup.bash

With Turtlesim running in another window, start your nodes (each terminal needs the overlay sourced): 

# Terminal 1: Run your circle driver
ros2 run my_robot_controller draw_circle

# Terminal 2: Run your pose logger
ros2 run my_robot_controller pose_subscriber

The turtle starts driving in circles, while your subscriber node prints its coordinates to the console.

11. Transferring skills to physical robots

Steering a cartoon turtle is a classic beginner exercise, but the same ideas carry over to real robots. For example, diff_drive_controller, the standard wheeled-robot controller in ros2_control, takes velocity commands on a ~/cmd_vel topic as geometry_msgs/msg/TwistStamped (a Twist with a timestamp and frame header) and publishes the robot's odometry on ~/odom as nav_msgs/msg/Odometry.[15] The node, publisher, subscriber and timer patterns you wrote here are the same rclpy patterns the official tutorials teach for any ROS 2 node.[13]

  • Velocity commands: Turtlesim reads a Twist; a real wheeled robot running diff_drive_controller reads the stamped version, with the same linear and angular fields.[6][15]
  • Position feedback: Turtlesim publishes a simple Pose; a real robot's controller publishes Odometry estimated from its wheels.[2][15]
  • Code structure: the rclpy.node.Node class, timer callbacks and create_publisher / create_subscription calls are the same whatever robot you are programming.[13]

In lesson 4.5, we look at the wider ROS toolset: visualising data in RViz2, inspecting node connections with rqt_graph, recording and replaying data with ros2 bag, and simulating robots in Gazebo.
