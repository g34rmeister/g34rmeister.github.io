4.7 Launch Files and Parameters

Gerald Lê

01. Why launch files exist

In lesson 4.4 you started Turtlesim and its teleop node by hand, one terminal per node, and in lesson 4.6 you wrote your own package with rclpy and turtlesim_msgs. That works for two or three nodes. A real robot is different: the ROS 2 documentation notes that a system "typically consists of many nodes running across many different processes (and even different machines)", and starting each one by hand "gets cumbersome quite quickly."[1]

The launch system solves this. It is "meant to automate the running of many nodes with a single command."[1] A launch description specifies what programs to run, where to run them, and what arguments to pass them. Applying ROS conventions such as names, namespaces and remappings allows the same component to be reused across different configurations.[1] Launch does more than start processes: it also monitors the state of the processes it launched and can report or react when that state changes.[1][2]

The second half of this lesson covers parameters, the settings that configure a node at startup and while it runs without changing its code.[3] Launch files and parameter files work together: the launch file decides which nodes run, and the parameter file decides how each one is tuned. On an industrial cell this is how one tested program can drive two identical robots, a simulated one and a real one, or a test bench and a production line, with only configuration changing.

Everything here targets ROS 2 Lyrical Luth, the long-term support release from May 2026, supported until May 2031.[4] The examples come from the official Lyrical tutorials, which in the Lyrical documentation tree live under Developer Tools → Launch and ROS Framework.[5][3]

02. From ROS 1 roslaunch to ROS 2 launch

ROS 1 had a tool called roslaunch. It read a static XML .launch file, started nodes locally or on remote machines over SSH, set values on the global Parameter Server, and could respawn processes that died. It handled large systems by composition with tags such as <include>, <group> and <machine>.[2]

The ROS 2 design article for the new launch system lists several reasons a straight copy would not work:[2]

  • Nodes are not processes: ROS 2 allows many nodes in one process, so "node" and "process" no longer mean the same thing.[2]
  • No global parameter server: in ROS 2 parameters are node specific, there are no truly global parameters, and the node itself manages them (it can even refuse a change).[2]
  • Richer reactions to events: ROS 1 could only respawn a dead process or shut everything down. ROS 2 aims to let users specify arbitrary responses to events.[2]
  • A programmatic API: besides static files, ROS 2 launch offers a more accessible programming interface.[2]

Some ideas carried over unchanged: launch still turns remapping and namespace settings into command-line arguments for each node, still manages complexity through includes and groups, and still aims to be portable across operating systems.[2] In ROS 2 the framework is the launch_ros package, which sits on top of the general-purpose, non-ROS-specific launch package.[5]

ROS 2 launch files can be written in Python, XML or YAML, and you run them with the ros2 launch command.[1] Which format should you choose? The official how-to says that for most applications "the choice of which ROS 2 launch format comes down to developer preference."[6] Python is the most flexible, because you can use the whole language and its libraries, and because launch itself is written in Python, so you get lower-level access to features that XML and YAML may not expose. The price is that a Python launch file "may be more complex and verbose."[6] The ROS 1 migration guide leans further toward the static formats, saying that "for typical use cases, XML and YAML should be preferred over Python."[7] This lesson teaches Python first, because it matches the rclpy track of this course, and shows the XML version alongside so you can read either.

If you ever port a ROS 1 file, the migration guide lists the main XML changes: on <node>, type becomes exec and ns becomes namespace; <param> can only appear inside a <node> because there is no global parameter concept; and <rosparam> is replaced by <param from="file.yaml"/>.[7]

03. Anatomy of a Python launch file

The official "Creating a launch file" tutorial builds a small system called turtlesim_mimic: two Turtlesim windows and a third node, mimic, that makes the second turtle copy whatever the first turtle does.[5] Here is the Python version exactly as the Lyrical documentation gives it:[5] 

from launch import LaunchDescription
from launch_ros.actions import Node


def generate_launch_description():
    return LaunchDescription([
        Node(
            package='turtlesim',
            namespace='turtlesim1',
            executable='turtlesim_node',
            name='sim',
            arguments=['--ros-args', '--log-level', 'info']
        ),
        Node(
            package='turtlesim',
            namespace='turtlesim2',
            executable='turtlesim_node',
            name='sim',
            ros_arguments=['--log-level', 'warn']
        ),
        Node(
            package='turtlesim',
            executable='mimic',
            name='mimic',
            remappings=[
                ('/input/pose', '/turtlesim1/turtle1/pose'),
                ('/output/cmd_vel', '/turtlesim2/turtle1/cmd_vel'),
            ]
        )
    ])

Read it from the outside in. A Python launch file must define a function called generate_launch_description() that returns a LaunchDescription; the ros2 launch command calls that function.[8] What does that function return? A LaunchDescription, which wraps a list of actions for the launch system to carry out. Here every action is a Node from launch_ros.actions.[8][5]

Each Node names the package and the executable to start (the same two words you would type after ros2 run), and can set a node name and a namespace.[5] Notice that both simulators are called sim. That is allowed only because they live in different namespaces, turtlesim1 and turtlesim2. The tutorial explains: "Unique namespaces allow the system to start two nodes without node name or topic name conflicts."[5] The full names become /turtlesim1/sim and /turtlesim2/sim, and each turtle's topics are prefixed the same way, for example /turtlesim1/turtle1/pose.

The two simulators also show the two ways to pass command-line options. The first uses arguments, which go straight to the executable, so ROS-specific options need the --ros-args flag in front. The second uses ros_arguments, which is designed for ROS arguments only, so the flag is not needed. The documentation recommends arguments when you mix ROS and non-ROS options, and ros_arguments for cleaner syntax when you only pass ROS options such as remappings, parameters or log levels.[5]

The third node does the interesting work. In the Turtlesim source code, mimic subscribes to a topic named input/pose (type turtlesim_msgs/msg/Pose) and publishes velocity commands on output/cmd_vel (type geometry_msgs/msg/Twist).[9] The remappings list connects those generic names to real topics: /input/pose becomes the first turtle's pose and /output/cmd_vel becomes the second turtle's velocity command. "In other words, turtlesim2 will mimic turtlesim1's movements."[5] This is the same remapping you met in lesson 4.4 with --ros-args --remap, written once in a file instead of typed every time.

04. Running the mimic system, and the same file in XML

You can run a launch file directly from its path, or from an installed package. The two forms are ros2 launch <path_to_launch_file> and ros2 launch <package_name> <launch_file_name>.[6][5] Save the code above as turtlesim_mimic_launch.py, source ROS 2, and run:[5] 

ros2 launch turtlesim_mimic_launch.py

Two Turtlesim windows open, and the terminal reports one line per process, such as [INFO] [turtlesim_node-1]: process started with pid [...], followed by [turtlesim_node-2] and [mimic-3].[5] To make the first turtle move, publish a velocity command to it from a second terminal:[5] 

ros2 topic pub -r 1 /turtlesim1/turtle1/cmd_vel geometry_msgs/msg/Twist "{linear: {x: 2.0, y: 0.0, z: 0.0}, angular: {x: 0.0, y: 0.0, z: -1.8}}"

You should see both turtles following the same path. Running ros2 run rqt_graph rqt_graph shows why: mimic subscribes to the pose published by /turtlesim1/sim and publishes to the cmd_vel topic that /turtlesim2/sim listens to.[5] Another way to test is to drive the first turtle with the keyboard, pushing the teleop node into the right namespace: ros2 run turtlesim turtle_teleop_key --ros-args --remap __ns:=/turtlesim1.[6]

Here is the identical system in XML, again verbatim from the tutorial:[5] 

<?xml version="1.0" encoding="UTF-8"?>
<launch>
  <node pkg="turtlesim" exec="turtlesim_node" name="sim" namespace="turtlesim1" args="--ros-args --log-level info" />
  <node pkg="turtlesim" exec="turtlesim_node" name="sim" namespace="turtlesim2" ros_args="--log-level warn" />
  <node pkg="turtlesim" exec="mimic" name="mimic">
    <remap from="/input/pose" to="/turtlesim1/turtle1/pose" />
    <remap from="/output/cmd_vel" to="/turtlesim2/turtle1/cmd_vel" />
  </node>
</launch>

The keywords map one to one: package becomes pkg, executable becomes exec, arguments becomes args, ros_arguments becomes ros_args, and each remapping tuple becomes a <remap from="..." to="..."/> tag. The YAML version uses the same keys with a remap: list of from/to pairs.[5] The large-projects tutorial calls the three formats "functionally equivalent", so once you can read one you can read the others.[10]

05. Installing launch files in a package

Running a launch file from a loose path is fine for experiments. For anything you want to keep, put it in a package. "By convention, all launch files for a package are stored in the launch directory inside of the package," at the top level, next to package.xml and setup.py.[8]

Placing the file there is not enough. When you build, colcon installs the files that the package lists into the workspace's install folder, and ros2 launch <package> <file> looks for launch files there.[10] For an ament_python package, such as the one you made in lesson 4.6, the documentation says: "To enable colcon to locate and utilize our launch files, we need to inform Python's setup tools of their presence."[8] You do that by adding an entry to data_files in setup.py:[8] 

import os
from glob import glob
# Other imports ...

package_name = 'py_launch_example'

setup(
    # Other parameters ...
    data_files=[
        # ... Other data files
        # Include all launch files.
        (os.path.join('share', package_name, 'launch'), glob('launch/*'))
    ]
)

Each entry is a pair: a destination folder under the install space (share/<package>/launch) and a list of source files. Parameter files need their own entry in the same list, for example (os.path.join('share', package_name, 'config'), glob('config/*.yaml')).[10] For a C++ ament_cmake package the equivalent is an install(DIRECTORY launch DESTINATION share/${PROJECT_NAME}/) command near the end of CMakeLists.txt, before ament_package().[8]

Three more rules from the documentation are worth following:

  • Name the file correctly: the _launch.py, _launch.xml and _launch.yaml suffixes are recommended but not required, but "the launch file name needs to end with launch.py to be recognized and autocompleted by ros2 launch."[8]
  • Declare the dependency: add <exec_depend>ros2launch</exec_depend> to package.xml, which makes sure the ros2 launch command is available after building and that all launch file formats are recognized.[5]
  • Build, then source: after colcon build succeeds and you have sourced the workspace, run ros2 launch py_launch_example my_script_launch.py.[8] The tutorials repeat the reminder to source the workspace after building, and to source ROS 2 in every new terminal.[11][5]

Because the build copies your files, an edit to src/.../launch/mimic_launch.py or to a YAML file has no effect until you build again (or until you build with --symlink-install, as described in lesson 4.4). Forgetting this is a very common source of confusion.

06. Launch arguments and substitutions

A launch file becomes far more useful when you can change it from the command line without editing it. ROS 2 does this with two tools that work together. A launch argument is declared with DeclareLaunchArgument, and its value is read with LaunchConfiguration.[11] Here is the pattern from the substitutions tutorial:[11] 

from launch.actions import DeclareLaunchArgument
from launch.substitutions import LaunchConfiguration
...
turtlesim_ns = LaunchConfiguration('turtlesim_ns')
...
DeclareLaunchArgument('turtlesim_ns', default_value='turtlesim1'),
Node(package='turtlesim', namespace=turtlesim_ns, executable='turtlesim_node', name='sim'),

LaunchConfiguration is a substitution. The documentation defines substitutions as "variables that are only evaluated during execution of the launch description," used to get information such as a launch configuration, an environment variable, or the result of a Python expression.[11] In other words, when Python reads your file, turtlesim_ns is not yet a string; it is a placeholder that the launch system fills in once it knows the argument's value. Note that the default is written as a string ('turtlesim1'); in the documentation's examples even numbers are passed to launch arguments as quoted strings.[11]

To set an argument when you launch, use name:=value after the file name, for example ros2 launch <package_name> <launch_file_name> background_r:=255.[6] To see which arguments a file accepts, add --show-args, which prints each argument with its description and default value:[11] 

Arguments (pass arguments as '<name>:=<value>'):
    'turtlesim_ns':
        no description given
        (default: 'turtlesim1')

In XML the same idea is written <arg name="background_r" default="0" /> and read with $(var background_r); in YAML it is an arg entry with a name and a default.[6]

Two other substitutions appear in almost every packaged launch file. FindPackageShare('pkg') finds the installed share folder of a package, and PathJoinSubstitution([...]) joins it with further folder and file names into a full path.[11] In XML and YAML the package lookup is written $(find-pkg-share pkg).[6] You will use these two in the hands-on task to locate your parameter file.

07. Larger systems: includes, namespaces and event handlers

Real robots are built from subsystems: drivers, perception, navigation, a user interface. The large-projects tutorial advises that "top-level launch files should be short, consist of includes to other files corresponding to subcomponents of the application, and commonly changed parameters."[10] The tool for this is IncludeLaunchDescription, which runs another launch file and can pass it arguments:[11] 

from launch import LaunchDescription
from launch.actions import IncludeLaunchDescription
from launch.substitutions import PathJoinSubstitution
from launch_ros.substitutions import FindPackageShare

def generate_launch_description():
    colors = {'background_r': '200'}
    return LaunchDescription([
        IncludeLaunchDescription(
            PathJoinSubstitution([
                FindPackageShare('launch_tutorial'),
                'launch',
                'example_substitutions_launch.py'
            ]),
            launch_arguments={
                'turtlesim_ns': 'turtlesim2',
                'use_provided_red': 'True',
                'new_background_r': colors['background_r'],
            }.items()
        )
    ])

Any of the three formats can include any other; in XML an include looks like <include file="$(find-pkg-share demo_nodes_cpp)/launch/topics/talker_listener_launch.py" />.[6]

To run a whole included file inside a namespace, wrap it in a GroupAction whose first action is PushROSNamespace('turtlesim2'), or in XML a <group> that starts with <push_ros_namespace namespace="turtlesim2" />. The order matters: "PushROSNamespace has to be the first action in the list for the following actions to apply the namespace."[10]

Finally, launch can react to what happens at runtime. Process start, output, completion and exit "are called events and can be handled by registering an event handler with the launch system."[12] The event handlers tutorial registers OnProcessStart, OnProcessIO, OnExecutionComplete, OnProcessExit and OnShutdown. One example shuts the whole launch down when the user closes the Turtlesim window:[12] 

RegisterEventHandler(
    OnProcessExit(
        target_action=turtlesim_node,
        on_exit=[
            LogInfo(msg=(EnvironmentVariable(name='USER'),
                    ' closed the turtlesim window')),
            EmitEvent(event=Shutdown(
                reason='Window closed'))
        ]
    )
),

The same idea matters on a factory floor: if a critical driver process dies, you usually want the rest of the system to stop cleanly rather than keep running with stale data.

08. Parameters belong to nodes

In ROS 2, "parameters ... are associated with individual nodes. Parameters are used to configure nodes at startup (and during runtime), without changing the code. The lifetime of a parameter is tied to the lifetime of the node."[3] Where are parameters stored in ROS 2? Not on a central server as in ROS 1, but on each individual node, which declares and manages its own parameters.[3][2] A parameter can be a bool, int64, float64, string, byte[], or an array of booleans, integers, floats or strings.[3]

"By default, a node needs to declare all of the parameters that it will accept during its lifetime."[3] In rclpy that looks like this:[13] 

self.declare_parameter('my_parameter', 'world')
my_param = self.get_parameter('my_parameter').get_parameter_value().string_value

The second argument to declare_parameter is the default value, which also fixes the parameter's type; changing a declared parameter's type at runtime fails unless it was declared with dynamic typing allowed.[13][3] If a node you write in lesson 4.6 should read a value from a YAML file, it must declare that parameter first.

Every node automatically offers services such as list_parameters, get_parameters and set_parameters, and the ros2 param command-line tool is built on them.[3] With a single Turtlesim running you can try the basic workflow:[14] 

ros2 param list
ros2 param get /turtlesim background_g
ros2 param set /turtlesim background_r 150
ros2 param dump /turtlesim > turtlesim.yaml
ros2 param load /turtlesim turtlesim.yaml

get prints a result such as Integer value is: 86, and set prints Set parameter successful and changes the background colour at once. A value set this way is lost when the node restarts.[14] dump saves all of the node's current parameters to a YAML file, and load applies a file to a running node. When loading at runtime, read-only entries such as qos_overrides.* fail with a "read-only" message; when the same file is given at node startup, all parameters are applied, including the read-only ones.[14]

A node can also guard its own parameters with callbacks. A pre-set callback can modify the list of parameters being set, an on-set callback can inspect a proposed change and explicitly reject it, and a post-set callback reacts after a change has been accepted.[3] That is how a motor driver could refuse a speed limit outside its safe range.

09. Parameter files and launch

A parameter file is a YAML file that sets parameters for one or more nodes. It is not a launch file; the large-projects tutorial stresses that it "is a configuration file for the turtlesim_node that sets parameters for the node."[10] Its structure is the node's fully qualified name, then the special key ros__parameters (with two underscores), then the values:[10] 

/turtlesim2/sim:
   ros__parameters:
      background_b: 255
      background_g: 86
      background_r: 150

In a YAML parameter file, what does the top-level key (for example /turtlesim2/sim) specify? The fully qualified name of the node, including its namespace, that the parameters under it apply to.[10] This is the most common trap: the tutorial shows that a third node, /turtlesim3/sim, loading the same file is not affected at all, because "its parameters are stored under another namespace."[10] The fix is a wildcard. "/** will assign all the parameters in every node, despite differences in node names and namespaces."[10] The command-line arguments guide gives the full rules: * matches a single name token between slashes, ** matches zero or more tokens, and partial matches such as foo* are not allowed. Nested YAML maps become dotted parameter names, such as some_lists.some_integers.[15]

There are three ways to hand a parameter file to a node. From the command line, use ros2 run ... --ros-args --params-file demo_params.yaml (or set a single value with -p name:=value).[15] In a Python launch file, put the file's path in the node's parameters list:[10] 

Node(
    package='turtlesim',
    executable='turtlesim_node',
    namespace='turtlesim2',
    name='sim',
    parameters=[PathJoinSubstitution([
        FindPackageShare('launch_tutorial'), 'config', 'turtlesim.yaml'])
    ],
),

In XML the same thing is a <param from="$(find-pkg-share launch_tutorial)/config/turtlesim.yaml" /> tag inside the <node>.[10] The parameters list can also hold plain dictionaries for quick inline values, such as parameters=[{'my_parameter': 'earth'}]; the parameters tutorial pairs this with output='screen', emulate_tty=True so the node's log messages appear in your console.[13] In XML, inline values are written <param name="..." value="..."/>, and the type is inferred from the text: value="1" is an integer, "1.0" a float, and "'1'" the string "1".[7]

You rarely need to type a parameter file from scratch. As the tutorial notes, "YAML files can be easily exported from the current ros2 param list": tune a running node with ros2 param set, then save the result with ros2 param dump.[10][14]

10. Common mistakes, and what is new in Lyrical

Most launch problems come from a small set of mistakes that the documentation itself warns about:

  • Files not installed: the launch or config folder is missing from data_files (or from install(DIRECTORY ...) in CMake), so ros2 launch or FindPackageShare cannot find it.[8][10]
  • Workspace not sourced: a new terminal does not know about your freshly built package until you source it.[11][12]
  • Wrong file name: a file that does not end in launch.py is not recognized or autocompleted by ros2 launch.[8]
  • Name collisions: two nodes with the same name and no distinct namespaces clash; unique namespaces avoid node and topic name conflicts.[5]
  • YAML keyed to the wrong node: a block for /turtlesim2/sim silently does nothing for any other node; check the full name with ros2 node list or use /**.[10]
  • Namespace pushed too late: PushROSNamespace must be the first action in its group.[10]
  • Include arguments without defaults: argument values only flow into an included file automatically for arguments that have a default there; required arguments must be passed explicitly.[7]

Lyrical Luth keeps the syntax taught above and adds a few conveniences. Launch files can now log at a chosen severity, with a level argument on log and new actions such as <log_warning message="..."/>.[4] XML and YAML files gain string-join and path-join substitutions, for example $(path-join opt ros lyrical $(string-join . setup bash)).[4] Parameter files accept YAML type tags such as string_param: !!str true or int_param: !!int 0, which fix cases where an ambiguous value was read as the wrong type.[4] On the command line, ros2 param get without a node name reads a parameter from all nodes,[14] and get and set can now handle several parameters in one call.[4] XML and YAML launch files can also pass arguments into an include with let; older distributions may require arg there instead, which matters when you read older tutorials.[16][10]

Try it
  1. In the src folder of your workspace, create a package with ros2 pkg create --build-type ament_python --license Apache-2.0 turtle_launch_demo, then add launch/ and config/ folders next to its setup.py, and add <exec_depend>ros2launch</exec_depend> to its package.xml. (You can add these files to your lesson 4.6 package instead if you prefer.)
  2. Save this parameter file as config/turtles.yaml. It is an example built from the documented format, so test it in the simulator before relying on it: 
    /turtlesim1/sim:
  ros__parameters:
    background_r: 150
    background_g: 86
    background_b: 255
/turtlesim2/sim:
  ros__parameters:
    background_r: 0
    background_g: 120
    background_b: 60
  3. Save this as launch/mimic_launch.py. It is the official turtlesim_mimic example with a parameters entry added to each simulator: 
    from launch import LaunchDescription
from launch.substitutions import PathJoinSubstitution
from launch_ros.actions import Node
from launch_ros.substitutions import FindPackageShare


def generate_launch_description():
    turtles_yaml = PathJoinSubstitution([
        FindPackageShare('turtle_launch_demo'), 'config', 'turtles.yaml'])
    return LaunchDescription([
        Node(package='turtlesim', namespace='turtlesim1',
             executable='turtlesim_node', name='sim',
             parameters=[turtles_yaml]),
        Node(package='turtlesim', namespace='turtlesim2',
             executable='turtlesim_node', name='sim',
             parameters=[turtles_yaml]),
        Node(package='turtlesim', executable='mimic', name='mimic',
             remappings=[
                 ('/input/pose', '/turtlesim1/turtle1/pose'),
                 ('/output/cmd_vel', '/turtlesim2/turtle1/cmd_vel'),
             ]),
    ])
  4. In setup.py, add import os and from glob import glob at the top, and add these two entries to the existing data_files list: 
    (os.path.join('share', package_name, 'launch'), glob('launch/*')),
(os.path.join('share', package_name, 'config'), glob('config/*.yaml')),
  5. From the workspace root, run colcon build --packages-select turtle_launch_demo, open a new terminal, run source install/setup.bash, then ros2 launch turtle_launch_demo mimic_launch.py. Two windows should open with different background colours.
  6. In another sourced terminal, publish the circle command from lesson 4.4 to /turtlesim1/turtle1/cmd_vel and check that the second turtle copies the first. Then confirm the parameters with ros2 param get /turtlesim2/sim background_g and ros2 param dump /turtlesim1/sim.
  7. Experiment: change the key /turtlesim2/sim to /turtlesim3/sim, rebuild and relaunch. What happens to the second window, and why? Then replace both blocks with one /** block and predict the result before you run it.
