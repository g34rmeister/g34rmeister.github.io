      4.7 Launch Files and Parameters

      Gerald Lê
      Chapter 4, lesson 7 of 10 ← Previous: 4.6 Writing Your First ROS 2 Package Next: 4.8 Moving an Arm with MoveIt 2 →

      01. Starting many nodes with one command

      Imagine starting a real robot by opening ten terminals and typing a command into each one. In lesson 4.4, you started Turtlesim and its keyboard controller by hand, one terminal per node. In lesson 4.6, you wrote your own package. That works for two or three nodes, but a real robot runs many programs at once.

      Robot Operating System 2 (ROS 2) splits a robot’s software into separate nodes working together. In everyday words, starting each node by hand does not scale. The ROS 2 documentation puts it this way: a system “typically consists of many nodes running across many different processes (and even different machines)”, and starting each one by hand “gets cumbersome quite quickly.”[1]

      The launch system solves this problem. In everyday words, a launch file lets you start your whole robot from one terminal. The documentation says it is “meant to automate the running of many nodes with a single command.”[1] A launch description lists what programs to run, where to run them, and what arguments to pass them. By using ROS conventions such as names, namespaces, and remappings, you can reuse the same component in different setups.[1] Launch also watches the processes it started. It can report or react when a process changes state, such as when a node exits.[1][2]

      The second half of this lesson covers parameters. Parameters are settings that configure a node at startup and while it runs, without changing its code.[3] Launch files and parameter files work together as a pair. The launch file picks which nodes run, and the parameter file tunes how each one behaves. On a factory floor, this lets one tested program drive two identical robots. You can run the same code on a simulated robot and a real one. You can also move from a test bench to a production line just by swapping settings.

      Everything here targets ROS 2 Lyrical Luth and its official tutorials.[4][5][3]

      For the curious: Lyrical Luth support window and documentation locations

      Lyrical Luth is the long-term support release from May 2026, supported until May 2031.[4] In the Lyrical documentation tree, the official launch tutorials live under Developer Tools → Launch, and the parameter concepts live under ROS Framework.[5][3]

      02. Choosing a launch format and why ROS 2 changed

      When you write a launch file in ROS 2, you can pick Python, Extensible Markup Language (XML), or YAML Ain’t Markup Language (YAML). You run any of the three formats with the same ros2 launch command.[1] Knowing why ROS 2 supports all three formats helps you pick one and read other people’s projects.

      Which format should you choose? In everyday words, there is no single winner, so pick the one that fits your task. The official how-to says that for most applications, “the choice of which ROS 2 launch format comes down to developer preference.”[6]

      Each format trades flexibility for simplicity. Python is the most flexible because you can use the whole language and its libraries. The launch tool itself is written in Python. That gives Python launch files low-level access to features that XML and YAML may not expose. The price is that a Python launch file “may be more complex and verbose.”[6]

      Meanwhile, the ROS 1 migration guide says that “for typical use cases, XML and YAML should be preferred over Python.”[7] This lesson teaches Python first because it matches the rclpy lessons in this chapter. It also shows the XML version alongside so you can read either format.

      Under the hood, ROS 2 uses the launch_ros package on top of the general-purpose, non-ROS-specific launch package.[5] Like older tools, launch still turns remapping and namespace settings into command-line arguments for each node. It also manages complexity through includes and groups, and aims to be portable across operating systems.[2]

      For the curious: how ROS 2 launch replaced ROS 1 roslaunch

      ROS 1 had a tool called roslaunch. It read a static XML .launch file and started nodes locally or on remote machines over Secure Shell (SSH). It also set values on the global Parameter Server and could respawn processes that died. It handled large systems by composition with tags such as <include>, <group>, and <machine>.[2]

      The ROS 2 design article for the new launch system lists several reasons a straight copy would not work:[2]

      • Nodes are not processes: ROS 2 allows many nodes in one process, so “node” and “process” no longer mean the same thing.[2]
      • No global parameter server: in ROS 2, parameters are node specific. There are no truly global parameters, and the node itself manages them (it can even refuse a change).[2]
      • Richer reactions to events: ROS 1 could only respawn a dead process or shut everything down. ROS 2 aims to let users specify arbitrary responses to events.[2]
      • A programmatic application programming interface (API): besides static files, ROS 2 launch offers a more accessible programming interface.[2]

      If you ever port a ROS 1 file, the migration guide lists the main XML changes. On <node>, type becomes exec and ns becomes namespace. In addition, <param> can only appear inside a <node> because there is no global parameter concept. Finally, <rosparam> is replaced by <param from="file.yaml"/>.[7]

      03. Reading your first Python launch file

      Suppose you want two Turtlesim windows open at once, with the second turtle copying the first turtle’s path. Opening three terminals and typing every remap flag by hand would take too long. A single Python launch file starts all three nodes and wires them together in one step.

      The official “Creating a launch file” tutorial builds a small system called turtlesim_mimic. It uses two Turtlesim windows and a third node, mimic, that makes the second turtle copy whatever the first turtle does.[5] Here is the Python version exactly as the Lyrical documentation gives it:[5] 

      from launch import LaunchDescription
from launch_ros.actions import Node


def generate_launch_description():
    return LaunchDescription([
        Node(
            package='turtlesim',
            namespace='turtlesim1',
            executable='turtlesim_node',
            name='sim',
            arguments=['--ros-args', '--log-level', 'info']
        ),
        Node(
            package='turtlesim',
            namespace='turtlesim2',
            executable='turtlesim_node',
            name='sim',
            ros_arguments=['--log-level', 'warn']
        ),
        Node(
            package='turtlesim',
            executable='mimic',
            name='mimic',
            remappings=[
                ('/input/pose', '/turtlesim1/turtle1/pose'),
                ('/output/cmd_vel', '/turtlesim2/turtle1/cmd_vel'),
            ]
        )
    ])

      Read it from the outside in. Every Python launch file must define a function called generate_launch_description(). When you run ros2 launch, ROS 2 calls that function.[8] It returns a LaunchDescription, which wraps a list of actions for the launch system to carry out. Here every action is a Node from launch_ros.actions.[8][5]

      Each Node names the package and the executable to start, the same two words you type after ros2 run. It can also set a node name and a namespace.[5] Notice that both simulators are called sim. That is allowed only because they live in different namespaces, turtlesim1 and turtlesim2. In everyday words, a namespace adds a unique prefix so two copies do not collide. The tutorial puts it this way: “Unique namespaces allow the system to start two nodes without node name or topic name conflicts.”[5] The full node names become /turtlesim1/sim and /turtlesim2/sim. Each turtle’s topics get the same prefix, such as /turtlesim1/turtle1/pose.

      The two simulators also show two ways to pass command-line options. The first uses arguments, which go straight to the executable. Because of that, ROS-specific options need the --ros-args flag in front. The second uses ros_arguments, which is built only for ROS options and drops that flag. The documentation recommends arguments when you mix ROS and non-ROS options. It recommends ros_arguments for cleaner syntax when you only pass ROS options like remappings, parameters, or log levels.[5]

      The third node, mimic, does the interesting work. In the Turtlesim source code, mimic subscribes to a topic named input/pose (type turtlesim_msgs/msg/Pose). It publishes velocity commands on output/cmd_vel (type geometry_msgs/msg/Twist).[9] The remappings list connects those generic names to real topics. Here /input/pose becomes the first turtle’s pose, and /output/cmd_vel becomes the second turtle’s velocity command. “In other words, turtlesim2 will mimic turtlesim1's movements.”[5] This is the same remapping you met in lesson 4.4 with --ros-args --remap, written once in a file instead of typed every time.

      04. Running the launch file and reading XML

      Once you write a launch file, you can run it straight from its file path to test it quickly. You can also write the same system in XML, which many ROS 2 projects use for simpler setups. Reading both formats side by side makes it easy to switch between them later.

      You can run a launch file from its path or from an installed package. The two forms are ros2 launch <path_to_launch_file> and ros2 launch <package_name> <launch_file_name>.[6][5] Save the code above as turtlesim_mimic_launch.py, source ROS 2, and run:[5] 

      ros2 launch turtlesim_mimic_launch.py

      Two Turtlesim windows open at once. The terminal prints one line per process, such as [INFO] [turtlesim_node-1]: process started with pid [...], followed by [turtlesim_node-2] and [mimic-3].[5] To make the first turtle move, publish a velocity command to it from a second terminal:[5] 

      ros2 topic pub -r 1 /turtlesim1/turtle1/cmd_vel geometry_msgs/msg/Twist "{linear: {x: 2.0, y: 0.0, z: 0.0}, angular: {x: 0.0, y: 0.0, z: -1.8}}"

      Both turtles should follow the same path. Running ros2 run rqt_graph rqt_graph shows why. It displays mimic subscribing to the pose published by /turtlesim1/sim and publishing to the cmd_vel topic that /turtlesim2/sim listens to.[5] Another way to test is to drive the first turtle with your keyboard. Push the teleop node into the right namespace: ros2 run turtlesim turtle_teleop_key --ros-args --remap __ns:=/turtlesim1.[6]

      Here is the identical system in XML, again verbatim from the tutorial:[5] 

      <?xml version="1.0" encoding="UTF-8"?>
<launch>
  <node pkg="turtlesim" exec="turtlesim_node" name="sim" namespace="turtlesim1" args="--ros-args --log-level info" />
  <node pkg="turtlesim" exec="turtlesim_node" name="sim" namespace="turtlesim2" ros_args="--log-level warn" />
  <node pkg="turtlesim" exec="mimic" name="mimic">
    <remap from="/input/pose" to="/turtlesim1/turtle1/pose" />
    <remap from="/output/cmd_vel" to="/turtlesim2/turtle1/cmd_vel" />
  </node>
</launch>

      The keywords map one to one. In XML, package becomes pkg, and executable becomes exec. Likewise, arguments becomes args, and ros_arguments becomes ros_args. Each remapping tuple becomes a <remap from="..." to="..."/> tag. The YAML version uses the same keys with a remap: list of from and to pairs.[5] The large-projects tutorial calls the three formats “functionally equivalent”.[10] Once you can read one format, you can read the others.

      The launch tree needs JavaScript. With it on, you can toggle launch arguments and see which parameter values survive a node restart.

      05. Putting launch files inside a package

      Running a launch file by typing its full file path works for quick experiments, but it gets messy fast. Putting launch files inside a ROS 2 package lets you start them from anywhere using the package name. To make that work, you must save the file in the right folder and tell the build tool to install it.

      “By convention, all launch files for a package are stored in the launch directory inside of the package”, at the top level next to package.xml and setup.py.[8]

      Placing the file there is not enough. When you build, colcon installs listed files into the workspace’s install folder. That install folder is where ros2 launch <package> <file> looks for launch files.[10] In everyday words, Python packages do not copy extra folders unless you list them in setup.py. For an ament_python package like the one you made in lesson 4.6, the documentation puts it this way: “To enable colcon to locate and utilize our launch files, we need to inform Python's setup tools of their presence.”[8] You do that by adding an entry to data_files in setup.py:[8] 

      import os
from glob import glob
# Other imports ...

package_name = 'py_launch_example'

setup(
    # Other parameters ...
    data_files=[
        # ... Other data files
        # Include all launch files.
        (os.path.join('share', package_name, 'launch'), glob('launch/*'))
    ]
)

      Each entry in data_files is a pair. The first item is a destination folder under the install space (share/<package>/launch), and the second item is a list of source files. Parameter files need their own entry in the same list, for example (os.path.join('share', package_name, 'config'), glob('config/*.yaml')).[10]

      Three more rules from the documentation are worth following:

      • Name the file correctly: the _launch.py, _launch.xml, and _launch.yaml suffixes are recommended, though not required. However, “the launch file name needs to end with launch.py to be recognized and autocompleted by ros2 launch.”[8]
      • Declare the dependency: add <exec_depend>ros2launch</exec_depend> to package.xml. That makes sure the ros2 launch command is available after building and recognizes all launch file formats.[5]
      • Build, then source: after colcon build succeeds and you source the workspace, run ros2 launch py_launch_example my_script_launch.py.[8] The tutorials repeat the reminder to source the workspace after building, and to source ROS 2 in every new terminal.[11][5]

      Remember that the build copies your files. An edit to src/.../launch/mimic_launch.py or to a YAML file has no effect until you build again. Alternatively, you can build with --symlink-install, as described in lesson 4.4.

      For the curious: installing launch files in a C++ (ament_cmake) package

      For a C++ ament_cmake package, the equivalent of adding to data_files is an install(DIRECTORY launch DESTINATION share/${PROJECT_NAME}/) command near the end of CMakeLists.txt, before ament_package().[8]

      06. Passing arguments into launch files

      Suppose you want to launch Turtlesim in a different namespace or with a different background color without editing your launch file. Launch arguments let you change settings right from the command line when you run ros2 launch. You declare what inputs the file accepts, and ROS 2 fills them in when the launch starts.

      ROS 2 does this with two tools that work together. You declare a launch argument with DeclareLaunchArgument, and you read its value with LaunchConfiguration.[11] Here is the pattern from the substitutions tutorial:[11] 

      from launch.actions import DeclareLaunchArgument
from launch.substitutions import LaunchConfiguration
...
turtlesim_ns = LaunchConfiguration('turtlesim_ns')
...
DeclareLaunchArgument('turtlesim_ns', default_value='turtlesim1'),
Node(package='turtlesim', namespace=turtlesim_ns, executable='turtlesim_node', name='sim'),

      LaunchConfiguration is a substitution. In everyday words, a substitution is a placeholder that waits until launch time to get its value. The documentation defines substitutions as “variables that are only evaluated during execution of the launch description,” used to get information such as a launch configuration, an environment variable, or the result of a Python expression.[11] When Python reads your file, turtlesim_ns is not yet a string. It is a placeholder that the launch system fills in once it knows the argument’s value. Note that the default is written as a string ('turtlesim1'). In the documentation’s examples, even numbers are passed to launch arguments as quoted strings.[11]

      To set an argument when you launch, write name:=value after the file name, for example ros2 launch <package_name> <launch_file_name> background_r:=255.[6] To see which arguments a file accepts, add --show-args. It prints each argument with its description and default value:[11] 

      Arguments (pass arguments as '<name>:=<value>'):
    'turtlesim_ns':
        no description given
        (default: 'turtlesim1')

      Two other substitutions appear in almost every packaged launch file. FindPackageShare('pkg') finds the installed share folder of a package. PathJoinSubstitution([...]) joins it with further folder and file names into a full path.[11] You will use these two in the hands-on task to locate your parameter file.

      For the curious: launch arguments and package lookups in XML and YAML

      In XML, the same argument idea is written <arg name="background_r" default="0" /> and read with $(var background_r). In YAML, it is an arg entry with a name and a default.[6] In both XML and YAML, the package lookup is written $(find-pkg-share pkg).[6]

      07. Combining launch files and reacting to events

      Real robots are built from subsystems such as drivers, perception, navigation, and a user interface. Putting every node into one giant launch file quickly becomes hard to read and maintain. Instead, you can split subsystems into separate files, group them under namespaces, and react if a process stops.

      In everyday words, your top-level launch file should act like a short index that pulls in smaller files. The large-projects tutorial advises that “top-level launch files should be short, consist of includes to other files corresponding to subcomponents of the application, and commonly changed parameters.”[10] The tool for this is IncludeLaunchDescription, which runs another launch file and can pass it arguments:[11] 

      from launch import LaunchDescription
from launch.actions import IncludeLaunchDescription
from launch.substitutions import PathJoinSubstitution
from launch_ros.substitutions import FindPackageShare

def generate_launch_description():
    colors = {'background_r': '200'}
    return LaunchDescription([
        IncludeLaunchDescription(
            PathJoinSubstitution([
                FindPackageShare('launch_tutorial'),
                'launch',
                'example_substitutions_launch.py'
            ]),
            launch_arguments={
                'turtlesim_ns': 'turtlesim2',
                'use_provided_red': 'True',
                'new_background_r': colors['background_r'],
            }.items()
        )
    ])

      Any of the three formats can include any other.[6] To run a whole included file inside a namespace, wrap it in a GroupAction whose first action is PushROSNamespace('turtlesim2'). The order matters: “PushROSNamespace has to be the first action in the list for the following actions to apply the namespace.”[10]

      Finally, launch can react to what happens at runtime. When a process starts, prints output, finishes, or exits, ROS 2 treats that moment as an event. Process start, output, completion, and exit “are called events and can be handled by registering an event handler with the launch system.”[12] One example shuts the whole launch down when the user closes the Turtlesim window:[12] 

      RegisterEventHandler(
    OnProcessExit(
        target_action=turtlesim_node,
        on_exit=[
            LogInfo(msg=(EnvironmentVariable(name='USER'),
                    ' closed the turtlesim window')),
            EmitEvent(event=Shutdown(
                reason='Window closed'))
        ]
    )
),

      When turtlesim_node exits, OnProcessExit logs who closed the window and emits a Shutdown event. The same idea matters on a factory floor: if a critical driver process dies, you usually want the rest of the system to stop cleanly rather than keep running with stale data.

      For the curious: XML includes, namespaces, and the five event types

      In XML, an include looks like <include file="$(find-pkg-share demo_nodes_cpp)/launch/topics/talker_listener_launch.py" />.[6] To push a namespace in XML, use a <group> that starts with <push_ros_namespace namespace="turtlesim2" />.[10]

      The event handlers tutorial registers five event types: OnProcessStart, OnProcessIO, OnExecutionComplete, OnProcessExit, and OnShutdown.[12]

      08. Parameters belong to nodes

      Suppose you want to change a Turtlesim window’s background color or adjust a motor driver’s speed limit without editing code. In ROS 2, you do that with parameters. Unlike ROS 1, which kept settings on one central server, ROS 2 stores each node’s settings inside the node itself.

      In everyday words, parameters are named settings that live inside a node while it runs. The documentation puts it this way: “parameters ... are associated with individual nodes. Parameters are used to configure nodes at startup (and during runtime), without changing the code. The lifetime of a parameter is tied to the lifetime of the node.”[3] Because there is no central server as in ROS 1, each individual node declares and manages its own parameters.[3][2]

      Before a node can use a parameter, it normally has to announce its name and starting value. As the documentation explains, “By default, a node needs to declare all of the parameters that it will accept during its lifetime.”[3] In rclpy, that looks like this:[13] 

      self.declare_parameter('my_parameter', 'world')
my_param = self.get_parameter('my_parameter').get_parameter_value().string_value

      The second argument to declare_parameter is the default value, which also fixes the parameter’s type. Changing a declared parameter’s type at runtime fails unless it was declared with dynamic typing allowed.[13][3] If a node you write in lesson 4.6 should read a value from a YAML file, it must declare that parameter first.

      Every node automatically offers services such as list_parameters, get_parameters, and set_parameters. The ros2 param command-line tool is built on those services.[3] With a single Turtlesim running, you can try the basic workflow:[14] 

      ros2 param list
ros2 param get /turtlesim background_g
ros2 param set /turtlesim background_r 150
ros2 param dump /turtlesim > turtlesim.yaml
ros2 param load /turtlesim turtlesim.yaml

      get prints a result such as Integer value is: 86. set prints Set parameter successful and changes the background color at once. A value set this way is lost when the node restarts.[14]

      dump saves all of the node’s current parameters to a YAML file, and load applies a file to a running node. When loading at runtime, read-only entries such as qos_overrides.* fail with a “read-only” message. When you give the same file at node startup, all parameters are applied, including the read-only ones.[14]

      A node can also guard its own parameters with callbacks. That is how a motor driver could refuse a speed limit outside its safe range.[3]

      For the curious: parameter data types and parameter callbacks

      A parameter can be a bool, int64, float64, string, byte[], or an array of booleans, integers, floats, or strings.[3]

      Nodes can attach three kinds of parameter callbacks. A pre-set callback can modify the list of parameters being set. An on-set callback can inspect a proposed change and explicitly reject it. A post-set callback reacts after a change has been accepted.[3]

      09. Saving and loading parameter files

      Typing ros2 param set every time you launch your robot gets tedious fast. Instead, you can save your settings in a YAML parameter file and load them automatically at startup. Keeping settings in a config file lets you tune your robot without editing code.

      A parameter file is not a launch file. The large-projects tutorial stresses that it “is a configuration file for the turtlesim_node that sets parameters for the node.”[10] Its structure starts with the node’s fully qualified name, then the special key ros__parameters (with two underscores), then the values:[10] 

      /turtlesim2/sim:
   ros__parameters:
      background_b: 255
      background_g: 86
      background_r: 150

      In a YAML parameter file, what does the top-level key (for example /turtlesim2/sim) specify? It specifies the fully qualified name of the node, including its namespace, that the parameters under it apply to.[10] This is easy to get wrong. Suppose a third node, /turtlesim3/sim, loads the same file. It is not affected at all, because “its parameters are stored under another namespace.”[10]

      The fix is a wildcard. As the tutorial explains, “/** will assign all the parameters in every node, despite differences in node names and namespaces.”[10]

      There are three ways to hand a parameter file to a node. From the command line, use ros2 run ... --ros-args --params-file demo_params.yaml (or set a single value with -p name:=value).[15] In a Python launch file, put the file’s path in the node’s parameters list:[10] 

      Node(
    package='turtlesim',
    executable='turtlesim_node',
    namespace='turtlesim2',
    name='sim',
    parameters=[PathJoinSubstitution([
        FindPackageShare('launch_tutorial'), 'config', 'turtlesim.yaml'])
    ],
),

      The parameters list can also hold plain dictionaries for quick inline values, such as parameters=[{'my_parameter': 'earth'}]. The parameters tutorial pairs this with output='screen', emulate_tty=True so the node’s log messages appear in your console.[13]

      You rarely need to type a parameter file from scratch. As the tutorial notes, “YAML files can be easily exported from the current ros2 param list”. Tune a running node with ros2 param set, then save the result with ros2 param dump.[10][14]

      For the curious: wildcard rules, nested keys, and XML parameter tags

      The command-line arguments guide gives the full wildcard rules. A single * matches one name token between slashes, while ** matches zero or more tokens. Partial matches such as foo* are not allowed. Nested YAML maps become dotted parameter names, such as some_lists.some_integers.[15]

      In XML, loading a parameter file is written as a <param from="$(find-pkg-share launch_tutorial)/config/turtlesim.yaml" /> tag inside the <node>.[10] Inline values in XML are written <param name="..." value="..."/>, and the type is inferred from the text: value="1" is an integer, "1.0" a float, and "'1'" the string “1”.[7]

      10. Common mistakes, and what is new in Lyrical

      When a launch file fails to start or silently ignores your settings, it is usually one of a few common slip-ups. Checking this short list saves you from guessing why a node did not run or why a color did not change. If you read older ROS 2 tutorials online, it also helps to know a few shortcuts added in Lyrical Luth.

      Most launch problems come from a small set of mistakes that the documentation itself warns about:

      • Files not installed: the launch or config folder is missing from data_files (or from install(DIRECTORY ...) in CMake). Because of that, ros2 launch or FindPackageShare cannot find it.[8][10]
      • Workspace not sourced: a new terminal does not know about your freshly built package until you source it.[11][12]
      • Wrong file name: a file that does not end in launch.py is not recognized or autocompleted by ros2 launch.[8]
      • Name collisions: two nodes with the same name and no distinct namespaces clash. Unique namespaces avoid node and topic name conflicts.[5]
      • YAML keyed to the wrong node: a block for /turtlesim2/sim silently does nothing for any other node. Check the full name with ros2 node list, or use /**.[10]
      • Namespace pushed too late: PushROSNamespace must be the first action in its group.[10]
      • Include arguments without defaults: argument values only flow into an included file automatically for arguments that have a default there. Required arguments must be passed explicitly.[7]

      Lyrical Luth keeps the syntax taught above and adds a few conveniences. On the command line, ros2 param get without a node name reads a parameter from all nodes,[14] and get and set can now handle several parameters in one call.[4] Launch files also gain severity logging, new string and path substitutions, and explicit YAML type tags.[4]

      For the curious: new launch and parameter syntax in Lyrical Luth

      Launch files can now log at a chosen severity, with a level argument on log and new actions such as <log_warning message="..."/>.[4] XML and YAML files gain string-join and path-join substitutions, for example $(path-join opt ros lyrical $(string-join . setup bash)).[4]

      Parameter files accept YAML type tags such as string_param: !!str true or int_param: !!int 0, which fix cases where an ambiguous value was read as the wrong type.[4] XML and YAML launch files can also pass arguments into an include with let. Older distributions may require arg there instead, which matters when you read older tutorials.[16][10]

      Try it
      1. In the src folder of your workspace, create a package with ros2 pkg create --build-type ament_python --license Apache-2.0 turtle_launch_demo. Next, add launch/ and config/ folders next to its setup.py, and add <exec_depend>ros2launch</exec_depend> to its package.xml. (You can add these files to your lesson 4.6 package instead if you prefer.)
      2. Save this parameter file as config/turtles.yaml. It is an example built from the documented format, so test it in the simulator before relying on it: 
        /turtlesim1/sim:
  ros__parameters:
    background_r: 150
    background_g: 86
    background_b: 255
/turtlesim2/sim:
  ros__parameters:
    background_r: 0
    background_g: 120
    background_b: 60
      3. Save this as launch/mimic_launch.py. It is the official turtlesim_mimic example with a parameters entry added to each simulator: 
        from launch import LaunchDescription
from launch.substitutions import PathJoinSubstitution
from launch_ros.actions import Node
from launch_ros.substitutions import FindPackageShare


def generate_launch_description():
    turtles_yaml = PathJoinSubstitution([
        FindPackageShare('turtle_launch_demo'), 'config', 'turtles.yaml'])
    return LaunchDescription([
        Node(package='turtlesim', namespace='turtlesim1',
             executable='turtlesim_node', name='sim',
             parameters=[turtles_yaml]),
        Node(package='turtlesim', namespace='turtlesim2',
             executable='turtlesim_node', name='sim',
             parameters=[turtles_yaml]),
        Node(package='turtlesim', executable='mimic', name='mimic',
             remappings=[
                 ('/input/pose', '/turtlesim1/turtle1/pose'),
                 ('/output/cmd_vel', '/turtlesim2/turtle1/cmd_vel'),
             ]),
    ])
      4. In setup.py, add import os and from glob import glob at the top, and add these two entries to the existing data_files list: 
        (os.path.join('share', package_name, 'launch'), glob('launch/*')),
(os.path.join('share', package_name, 'config'), glob('config/*.yaml')),
      5. From the workspace root, run colcon build --packages-select turtle_launch_demo, open a new terminal, run source install/setup.bash, then ros2 launch turtle_launch_demo mimic_launch.py. Two windows should open with different background colors.
      6. In another sourced terminal, publish the circle command from lesson 4.4 to /turtlesim1/turtle1/cmd_vel and check that the second turtle copies the first. Then confirm the parameters with ros2 param get /turtlesim2/sim background_g and ros2 param dump /turtlesim1/sim.
      7. Experiment: change the key /turtlesim2/sim to /turtlesim3/sim, rebuild and relaunch. What happens to the second window, and why? Then replace both blocks with one /** block and predict the result before you run it.
