6.2 Capstone: ROS 2 Pick-and-Place with MoveIt 2

Gerald Lê

01. What you will build and why

In this capstone you will program a simulated Universal Robots arm to pick up an object from a table and put it down somewhere else, using ROS 2 and MoveIt 2. The arm never touches real hardware. It runs on ros2_control mock hardware, and if you want physics you can move it into Gazebo. The planning is done with the MoveIt Task Constructor (MTC), which breaks a pick-and-place job into a chain of small, inspectable steps called stages.

You do not start from a blank page. The official MoveIt 2 tutorial "Pick and Place with MoveIt Task Constructor" is a complete, staged pipeline: it reads the current state, opens the hand, approaches, generates grasp poses and solves inverse kinematics for them, allows contact with the object, attaches it, lifts, generates place poses, detaches, retreats and returns home.[1] The catch is that the tutorial uses the Franka Panda robot.[1] Your job is to get that pipeline working as-is, then move it onto a UR5e, add your own planning scene, and show with evidence how reliable it is.

Pick and place is the "hello world" of industrial manipulation. It pulls together most of the ROS chapter (workspaces, launch files, robot descriptions, ros2_control, MoveIt and RViz), and it has a clear pass or fail result that you can test and measure.

This page is a project brief, not a lecture. Read all of it, including the rubric, before you write any code. Teaching guidance on project work recommends sharing the criteria and rubric when the project starts, not at the end, so you know what "good" looks like while you still have time to aim for it.[2]

02. Prerequisites

If one of these lessons feels shaky, revisit it first.

  • 3.3 Installing ROS: a working ROS 2 install that you can source in every terminal (see 3.3).
  • 3.6 Your first package: creating a workspace, cloning packages into src, running rosdep and colcon build (see 3.6).
  • 3.7 Launch files and parameters: reading a launch file, passing launch arguments such as ur_type:=ur5e, and knowing which nodes a launch starts (see 3.7).
  • 3.8 MoveIt 2: the URDF and SRDF, planning groups, the planning scene, mock hardware, and bringing up a UR5e with MoveIt in RViz (see 3.8). This is the most important prerequisite.
  • 3.9 Vendor drivers: what the UR ROS 2 driver does and how URSim fits in (see 3.9).
  • 2.8 Vision-guided picking: the idea of a grasp pose relative to an object, approach and retreat moves, and why the pick pose comes from somewhere else in a real cell (see 2.8).

You will also read and edit C++. The MTC tutorial node, mtc_node.cpp, is written in C++, so be ready to work in that language even if you write most of your other ROS code in Python.[3]

03. Equipment and software

Everything here is free software and runs on one Linux computer or virtual machine. You need no robot.

  • ROS 2 and MoveIt 2: the same install you used in 3.8.
  • MoveIt Task Constructor: built from source in your workspace. The tutorial says to clone moveit_task_constructor on the humble branch for ROS 2 Humble, or on the ros2 branch to build against MoveIt 2 main, then run rosdep and colcon build.[1] The tutorial names only these two branches, so check the repository's branch list for your ROS 2 release before you clone.
  • The UR ROS 2 driver and MoveIt config: ur_robot_driver and ur_moveit_config, as in 3.8. The driver can run against ros2_control mock hardware or against URSim, and from the driver's point of view the two are equivalent.[4]
  • Optional, Gazebo: the separate ur_simulation_gz package (repository Universal_Robots_ROS2_GZ_Simulation). Its branches are humble, jazzy (also used for Kilted) and ros2 (for Lyrical and Rolling).[5] Gazebo Classic and GZ Sim support live in separate packages from the driver itself.[4]
  • Optional, URSim: Universal Robots' simulator in Docker. With URSim running, the driver connects with ros2 launch ur_robot_driver ur_control.launch.py ur_type:=ur5e robot_ip:=192.168.56.101 launch_rviz:=true.[4] It is not needed for the core project.

Choosing mock hardware or Gazebo. Start with mock hardware: it is the lightest option and enough to test planning and the MTC stage chain. Know its limits. UR's simulation page lists that on mock hardware there is no TCP pose broadcaster, the passthrough trajectory controller and force mode do not work, and the GPIO controller reports a failure when you try to set I/O.[4] So if you planned to open and close a gripper through UR digital outputs, you cannot check that in mock mode.[4] Gazebo adds a physics simulation and comes with its own MoveIt launch (milestone 4).[5]

04. Milestones and what to hand in

Complex project work is easier to manage, and to grade fairly, when it is split into milestones such as a plan, a prototype and a progress briefing.[2] Each milestone below has a short, concrete hand-in. Hand them in as you go, not all at the end. If you work in a team, add a short contribution statement to every hand-in that says who did what. Teaching guidance recommends collecting individual evidence of this kind alongside the team product, and grading group, individual, process and product parts separately.[2] One engineering capstone used milestone evaluations for exactly this purpose: to keep each team member accountable to the group.[6]

Milestone Goal Hand in
M0 Plan and baseline Build MTC and run the Panda pick-and-place demo unchanged. One-page plan (scope, risks, test plan), a screenshot of the demo's stage tree in RViz, and a short reflection.
M1 UR5e moves Bring up a UR5e on mock hardware with MoveIt and plan joint and pose goals in RViz. Screenshots of one joint goal and one pose goal planned and executed; the exact launch commands you used.
M2 Planning scene Add a table and a box or cylinder as collision objects. Screenshot of the scene; a plan that moves around the table instead of through it.
M3 MTC on the UR Port the MTC node to UR group and frame names and complete a full pick and place. Your source code in a Git repository, a stage tree screenshot, and a screen recording of one full run.
M4 Gazebo (optional) Run the same task through the Gazebo MoveIt launch. Screen recording and a note on anything that behaved differently from mock hardware.
M5 Test evidence and report Measure success over many runs with randomised object poses and analyse failures. Test table, failure analysis, final report (3 to 5 pages) and final reflection.

This structure (a plan, working subsystems, an integrated demo, test evidence and a written report) mirrors capstones described in the engineering education literature, where students wrote specifications, planned milestones, gave oral presentations and wrote a final report.[7]

05. M0: run the Panda demo and read the stage tree

Begin with code that is known to work. Clone moveit_task_constructor into the src folder of your workspace on the right branch, install dependencies and build:[1] 

cd ~/ws_moveit/src
git clone https://github.com/moveit/moveit_task_constructor.git -b ros2
cd ~/ws_moveit
rosdep install --from-paths src --ignore-src -r -y
colcon build
source install/setup.bash

Use -b humble instead if you are on Humble.[1] Then start the demo environment in one terminal and the pick-and-place demo in a second one:[1] 

# Terminal 1: move_group, ros2_control, RViz and the robot
ros2 launch moveit_task_constructor_demo demo.launch.py

# Terminal 2: the pick-and-place task
ros2 launch moveit_task_constructor_demo run.launch.py exe:=pick_place_demo

The first launch file starts move_group, ros2_control, a static TF publisher, robot_state_publisher and RViz.[1] In RViz, add the Motion Planning Tasks display and set its Task Solution Topic to /solution.[1] You can now click on each stage to see its successful and failed solutions and their costs.[1] Take your stage-tree screenshot here.

How MTC thinks. MTC splits a task into stages of three kinds.[1] Generators create states on their own (the current state, candidate grasp poses). Propagators take a neighbour's state and push it forward or backward ("move 10 cm up"). Connectors plan a free motion between two states that already exist. Stages can be grouped in containers: wrappers, serial containers and parallel containers.[1] MTC also has three planners (solvers) a stage can use: a Cartesian planner for straight-line moves, joint interpolation for simple moves, and the full planning pipeline (OMPL). The tutorial uses joint interpolation for the simple hand move.[1]

The tutorial's task is this sequence of stages:[1]

  1. CurrentState: start from where the robot is now.
  2. MoveTo "open hand", to the named SRDF pose open.
  3. Connect: plan a free move to the pre-grasp area.
  4. "approach object": a MoveRelative of between 0.1 and 0.15 m.
  5. GenerateGraspPose, wrapped in ComputeIK (up to 8 IK solutions).
  6. ModifyPlanningScene: allow collisions between hand and object.
  7. Close the hand.
  8. ModifyPlanningScene: attachObject("object", hand_frame).
  9. "lift object": a MoveRelative of between 0.1 and 0.3 m.
  10. GeneratePlacePose plus ComputeIK.
  11. Open the hand.
  12. allowCollisions(..., false): forbid hand and object contact again.
  13. detachObject("object", hand_frame).
  14. Retreat.
  15. MoveTo "return home".

In your M0 reflection, label each stage as a generator, propagator or connector, and say in one sentence why the grasp pose generator has to be wrapped in ComputeIK. (Hint: a grasp pose is a pose for the hand in space. The planner needs joint angles.)

06. M1 and M2: a UR5e and its planning scene

M1. Bring up the UR5e on mock hardware with MoveIt exactly as you did in 3.8, with the driver in one terminal and ur_moveit_config in another, using the same ur_type in both. In RViz, drag the interactive marker to plan a pose goal, then pick a named state for a joint goal, and execute both. Record the exact commands in your hand-in.

M2. Now give the robot something to work with. The MTC tutorial adds a cylinder to the planning scene as a collision object, and it shows that if you move the cylinder out of the robot's reach, planning fails.[1] Add two objects: a flat box for the table and a small box or cylinder for the part. The snippet below follows the pattern of the tutorial node. It is an example: try it in simulation first, and set the sizes, positions and frame_id to match your own scene (check the Fixed Frame in RViz). 

moveit_msgs::msg::CollisionObject object;
object.id = "object";
object.header.frame_id = "world";          // use your scene's fixed frame
object.primitives.resize(1);
object.primitives[0].type = shape_msgs::msg::SolidPrimitive::CYLINDER;
object.primitives[0].dimensions = { 0.10, 0.02 };   // height, radius in m

geometry_msgs::msg::Pose pose;
pose.position.x = 0.5;
pose.position.y = -0.25;
pose.position.z = 0.05;
pose.orientation.w = 1.0;
object.pose = pose;

moveit::planning_interface::PlanningSceneInterface psi;
psi.applyCollisionObject(object);

Keep the object id as "object" for now, because the tutorial's attach and detach stages refer to it by that name.[1] Add the table the same way with a BOX primitive and a different id. Your M2 hand-in should show a plan that clearly goes around the table. If MoveIt happily plans through it, the table is in the wrong frame or was never applied.

07. M3: port the MTC node to the UR

This is the main engineering step. Copy the tutorial's mtc_node.cpp into your own package (as in 3.6) and change the robot-specific names. The tutorial node uses panda_arm as the arm group, hand as the hand group and panda_hand as the hand frame.[1][3] On the UR the arm group is the ur_manipulator chain you met in 3.8, which ends at tool0. 

// Panda names in the tutorial:
//   arm "panda_arm", hand group "hand", hand frame "panda_hand"
const auto& arm_group_name = "ur_manipulator";
const auto& hand_frame     = "tool0";   // or your gripper's TCP link

The gripper problem. The default UR description has no gripper, so there is no hand group and no SRDF poses called open or close. You have two options. Choose one in your M0 plan and justify it.

  • Option A, fixed tool (recommended): delete the "open hand" and "close hand" MoveTo stages. Keep the allowCollisions, attachObject and detachObject stages, pointed at tool0 or a simple tool link you add. The part is "picked" when it is attached to the tool in the planning scene. This is a common simplification, and it isolates the planning problem.
  • Option B, add a gripper: add a gripper's links, a hand planning group and open and closed poses to your URDF and SRDF. One lead is PickNik Robotics' ros2_robotiq_gripper, which provides "the ROS 2 driver, controller and description packages for working with a Robotiq Gripper", starting with the 2F-85.[8] It is not sponsored or maintained by Robotiq, and its README lists its main branch for Humble, Iron and Rolling, not Jazzy.[8] No source used for this page covers combining it with the UR description, so treat Option B as a stretch goal.

For Option A, the attach stage looks like this in the tutorial's style. Again, it is an example to try in simulation first:[1][3] 

auto stage = std::make_unique<mtc::stages::ModifyPlanningScene>("attach object");
stage->attachObject("object", hand_frame);
grasp->insert(std::move(stage));   // inside the "pick object" container

In the tutorial, allowCollisions uses the links of the hand group. Without a hand group, you must list the link names of your tool yourself. Read the tutorial's version of that stage carefully before you change it.[1]

Plan, then execute. At the end of the node, task.plan(5) searches until it has found 5 complete solutions, and task.execute() runs the chosen solution through an action server.[1][3] On mock hardware the "execution" just copies commanded positions into the joint states, but the arm still moves in RViz. Watch the object: when it is attached, RViz draws it in a different colour and it moves with the tool. When it is detached, it stays at the place pose.

Tune one thing at a time. The tutorial's approach and lift distances (0.1 to 0.15 m and 0.1 to 0.3 m) were set for the Panda hand.[1] With a bare tool0 you will probably need to change the grasp transform and approach direction. Log each change and its effect; that log feeds your failure analysis.

08. M4 (optional): run it in Gazebo

Once the task works on mock hardware, try it with physics. The UR Gazebo package has a launch that starts the simulated robot with its controllers, and another that adds MoveIt:[5] 

# Robot and controllers only
ros2 launch ur_simulation_gz ur_sim_control.launch.py

# Robot, controllers and MoveIt
ros2 launch ur_simulation_gz ur_sim_moveit.launch.py

Use the branch of ur_simulation_gz that matches your ROS 2 release (humble, jazzy for Jazzy and Kilted, or ros2 for Lyrical and Rolling).[5] Start your MTC node against this MoveIt instance instead of the mock-hardware one.

Be careful what you claim. The sources for this page do not cover whether a part attached in MoveIt's planning scene also follows the tool in Gazebo's physics. If the part stays on the table while MoveIt shows it attached, explain that in your report; a physically gripped part is a stretch goal.

09. M5: testing and verification

One successful run proves very little. Your test plan must show how often the task works and why it fails. As in the 6.1 test sheets, record for each test an ID, the expected and actual result, pass or fail, and evidence (a screenshot or log).

ID Test Pass if
T1 Attach and detach The object visibly changes to attached at pick, moves with the tool, and is detached at the place pose.
T2 Table clearance No stage solution passes through the table, and no collision is reported.
T3 Planning time A plan is found within the time limit you set in your M0 plan.
T4 Out of reach With the object moved out of reach, planning fails and your node prints a clear message instead of crashing or executing anything.
T5 Success rate Over N runs (N of at least 20) with randomised object positions inside a stated area, you report successes and failures and classify every failure.

T4 builds on a behaviour the tutorial itself points out: moving the object out of reach makes planning fail.[1] Your node should check the result of plan() and report it. For T5, randomise the object's x and y within a rectangle on the table and log the seed, so that a failing case can be repeated exactly. For each failure, note which stage failed. The Motion Planning Tasks panel shows failed solutions per stage, and the tutorial has a section on the debugging information MTC prints to the terminal.[1] Typical classes are "no IK solution", "connect failed" and "table collision".

10. Common problems

  • The Motion Planning Tasks panel is empty. Check that the display is added and its Task Solution Topic is /solution.[1]
  • Every run fails at the grasp stage. Click the ComputeIK stage and look at its failed solutions.[1] Usually the object is out of reach, the grasp transform points the tool the wrong way, or the frame names still say panda_hand.
  • The node crashes at start-up with an unknown group. A Panda name is left over. Search your code for panda and hand.
  • Setting a gripper output fails on mock hardware. That is a documented limit: the GPIO controller reports a failure when setting I/O in mock mode.[4] Use attach and detach in the planning scene instead, or move to a simulator that supports it.
  • The build fails inside moveit_task_constructor. The most likely cause is a branch that does not match your ROS 2 and MoveIt version. Re-check the branch before anything else.[1]

From simulation to a real cell. Nothing you verify here is a safety validation. Mock hardware has no physics, Gazebo is an approximation, and the speeds, accelerations and collision margins that work in simulation do not carry straight over to a real robot. A real UR cell would need its own risk assessment, a safety configuration on the robot controller, reduced-speed first runs and the safeguards discussed in 4.4 Making a Robot Cell Safe. Your reflection should name at least two things you would have to check before running your node on real hardware.

11. Grading rubric

The rubric uses four levels with no neutral middle. An ASEE paper on capstone rubrics used a 1 to 4 scale from "Not Acceptable" to "Exemplary" and chose an even number of levels on purpose, so that evaluators must decide whether expectations were met.[7] (The two middle labels below are this course's own.) Capstone research also warns that very detailed rubrics can narrow students' creativity, so the rows describe outcomes, not one fixed way to reach them.[9]

Criterion 1 Not acceptable 2 Developing 3 Meets expectations 4 Exemplary
Functionality The UR task does not complete. Completes for one hand-placed object pose only. Completes a full pick and place with attach and detach for the stated area. As 3, plus a stretch goal (gripper, Gazebo, several objects) working.
Planning scene and collisions No table, or plans pass through it. Table present, but collisions are allowed too broadly. No table collisions; collisions with the object are allowed only between grasp and release. As 3, and the scene is built from parameters, not hard-coded numbers.
Test evidence No test results. A few runs, with no randomisation or failure classes. T1 to T5 done, with N of at least 20 and every failure classified by stage. As 3, plus a change made in response to the failure analysis and re-tested.
Robustness and safety awareness The node crashes or hangs when planning fails. Failure is logged, but the message is unclear. Clear out-of-reach message; the report states the sim-to-real limits. As 3, plus a concrete list of real-cell checks tied to 4.4.
Code and documentation Code missing or does not build. Builds, but no README or launch instructions. Git repository with a README that lets someone else reproduce a run. As 3, with clear commits, comments where the UR port differs from the tutorial, and a launch file that starts everything.
Reflection Missing. Describes what was done, not what was learned. Answers the milestone prompts with specific examples. As 3, and connects the failures to what would change in a real cell.

12. Reflection questions

Reflection can be brief and frequent, or longer at key milestones.[2] This project uses both: a few sentences with every hand-in, and a longer reflection with the M5 report.

  1. What failed first, and how did you work out why? Name the tool you used (stage tree, terminal output, RViz).
  2. Which stage was hardest to get working on the UR, and what was different about it compared with the Panda?
  3. What does your success rate mean? Over what range of object poses does it hold, and where does it break down?
  4. In a real cell the object pose would come from a camera (see 2.8). What new failure modes would that add to your test plan?
  5. What would you change, check or measure before running this node on a real UR in a real cell?

13. Stretch goals

  • A real gripper model. Add a gripper to the UR description and SRDF (Option B) and restore the open and close stages.[8]
  • Gazebo physics. Make the part physically move with the tool in Gazebo, and document how you did it.
  • URSim. Run the driver against URSim instead of mock hardware, which from the driver's point of view is equivalent, and compare the behaviour.[4]
  • Choose by cost. Plan more than 5 solutions and compare the costs shown in the stage tree before executing the cheapest.[1]
Try it
  1. Before you start: confirm that you can still launch the UR5e on mock hardware with MoveIt from 3.8, and plan one pose goal in RViz.
  2. Clone and build moveit_task_constructor on the branch that matches your ROS 2 release, run demo.launch.py and the pick_place_demo, and add the Motion Planning Tasks display on /solution.
  3. Click through all the stages, then move the cylinder out of reach in the demo code, rebuild and run again. Screenshot the stage that fails. That screenshot and a one-page plan are your M0 hand-in.
