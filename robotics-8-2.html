8.2 Industrial Ethernet Protocols

Gerald Lê

01. The industrial Ethernet landscape

In an industrial robotic workcell, machines must constantly exchange information to coordinate actions. In Lesson 1.7 The Industrial Robot Cell, we examined how a central programmable logic controller (PLC) coordinates cell operations using discrete handshake signals, while keeping personnel safety circuits on separate dedicated pathways. In Lesson 2.5 End-of-Arm Tooling and I/O, we connected grippers, vacuum switches, and part-detection sensors to robot controller and tool-flange terminals.

In Lesson 8.1 From Wires to Networks, we saw why manufacturing plants shifted away from point-to-point wiring. Digital fieldbuses solved this challenge by grouping signals onto a shared digital bus. Over time, Ethernet replaced serial fieldbuses as standard office networking technologies entered the plant floor.

However, standard commercial Ethernet was not designed for industrial machinery. A late message on a machine network can make moving equipment act on old data. Factory automation requires determinism, meaning that data packets must arrive within a defined, predictable time interval.

To achieve deterministic performance across Ethernet media, automation manufacturers developed specialized industrial Ethernet protocols. This lesson covers four of them: EtherNet/IP, PROFINET, EtherCAT and Modbus TCP. They differ in how they structure process data, bypass protocol overhead, and achieve real-time response.

02. EtherNet/IP and the Common Industrial Protocol

EtherNet/IP is an open industrial Ethernet network standard managed by ODVA, a global trade and standards development organization. EtherNet/IP combines standard Ethernet and TCP/IP technologies with the Common Industrial Protocol (CIP) for industrial automation communication.[1]

The Common Industrial Protocol follows the Open Systems Interconnection seven-layer reference model across physical and application layers.[1]

CIP uses a Producer/Consumer networking model instead of a source/destination model to reduce traffic and increase transmission speed.[2] Under this model, a transmitting device produces a message onto the network with an identifier. Any number of interested consumer devices on the network can listen for that identifier and process the data simultaneously from a single transmission.

Data production in a CIP network is managed to optimize network bandwidth. Digital input modules on CIP networks produce data either upon a change of state or at a requested packet interval.[2] Change-of-state (COS) transmission allows a sensor module to transmit immediately when an input transitions from off to on, eliminating the latency of waiting for a polling cycle. The requested packet interval (RPI) defines the cyclic rate at which data is regularly produced regardless of state changes.

EtherNet/IP separates communications into two primary message categories: implicit messaging and explicit messaging. Each category uses a different transport-layer protocol to match its functional requirements.

Implicit messages in EtherNet/IP are time-critical connected communications that transport I/O data using UDP without embedded protocol headers.[2] In implicit communications, an association called a connection is established between the scanner (the controlling PLC) and the adapter (such as a robot controller) during startup. Both endpoints already know the meaning, length, and internal offset of every byte in the data exchange. Because the data structure is understood beforehand, the message carries no protocol decoding headers. By transmitting pure I/O payload over lightweight User Datagram Protocol (UDP), implicit messaging delivers the speed required for cyclic real-time control.

Explicit messages in EtherNet/IP use TCP for request-reply client-server transactions addressed to the Message Router object.[2] Unlike cyclic I/O, explicit messages are acyclic, meaning they occur on an as-needed basis. Explicit messages contain explicit descriptions of the requested service, the object class, the instance number, and the attribute identifier. By transmitting over Transmission Control Protocol (TCP), explicit messaging ensures reliable delivery through point-to-point connections with error checking and retries. Integrators use explicit messaging for tasks that do not require cycle-by-cycle deterministic delivery, such as reading fault logs, reconfiguring drive parameters, or querying firmware versions.

03. PROFINET: real-time deterministic Ethernet

PROFINET (Process Field Network) is an open industrial Ethernet standard maintained by PROFIBUS & PROFINET International (PI).

In a PROFINET installation, the PLC acts as the IO Controller. Field devices, such as industrial robot controllers, pneumatic valve manifolds, and vision sensors, operate as IO Devices. During operation, the IO Controller and its IO Devices continuously exchange cyclic input and output data.

To satisfy diverse performance demands across manufacturing plants, PROFINET specifies distinct communication channels over the same physical infrastructure. For standard factory automation, PROFINET RT bypasses TCP/IP layers to achieve deterministic communication in the 1 to 10 millisecond range.[3] Skipping the TCP/IP layers removes the processing time and delay those layers add.

For demanding motion control tasks, such as coordinating multiple robot axes or synchronizing printing rolls, even a few milliseconds of jitter is unacceptable. To address these applications, PROFINET IRT uses scheduled switching and hardware ASICs to achieve sub-millisecond cycle times with microsecond-level jitter.[3] IRT stands for Isochronous Real-Time and is aimed at motion control.

Field equipment configuration in PROFINET follows a structured hierarchy. PROFINET organizes field equipment using a hierarchical device model comprising Device, Module, and Channel.[3] Under this model:

  • Device: The physical node on the network, such as a robot controller.
  • Module: A physical or logical sub-unit residing inside the device (such as a digital input block).
  • Channel: The individual signal point within a module (such as one digital input wired to one sensor).

Modern manufacturing facilities require supervisory IT systems, diagnostic web pages, and engineering tools to connect to production machinery without disrupting production. PROFINET bandwidth reservation ensures that at least 50 percent of each I/O cycle remains available for standard TCP/IP communications.[3]

04. EtherCAT: processing on the fly

EtherCAT works differently from the protocols above.

In an EtherCAT network, the master controller transmits a single Ethernet frame that passes sequentially through every node in the network segment. In an EtherCAT network, slave devices read incoming data and insert outgoing data on the fly as the frame passes downstream.[4]

This operational architecture creates a deliberate division of complexity between the network controller and the connected nodes. An EtherCAT master runs using a standard Ethernet controller, whereas slave devices require a dedicated hardware EtherCAT Slave Controller.[4] So a PC with an ordinary Ethernet port can be the master, while each slave carries a special chip.

Coordinated multi-axis motion, such as synchronizing multiple robotic joints or interpolating a cartesian gantry, requires simultaneous sampling and actuation across distributed drives. EtherCAT distributed clocks synchronize device clocks in hardware to achieve system synchronization jitter significantly below 1 µs.[4] One device acts as the reference clock; because its time messages reach the other devices slightly late, that propagation delay is measured and compensated.[5]

EtherCAT maintains high transmission efficiency by stripping unnecessary network layer overhead from cyclic data. EtherCAT frames are identified by EtherType 0x88A4 in standard Ethernet frames, eliminating the overhead of TCP/IP or UDP/IP stacks.[5]

05. Modbus TCP: industrial messaging on port 502

The Modbus Organization describes Modbus as the industry's serial de facto standard since 1979.[6] Modbus TCP carries the same messages over Ethernet.

The Modbus protocol defines a straightforward client/server architecture. A client (such as a supervisory PLC, an HMI terminal, or a Python script) initiates requests to read or write data. A server (such as an industrial robot controller) listens for incoming requests, executes the requested action, and returns a response.

To represent automation variables, the Modbus data model provides four primary tables comprising discrete inputs, coils, input registers, and holding registers.[6] These tables organize boolean and numerical information into distinct access categories:

  • Discrete Inputs: Single-bit binary data that is read-only. Discrete inputs represent physical digital sensor signals, such as optical proximity switches or emergency stop contact monitors.
  • Coils: Single-bit binary data that can be both read and written. Coils represent controllable on/off outputs, such as energizing a pneumatic solenoid valve or triggering a conveyor motor starter.
  • Input Registers: 16-bit word data (two bytes) that is read-only. Input registers carry analog measurements and numerical status flags provided by field hardware, such as motor temperature readings or joint encoder values.
  • Holding Registers: 16-bit word data (two bytes) that can be both read and written. Holding registers serve as general-purpose read/write storage, used for passing target coordinate setpoints, speed overrides, recipe numbers, and operational handshake words.

Because industrial controllers employ different internal microprocessor architectures, network protocols must specify consistent byte serialization rules. Modbus transmits numerical values and addresses in big-endian representation with the most significant byte transmitted first.[6] For example, the 16-bit value 0x1234 is sent as byte 0x12 and then byte 0x34.

Modbus TCP messages include a 7-byte MBAP header and transmit over TCP on registered port 502.[7]

The Modbus Application Protocol (MBAP) header prefixes the Modbus function code and data payload. The 7-byte header consists of four fields:

  • Transaction Identifier (2 bytes): An identification number assigned by the client to pair request messages with their corresponding server responses.
  • Protocol Identifier (2 bytes): Set to 0 to indicate the Modbus protocol.
  • Length (2 bytes): A byte count specifying the remaining bytes in the message, including the unit identifier and data payload.
  • Unit Identifier (1 byte): Used for routing to identify a sub-device when communicating through a gateway to a serial Modbus network.

In Lesson 8.3 Lab: Connecting a Robot to a PLC, you will put these principles into practice by writing and reading holding registers from a Python client, using a stand-in for a robot's Modbus TCP server.

06. Device description files in engineering software

When an engineer integrates a robot arm, a vision system, or an intelligent drive into a modern automation project, the engineering software must understand the communication capabilities of that device. Without a standardized description, the engineer would need to manually look up register addresses, configure byte lengths, and define diagnostic structures by hand in software. To automate and standardize this process, industrial communication bodies established standardized device description files.

In the PROFINET ecosystem, field devices are characterized using standardized station description files. GSDML files use an XML-based markup language compliant with ISO 15745 to define the properties of PROFINET field devices.[8] The GSDML (General Station Description Markup Language) specification is structured under the ISO 15745 application integration framework. A GSDML file contains human-readable XML tags defining the device manufacturer, device identification codes, supported communication interfaces, timing parameters, and available physical or virtual I/O modules.

Before a third-party device can be programmed in a PLC project, its station file must be imported into the programming environment. Engineering software requires installing a manufacturer GSD file to integrate third-party field devices into the hardware configuration catalog.[8] Once installed, the device appears in the hardware catalog and can be placed in the network layout.

EtherCAT follows a similar standardization model for its connected devices. An EtherCAT SubDevice Information (ESI) file is an XML document containing the complete description of a device's process data mapping and supported communication features.[5]
