6.7 State Machines

Gerald Lê

01. Why robots require state machines

An autonomous robot rarely performs a single uninterrupted task. A warehouse mobile robot must follow a guide line, navigate around obstacles, search for missing paths, and halt immediately if a safety button is pressed. Novice programmers often attempt to coordinate these behaviors by nesting if and else if conditional statements inside the main control loop.

As robot capabilities grow, this ad hoc approach rapidly degenerates into fragile "spaghetti code." Adding a single new behavior requires modifying multiple nested conditional branches. Hidden side effects emerge, two branches can fight over the same motor command, and it becomes hard to predict what the robot will do when a sensor reading is unexpected. Behavior-tree researchers Colledanchise and Ögren make the same point about poorly structured controllers: every new behavior means re-checking a large number of existing decisions, which makes the code error-prone to change.[1]

To bring formal structure to robot behavior, engineers use a Finite State Machine (FSM).[2] An FSM is a mathematical model of computation consisting of a predetermined set of states, incoming events, and guarded transitions between states. At any given instant, the robot resides in exactly one state. By decoupling what the robot does (the state action) from when it switches behaviors (the state transition), state machines organize the "think" stage of the sense-think-act cycle into modular software components that are easier to check.

02. Core components of a state machine

The state diagrams described by David Harel in his classic statecharts paper are built from five elements: states, events, conditions (guards), transitions and actions.[2]

  • State: A unique operating mode or behavioral condition in which the robot resides. While in a state, the robot executes specific actions. For example, in FOLLOW_LINE, the robot executes differential motor velocity adjustments based on line reflectance sensors. The system remains in exactly one state at a time; in a state diagram each state is a node of the graph.[2]
  • Event: An external or internal stimulus detected by the system. Events originate from hardware sensors (ultrasonic distance drops below 20 cm), timer triggers (elapsed time exceeds 600 ms), or user inputs (digital emergency stop button pressed). In Harel's notation, each transition arrow is labelled with the event that triggers it.[2]
  • Guard: A Boolean conditional expression that must evaluate to true for an event to trigger a transition. For example, the event "turn completed" may be guarded by the condition [path ahead is clear]. If the guard evaluates to false, the transition is inhibited. Harel writes the guard as a condition in parentheses next to the event; the transition fires only if the condition holds when the event occurs.[2]
  • Transition: The deterministic progression from the current source state to a target destination state, triggered when an event occurs and its associated guard evaluates to true.[2]
  • Action: Executable code invoked by the state machine. In classic automata theory, state machines execute actions either during states (a Moore machine) or during state transitions (a Mealy machine); Harel's statecharts allow both, and also allow actions on entering and on leaving a state.[2] In embedded robot code it is common to split a state's work into entry actions (executed once upon arrival, such as resetting a timer), execution actions (evaluated continuously each control loop), and exit actions (executed once upon departure, such as turning off an indicator LED).

03. Worked example: line follower with obstacle avoidance

This section is the lesson's own worked example. To observe an FSM in action, examine a differential-drive robot equipped with two analog floor reflectance sensors (A0 and A1), an HC-SR04 ultrasonic range finder (trigger pin 9, echo pin 10; the module measures roughly 2 cm to 4 m),[3] two DC motors controlled via PWM H-bridge drivers, and a normally high digital emergency stop push-button (pin 2).

The behavioral logic of this robot is partitioned into four distinct states:

  1. FOLLOW_LINE: The robot steers its drive wheels to center a black electrical floor tape between its two reflectance sensors.
  2. AVOID_OBSTACLE: The robot stops forward drive and spins in place to steer clear of an obstacle in its immediate path.
  3. SEARCH: Having lost the line, the robot drives along a wide curved arc seeking to re-acquire the black tape.
  4. STOP: Actuator PWM duty cycles are set to zero. This represents the fail-safe resting state.

Before writing a single line of embedded code, an engineer creates a state transition table. This table lists every valid transition and its guard, so the engineer can check, row by row, that no sensor event is left without a defined response. The table below is the design for this lesson's example robot:

Current State Event Trigger [Guard Condition] Target State Actions Performed
FOLLOW_LINE Obstacle detected [distance < 20 cm] AVOID_OBSTACLE Record state entry timestamp; command right spin.
FOLLOW_LINE Line lost [both sensors off tape] SEARCH Record state entry timestamp; command arc sweep.
AVOID_OBSTACLE Turn timer expired [elapsed ≥ 600 ms AND distance ≥ 20 cm] SEARCH Transition to search mode to locate line.
SEARCH Line detected [left OR right sensor on tape] FOLLOW_LINE Resume closed-loop differential line tracking.
SEARCH Search timer expired [elapsed > 5000 ms] STOP Halt all motors; lock system in safe state.
Any State Emergency stop button pressed [pin LOW] STOP Instantly cut PWM to all motors; require manual reset.

With JavaScript on, you can send events to this state machine and watch it change state.

04. Non-blocking timing: why delay() is fatal in robotics

In introductory microcontroller tutorials, pauses are commonly implemented using the built-in Arduino delay() function. However, using delay() inside autonomous robot code is dangerous.

The delay() function is a blocking call: the Arduino reference warns that "no other reading of sensors, mathematical calculations, or pin manipulation can occur during the delay function." Interrupts and PWM outputs keep working, but the main program does nothing else until the pause ends.[4] If the robot enters AVOID_OBSTACLE and commands a spin using delay(600), the CPU is completely frozen for 600 milliseconds. During this freeze:

  • The robot cannot read its ultrasonic range finder or bumper switches to detect an oncoming wall or sudden drop-off.
  • An emergency stop button that is read in loop() (as in this example) is ignored until the pause ends, which is a serious safety problem.
  • Sensory feedback is cut off, while PWM outputs stay at their last values, so the motors keep driving at their previously set speed.[4]

Robot software avoids this with cooperative multitasking: each task checks the clock and returns immediately instead of waiting. Arduino's official Blink Without Delay example shows the pattern, because "Arduino pauses your program during the delay()."[5] The millis() function returns the number of milliseconds since the program started, as an unsigned long, without halting program execution.[6]

To time a 600 ms turning maneuver without blocking, software records the timestamp when the state is entered (stateStart = millis()). On every subsequent pass of the main loop(), the code evaluates elapsed time using unsigned modular subtraction:

\[\text{elapsed} = \text{now} - \text{stateStart}\]

Because loop() keeps running instead of waiting, the robot reads its ultrasonic sensor and emergency stop button on every pass throughout the turn.

Crucially, embedded software must always write the check as (now - stateStart >= duration) rather than (now >= stateStart + duration). The Arduino reference notes that millis() overflows (goes back to zero) after approximately 50 days.[6] On boards where unsigned long is 32 bits, that is \(2^{32}\) ms, about 49.7 days. In C and C++, unsigned integer arithmetic is always performed modulo \(2^n\), where \(n\) is the number of bits.[7] When now rolls over, the unsigned subtraction (now - stateStart) correctly computes elapsed duration across the rollover boundary. The addition form can fail near rollover: if stateStart + duration wraps past zero, the comparison becomes true too early (or, in other layouts of the test, never), so the state ends at the wrong time.

05. Embedded C++ implementation

The listing below is the lesson's own implementation of the example. In embedded C++, the state machine is implemented cleanly using an enum to name the states, an enterState() helper function that changes the state and records the timestamp in one place, and a switch statement inside loop(): 

enum State { FOLLOW_LINE, AVOID_OBSTACLE, SEARCH, STOP };
State state = FOLLOW_LINE;
unsigned long stateStart = 0;      // Timestamp when entering current state
unsigned long lastPing = 0;        // Ultrasonic sensor rate limiter
float distanceCm = 999.0;

const int LEFT_PWM = 5, LEFT_DIR = 4, RIGHT_PWM = 6, RIGHT_DIR = 7;
const int TRIG = 9, ECHO = 10, STOP_BUTTON = 2;
const int LINE_THRESHOLD = 600;    // analogRead threshold over black tape

void setMotor(int pwmPin, int dirPin, int speed) {   // speed: -255 to 255
  digitalWrite(dirPin, speed >= 0 ? HIGH : LOW);
  analogWrite(pwmPin, constrain(abs(speed), 0, 255));
}

void drive(int left, int right) {
  setMotor(LEFT_PWM, LEFT_DIR, left);
  setMotor(RIGHT_PWM, RIGHT_DIR, right);
}

void enterState(State next) {
  state = next;
  stateStart = millis(); // Atomic entry action: record timestamp
}

void setup() {
  pinMode(LEFT_DIR, OUTPUT);  pinMode(RIGHT_DIR, OUTPUT);
  pinMode(TRIG, OUTPUT);      pinMode(ECHO, INPUT);
  pinMode(STOP_BUTTON, INPUT_PULLUP);
  enterState(FOLLOW_LINE);
}

void loop() {
  unsigned long now = millis();

  // --- 1. SENSE STAGE ---
  bool leftOnLine  = analogRead(A0) > LINE_THRESHOLD;
  bool rightOnLine = analogRead(A1) > LINE_THRESHOLD;

  // HC-SR04 sonar ping: at most once every 60 ms (datasheet minimum measurement cycle)
  if (now - lastPing >= 60) {
    lastPing = now;
    digitalWrite(TRIG, HIGH);
    delayMicroseconds(10);
    digitalWrite(TRIG, LOW);
    unsigned long echo = pulseIn(ECHO, HIGH, 12000); // 12 ms timeout (~2.0 m max range)
    distanceCm = (echo == 0) ? 999.0 : (echo * 0.0343) / 2.0;
  }

  // Asynchronous Emergency Stop: monitored on every single loop iteration
  if (state != STOP && digitalRead(STOP_BUTTON) == LOW) {
    enterState(STOP);
  }

  // --- 2. THINK & ACT STAGES ---
  switch (state) {
    case FOLLOW_LINE:
      if (distanceCm < 20.0) {
        enterState(AVOID_OBSTACLE);
      } else if (!leftOnLine && !rightOnLine) {
        enterState(SEARCH);
      } else if (leftOnLine && !rightOnLine) {
        drive(80, 180);   // Steer left toward tape
      } else if (rightOnLine && !leftOnLine) {
        drive(180, 80);   // Steer right toward tape
      } else {
        drive(160, 160);  // Both sensors centered on tape
      }
      break;

    case AVOID_OBSTACLE:
      drive(150, -150);   // Spin right in place
      if ((now - stateStart >= 600) && (distanceCm >= 20.0)) {
        enterState(SEARCH);
      }
      break;

    case SEARCH:
      drive(140, 90);     // Trace broad curved arc to re-acquire line
      if (leftOnLine || rightOnLine) {
        enterState(FOLLOW_LINE);
      } else if (now - stateStart > 5000) {
        enterState(STOP); // Line lost timeout: stop robot safely
      }
      break;

    case STOP:
      drive(0, 0);        // De-energize all drive actuators
      break;
  }
}

The HC-SR04 datasheet asks for a 10 µs trigger pulse, gives range as echo time × speed of sound (340 m/s) ÷ 2, and recommends a measurement cycle of over 60 ms so that one ping's echo does not interfere with the next; the code follows all three.[3] Notice also that pulseIn() is given an explicit timeout of 12,000 µs (12 ms). The timeout argument is in microseconds and defaults to one second,[8] so without it a missing echo (for example, ultrasound scattering into an open room) could stall the loop for up to a second. With the short timeout, a failed ping costs only a few milliseconds, and 12 ms of round-trip travel at about 343 m/s corresponds to a maximum range of about 2 m.

06. State machine anti-patterns and pitfalls

The following five pitfalls are the lesson's own design guidance, drawn from the example above:

  • Blocking Delays: Introducing delay() calls inside state branches blinds the robot to sensory events and user e-stops, because nothing else in the program runs during the pause.[4] Every timed behavior should rely on millis() delta comparisons.
  • Neglected Entry Actions: If an engineer changes state = SEARCH; directly in multiple places without updating stateStart, the state timer operates with stale timestamps, causing premature or delayed timeouts. Centralizing transitions inside enterState() guarantees uniform execution.
  • Chattering and State Flapping: If a sensor value hovers directly on a decision boundary (such as distance oscillating between 19.9 cm and 20.1 cm), the FSM can oscillate between FOLLOW_LINE and AVOID_OBSTACLE on successive loop passes. This is resolved by adding hysteresis: trigger obstacle avoidance at 20 cm, but require the path to clear 25 cm before exiting.
  • Terminal Traps: An unhandled exception or missing transition row in the state table can strand a robot in an active state indefinitely. Every state must have at least one valid transition path, and every active state must transition to STOP upon an e-stop event or safety timeout.
  • Duplicate Output Actuation: Writing motor speeds inside scattered conditional checks creates conflicting actuator commands within the same cycle. A well-structured FSM updates actuator outputs only once per pass based on the active state.

07. Industrial automation standards: IEC 61131-3 SFC and PackML

Industrial machines use standardized state models too, so that machines from different vendors behave and report their status in the same way. ISA describes its machine-state technical report as a way to standardize "machine states, modes and PackTags" to improve interoperability.[9]

The international standard IEC 61131-3 defines the syntax and semantics of programming languages for Programmable Logic Controllers (PLCs). The current edition (4.0, 2025) defines Structured Text, Ladder Diagram and Function Block Diagram, plus Sequential Function Chart (SFC) elements for structuring programs; the 2013 edition also included Instruction List.[10] PLCopen describes SFC as an additional set of graphical and textual elements, and the standard's SFC definitions are taken from the earlier function-chart standard IEC 848.[11] SFC models machine operations as a directed graph of:

  • Steps: Discrete operating states: "a step is either active or inactive." Each SFC network has exactly one initial step, which can be drawn with double lines for its borders.[11]
  • Transitions: Boolean conditions between steps. A transition is enabled when all of its preceding steps are active, and it "clears" when it is enabled and its condition is true; clearing hands activity from the preceding steps to the following ones.[11]
  • Action Blocks and Qualifiers: The standard defines action qualifiers (ten in the PLCopen excerpt, including N, R, S, L, D and P).[11] As the CODESYS manual explains them: N (Non-stored) runs as long as the step is active; S (Set/Stored) keeps running after the step ends, until it is reset; R (Reset) stops a stored action; L (time Limited) runs until the step ends or a time span elapses; and D (time Delayed) starts only after the step has been active for a set delay.[12]

For packaging machinery, the PackML state model associated with the Organization for Machine Automation and Control (OMAC) is published by ISA as technical report ISA-TR88.00.02 (current version 2022).[9] A PackML unit mode can contain up to 17 machine states, among them Idle, Starting, Execute, Holding, Held, Suspended and Aborted.[13] The OPC UA companion specification for PackML defines Execute as the machine actively carrying out the behavior of the selected mode, Held as paused "waiting for internal process conditions to clear," Suspended as paused "waiting for external process conditions to clear" (for example, an upstream machine starving it of product), and Idle as error-free and waiting to start.[14]

Because PackML machines share this vocabulary, plant supervisory software can read the state of machines from different vendors in the same way, which is the interoperability goal ISA states for the report.[9]

08. ROS 2 managed nodes: the rclcpp_lifecycle state machine

An ordinary ROS node starts working as soon as its process starts. If a motor controller node started before the laser scanner or safety supervisor was ready, the robot could move without its safety checks running. The ROS 2 design article on managed nodes gives the motivation for fixing this: a managed life cycle lets the launch system "ensure that all components have been instantiated correctly before it allows any component to begin executing its behaviour," and lets nodes be restarted or replaced while the system runs.[15]

ROS 2 addresses this with managed (lifecycle) nodes.[15] Every server in the Nav2 navigation stack is a lifecycle node.[16] A lifecycle node follows a state machine with four primary states and six transition states:[15]

Primary State Operational Characteristics Permitted Transitions
Unconfigured The state the node is in right after it is created, before it has been configured. Transitions to Inactive via configure(), or to Finalized via shutdown().
Inactive Configured but not running: the node gets no execution time, so it does not read topics, process data or answer its functional service requests. Transitions to Active via activate(), to Unconfigured via cleanup(), or to Finalized via shutdown().
Active Full operation: the node processes data, answers requests and publishes its outputs. Transitions to Inactive via deactivate(), or to Finalized via shutdown().
Finalized The node has shut down and is waiting to be destroyed. Terminal state: the only permitted transition is destroy.

The six transition states (Configuring, Activating, Deactivating, CleaningUp, ShuttingDown, ErrorProcessing) run the node's callbacks for each change (for example, the configure callback). If a callback returns an error or throws an exception, the node enters ErrorProcessing; if the error handler succeeds the node returns to Unconfigured, otherwise it moves to Finalized.[15] A sensor driver that cannot reach its hardware during configuration therefore never becomes active.

09. Beyond state machines: Behavior Trees in ROS 2 Nav2

While finite state machines work well for simple behaviors, they become hard to maintain as robots gain more behaviors. Colledanchise and Ögren point out that a reactive FSM needs many transitions, and that "adding or removing states requires the re-evaluation [of] a potentially large number of transitions."[1] With \(N\) states, a directed graph can have up to \(N(N-1)\) transitions, so in the worst case the number of transitions grows quadratically:

\[\text{Number of Transitions} \approx \mathcal{O}(N^2)\]

Adding a new behavior can mean editing transitions in many existing states, which couples the code tightly. A related problem, which Harel called the "exponentially growing multitude of states," appears when independent behaviors are combined into one flat machine: two components with 1,000 states each give a product machine with a million states.[2]

To achieve modular autonomy, many robotics frameworks use Behavior Trees (BTs). In their textbook, Michele Colledanchise and Petter Ögren describe BTs as a way to structure switching between tasks that is both modular and reactive. The root of the tree generates an enabling signal called a tick at a given frequency, and a node runs only while it receives ticks.[1] In ROS 2, the Nav2 stack coordinates navigation with behavior trees run by its BT Navigator, using the BehaviorTree.CPP library.[16]

In Nav2 each iteration of the tree takes 10 ms by default (the bt_loop_duration parameter), so the tree is ticked at about 100 Hz.[17] Each tick flows downward through four kinds of node:[1]

  • Control Nodes: Route ticks to children: Sequence, Fallback (Selector), and Parallel.
  • Decorator Nodes: Control nodes with a single child that change how the child is run or what it returns (such as an inverter, or Nav2's RateController, which ticks its child at a fixed frequency).[1][18]
  • Action Nodes: Execute tasks (Nav2 action plugins include ComputePathToPose, FollowPath, Spin, BackUp and ClearEntireCostmap).[19]
  • Condition Nodes: Check a condition and return SUCCESS or FAILURE, never RUNNING[1] (Nav2 condition plugins include IsBatteryLow, GoalReached, IsStuck and TransformAvailable).[19]

Every node in a Behavior Tree returns one of three statuses when ticked: SUCCESS if it achieved its goal, FAILURE otherwise, or RUNNING while it is still working.[1]

The two core control nodes govern navigation and error recovery:[1]

  • Sequence Node (→): Ticks children from left to right. If a child returns SUCCESS, it ticks the next child. If a child returns RUNNING, the Sequence returns RUNNING. If any child returns FAILURE, the Sequence immediately halts remaining children and returns FAILURE to its parent. It succeeds only if every child succeeds.[1]
  • Fallback Node (?): Implements reactive recovery. Ticks children from left to right. If a child returns SUCCESS, the Fallback immediately succeeds. If a child returns FAILURE, the Fallback ticks the next child (the recovery action). If a child returns RUNNING, the Fallback returns RUNNING. It returns FAILURE only if all children fail.[1]

The tree below is the lesson's simplified sketch of the idea. Nav2's real default tree is more elaborate: its recovery subtree runs only when the navigation subtree returns FAILURE, and a RoundRobin node then cycles through clearing the costmaps, Spin (1.57 rad), Wait (5 s) and BackUp (0.15 m), retrying navigation after each.[20]

Fallback: NavigateWithRecovery

 └ Sequence: PrimaryNavigate

   └ ⟨Action: ComputePathToPose⟩

   └ ⟨Action: FollowPath⟩

 └ Sequence: RecoveryBehaviors

   └ ⟨Action: ClearEntireCostmap⟩

   └ ⟨Action: Spin 1.57 rad⟩

   └ ⟨Action: BackUp 0.15 m⟩

In this sketch, if a human blocks the hallway, FollowPath returns FAILURE. The PrimaryNavigate Sequence halts and returns FAILURE. The parent Fallback catches the failure and immediately ticks RecoveryBehaviors. The robot clears its obstacle costmap, spins in place, and backs away before re-attempting path tracking. Because each behavior is a modular leaf node, new recovery strategies can be inserted without altering existing navigation code; Nav2's documentation notes that its clear-costmap, spin and back-up recoveries exist to move the robot out of a poor location.[16]
